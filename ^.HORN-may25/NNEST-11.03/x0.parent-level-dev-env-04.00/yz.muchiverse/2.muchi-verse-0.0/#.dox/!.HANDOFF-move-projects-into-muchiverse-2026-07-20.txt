REAL GOTCHA HIT DURING THIS MOVE, WORTH KNOWING BEFORE YOU DO ANOTHER
ONE: after killing the two processes originally found (a bash + a
qterm), a THIRD, previously-unnoticed leftover `prisc+x` process (a
child of one of those two, already reparented to init by the time it
was found - ppid 1 in `ps`) was still running. Its own KERNEL cwd
correctly followed the `mv` (Linux transparently updates an open
process's cwd handle when the directory it's in gets renamed/moved on
the same filesystem) - so a `/proc/$pid/cwd` sweep right after the mv
looked clean. But this process's own `PRISC_PROJECT_ROOT` had been read
ONCE at its own startup into a static C string (exactly how every
op/prisc+x in this family's own `resolve_root()` works - matches
!.pal-standards.txt's own documented pattern) - that STRING still held
the OLD absolute path text, completely unaffected by the directory
rename elsewhere. Every tick, it kept recreating a fresh `pieces/`
tree (ephemeral UI state only, no real data - confirmed by inspection
before deleting it) AT THE OLD LOCATION, using that stale string,
independent of its own correctly-updated kernel cwd. Found by noticing
a `pieces/` directory had reappeared at the just-emptied old path with
a timestamp AFTER the move. LESSON: after any `mv` of a live-or-
recently-live project, re-run the /proc/$pid/cwd sweep A SECOND TIME,
a few seconds later, specifically watching for anything reappearing at
the OLD path - a clean sweep immediately after the mv is not
sufficient proof nothing is still writing there, because a process's
own cached PRISC_PROJECT_ROOT string (not its kernel cwd) is what
actually determines where its file I/O lands.

2. WHAT BREAKS ON A MOVE, AND HOW TO FIX IT - PER PROJECT CHECKLIST
========================================================================
Run this checklist for EACH project moved, not just once overall:

  [ ] Move the directory itself (plain `mv` - this is NOT a git repo,
      confirmed at session start, no git mv needed, no history to
      preserve beyond the files themselves).
  [ ] Grep the moved project's own button.sh + every ops/*.c file for
      any hardcoded path containing the OLD parent directory name
      (e.g. "y0.mutaclsym+06.01", "z0.egg-pals+plats-8.01",
      "y0.muchi-pal-llm-00.00") - fix any found to the new location.
  [ ] If the project launches palnet_peer.+x (grep button.sh for
      "palnet_peer"): check whether it needs an explicit
      `PRISC_NET_ROOT` override (sec. 1(d)'s zoo_0000 case) or should
      rely on the new default (which will now point at yz.muchiverse/
      2.muchi-verse/net/presence, the same pool pal-chain/pal-forum/
      pal-chat-irc already use) - this is a real behavioral decision,
      not just a path fix. See !.pal-standards.txt's own sec. 23
      writeup on the PRISC_NET_ROOT bug pal-forum/pal-chat-irc hit for
      the full mechanism if you need the background.
  [ ] If the project uses pet_export.c/pet_import.c (grep for
      "resolve_exchange_root" or "PRISC_EXCHANGE_ROOT"): same
      consideration for the exchange/ directory (sec. 1's own note).
  [ ] Update shared-ops-manifest.txt: it has example sync commands with
      hardcoded OLD paths, at minimum this one confirmed line (search
      for it, there may be others added since this was written):
        "bash sync_shared_op.sh chtpm_parser_pal ../../y0.mutaclsym+06.01/mutaclsym/system"
      should become (once mutaclsym is a direct sibling under
      2.muchi-verse/, matching pal-chain/pal-forum's own reference
      shape):
        "bash sync_shared_op.sh chtpm_parser_pal ../mutaclsym/system"
  [ ] Rebuild the moved project (`bash scripts/build.sh` or
      `./button.sh compile`, whichever it uses) from its NEW location -
      confirms no other stale absolute path broke the build silently.
  [ ] If the project has its own button.sh `run` action already using
      session isolation (none of these four are confirmed to yet -
      that's a SEPARATE, later task, matching pal-chat-irc/pal-forum/
      pal-chain/user-pal's own precedent, not required just to
      complete this move) - if it does, verify pieces/sessions/ still
      resolves correctly relative to the new location (it will, since
      SCRIPT_DIR is computed dynamically in every button.sh via
      `cd "$(dirname "$0")" && pwd` - this is location-independent by
      construction, just confirm no OTHER script hardcodes a session
      path).
  [ ] Live-verify the moved project still actually runs (its own
      basic real interactive test, or whatever the project's own dox
      says is the minimum smoke test) BEFORE considering that
      project's move done. Don't just confirm "it compiles."

BEFORE MOVING ANYTHING, for every project in sec. 1: run
`ps aux | grep -i <project_name_or_binary>` and check for any live
process with that project's own path in its cwd (readlink -f
/proc/$pid/cwd) - this whole family's own session-isolation testing
gotcha (pal-standards.txt sec. 23's own "manual/agent testing gotcha"
entry) applies here even harder: moving a directory out from under a
RUNNING process is worse than launching a second process against a
live one. If anything is running against a project you're about to
move, either wait for it to exit naturally or ask the user before
killing it - never assume a live process is safe to kill just because
it's inconvenient for this move (same standing rule the whole family
already follows for any destructive-adjacent action).
