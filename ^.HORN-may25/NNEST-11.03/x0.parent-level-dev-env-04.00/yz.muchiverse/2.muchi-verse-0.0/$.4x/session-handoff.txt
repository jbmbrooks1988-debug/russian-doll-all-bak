2. THE REAL, UNRESOLVED GAP - MY OWN TEST HARNESS, NOT THE CODE
================================================================================
While live-testing the new combat mechanics, I hit a confusing result:
calling `ops/+x/move_player.+x 1001` DIRECTLY, repeatedly, moved the
possessed player correctly every single time (4 calls in a row, each
advancing pos_x by 1, no issue). But feeding the SAME keys through the
real backgrounded `prisc+x pal/main_loop.pal` process (via appending to
history.txt with sleeps between, the "more real" testing method this
whole session has preferred) moved the player ONE tile and then
appeared to stop responding to further RIGHT presses, across multiple
retries at different timings (0.15s, 0.2s, 0.4s between keys).

I did NOT get to the bottom of this before being asked to write this
handoff. Known facts, not yet reconciled:
  - The underlying move_player.c/choice.c logic is confirmed correct
    via direct invocation - this is very unlikely to be a real logic
    bug in the combat/movement code itself.
  - This session already found and fixed ONE real class of "looks
    broken through the full loop, works fine standalone" bug earlier
    (a stale, un-`wait`-ed background prisc+x process left over from a
    PRIOR test, racing on the same history.txt) - ps aux confirmed NO
    such stray process this time, so it's not literally the same cause,
    but could be something adjacent (a timing/ordering issue in how
    fast bash can append to history.txt vs. how fast the loop's own
    30ms poll + full move_player/choice/tick_jobs/compose_frame/
    compose_rgb_frame chain can actually execute per real keypress -
    each of those is a real fork/exec, not free).
  - history.txt NOT being truncated between separate test invocations
    was confirmed as a real, separate mistake earlier in THIS same
    debugging sub-thread (prisc+x's own read cursor is an in-memory
    register that resets to 0 on every process restart, so restarting
    without clearing history.txt replays the ENTIRE accumulated history
    from scratch) - already corrected for in the later attempts, did
    NOT explain the final failure.
FIRST CONCRETE STEP for whoever picks this up: don't assume this is a
real code bug OR dismiss it as "just timing" without checking - add
temporary logging (or just cat history.txt + the read-cursor's own
implied position, if inferrable) immediately after a full-loop test
that appears to only consume one key, and compare against what a
correctly-behaving run should show. If it turns out to be genuinely
about per-key processing latency, consider whether 30ms polling +ave
5 forked ops per tick is fast enough for rapid input in general (a
real, family-wide performance question, not just a test-harness one) -
don't assume "slower sleeps fixed it" without confirming WHY.

================================================================================
4. THIS FAMILY'S OWN STANDING TESTING LESSON (learned hard, worth
   restating for whoever's next)
================================================================================
- Direct op invocation (`ops/+x/foo.+x <args>`) proves the C LOGIC is
  internally correct. It does NOT prove the real prisc+x/pal loop
  reads/dispatches correctly - this session got burned by trusting
  direct-invocation-only testing more than once before switching to
  real-loop testing as the actual standard.
- Real-loop testing (background `prisc+x pal/main_loop.pal` +
  incrementally appending real keycodes to history.txt with real sleep
  gaps between them) is closer to truth but has its OWN failure modes
  (stale un-killed processes from a prior test, history.txt not
  truncated between runs, and now sec. 2's own unresolved timing
  question) - always `pkill` + `sleep` + truncate history.txt fresh
  before a new test sequence, and don't fully trust a single run's
  result if it contradicts direct-invocation testing without
  understanding why.
