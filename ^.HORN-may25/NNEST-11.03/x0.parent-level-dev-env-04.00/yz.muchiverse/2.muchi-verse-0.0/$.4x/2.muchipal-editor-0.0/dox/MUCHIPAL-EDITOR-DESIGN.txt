========================================================================
0. WHAT THIS PROJECT IS, IN ONE SENTENCE
========================================================================
A cross-project browser+editor for the $.4x family: pick one of the
family's real, live projects from a registry, browse its pieces
read-only, or open its map and actually edit terrain in place - built
on the REAL chtpm_parser_pal.c engine (not the flat PDL-action-bar
engine the 4 game projects use), because editing is a fundamentally
different interaction shape than playing a turn-based game.

========================================================================
1. TWO SOURCES OF VISION - WHAT EACH ACTUALLY SAYS
========================================================================
1.1 The real reference project: 1.TPMOS_c_+rmmp.0102.0028/projects/
    op-ed/README.md ("OP-ED: The Sovereign RPG Editor")

  This is the aspirational, full-scope vision. Key ideas worth
  carrying forward (NOT all to be built now - see sec. 4 "deferred"):

  - Sovereign Architecture: each game the editor works on is a
    "Sovereign Context." A Context Switch operation copies the WHOLE
    target project's directory into the editor's own working area
    before editing (a real disk buffer, not editing files in place
    live). Games are encapsulated one-per-directory under
    projects/op-ed/games/<name>/.
  - Standardized file-interaction model for Save As / Load, matching
    a sibling project (agy-text-editor)'s own conventions - i.e. this
    isn't a bespoke UI, it reuses a proven pattern from elsewhere in
    the family.
  - Two engine modes for the exported/played game itself: Mode 1
    (realtime WASD movement, straight C) vs Mode 2 (scripted PRISC
    interactions) - a fork in how the EDITED game runs, not how the
    editor itself runs.
  - Roadmap (explicitly phased, i.e. NOT all at once):
      Phase A - High-Level Event Editor: an "Op Selection" builder
        that generates real .asm scripts from a menu, rather than the
        author hand-writing PRISC assembly.
      Phase B - Standalone Exporter: bundles a project + a minimal
        runtime + an auto-generated boot.asm manifest into something
        that runs without the editor present.
      Phase C - Z-Level Editing (multi-layer maps) + Custom Traits (a
        no-code trait binder - e.g. attaching "Inventory" or "Health"
        to any entity without writing C).
  - Engineering doctrine worth keeping regardless of scope: "If it's
    not in a file, it's a lie" (state must be real files, not
    in-memory-only); the One Writer Rule (exactly one process owns
    writing current_frame.txt; everyone else reacts to
    frame_changed.txt) - this second one is the REAL origin of the
    "cooperating ops, self-filtering, one writer" pattern already used
    throughout the $.4x family's own ops.

1.2 The existing internal vision: 0.HANDOFF-2026-07-16.md's own
    "### muchipal-editor" section

  This is the SCOPED-DOWN, already-partially-built target - closer to
  what actually exists in this directory today. Its stated shape:
  - A title screen: pick a known project from a registry -> either
    "Browse Pieces" (read-only piece.pdl viewer) or "Edit Map" (a real
    editor: move a cursor, arm a tile type by digit from that
    project's own registry, Enter places the glyph AND saves
    immediately, ESC backs out of the screen).
  - Reads BOTH real tile-registry shapes the family has produced so
    far: "pipe" (glyph|id|name|walkable|rgb_top, one file - mutaclsym
    and, as confirmed this session, ALL FOUR current $.4x game
    projects) and "equals" (glyph=id in one file + a *.tile.txt per id
    - piececraft-3d-pal's own shape). Handling BOTH through one screen
    was called out explicitly as "the actual point of building it, not
    incidental" - i.e. registry-format-agnosticism is a real design
    goal, not an accident of whatever was built first.
  - Documented, still-open gaps at that point: no scrolling for maps
    bigger than the viewport, no undo, no furniture/second-layer
    editing, no way to register a new project except hand-editing
    known_projects.txt.
  - A documented real incident: a test run once wrote a stray test
    tile into a LIVE registered project's actual map.txt (recovered,
    but it's a standing risk any future agent must respect - see
    sec. 6).

1.3 How these two relate

  Op-ed is the "someday" ceiling; the internal vision is the "now"
  floor, and what's actually half-built in this directory IS that
  floor. This design doc's job is to describe the next real steps
  ABOVE the floor and BELOW the ceiling - not to jump straight to
  op-ed's full scope.

3. WHAT TO ACTUALLY BUILD NEXT (in priority order)
========================================================================
3.1 Self-maintaining known_projects.txt (small, high value)
  Currently the only way to register a new project is hand-editing
  the file (a documented, named gap in 0.HANDOFF-2026-07-16.md).
  Build a small "register_project" op: given a project's own root
  path, auto-detect its map_rel_path (find pieces/world_*/map_start/
  map.txt, prefer the non-template one) and registry_format/
  registry_rel_path (does pieces/registry/terrain/terrain_types.txt
  exist -> "pipe"; else does pieces/registry/tiles/registry.txt exist
  -> "equals"), then append a real row. This directly prevents the
  next stale-registry problem from recurring, and it's a small,
  self-contained op consistent with the family's "one binary per
  verb" convention.

3.2 Instance editing (bank-vs-instance-dir), not just terrain
  Today's editor only edits TERRAIN glyphs on the map. But every
  $.4x game project now also has real spawnable INSTANCES (units in
  civ-pal, anglers in angler-empires, entities in muchimon-pal,
  players in pal-craft) living in pieces/world_*/*/​<kind>/<id>/
  state.txt, built from a *_bank.txt template registry (unit_bank.txt,
  angler_bank.txt, entity_bank.txt, player_bank.txt - see pal-
  standards.txt's own bank-vs-instance-dir section for the general
  pattern). An editor that can only paint terrain but can't place a
  Settler or a wild Sparkit onto the map is missing half the actual
  authoring surface.
    Concrete addition: extend "Edit Map" with a second armed-item
  class alongside terrain rows - bank rows, read from whichever
  *_bank.txt the current project's known_projects.txt row points at
  (this needs a NEW field, e.g. `bank_rel_path`, added to
  known_projects.txt's schema). Placing one calls that project's own
  spawn_<kind>.c op via system() with the target tile's coordinates -
  reuse the existing spawn machinery, don't reimplement it.
    This also means known_projects.txt's schema needs a `bank_rel_
  path` column added (currently
  id|display_name|path|map_rel_path|registry_format|registry_rel_path)
  - do this as part of 3.1's rebuild, not as a second breaking schema
  change later.

3.3 Z-layer map support
  pal-craft's own map format already has real Z-layers (map_z<N>.txt,
  ported from piececraft-wraith's proven convention - see PAL-CRAFT-
  DESIGN.txt). The current editor only knows a single map.txt per
  project (a documented gap: "no furniture-layer editing" in
  0.HANDOFF-2026-07-16.md is this same gap under an older name).
  Concrete addition: known_projects.txt's map_rel_path should support
  a small convention - if the path contains a "%Z%" token, treat it as
  a per-layer template (map_z%Z%.txt) and add a "change layer" input
  (e.g. '[' / ']') to map_edit_input.c that switches which physical
  file subsequent edits write to. Projects without Z-layers (the
  other three) simply don't use the token and behave exactly as today.

3.4 Consider porting the xlector/interact model - RECOMMENDATION:
  DO NOT PORT IT HERE, at least not this pass.
  Rationale: sec 28/30/31/32's whole model exists to solve a problem
  this editor doesn't have - choosing between "control the free
  cursor" vs "control/focus a possessed piece" during PLAY. The
  editor's own arm-a-registry-row/place/save loop already IS its own
  correct, simpler analogue of the same idea (a cursor plus an "armed"
  selection), built against the real 1.TPMOS map-editor precedent
  rather than the game engine's own possession model. Forcing the
  possession-config/interact_mode machinery in here would be solving
  an already-solved problem with a heavier, genre-mismatched pattern
  purely for consistency's sake - exactly the kind of premature
  unification this family's own standards argue against. Keep
  map_edit_input.c's existing scheme; extend it (sec 3.1-3.3) rather
  than replace it.

4. EXPLICITLY DEFERRED (real, from op-ed's roadmap, not being built now)
========================================================================
  - Sovereign Architecture / Context Switch (copy-into-working-buffer
    before editing). Currently this editor edits a registered
    project's real files in place. This is the single biggest
    divergence from op-ed's own doctrine and the DIRECT cause of the
    real incident in sec. 6 below - worth doing eventually, explicitly
    NOT required to start sec. 3's work, since sec 3 is additive to
    the existing in-place model.
  - High-Level Event Editor (.asm-generating "Op Selection" builder).
  - Standalone Exporter / Project Bundler / boot.asm manifest.
  - Custom Traits / no-code trait binder.
  - Undo (named gap since 0.HANDOFF-2026-07-16.md, still real, still
    not addressed by anything in sec. 3 - flagging again rather than
    letting it go stale a second time).

6. SAFETY - CARRY THIS FORWARD, DON'T LOSE IT AGAIN
========================================================================
0.HANDOFF-2026-07-16.md documents a REAL past incident: a test run
once wrote a stray test tile directly into a LIVE registered project's
actual map.txt (recovered before that session ended, but it happened).
Because sec. 4 confirms Sovereign-Architecture copy-before-edit is
being deferred, this risk is STILL LIVE today and will remain live
through all of sec. 3's work too, since none of it changes the
in-place-editing model. Standing rule for whoever works on this next:
before testing ANY edit-and-save path, either (a) point known_
projects.txt's test row at a throwaway scratch copy of a project, not
a real registered one, or (b) `git status`/back up the real project's
map.txt first. Don't rediscover this the hard way a second time.
