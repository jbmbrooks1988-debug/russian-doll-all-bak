CORRECTION FIRST: it didn't compare, because I built pal-op's event catalog
(message/teleport/spawn) without ever opening the 4 reference files already
sitting in this exact directory (10.top-scratch-pieces.txt, event.commands.

was the actual point of dropping them here, and I skipped it. This document
does the comparison for real, against the real files.

TAKEAWAY: 7 of Scratch's 10 "essential" blocks already have a real
equivalent SOMEWHERE in this family's existing engine code - they're just
locked inside hardcoded C, never exposed as something an author can PLACE
without writing a line of code. That's the actual gap pal-op's event editor
should be closing, and right now it only closes 1 of those 7 (teleport).
The 3 genuinely new-machinery items (author-placeable If/conditional,
author-placeable variable control, broadcast/signal) are covered by RPG
Maker's own menu below (sec. 2), which is a much more complete reference
than Scratch's 10-block summary.

2. RPG MAKER MV'S EVENT COMMANDS MENU vs. PAL-OP'S 3-ITEM CATALOG
================================================================================
Per event.commands.1/2/3.txt (the real, in-full RPG Maker MV command
palette - ~15 categories, ~70 commands). Pal-op's current catalog
(message/teleport/spawn) maps onto exactly 3 of these ~70 commands. Full
category-by-category comparison:

  --- event.commands.1.txt ---
  Message category:
    Show Text...          -> THIS IS pal-op's "message" op, minus real text
                             entry (canned "Welcome!" only - see pal-op-
                             handoff.txt sec. 3.2's own named gap).
    Show Choices...        -> NOT BUILT. Real gap - would need a menu-
                             building primitive (a numbered list an author
                             defines per-event), structurally similar to
                             project_browser.c's own digit-select screens
                             but AUTHORED per event, not hardcoded per
                             screen. Genuinely new machinery.
    Input Number...        -> NOT BUILT. Needs real numeric text entry
                             (named gap in pal-op-handoff.txt sec. 3.2) -
                             this is likely the SAME underlying primitive
                             Input Number/Select Item/teleport-target-entry
                             all need; worth building ONCE, not 3 times.
    Select Item...         -> NOT BUILT, needs inventory system + the same
                             numeric-entry primitive above.
    Show Scrolling Text... -> NOT BUILT, cosmetic, low priority.

  Party category (Change Gold/Items/Weapons/Armors/Party Member):
    ALL NOT BUILT for $.4x - none of the 4 game projects have a shared
    "party" resource concept the way an RPG does. Muchimon-pal is the
    closest fit (it has an inventory/hero concept) but even there, "Change
    Party Member" would map onto something like "swap active possessed
    entity," which pal-op's OWN xlector/possession investigation this
    session (see !.pal-standards.txt sec. 28/30/31/32) already fully
    solved the mechanics for - just never exposed as an event.

  Game Progression category:
    Control Switches...    -> NOT BUILT as an author primitive, but this is
                             EXACTLY what a generalized "Change Variable"
                             event op would be for boolean state - real,
                             valuable, and cheap once the underlying
                             mechanism (write an arbitrary key=value into
                             some project state file) exists.
    Control Variables...   -> Same as above, numeric version. THIS PAIR
                             (switches+variables) is arguably the single
                             most valuable RPG Maker command to port,
                             because virtually every OTHER event type in
                             this whole menu (conditional branches, shop
                             unlocks, quest flags) is built ON TOP of
                             switches/variables in a real RPG Maker
                             project. Building this before "Show Choices"
                             is the right order - it's the load-bearing
                             primitive underneath most of the rest.
    Control Self Switch... -> Same mechanism, scoped to one event instance
                             instead of project-wide - directly maps onto
                             pal-op's own events.txt row concept (add a
                             4th field, e.g. x|y|op_id|self_switch_state).
    Control Timer...       -> NOT BUILT, low priority (no $.4x project
                             currently has time-pressure mechanics).

  Actor category (Change HP/MP/TP/State/EXP/Level/Parameter/Skill/
  Equipment/Name/Class/Nickname/Profile):
    PARTIALLY ANALOGOUS - civ-pal/angler-empires/muchimon-pal's own bank
    rows already carry hp/attack/defense fields (see zest-er-summary's own
    bank-vs-instance-dir doctrine), and muchimon-pal's choice.c already
    mutates hp at runtime (its attack/capture dispatch). An "event that
    changes an instance's own stat field" is a real, cheap extension of
    pal-op's existing "spawn" op pattern - same events.txt row shape,
    different op_id, writing directly into an instance's state.txt instead
    of creating a new one.

  --- event.commands.2.txt ---
  Movement category:
    Transfer Player...     -> THIS IS pal-op's "teleport" op exactly,
                             minus real target-coordinate entry (hardcoded
                             to (0,0) right now).
    Set Vehicle Location.../Set Event Location.../Scroll Map.../Set
    Movement Route.../Get on/off Vehicle -> NOT BUILT, all assume game
                             mechanics (vehicles, scripted NPC movement
                             routes) none of the 4 $.4x projects currently
                             have. Real, but far-future.

  Character category (Change Transparency/Followers/Show Animation/Show
  Balloon Icon/Erase Event):
    Erase Event            -> CLOSEST NEW THING WORTH BUILDING. A "remove
                             this event/this instance" op_id is genuinely
                             cheap (muchimon-pal's own choice.c already
                             deletes a fainted entity outright on hp<=0 -
                             same primitive, exposed as an event instead of
                             hardcoded combat logic).
    Everything else        -> cosmetic/animation, real but low priority
                             until pal-op's own ASCII/GL renderers support
                             more than flat glyphs/tiles.

  Timing/Screen/Audio&Video/Picture categories:
    ALL NOT BUILT and genuinely far from this family's current scope (no
    project has BGM/SE, screen tint/shake, or picture layers at all yet) -
    not worth detailing further here; flagging only so nobody assumes
    these are small additions. They are not.

  --- event.commands.3.txt ---
  Scene Control category (Battle Processing/Shop Processing/Name Input/
  Open Menu/Save/Game Over/Return to Title):
    Battle Processing...    -> muchimon-pal's own on-map tactics battle
                             (already built, per MUCHIMON-DESIGN.txt sec.
                             8) is a DIFFERENT design choice than RPG
                             Maker's separate battle scene, made
                             deliberately this session - not a gap, a
                             considered divergence. Worth stating
                             explicitly so nobody "fixes" muchimon-pal
                             toward RPG Maker's own shape by mistake.
    Shop Processing...      -> NOT BUILT, needs Party/Gold (not built) as
                             a prerequisite.
    Open Menu Screen/Open Save Screen/Game Over/Return to Title -> these
                             are all real, TITLE-SCREEN-ADJACENT flow
                             control every $.4x game's own title_input.c
                             already partially has (New Game/Load Game) -
                             "Game Over"/"Return to Title" as an
                             AUTHOR-PLACEABLE event (vs. hardcoded on
                             hp<=0) is a small, real, cheap extension.

  Map/Battle/System Settings/Advanced categories:
    Script.../Plugin Command... (Advanced) -> WORTH NOTING SPECIFICALLY:
    RPG Maker's own escape hatch for "there's no menu command for this" is
    literally "write a script" - i.e. even RPG Maker's own real, mature,
    commercially-shipped event system doesn't try to cover 100% of cases
    with canned menu items; it always keeps a raw-code fallback. Op-ed's
    own real roadmap (README.md's Phase A, cited in MUCHIPAL-EDITOR-
    DESIGN.txt) already plans for exactly this shape eventually (an Op
    Selection builder that GENERATES scripts, not one that replaces
    scripting entirely) - the 3-canned-op catalog built this session is a
    reasonable FIRST rung of that ladder, not a wrong design, just a very
    early one relative to RPG Maker's own ~70-command, decade-mature menu.
    Everything else in Map/Battle/System Settings is not applicable yet
    (no $.4x project has a battle-scene/tileset-switching/vehicle system).

================================================================================
3. THE ACTUAL PRIORITIZED GAP LIST (what this comparison changes)
================================================================================
Before this comparison, pal-op-handoff.txt's own sec. 3.2 just said
"argument entry for events... a scoped, doable next step," with no real
ordering. Now, cross-referenced against the real RPG Maker menu, the
priority order should be:

  1. Control Switches/Control Variables (a generic "write key=value into
     project state" event op) - THE load-bearing primitive almost every
     other real RPG Maker command sits on top of. Build this before
     anything else in this list.
  2. Numeric argument entry (blocks Input Number, Select Item, and real
     teleport-target-coordinate entry all at once - one primitive, three
     unlocked features).
  3. Control Self Switch (trivial once events.txt gets a 4th field) -
     unlocks per-instance state (e.g. "this door is already open").
  4. Erase Event / a "delete this instance" op_id (cheap - muchimon-pal's
     own choice.c already has the exact primitive, just needs exposing).
  5. Change Actor Stat (HP/MP/etc.) - cheap, same row shape as spawn,
     writes into an existing instance's state.txt instead of creating one.
  6. Show Choices... - needs (1) and a real menu-building primitive; do
     this AFTER switches/variables exist, since choices are usually used
     to SET a switch/variable in a real RPG Maker project.
  Everything else in the RPG Maker menu (Party/Shop/Battle/Screen/Audio/
  Vehicles) assumes game systems no $.4x project has yet - real, but
  correctly out of scope until those systems exist, not a pal-op gap.

This list supersedes pal-op-handoff.txt sec. 3.2's own vaguer framing -
that document should be read as "argument entry is A real gap"; THIS
document is the one that says which arguments, in which order, and why.
