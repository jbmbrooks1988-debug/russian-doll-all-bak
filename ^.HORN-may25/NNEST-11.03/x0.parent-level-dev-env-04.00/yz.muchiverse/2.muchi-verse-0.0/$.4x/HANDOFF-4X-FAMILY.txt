========================================================================
1. WHY THESE FOUR PROJECTS EXIST (one paragraph each)
========================================================================
angler-empires: player controls 7 alien "anglers" (Dwarf Fortress's 7
starting dwarves, reskinned) building an "Expanse" (fortress) on a home
planet, while 6 other planets each hold a rival 7-alien tribe (NPC,
hostile). New mechanic: designate/build jobs executed by idle-labor AI.

muchi-civ-pal: Civilization-style 4X, explicitly NOT a single continent
- a SOLAR SYSTEM map where each PLANET is itself an embark/city site
(direct user correction during design: "not a world map a solar system
map"). Multiple cities per civ, spread across multiple planets, plus a
tech tree.

muchimon-pal: Pokemon Red/Blue clone - overworld towns/routes (near-
identical fit to the existing mansion-room engine), wild encounters via
tall-grass tiles, a new turn-based battle mode, a 6-slot player party of
caught, individually-stateful muchimon.

pal-craft: Minecraft-style voxel builder. The one project needing a
REAL engine gap filled (today's engine has exactly one flat 2D map.txt,
no Z-concept) - solved by porting the ALREADY-PROVEN Z-layer map format
from a DIFFERENT real project in this machine's own history,
piececraft-wraith (1.TPMOS_c_+rmmp.0102.0028/projects/wraith-alpha/
wraith-projects/piececraft-wraith) - one flat text grid file per Z-
level (map_01_z0.txt, z1.txt, z2.txt...) plus per-tile extrude/solid/
rgb_side properties, NOT a new voxel format invented from scratch.

------------------------------------------------------------------------
3.1 BUILD THE INSTANCE MACHINERY (do this FIRST, it's shared
    infrastructure all four projects' own new mechanics depend on)
------------------------------------------------------------------------
Every one of the four design docs independently specifies the SAME
bank-vs-instance-dir split (angler_bank.txt/unit_bank.txt/monster_
types.txt-as-species-bank + a per-instance piece dir under state.txt) -
this is not four separate features, it's ONE reusable pattern that
needs building once, then applied four times with different bank
content. Concretely, for whichever project is picked first (see 3.2):

  1. Write the project's own BANK file (angler_bank.txt / unit_bank.txt
     / monster_types.txt-extended / the block/species bank that
     project's own doc names) - a static pipe-delimited registry, no
     code yet, just the data file with a handful of real rows (not a
     placeholder - real content the user has approved, since every doc
     ends with "TBD with user" on final names/values; get that
     confirmed before or while writing the bank).
  2. Write ONE new op that SPAWNS a living instance from a bank row:
     reads a bank id, creates pieces/world_<x>/map_start/<kind>/
     <instance_id>/state.txt (or the project-specific instance-dir
     path its own doc names in sec. 3/4) with the bank's own default
     fields copied in as STARTING state (hp, position, etc.) - same
     shape as how monster_types.txt's existing hp column already
     doubles as a spawned instance's starting max_hp today (see that
     file's own header comment, already true in the CURRENT engine,
     not new) - this op is mostly a generalization of a pattern that
     partially already exists for monsters, not built from zero.
  3. Confirm every OTHER op that needs to read a living instance's
     state (move_player.c for position, compose_frame.c for rendering,
     a future tick_jobs.c-equivalent for AI) reads from the INSTANCE
     dir, never the bank file directly for anything that can change at
     runtime - the bank is read-only template data once the game is
     running; grep for this before assuming it, don't guess.
  4. Verify end-to-end with the SAME direct-binary-invocation method
     already proven throughout this family (see PAL-craft's own dox 04
     status doc, sec. 5's "Testing Notes" for the exact worked example:
     export PRISC_PROJECT_ROOT, call ops/+x/<op>.+x directly, inspect
     the resulting state.txt file by hand) BEFORE wiring it into the
     real keypress-driven game loop.

  Once this is proven for ONE project, porting it to the other three
  is mostly "same op shape, different bank content, different instance
  path" - the pattern, not four separate implementations, per this
  family's own "prove one thing, then reuse the pattern" discipline
  (see zest-er-summary sec. 5's own "if you only remember one thing").

========================================================================
4. STANDING GOTCHAS THAT APPLY TO ALL FOUR PROJECTS (from the base
   engine + this family's own history - not new to this session)
========================================================================
  - PRISC_PROJECT_ROOT is cached at process startup, not re-read live -
    after ANY directory move/rename (including the $.4x/ move just
    done), sweep for orphaned processes by real /proc/$pid/cwd (not by
    name) before assuming a stale process isn't still writing to an
    old path. Nothing was running during this session's move, but this
    is a real, previously-reproduced bug elsewhere in this family - do
    the sweep as a habit, not just when something looks wrong.
  - ONE VISIBLE FRAME WRITER RULE: no op writes pieces/display/
    current_frame.txt directly except compose_frame.c's own step - a
    new op writes its own view/state, then pings frame_changed.txt (or
    calls compose_frame.c directly if it needs an immediate re-render,
    per PAL-NET-STANDARD sec. 6's own documented "pinging the marker
    alone is not enough" bug class).
  - APPEND, DON'T REORDER pipe-delimited registry columns - every new
    column added to an existing registry (terrain_types.txt,
    monster_types.txt, characters.txt) must go at the END, since ops
    read these files by fixed column index; a reorder silently breaks
    every existing reader. Every design doc in this directory already
    states this per-file; it's restated here because it applies to
    ALL of them uniformly.
  - DESIGN-DOC-FIRST held for all four so far - keep holding it for
    3.1/3.2's actual code: if the instance-machinery op's exact
    calling convention isn't obvious from a design doc alone, write a
    short note (even a comment block) before coding it, don't
    freehand a shape and hope it matches what four documents implied.
  - Session isolation / kill-by-cwd / register-sentinel-bug-class -
    all still apply if/when any of these projects grows a persistent
    background poll process (tick_jobs.c-equivalent, battle-mode
    ticker, etc.) - re-read zest-er-summary sec. 6's own "standing
    conventions that apply everywhere" block before building one,
    not summarized again here to avoid drift from the source.
