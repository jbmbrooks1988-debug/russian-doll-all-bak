================================================================================
1. WHAT PAL-OP IS, IN ONE SENTENCE
================================================================================
A cross-project browser+editor: pick a real, live $.4x/mutaclsym-family
project from a registry, browse its pieces read-only, edit its terrain map,
place real spawned instances (units/anglers/players/entities) from that
project's own bank, author simple canned events, and launch that project's
own real game session - all from one chtpm-based tool, built on top of the
same prisc+x/pal engine every other project in this family shares.

3.1 Runtime event triggering (the biggest real gap) - CORRECTED

  THE CORRECTION: an earlier draft of this section (and of common-ops-
  catalog.txt sec. 5) described a "dispatch_event.c" as something baked
  INTO each project's own move_player.c - a C function call added to
  existing movement logic. That's the wrong shape. RPG Maker's own events
  are invisible to the player precisely because they're a separate
  authoring/runtime layer the ENGINE runs on its own tick - not hand-
  written game logic threaded through the player's own movement code.
  The correct equivalent in this family is a STANDALONE OP, registered in
  default_op.txt and called as its own line in main_loop.pal, the exact
  same shape angler-empires' own tick_jobs.c already uses (called right
  after end_turn, every turn, self-filtering, invisible to the player -
  they just see a job get done, never "a tick_jobs op ran"). Event
  dispatch should be architected the SAME way: a new line in main_loop.pal
  right after move_player, not a function bolted inside move_player.c
  itself. This keeps the "one verb, one binary" convention intact and
  means the event catalog can grow without ever recompiling move_player.c
  - which IS what "built on pal, invisible to the player" concretely
  means in this engine: the player experiences the effect (teleported,
  saw a message), never the mechanism (a specific op ran this tick).

3.2 Argument entry for events - CORRECTED PRIORITY ORDER (2026-07-21, per
    #.rpgmv-events-menu/EVENT-CATALOG-COMPARISON.txt - a real, overdue
    comparison against RPG Maker MV's own actual ~70-command Event
    Commands menu and Scratch's 10 essential blocks, both of which were
    sitting in that directory, unread, when the 3-op catalog was built).
  This used to just say "argument entry is a real gap, teleport target
  entry is a scoped next step" with no real ordering. The comparison
  changes that: RPG Maker's own "Control Switches.../Control Variables..."
  commands are the LOAD-BEARING primitive almost every other real event
  type sits on top of (branches, shop unlocks, quest flags, choice
  outcomes are all built on a switch/variable write in a real RPG Maker
  project) - NOT a 4th peer alongside message/teleport/spawn, but
  conceptually op #1, even though it wasn't built first here. Corrected
  build order for whoever picks this up:
    1. A generic "write key=value into project state" event op (Control
       Switches/Variables' own equivalent) - build this BEFORE anything
       else below, even though it wasn't built first historically.
    2. Numeric argument entry (a "digit-accumulator enters a number"
       input mode, reusing project_browser.c's own digit_accum field/
       pattern) - unlocks real teleport-target x/y entry AND RPG Maker's
       own Input Number/Select Item commands at once, one primitive,
       three features.
    3. Control Self Switch equivalent (trivial once events.txt gets a 4th
       field) - per-instance state, e.g. "this door is already open."
    4. An Erase Event / "delete this instance" op_id - cheap, muchimon-
       pal's own choice.c already has the exact primitive (deletes a
       fainted entity outright), just needs exposing as an event.
    5. Change Actor Stat (HP/etc.) - same events.txt row shape as spawn,
       writes into an existing instance's state.txt instead of creating
       one.
    6. Show Choices... (a real menu-building primitive) - do this AFTER
       1-2 exist, since in a real RPG Maker project, choices are usually
       used to SET a switch/variable, not stand alone.
  Free text (custom messages, as opposed to numbers) still genuinely
  needs a new input primitive this whole family has never built - don't
  attempt it as a side effect of any of the above; it's a separate,
  larger, later thing.
  See EVENT-CATALOG-COMPARISON.txt's own sec. 3 for the full reasoning,
  including which RPG Maker categories are correctly OUT of scope
  entirely (Party/Shop/Battle/Vehicles/Screen/Audio - all assume game
  systems no $.4x project has yet, not a pal-op gap).

4. HOW THIS INTEGRATES WITH PAL-AGENT AND THE OTHER MUCHI-VERSE VISIONS
================================================================================
(Read yz.muchiverse/$.zest-er-summary-FIN❤️‍🔥️+.txt in full before acting on
this section - it is the authoritative source for everything summarized
below, this is only the bridge between that world and pal-op specifically.)

4.1 pal-agent can ALREADY drive pal-op today, with zero new connector code
  muchi-pal-agent's own tool-calling layer (file_ops.c, edit_file.c,
  cmd_exec.c, list_dir.c, search_in_files.c - all "provider-agnostic,
  already proven," per zest-er-summary sec. 4.1) is exactly the shape
  needed to operate pal-op RIGHT NOW, because almost every pal-op action
  is already a single, self-contained CLI exec:
    - register_project.c takes its args directly (root_path, display_name)
      - trivially one cmd_exec.c call, no state-file dance needed at all.
    - map_edit_input.c/compose_title_frame.c/compose_rgb_frame.c all read
      pieces/system/editor_state.txt and take one keycode argument - an
      agent (or a thin wrapper script) can write cursor_x/cursor_y/
      armed_idx/arm_mode into editor_state.txt directly (file_ops.c can
      already do this - it's a plain key=value text file, same as every
      other piece of state in this whole family), then exec
      map_edit_input.+x with the right keycode (13 for Enter, 'b'/98 or
      'v'/118 to switch modes, '1'-'9' to arm) to actually place terrain/
      an instance/an event.
    - Reading pal-op's own output is just as direct: file_ops.c reading
      pieces/display/current_frame.txt gives an agent the exact same
      ASCII view a human sees.
  CONCRETE NEXT STEP if this integration is wanted: write a thin
  TOOL:-convention wrapper specifically for pal-op (matching sec. 4.1's
  own gemma "TOOL: <verb> <args>" pattern exactly) - e.g.
    TOOL: pal_edit_terrain <glyph_idx> <x> <y>
    TOOL: pal_edit_place_bank <bank_idx> <x> <y>
    TOOL: pal_edit_place_event <op_id> <x> <y>
    TOOL: pal_edit_register_project <path>
  where the parser translates each verb into exactly the
  editor_state.txt-write + exec sequence above. This is a NEW parser +
  4 short case branches, reusing cmd_exec.c/file_ops.c's own execution
  layer untouched - same "only the parsing layer is new" principle
  zest-er-summary's own sec. 4.1 already establishes for gemma's tool
  calling, applied to a new verb set instead of a new model.

4.2 The not-yet-built "ui_drive connector" is the other half - PLAYING,
    not just authoring
  CHAT-INTEGRATION-ARCHITECTURE.txt's own sec. 2 (per zest-er-summary)
  describes a generic connector (session launch/inject-key/read-frame/
  kill ops) for driving a live, continuously-running chtpm session from
  outside it - DESIGNED, NOT built yet; irc-agent-0000 used a simpler
  direct_ops path instead because it didn't need this. pal-op's own new
  "Play Project" launcher (sec. 2.4 above) is exactly the hook point
  where this connector WOULD attach once built: an agent could launch a
  project via pal-op, then use inject-key/read-frame to actually watch
  and react to a live playthrough - the same shape irc-agent-0000 already
  proves works for pal-chat-irc, just applied to a $.4x game session
  instead of a chat room. Don't build this FOR pal-op specifically -
  build the generic connector once (as zest-er-summary's own sec. 2
  already scopes it), and pal-op's Play Project button becomes one of
  several places it plugs in.

4.3 pal-scripts/ meta-orchestration is the natural home for an agent-driven
    launcher
  pal-scripts/pal-chat-agent.pal + launch_irc_agent.sh (a thin .pal that
  execs into a launcher shell script, which starts a project in a
  session-isolated, keyboard-input-less mode - renderer + prisc+x only,
  no human at the keyboard - then injects keys via the same file-
  injection technique used everywhere in this family) is the exact
  precedent for a future pal-scripts/pal-edit-agent.pal: launch pal-op
  headless, inject registration/placement keys the same way, no new
  launch mechanism needed - just a new script following the proven
  shape.

4.4 pal-op is already a conformant citizen of the registry+switch/bank
    convention
  known_projects.txt IS the same "one file, many rows, pipe-delimited"
  BANK shape as model_list.txt/trigger_list.txt/the npc_bank idea (zest-
  er-summary sec. 4.4/4.6) - nothing to change here. register_project.c
  is the equivalent of switch_model.c: it's the op that adds a new row
  to the bank. This alignment happened naturally (both families evolved
  the same pattern independently, for the same reasons) rather than by
  deliberate cross-reference - worth knowing so nobody "fixes" pal-op's
  registry into some other shape without realizing it already matches.

4.5 SCALE_BANK - a real future consideration for event triggering (3.1
    above), not for pal-op itself
  Once runtime event triggering (sec. 3.1) exists, an event's own
  fidelity is exactly a (entity_type=event, domain=trigger_behavior,
  scale_level) SCALE_BANK key (zest-er-summary sec. 4.6) - e.g. "message"
  could stay a flat log-append forever (small scale is always enough),
  while "spawn" might eventually want a large-scale tier (a real cutscene
  sequence, multiple spawns, a camera pan) versus today's small-scale
  single spawn. Flagging this now so whoever eventually builds 3.1 knows
  the SCALE_BANK pattern exists and fits - but per that section's own
  "prove one thing before generalizing" discipline, do NOT build a
  SCALE_BANK abstraction before runtime triggering itself is even proven
  once. This is a note for later, not a task for now.
