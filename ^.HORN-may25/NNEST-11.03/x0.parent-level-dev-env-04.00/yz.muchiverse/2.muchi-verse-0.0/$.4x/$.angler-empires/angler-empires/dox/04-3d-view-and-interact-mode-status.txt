2. 3D VIEW - PORTED THIS SESSION, GL-ONLY
========================================================================

Ported from mutaclsym's own compose_rgb_frame.c (the CURRENT copy, see
§0) into this project's ops/compose_rgb_frame.c. ASCII rendering
(ops/compose_frame.c) never reads render_mode at all - 3D only affects
the GL/RGB mirror window, matching mutaclsym's own convention.

2.1 New hero/state.txt fields (added to both pieces/world_angler_home/
    map_start/hero/state.txt and pieces/world_angler_home_template/map_start/
    hero/state.txt):
      render_mode=0      (0=2D, 1=3D - '0' toggles)
      camera_mode=1      (1=1st person, 2=3rd person, 3=free camera)
      cam_pan_x=0.00     (free-camera pan offset, POV 3 only)
      cam_pan_y=0.00
      cam_pan_z=0.00
      facing=1002        (last arrow direction pressed - drives 1st-
                          person view direction)

2.2 Controls:
  - Arrows: movement, ALWAYS - both the hero (normal mode) and the
    xlector cursor (interact_mode=1), in BOTH 2D and 3D.
  - wasd: NO LONGER MOVES THE HERO. Real, deliberate behavior change
    (matches mutaclsym's own identical change) - freed up entirely for
    3D camera pan. If this project ever wants wasd back for movement,
    that's a conscious reversal to make later, not an oversight to fix.
  - '0': toggles render_mode. Global preference, works even with a
    panel (craft/inventory) open - same as 'e' (emoji toggle).
  - '1'/'2'/'3' (only while render_mode==1): sets camera_mode. Outside
    3D mode these keys keep their EXISTING action-bar meaning.
  - wasd (only while render_mode==1 AND camera_mode==3 - free camera):
    pans the camera. w/s forward/back, a/d left/right, x/z up/down.

2.3 Renderer (ops/compose_rgb_frame.c): project_3d() (perspective
    projection), yaw_rotate()/facing_to_yaw() (so "forward" always
    renders into the screen), a real per-pixel DDA ray marcher for
    walls (raymarch_walls_3d() - correct occlusion, correct per-angle
    face visibility, optional voxels_8.csv emoji texture per face if
    angler-empires ever generates those assets - gracefully falls back to
    a flat darkened color if it hasn't), flat floor quads for walkable
    tiles. Wired into main() as `if (render_mode==1) render_3d_view(...)
    else <original 2D tile loop>`.

2.4 Build: scripts/build.sh's compose_rgb_frame.c line now links -lm
    (needed for cos/sin/floor/fabs).

2.5 Footer indicator added (NOT present in mutaclsym - a real,
    small improvement made here, not a straight port): '[0] 3D:ON/OFF'
    in the action-bar footer (ops/compose_frame.c's build_choice_footer,
    now takes a render_mode parameter) - discoverability fix, since the
    ASCII view itself never visibly changes when 3D is toggled and a
    player would otherwise have no on-screen confirmation the key did
    anything. mutaclsym's own dox 06 §3.5 names this exact gap as still
    open there - it is NOT open here anymore, and this same footer
    indicator should probably be back-ported to mutaclsym too if/when
    convenient (not done this session - out of scope, this session's
    mutaclsym edits were limited to the bug fixes in §3 below).

3. REAL BUGS FOUND DURING LIVE PLAYTEST, FIXED IN BOTH PROJECTS
========================================================================

The ported 3D code compiled clean and produced real (non-blank, varied)
pixel output on the first pass, but two real orientation bugs surfaced
once actually played:

3.1 "Camera facing the player's back" (report: view showed what's
    BEHIND the hero, not what's ahead). Root cause: project_3d()
    structurally treats +Z (rz = wz - cam_z > 0) as "in front of the
    camera" - that's baked into its perspective-divide math, not a
    convention facing_to_yaw() gets to redefine independently.
    facing_to_yaw()'s ORIGINAL mapping (ARROW_UP=0°, ARROW_DOWN=180°)
    put north (ahead, when facing up) at negative rz - wrongly treated
    as behind - and south (actually behind) at positive rz - wrongly
    "in front". ARROW_RIGHT/LEFT had the identical class of inversion
    (confirmed by a second live playtest after the UP/DOWN fix landed).

    FIX (ops/compose_rgb_frame.c's facing_to_yaw()): swapped BOTH pairs
      ARROW_UP:    0deg   -> 180deg
      ARROW_DOWN:  180deg -> 0deg
      ARROW_RIGHT: 90deg  -> 270deg
      ARROW_LEFT:  270deg -> 90deg

    An EARLIER attempted fix (negating the whole `yaw` variable once at
    its definition) was tried first and was WRONG/incomplete - it left
    yaw=0 unchanged for the default ARROW_UP case (the most common
    facing), so it fixed nothing for the actual reported symptom. Left
    as a cautionary note, not because any trace of it remains in the
    code (it was fully reverted before the real fix above landed).

3.2 "The whole map seems inverted right and left" (a separate, static
    left-right MIRROR of the entire rendered scene, independent of
    facing - not a turning-direction issue, everything east/west was
    swapped regardless of which way the hero faced). Root cause: this
    project's world uses row-increases-DOWNWARD as its Z axis - a
    left-handed 2D plane - but yaw_rotate()'s rotation formula and
    project_3d()'s screen_cx + rx projection both assume the standard
    right-handed convention. That mismatch put east/west content on the
    opposite screen side from every other renderer (ASCII, item/monster
    placement, etc).

    FIX (two call sites, must change together or floor/walls misalign):
      - project_3d(): `screen_cx + rx*scale*persp` -> `screen_cx -
        rx*scale*persp`
      - raymarch_walls_3d(): `dx_cam = (sx - screen_cx)/(scale*focal)`
        -> `dx_cam = (screen_cx - sx)/(scale*focal)` (this is
        project_3d()'s own algebraic inverse - the per-pixel ray
        direction the wall marcher casts must invert the same way the
        floor pass's own projection did, or the two passes stop
        agreeing on which side of the screen is which).

Both fixes verified live in angler-empires first (user confirmation: "it
works" after each), THEN ported to mutaclsym's own compose_rgb_frame.c
verbatim (same three edits, same reasoning) per direct instruction -
mutaclsym's OWN 3D view had the identical bug, inherited from the same
original math this project's port came from. mutaclsym's copy compiles
clean after the port (gcc -Wall -Wextra -O2 -lm, zero warnings) but was
NOT independently re-playtested in mutaclsym itself this session - the
fix is a straight, verified-equivalent port of what was confirmed
working in angler-empires, not a separately-re-derived one. If mutaclsym's
own render_3d_view()/camera presets have since diverged further from
what this session read, re-verify there before trusting it blind.
