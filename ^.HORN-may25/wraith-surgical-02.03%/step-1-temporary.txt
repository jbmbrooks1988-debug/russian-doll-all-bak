## 2. Current State / Confusing Behavior To Fix First
- **POC target:** `mouse-test` was built with partially non-standard assumptions and should be cleaned first before applying the pattern to Wraith.
- **Project-specific lock drift:** `keyboard_input.c` still hardcodes project lock checks such as `projects/mouse-test/session/mouse_enabled.lock`.
- **Dual pipeline confusion:** raw `MOUSE_EVENT:` logging exists in `pieces/keyboard/history.txt`, while semantic `COMMAND: MOUSE_MOVE ...` traffic already exists in project session histories and is what managers actually consume.
- **Canonical inbox pattern already exists:** `mouse-test` and Wraith both already have semantic project inboxes in `projects/<id>/session/history.txt`.
- **Input path mismatch:** `projects/wraith-alpha/session/history.txt` already contains live `COMMAND: MOUSE_MOVE ...` traffic, but `wraith-alpha_manager.c` is still pointed at `projects/wraith-alpha/history.txt`.
- **Standard violation:** Wraith should follow the same clear TPM pattern seen in `fuzz-op` / `op-ed`: one primary project inbox for project semantics, then manager-owned state writes, then render pulse.
- **Verification risk:** If we start adding hot-zones before fixing the inbox path, we can misread failures as UI logic bugs when the manager simply never saw the event.

## 3. Canonical Directory / Data Flow

### A. Directory Roles
- `pieces/keyboard/plugins/keyboard_input.c`
  - Raw terminal listener.
  - Responsible for key capture and terminal mouse mode toggling.
- `pieces/keyboard/history.txt`
  - Global raw input ledger.
  - Good for raw `KEY_PRESSED:` and optional raw mouse audit.
- `projects/mouse-test/session/history.txt`
  - Canonical `mouse-test` semantic inbox.
  - This is where `mouse-test_manager.c` should read project-level mouse commands.
- `projects/mouse-test/manager/mouse-test_manager.c`
  - Proof-of-concept mouse manager.
  - Owns `mouse-test` GUI state writes and render pulse behavior.
- `projects/wraith-alpha/ops/wraith_parser_alpha.c`
  - Wraith semantic bridge.
  - Writes `COMMAND:` messages into the Wraith project inbox.
- `projects/wraith-alpha/session/history.txt`
  - Canonical Wraith semantic inbox.
  - This is where Wraith manager should read project-level commands like `MOUSE_MOVE`.
- `projects/wraith-alpha/manager/wraith-alpha_manager.c`
  - Owns Wraith desktop state transitions.
  - Reads semantic project commands and keyboard inputs, writes session state, pulses render.
- `projects/wraith-alpha/session/alpha_state.txt`
  - Manager-owned desktop/session state sink.
- `projects/wraith-alpha/session/desktop_ui_state.txt`
  - Manager-owned UI projection sink.
- `pieces/display/frame_changed.txt`
  - Global render pulse channel.

### B. Canonical Input Flow
1. `keyboard_input.c` reads raw terminal input.
2. Raw keyboard events append to `pieces/keyboard/history.txt`.
3. Mouse mode, when enabled, allows project semantic layers to produce `COMMAND: MOUSE_MOVE btn x y`.
4. Project semantic layers append those commands to `projects/<id>/session/history.txt`.
5. Project managers tail:
   - `projects/mouse-test/session/history.txt` for `mouse-test`.
   - `pieces/keyboard/history.txt` for raw keyboard nav.
   - `projects/wraith-alpha/session/history.txt` for Wraith semantic commands.
6. Managers update their project state sinks.
7. Managers append to `pieces/display/frame_changed.txt`.
8. Renderer/parser refreshes the frame.

### C. Standard Rule For This Work
- Raw input may exist in shared ledgers.
- Project behavior must be driven from the project semantic inbox, not from duplicate raw mouse paths.
- Mouse clicks must trigger one action path only. No fake Enter injection for click actions.
- Mouse focus and activation should mirror keyboard semantics:
  - First click on an unfocused interactive region focuses it.
  - Second click on the already-focused region activates it.
  - If a region is already focused, a single click may activate it.
