WRAITH J8 ONESHOT RESEARCH
Date: 2026-06-08
Source handoff: wraith-dev-notes-cal/wraith-j8/handoff-j8.txt

Goal
- Research the restore/minimize failure deeply enough to make a single confident fix pass later.
- Compare Wraith against known-working standards, not just local intuition.

Executive conclusion
- The current Wraith failure is not primarily a file-write race.
- The real break is an architecture mismatch between parser-visible navigation indices and manager-private action indices, plus a split inbox problem:
  - The parser delegates toolbar clicks as `COMMAND: SET_ACTIVE:n` into `projects/wraith-alpha/history.txt`.
  - The manager only watches `pieces/keyboard/history.txt`.
  - Numeric keyboard input still reaches the manager directly through `pieces/keyboard/history.txt`.
  - After minimize, the visible taskbar buttons are parser indices `1` and `2`, but the manager expects actions `5` and `6`.
  - Result: restore UI can look correct while Enter still executes the wrong manager action or no action at all.

Primary evidence

1. The manager generates hardcoded private action ids for toolbar buttons.
- File: `1.TPMOS_c_+rmmp.0102.0020/projects/wraith-alpha/manager/wraith-alpha_manager.c`
- `generate_toolbar_markup()` always emits:
  - launcher -> `SET_ACTIVE:5`
  - minimized window restore -> `SET_ACTIVE:6`

2. The layout exposes only currently visible interactives, so parser numbering is local, not manager-global.
- File: `1.TPMOS_c_+rmmp.0102.0020/projects/wraith-alpha/layouts/alpha-shell.chtpm`
- When the window is minimized, the titlebar controls disappear.
- The taskbar then shows only two visible buttons:
  - taskbar launcher
  - minimized window restore target
- In the frame history the user correctly navigates to visible item `2`, but the manager does not understand visible index `2` as restore.

3. The manager does have a restore action, but only for internal action id `6`.
- File: `1.TPMOS_c_+rmmp.0102.0020/projects/wraith-alpha/manager/wraith-alpha_manager.c`
- `execute_action(6)` restores the minimized window.
- `execute_action(2)` does nothing.

4. The failing restore attempt did not arrive as a delegated command.
- Manager log excerpt shows:
  - launch succeeded
  - minimize succeeded
  - then `Input received: 50`
  - then `Input received: 13`
  - no `Command received: SET_ACTIVE:6`
- File: `1.TPMOS_c_+rmmp.0102.0020/projects/wraith-alpha/manager/alpha_manager.log`
- This proves the manager processed raw key history, not the parser command inbox.

5. The parser delegates desktop actions into project session history, not keyboard history.
- File: `1.TPMOS_c_+rmmp.0102.0020/projects/wraith-alpha/ops/wraith_parser_alpha.c`
- `handle_desktop_action_command()` calls `inject_command(cmd)`.
- `inject_command()` writes `COMMAND: ...` into `projects/<project_id>/history.txt`, which for Wraith is `projects/wraith-alpha/history.txt`.

6. The manager never reads that delegated command file.
- File: `1.TPMOS_c_+rmmp.0102.0020/projects/wraith-alpha/manager/wraith-alpha_manager.c`
- Main loop only tails:
  - `pieces/keyboard/history.txt`
- It parses both `KEY_PRESSED:` and `COMMAND:`, but only from that one file.
- Therefore parser-delegated toolbar commands are invisible to the manager unless some other path mirrors them.

7. The current keyboard history confirms only raw keys were observed during the repro.
- File: `1.TPMOS_c_+rmmp.0102.0020/pieces/keyboard/history.txt`
- Tail contains only `KEY_PRESSED:` entries for the minimize/restore repro.
- No `COMMAND: SET_ACTIVE:6` entries are present there.

Why the original handoff's race theory looked plausible
- The state files do get rewritten in multiple places:
  - `alpha_state.txt`
  - `desktop_ui_state.txt`
- The parser also reloads Wraith state repeatedly.
- That can produce stale-looking UI symptoms.
- But the restore repro is explainable before any race analysis:
  - the restore command is not entering the manager on the correct channel
  - and the fallback raw Enter path uses the wrong index namespace
- So the first confident fix should target routing correctness, then only revisit sync timing if a residual bug remains.

Observed failure chain from the provided frame history
1. Loader launches Wraith.
2. Enter on taskbar launcher opens Terminal #1.
3. `3` then Enter minimizes it.
4. Manager explicitly jumps its own focus to internal index `5`.
5. Parser redraw now shows only two visible taskbar items:
   - visible `1` = launcher
   - visible `2` = minimized Terminal #1
6. User presses `2` then Enter.
7. Manager receives raw key `50` then raw Enter `13`.
8. No delegated `SET_ACTIVE:6` reaches manager.
9. Manager executes `execute_action(g_active_gui_index)` where `g_active_gui_index == 2`.
10. Action `2` is a no-op.
11. Restore appears broken.

Working implementation comparisons

A. Fuzz-op: working dynamic method pattern
- Files:
  - `1.TPMOS_c_+rmmp.0102.0020/projects/fuzz-op/manager/fuzz-op_manager.c`
  - `1.TPMOS_c_+rmmp.0102.0020/projects/fuzz-op/layouts/fuzz-op.chtpm`
- Standard used:
  - manager generates dynamic button markup
  - layout renders `${piece_methods}`
  - interaction channel is explicit through `<interact src="pieces/apps/player_app/history.txt" />`
  - manager watches the same logical command path for project actions
- Why it matters:
  - dynamic markup is fine when the command path is singular and agreed upon
  - Wraith currently lacks that inbox parity

B. Gem-dev: simpler and more directly relevant dynamic menu standard
- Files:
  - `1.TPMOS_c_+rmmp.0102.0020/projects/gem-dev/layouts/gem-dev.chtpm`
  - `1.TPMOS_c_+rmmp.0102.0020/projects/gem-dev/manager/gem-dev_manager.c`
  - `1.TPMOS_c_+rmmp.0102.0020/projects/gem-dev/#.dox/api-menu-fix-m19.txt`
- Standard used:
  - dynamic menu content is nested inside parser-native `ACTIVATE`
  - each dynamic option emits semantic commands like `SET_API:<url>`
  - manager reads those semantic commands from the same history stream
  - the design note explicitly says this avoids index conflicts and mapping issues
- Why it matters:
  - this is the cleanest direct precedent for Wraith
  - Wraith should prefer semantic commands like `RESTORE_WINDOW:terminal` or `DESKTOP_ACTION:restore:terminal`
  - not parser-visible index -> manager-private index translation

C. +-demo: simplest parser-native submenu standard
- File:
  - `1.TPMOS_c_+rmmp.0102.0020/projects/+-demo/layouts/+-demo.chtpm`
- Standard used:
  - `ACTIVATE` for scoped submenu
  - `BACK` for escape path
  - visible numbering belongs entirely to parser navigation
- Why it matters:
  - if Wraith wants taskbar items to behave like a dynamic menu, parser owns visible selection
  - manager should only receive semantic actions, never depend on parser's temporary visual numbering

What is currently non-standard in Wraith
- Dynamic taskbar buttons are rendered by the manager, but their `onClick` payloads are manager-private numeric ids.
- Parser-visible numbering changes as elements appear/disappear.
- Manager-global numeric action ids stay fixed at 1..6.
- Parser and manager are reading different histories for the same conceptual toolbar action.
- This violates the working standard seen in both `fuzz-op` and `gem-dev`.

Confident fix direction for a one-shot implementation

Recommended standard
- Use semantic command routing for dynamic taskbar actions.
- Keep manager-private index handling only for raw local keyboard fallback if needed.
- Make parser and manager agree on one inbox for Wraith commands, or have manager watch both inboxes.

Minimum robust fix set
1. Replace manager-generated dynamic toolbar commands:
   - launcher: not `SET_ACTIVE:5`
   - restore: not `SET_ACTIVE:6`
   - use semantic commands instead, for example:
     - `DESKTOP_ACTION:launch_terminal`
     - `DESKTOP_ACTION:restore_terminal`

2. Extend manager command routing to parse those semantic commands directly.
- Example:
  - `DESKTOP_ACTION:launch_terminal` -> launch logic
  - `DESKTOP_ACTION:restore_terminal` -> restore logic
  - optional `DESKTOP_ACTION:minimize_terminal`
  - optional `DESKTOP_ACTION:close_terminal`

3. Make the manager watch the parser-delegated history file in addition to keyboard history.
- Add a second tailed file:
  - `projects/wraith-alpha/history.txt`
- This is the safest alignment with current parser behavior.
- Without this, semantic commands still risk disappearing into the wrong inbox.

4. Preserve raw keyboard support separately.
- Raw keys from `pieces/keyboard/history.txt` can still drive:
  - digit shortcuts
  - arrows
  - Enter fallback
- But visible taskbar buttons should no longer depend on raw numeric coincidence.

5. After restore, explicitly project focus/index to a visible window control state.
- Suggested:
  - set `g_active_gui_index = 1` on restore, or another consistent open-window control target
- This prevents strange post-restore focus carryover.

Secondary cleanup worth doing in same pass if small
- Stop setting `desktop_focused_window_title` to `Terminal #1` when minimized/open=false in the manager projection.
- During minimized state, focus/title should probably reflect `Desktop`, matching visible reality.
- This is not the root cause of restore failure but it is currently misleading in state output.

What I do NOT currently think is the first fix
- I would not start with reorder-only changes around `rename(tmp, path)` and `trigger_render()`.
- That may still deserve verification later, but it does not explain the missing restore command in the log.

One-shot patch hypothesis
- A single confident patch should:
  - change Wraith toolbar markup to semantic commands
  - update manager routing to handle them
  - tail `projects/wraith-alpha/session/history.txt` alongside `pieces/keyboard/history.txt`
  - keep render triggering after state write completion as it already does
- If this patch is applied, the restore path should stop depending on parser/manager index parity and should match the working standard from `gem-dev`.

Validation plan for the later fix
1. Launch Wraith from loader.
2. Open Terminal #1.
3. Minimize Terminal #1.
4. Select taskbar restore target using visible nav index `2`.
5. Confirm manager log shows semantic restore command receipt, not just raw Enter.
6. Confirm `alpha_state.txt` flips to:
   - `desktop_window_1_open=true`
   - `desktop_window_1_minimized=false`
   - `desktop_window_1_body_visible=true`
7. Confirm frame redraw shows restored terminal body.
8. Repeat with launcher button after minimize to confirm no index collision remains.

Standardization note for future agents
- Prefer this order when implementing dynamic menus in this codebase:
  1. parser owns visible navigation
  2. dynamic markup emits semantic commands, not private numeric ids
  3. manager consumes one shared command stream
  4. raw key handling remains a fallback path, not the primary contract for dynamic UI actions
- Best parity references for that standard:
  - direct dynamic-command pattern: `gem-dev`
  - dynamic content injection pattern: `fuzz-op`
  - pure parser submenu pattern: `+-demo`
