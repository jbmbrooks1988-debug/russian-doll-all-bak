## 🧑‍🤝‍🧑 Part 1 — for humans: what happened today, in plain language

### 1️⃣ Renamed atlas-editor → aomorai-editor
Simple mechanical rename (project folder + internal strings), same "outer identity only" pattern used before. Shorthand: **"aomo"**.

### 2️⃣ Proved tile-picker's desktop chain actually works (and found it half-didn't)
We asked "does picking a tile really do anything?" and tested it for real instead of trusting old reports. Found: yes, the pipe works (`tile-picker → mutaclysm inbox → real map.txt edit`), **but** nothing runs the "drain" step automatically, and a couple of real bugs (missing directories, wrong file paths) meant it silently failed for a fresh project. Fixed those.

### 3️⃣ Tile-picker got a real "desktop placer"
Picking an emoji now:
- Writes a real, portable little package onto `#.desktop/tiles/<name>/`
- **Pops open a real, live GL window on your actual desktop** showing that emoji
- That window is draggable, snaps to the same invisible 80px grid your egg-pals already use, closes itself if you delete its package, and is capped at 30fps so it doesn't cook your CPU
- The emoji is rendered as a **real texture** (same FreeType/NotoColorEmoji pipeline egg-pals use to hatch), not just a colored square

### 4️⃣ The picker itself got rebuilt — twice
First attempt was a bespoke window that **you literally could not interact with** — it didn't plug into this house's real keyboard pipeline. Second attempt copied the real, proven pattern from `file-menu` (a real CHTPM screen: numbered buttons, real digit-jump nav, the works). This is now a real, working, house-standard widget. 🧠 **Lesson learned the hard way, now written down** so it doesn't happen a third time.

### 5️⃣ Real bugs found and fixed along the way
- A build script was silently deleting tile-picker's own "what do these keys mean" file and replacing it with an unrelated stock-trading game's version — keys just did nothing, no error.
- The desktop-tray path math was wrong for how this widget is actually laid out — tiles were landing inside tile-picker's own folder instead of the real shared desktop.
- Missing font/emoji-generator files meant the window rendered blank, then colors-only.
- A double-numbering bug on the buttons (fixed).
- **A pile of leftover test processes were eating real CPU** (~40% from one alone) — cleaned up, and the live window now hard-caps its own framerate.

### 6️⃣ "Any window has a PID now" + the "^" aiming mode 🎯
You asked: can I drag a placed tile straight into a board-view window, even without pre-pairing them? Real answer: yes, and here's what that took:
- Every widget window now gets tagged with its **real process ID** (a standard X11 thing called `_NET_WM_PID` that nothing in this house was setting before) — found and fixed a sneaky bug where two windows open at once could get mixed up.
- New design (**replaces** an earlier "type in a PID" idea you decided you didn't like): press Enter on an emoji and instead of placing it immediately, it goes into **"^" mode** — a crosshair-style aim state. Click **anywhere on screen** — bare desktop, or inside a board-viewer window — and it places there. Escape cancels.
- **What works right now:** click on bare desktop → places for real. Click inside a board-viewer window → **detects** that correctly now (this took a second bug fix — the first version was quietly missing every board-viewer click and just placing on the desktop instead), but only *actually materializes into the game* if that game uses mutaclysm's tile format. Aomorai-editor's own 3D world doesn't yet — you'll see an honest "not supported yet" message there instead of it silently failing.

### 7️⃣ Daylight fix
New worlds in aomorai-editor now start at **noon**, not midnight — a real bug where every fresh world's sun started below the horizon. Also nudged the one live test-save so you could actually see the fix in the board-viewer window.

### ✅ What to actually go test right now
1. Launch tile-picker (`&.widgits/tile-picker/button.sh run-widget`) — press a digit, press Enter, you should see **"^ ARMED"**. Click on your bare desktop. A little emoji window should appear right where you clicked.
2. Launch board-viewer focused on aomorai-editor (`&.widgits/board-viewer/button.sh run-widget /path/to/aomorai-editor`) at the same time. Arm another tile, click **inside** the board-viewer window this time. You should now get a real "detected, but not placeable here yet" message — not silent desktop placement.
3. Confirm board-viewer looks like daytime, not night.
4. If anything feels laggy or your fans spin up — tell me, there shouldn't be any leftover processes, but this is new enough to double check.

## 🤖 Part 2 — handoff to the next AI: how to grok this whole project and what's next

### The one-paragraph mental model
This house has exactly **one real input pipeline** (`keyboard_input.c`/`gl_mirror.c` → `history.txt` → `chtpm_parser_pal.c` → `interact_relay.txt` → `<project>_menu_input`), and every widget is a **fully self-contained session** (own copy of `system/`, own PAL loop, own CHTPM layout) that cross-links to a host only through small state files, never shared process infrastructure. **Read `&.widgits/tile-picker/TILE_PICKER_DESIGN.md` in full** — it has the complete, evidence-based build history, every real bug found this session, and exact file/function references. Don't re-derive any of it from scratch.

### The real scope, going forward
Direct instruction, 2026-08-04: the actual end goal is a **game editor** whose widgets let creators build and modify game entities either **on the literal desktop** or **inside a game/board view** — and, crucially, this is the *same* mechanism as letting end-users create and customize their own **desktop pets/items** (hikikomorai's whole premise). Tile-picker's desktop-placer + "^" aim mode is the **first working slice** of that unified idea — a "thing" (right now: a bare emoji) that can live on the desktop or inside a game view, movable between the two. Everything built this session is infrastructure for that bigger idea, not a one-off feature.

### What's next: the event editor, and why it's next
Direct instruction: desktop-placed things (and eventually in-game entities) need a **right-click context menu** with real methods — not just "Close" (which is all `egg_window.c` has today), but things like "open event editor for this," Play/Pause, Attack, Inventory, etc. (see `TILE_PICKER_DESIGN.md` §4.5 — this was already scoped once, now it's actually next). That means **the event editor has to exist first**, since "open event editor for this entity" is the very first real context-menu method worth building.

**There is already a mock of this to study/mirror**, at `201.rpg-maker-clone/` — a single freeglut binary that's both a map/event editor AND a player, deliberately shaped to match house data conventions (`project.pdl`, `switches.pdl`, `maps/<id>/map.txt`, `maps/<id>/events/ev_X_Y/state.txt` + `event.pal`) so it can be wired in later without a format rewrite. Read `201.rpg-maker-clone/ARCHITECTURE.md` and `README.md` before designing the real `&.widgits/event-editor/` build — this is the reference implementation's real shape (mode machine: Title → Map → Event → Play; event editor chrome: methods 1–8, pages 9–12, fields 13–16, contents 17–28, footer 29–34), not something to reinvent.

**A new design doc has been written inside `&.widgits/event-editor/` itself** (`EVENT_EDITOR_FOR_AOMO_AND_HIKIKOMORAI.md`) covering exactly how this applies to both aomorai-editor and hikikomorai going forward — read that before writing any event-editor code.

### Suggested real next steps, in order
1. Read `201.rpg-maker-clone`'s mock in full (source, not just docs) to understand the real command-IR shape it already proves out.
2. Build `&.widgits/event-editor/` as a real house-standard CHTPM widget (same file-menu-modeled pattern tile-picker now uses) — NOT the raw-GLUT mock's own rendering style; the mock is a reference for data shape and UX flow, not for how to build a house widget.
3. Give desktop-placed things (tile-picker's own live windows, egg-pals) a real, data-driven context menu (methods stored per-instance, in the thing's own package dir — already designed in `TILE_PICKER_DESIGN.md` §4.5), with "Open Event Editor" as the first real method.

## 🆕 Update — 2026-08-04, ~20:39

Real work since the section above, in order:

### Real context menus, ported from egg-pal
Tile-picker's own live desktop windows (`tp_desktop_window.c`) got a real, working right-click popup menu — same technique `egg_window.c` already uses (override_redirect popup + pointer grab). Data-driven: reads `METHOD` rows from the entity's own `meta.pdl`.

### A real CPU bug found and fixed — NOT the shared house binaries
High, sustained CPU (chtpm_rgb_render ~40%, chtpm_parser_pal ~500MB RES after being left running) was traced to a **real bug in my own `tp_menu_input.c`**: `bump_screen()` fired unconditionally on every call, including the two idle no-op pre-sync calls the PAL loop makes every single 16ms cycle — so the "screen changed" marker grew every cycle forever, driving a continuous re-render loop even fully idle. **Confirmed the identical bug exists in file-menu's own `fm_menu_input.c`** (the real precedent this was modeled on) — a real, pre-existing house-wide issue, not unique to tile-picker. Fixed by only bumping the marker on a real keypress. Verified: idle CPU dropped from ~40%/11% to <1%/<1%, stable over 10+ seconds, no memory growth. Separately compared the "old standard" `1.TPMOS_c_+rmmp.0103.0001/pieces/chtpm/plugins/chtpm_parser.c` directly — it's the **literal identical** polling design, confirming the shared parser itself was never at fault.

### `asa-&-ava` — real, running app
`@.apps/asa-&-ava/` now exists for real: `pieces/asa/` and `pieces/ava/`, each with its own independent `button.sh` (spawns a real live desktop window, grid-spaced apart, male/female emoji — 👨/👩), its own `methods.pdl` (real, user-editable METHOD table, not hardcoded in the launcher), its own `personality.txt`, and its own `master_ledger.txt`.

## 🆕 Update — 2026-08-04, ~21:35

### fo-menu-sys.md's REAL convention adopted (correcting the earlier note above)
The `Chat`/`Ledger` methods above were originally dispatched via an invented action-keyword scheme. Corrected to this house's actual, canonical convention (`#.haiku+/tpmos-re-dox/fo-menu-sys.md`): a `METHOD`'s `VALUE` is a real, directly-executable command, or `void` for a no-op — `system()`-executed directly, package dir passed as an argument. `MethodItem.action` had to be widened from `char[64]` to `char[PATH_BUF]` — the old size silently dropped real rows once VALUEs became full command lines (a real, live-caught bug).

### Custom assets — real, working, with two real gotchas found and fixed
Any entity can now have a real custom image (PNG/JPG, any size) via `asset.pal` (`asset_path=` or `glyph=`), applied at window startup. Two real bugs found building this:
1. `emoji_xtract.+x` isn't a general image converter — it crops one 64×64 atlas cell. A new op, `tp_asset_to_sprite.c`, does a real whole-image downscale instead.
2. `GL_BLEND` alone doesn't make an X11 window transparent to the real desktop — needed the X11 Shape Extension (`build_shape_mask()`, ported from `egg_window.c`) to actually cut the window's shape to the sprite's alpha.

Verified live with two real user-supplied images (`il-dj.png` for asa, `nyeoni8.png` for ava).

### Real RPG Maker MV pets — dog, cat, chicken
New op `tp_rmmv_character_extract.c` correctly parses a real RPG Maker MV/MZ character sheet (confirmed real 8-slot/48px layout via direct inspection) and extracts one *individual* character (not a whole tilemap — that's separate, later scope). Three real pets — dog, cat, chicken — extracted from a real `Nature.png` sheet and placed as live desktop windows, confirmed on screen. Direction is a real parameter on the extraction op (not hardcoded), specifically so a future AI tick loop can update a pet's facing as it moves.
