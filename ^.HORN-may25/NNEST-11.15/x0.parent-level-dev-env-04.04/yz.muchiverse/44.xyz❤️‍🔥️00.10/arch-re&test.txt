================================================================================
PART 1: WHY - THE GAP THIS CLOSES
================================================================================

Per quick-summar-j26.txt (written earlier this session): 044.pal-chat-irc+2 had
NO master ledger. Messages lived only in rooms/<room>/messages.txt (per-room
flat files) and users/<user>/profile.txt (current-value flat files). There was
no single global source of truth, no crash-recovery-via-replay, and
LEDGER_ADVANCED_STUDY.txt's own claim that "Pal-Chat-IRC (social messages)" is
a proven use case of the ledger pattern was aspirational, not accurate to the
actual codebase.

This pass makes that claim true.

================================================================================
PART 2: ARCHITECTURE CHANGE - WHAT WAS BUILT
================================================================================

New shared file: data/master_ledger.txt
  - Global, append-only, ALL MSG lines across ALL rooms, same line format
    already used by rooms/*/messages.txt: MSG|<msg_id>|<room>|<user>|<ts>|<text>
  - Lives in a new data/ directory, symlinked into every session the same way
    rooms/ and users/ already are (button.sh: `ln -s "$SCRIPT_DIR/data"
    "$SESSION_DIR/data"`) - so it's real, shared, single-copy state, not a
    per-session artifact like net/ is.

Write path changes (dual-write, both files updated together, no separate
resync pass needed for the common case):
  - ops/chat_post_message.c - now appends every locally-posted MSG line to
    data/master_ledger.txt in addition to the existing rooms/<room>/
    messages.txt and net/outbox.txt writes.
  - ops/chat_inbox_watcher.c - now appends every P2P-received MSG line to
    data/master_ledger.txt in addition to rooms/<room>/messages.txt. The
    existing already_has_line() dedup guard was re-pointed to check against
    master_ledger.txt (the canonical truth) rather than the per-room file -
    functionally equivalent today since both are written in lockstep, but
    correct in intent (the question being answered is "is this new to the
    ledger", not "is this new to this one room's view").

New op: ops/chat_replay_ledger.c
  - Standalone recovery/audit tool. Reads data/master_ledger.txt in full,
    groups MSG lines by room field, rewrites every rooms/<room>/messages.txt
    from scratch. Idempotent, safe to run any time.
  - This is the actual "replay" half of the ledger pattern - without it,
    master_ledger.txt would just be a second copy written in lockstep, not a
    real source of truth you could recover FROM.
  - Wired into button.sh as `./button.sh replay-ledger` (alias `replay`), and
    into the `check` action's binary list, and into scripts/build.sh.
  - Bug caught and fixed during implementation: first draft read the room name
    from the wrong pipe-delimited field (fields[1], the msg_id) instead of
    fields[2] (the actual room) - caught before testing by cross-checking
    against chat_inbox_watcher.c's own known-correct parse of the same line
    format, fixed before compiling.

Migration: one-time backfill
  - Pre-existing room history (rooms/guest, muchi-test, t1, test-1 - 10
    messages total, real prior chat history) was merged into
    data/master_ledger.txt, sorted by timestamp field, so it isn't orphaned
    from the new source of truth:
      cat rooms/*/messages.txt | sort -t'|' -k5,5n > data/master_ledger.txt
  - Verified: line count matched exactly (10 lines in, 10 lines out), and
    running chat_replay_ledger.+x immediately after reproduced byte-identical
    rooms/*/messages.txt content (see Part 3, Test 1).

Files touched:
  044.pal-chat-irc👥️+2/ops/chat_post_message.c     (modified)
  044.pal-chat-irc👥️+2/ops/chat_inbox_watcher.c    (modified)
  044.pal-chat-irc👥️+2/ops/chat_replay_ledger.c    (NEW)
  044.pal-chat-irc👥️+2/button.sh                   (modified - data/ mkdir+symlink,
                                                       replay-ledger action, check
                                                       list, help text)
  044.pal-chat-irc👥️+2/scripts/build.sh             (modified - compiles new op)
  044.pal-chat-irc👥️+2/data/master_ledger.txt       (NEW - backfilled, 10 lines)

Deliberately NOT changed: ops/chat_compose_frame.c (still reads
rooms/<room>/messages.txt directly - zero risk to the rendering/marker rules
this session's earlier passes already fixed there), pal/main_loop_chtpm.pal,
any CHTPM layout. The ledger sits underneath the existing room-view layer, it
does not replace the UI/render path.

PART 5: THE REAL BUG - orchestrator launch_redirect() argv truncation
================================================================================

User pushback ("did u test this using a real user flow?") led to building
a REAL key-injected 2-user test (testing/test_real_ux_2users.sh, then
formalized as test-harn-same/). That immediately found the P2P layer
completely dead in real use: `./button.sh run`'s own orchestrator.c called
`launch_redirect(path, arg1, arg2, logfile)` - a FIXED 2-argv-slot
execl() wrapper - for palnet_peer, which needs 5-6 real args. The 5 args
got crammed into one string in arg2, which execl() never splits -
palnet_peer saw argc=3, printed its own usage message into a log file
nobody checked, and exited immediately. Confirmed via
/tmp/pal_chat_irc_palnet_peer.log literally containing that usage text.

Root cause + fix + directory-wide scope: see #.haiku+/!.pal-pitfalls+1.txt
PITFALL 20/21. Fixed via a new launch_argv_redirect() (real argv[] +
execv(), mirroring 041.pal-chain's own orchestrator.c pattern).

Verified: full real 2-user chat (real signup, login, room join, typed
messages) via real key injection - both users see each other's messages
live with zero manual intervention on the idle side. See
test-harn-same/proof/ for saved evidence.

PART 6: DIRECTORY-WIDE BUGS FOUND AND FIXED THIS SESSION
================================================================================

Three separate, previously-undiscovered bugs turned out to affect EVERY
project in this family (11 copies of the shared-ops files), not just
044. All confirmed via live testing, not just code reading, and all now
fixed everywhere:

1. keyboard_input.c CPU-spin (PITFALL 22): read_key()'s retry loop had
   no sleep on the nread==0 path. A real terminal's VMIN/VTIME setting
   throttles this naturally; a non-tty stdin (any headless test) never
   blocks, so the loop spins at ~100% CPU per session, indefinitely.
   Fixed: usleep(20000) on the retry path. Verified: CPU usage for this
   process dropped from ~100% to ~0.1% after the fix, same test shape.

2. chtpm_parser_pal.c heap-buffer-overflow (PITFALL 23): parse_attributes()
   had `while (*(++pos) && isspace(*pos));` which unconditionally reads
   ONE BYTE PAST a strdup'd buffer's end when an attribute name runs to
   the string's own end with no trailing separator. Corrupts malloc's
   own bookkeeping; a later malloc/free aborts with "malloc(): invalid
   next size (unsorted)" several frames later, with no obvious
   connection to the real bug. This was 041.pal-chain's actual "hang" -
   it wasn't hanging, chtpm_parser_pal was silently dying seconds after
   startup. Found via AddressSanitizer in under 5 minutes; would have
   been very hard to find by code reading alone. Fixed in all 11
   copies.

3. Unescaped `+` in every project's kill_all.sh / button.sh pgrep/pkill
   patterns (e.g. `pgrep -f "ops/+x/palnet_peer"`): pgrep/pkill treat an
   unescaped `+` as an extended-regex quantifier ("one or more of the
   preceding char"), not a literal plus - so these patterns NEVER
   matched the real literal paths they were meant to target, across
   044, 041.pal-chain, 041.pal-forum, AND 045.muchi-pal-agent. This is
   the actual explanation for a mystery this same session had earlier
   documented as "not root-caused" (PITFALL 20/21's original text: "was
   observed to NOT reliably kill these two daemons... possibly a race").
   It was never a race - the kill commands were silently killing
   nothing, every single time, in every project, the whole session.
   Fixed everywhere by escaping the +.

Also fixed (pal-chain/pal-forum only, session-isolated projects): a
`(deleted)` cwd-suffix bug (once a session dir is `rm -rf`'d, a process
still holding it as cwd shows up as "$SESSION_DIR (deleted)" in
/proc/$pid/cwd, which never string-matches a bare comparison against
$SESSION_DIR) and a missing `wait "$ORCH_PID"` before that rm -rf in
button.sh's own trap (a real race between the trap's own cleanup and
orchestrator's async signal-triggered shutdown).

PART 7: 041.pal-chain - FULL CONVERSION + REAL MONEY-FLOW TEST
================================================================================

The hang from convert-report-j26.md was the heap-overflow bug in PART 6,
item 2 - not an orchestrator/networking issue as originally suspected.
Fixed, then built test-harn-same/ (button.sh + ops/ + scenarios/
demo_2wallet_ux.sh): 2 concurrent wallet sessions of the SAME install,
real signup, real login, real mining (CHAIN_DIFFICULTY_HEX_ZEROS=1 env
var override, already supported in chain_miner.c, no code change
needed), a REAL send transaction, and the recipient's balance actually
updating - all via real key injection.

Real bugs found and fixed building this test (all documented in
!.pal-pitfalls+1.txt and this project's own test-harn-same/scenarios/
comments):
  - a cli_io field re-activated with existing content APPENDS instead
    of replacing on retype - fixed with a clear-with-backspace-first
    fill_field() helper.
  - chain_send.c only writes a PENDING transaction - it is not applied
    to any balance until a miner actually includes it in a mined block;
    the scenario's first draft stopped mining BEFORE sending "to avoid
    a race", which meant the transaction never got mined in at all.
  - navigating "Stop Mining" while still on send_screen.chtpm (which has
    no such button) silently failed and left chain_miner.+x running
    forever at high CPU - fixed by navigating back to wallet_main first,
    plus an explicit pkill fallback in cleanup regardless.
  - mining at low difficulty races through thousands of blocks per
    second, exhausting the reward halving schedule within 2-3 repeated
    test runs (after which mining silently idles forever, looking like
    a fresh regression) - fixed by having the scenario back up and
    reset data/blockchain.txt to a fresh chain at the start of every run.

Verified: 3 consecutive full runs, each with a real mined block, a real
transfer, and the recipient's real balance increasing - all PASS, zero
process leaks confirmed independently each time.

PART 9: 045.muchi-pal-agent - AUDIT + list_dir TOOL REGRESSION TEST
================================================================================

Audit: the directory-wide fixes from PART 6 (keyboard_input, chtpm_parser_pal)
were already present. Found and fixed the SAME unescaped-`+` kill_all.sh
bug as PART 6 item 3 (manager/+x/path_nav_manager never actually got
killed). Hardened button.sh's own kill action with the same independent
verify-and-retry pattern used in the other 3 projects.

This project is single-instance by design (its own "run" action reaps
any existing session first) - the harness runs one session, not two
concurrent users.

Built test-harn-same/scenarios/demo_list_dir_tool.sh to verify the
"list_dir" tool still executes correctly after the refactor. This
project's real flow (LLM decides whether to call a tool) requires a
live LLM backend and is non-deterministic - not suitable for a
refactor-safety regression test. Instead the scenario directly seeds
the exact state a real LLM tool-call decision would have produced
(ai_state=PENDING_PERM, pending_tool_name=list_dir) into the real
session's own state.txt, then drives the actual at-risk part (the
confirmation step) through real key injection: type "y", press Enter.

Real bug found and fixed building this: pieces/world_01 is COPIED (not
symlinked) per session and can carry real leftover state from a genuine
prior chat session - this system's own state.txt already had a real
"ai_state=IDLE" line in it. A plain `>>` append put the new value LAST,
but read_state_field() returns the FIRST matching line, so the stale
value kept winning. Fixed with a proper key-replacing
set_state_field() helper.

Verified: real execute_tool.+x dispatch to real list_dir.+x, with the
real directory-listing output appearing in the rendered frame. 2
consecutive runs, both PASS, zero process leaks. Full writeup:
045.muchi-pal-agent🤖️+1/forum-summary-claude.txt.
