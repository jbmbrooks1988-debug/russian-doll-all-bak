## A. Core CHTPM/PAL mechanics (applies to nearly every project here)

### A.1 The basic shape

Every project in this style has:
- `system/` — shared engine binaries (`prisc+x` the PAL VM, `chtpm_parser_pal` the menu/layout engine, `keyboard_input`, `renderer`, optionally `chtpm_rgb_render`/`gl_mirror` for a GL window). These are almost always **copied** (not symlinked) from a canonical source project into each consuming project — see §A.4.
- `ops/` — project-specific C binaries (compiled to `ops/+x/<name>.+x`) that do real work: read/write state, render content, dispatch commands.
- `pal/*.pal` — tiny PAL scripts that glue ops together in a loop (read a key, dispatch it, compose a frame, sleep, repeat).
- `pieces/chtpm/layouts/*.chtpm` — XML-ish layout files defining screens: buttons, text, substitution variables.
- `pieces/system/`, `pieces/display/`, `pieces/apps/player_app/` — where state, frame buffers, and trigger/marker files actually live.
- `default_op.txt` — registers every op name your `.pal` scripts can call, format: `name type handler {description}`.
- `button.sh` — the launcher; conventionally supports `run`/`build`/`kill`/`check` verbs at minimum.

### A.2 Session isolation

A "session" is `pieces/sessions/<timestamp>-<pid>/` — a fresh, isolated working directory for one running instance. `system`/`ops`/`pal`/`pieces/chtpm`/`pieces/registry` are typically **symlinked** into it (so binary rebuilds apply live); anything that needs to actually **persist** across the session's lifetime or be genuinely writable (state files, board data) must be explicitly touched + symlinked in `button.sh`, or it silently writes into the ephemeral session dir and vanishes on cleanup. **This exact class of bug (a real state file never symlinked, writes silently going nowhere) has been found and fixed multiple times across different projects this house** — always check `button.sh`'s own symlink list against every file your ops actually write to.

### A.3 The digit-dispatch / numbered-button convention — READ CAREFULLY, a real mistake was made and corrected here

Almost every screen shows numbered items (`[>] 1. Label`, `[ ] 2. Label`...), driven by a `piece.pdl` file with `METHOD | Label | COMMAND` rows. **`resolved_item = (key - '0') - 1` is CORRECT for this dispatch path, not a bug** — this was gotten wrong once this session (a "fix" was briefly applied to civ-txt/tactics-txt's own copies, live-caught as breaking working code, and reverted before being tested/shipped). The reason it's correct: `chtpm_parser_pal.c`'s own `${piece_methods}` button-generator starts its internal `method_idx` at **2**, not 0 or 1 (`method_idx = (loader) ? 1 : 2`, `chtpm_parser_pal.c:1115`) — so the FIRST numbered row's `onClick` becomes `"KEY:2"`, which `send_command()`'s own `"KEY:"` handler turns into the raw ASCII digit `'2'` (not `'1'`) via `inject_raw_key('0'+k)`. `(key-'0')-1` is the correct compensation for that +2 offset: key=`'2'`(50) → `resolved_item=(50-48)-1=1` → `items[0]`, the real first item. **Do not "fix" this in any file whose numbered items are auto-generated via `${piece_methods}`** — that's the standard, dominant case across this house.

**Where the `-1` genuinely IS wrong**: only in code paths that receive a truly raw, literal keyboard digit that never passed through the engine's own `KEY:N` regeneration — e.g. a hand-rolled digit accumulator reading `interact_relay.txt` directly outside the normal numbered-button system (this was real, and fixed, in `board-viewer`'s own now-deleted nav-mode digit dispatch, before that whole mechanism was replaced by the real `onClick="INTERACT"` static button, §D.2 — that code path never went through `${piece_methods}` at all, so the +2 offset never applied there). **Before touching this formula in any file, first determine whether the numbers on screen come from `${piece_methods}` (almost certainly yes, and the `-1` is correct) or from something reading raw keys directly (rare, and only there might the `-1` be wrong).** When genuinely unsure, verify against `chtpm_parser_pal.c`'s own `method_idx` initial value directly, don't assume either direction.

### A.4 Real code over stale docs, always

Doc comments in this house are sometimes wrong/stale — several were found and corrected this session (mutaclysm's own `ops/choice.c` header claimed `'i'`/`'e'` were still live interact/emoji toggles; they'd been removed). **When a doc comment and the actual code disagree, trust the code, verify by direct read, and fix the doc** (standing instruction: "if u need to update stale docs, pls do, no need to have confusion in future agents"). Never assume a comment describes current behavior without spot-checking against the real function it's attached to, especially for anything load-bearing you're about to build on top of.

### A.5 The `[>]`/`[^]`/`[ ]` focus-glyph convention

Numbered/interactive elements render with a 3-char prefix: `[>]` = focused (navigable, not yet active), `[^]` = active/engaged (typing, or a real `onClick="INTERACT"` element currently owns input), `[ ]` = neither. This is drawn **entirely inside the shared `chtpm_parser_pal.c` engine** (`render_element()`), not by any project's own compose op — don't try to reimplement this glyph logic yourself.

## B. The rendering/display pipeline, end to end

Understanding this chain is required before touching any GL-related work — most of the real bugs this session were races or misunderstandings within this pipeline.

```
your compose op (writes text)
  → pieces/apps/player_app/view.txt  (your own raw content)
  → pieces/display/current_frame.txt  (chtpm_parser_pal's own chrome-wrapped composition, substituting ${game_map} etc from view.txt)
      [trigger: pieces/display/frame_changed.txt grown by chtpm_parser_pal.c's process_key() on EVERY key, unconditionally]
      [trigger: pieces/display/renderer_pulse.txt grown by chtpm_parser_pal.c's own internal compose_frame(), also unconditional]
  → system/renderer (ASCII terminal path) — polls frame_changed.txt-equivalent markers, prints current_frame.txt, logs to frame_history.txt
  → system/chtpm_rgb_render (GL path, persistent background daemon) — polls BOTH trigger files above, font-rasterizes current_frame.txt into:
      pieces/display/rgb_frame.raw (raw RGBA32 buffer) + rgb_frame.receipt.txt (frame_w/frame_h/checksum)
      [trigger: pieces/display/rgb_frame_changed.txt grown once a new rgb_frame.raw is ready]
  → system/gl_mirror (real GLUT window) — polls rgb_frame_changed.txt, uploads rgb_frame.raw as a GL texture, blits one quad
      [receipt: pieces/display/gl_display.receipt.txt, for cross-checking source vs. what actually got uploaded]
```

**Key facts that cause real bugs if missed**:
- `chtpm_rgb_render` is a genuinely project-agnostic daemon — it has zero game-state awareness, it just rasterizes whatever text is in `current_frame.txt`. It re-renders on EITHER trigger file growing, and **both grow unconditionally on every key**, regardless of what your own project's ops do or don't call. You cannot suppress this from your side.
- If your own project ALSO writes `rgb_frame.raw` directly (e.g. a custom 3D renderer), you get a real write-write race against this daemon — see §E.1 for the actual fix (write a separate overlay file instead).
- The **receipt + checksum pattern** (`rgb_frame.receipt.txt`'s `frame_w`/`frame_h`/`checksum_fnv1a64`, `gl_display.receipt.txt` for the GL-upload side) is real, working, and load-bearing — `gl_mirror.c` reads its OWN window/texture dimensions from the receipt dynamically rather than hardcoding them, specifically because two different renderers can write different-sized frames to the same path. If you add a new renderer, follow this pattern rather than hardcoding dimensions anywhere downstream.
- **Headless GL verification**: `ops/dump_rgb_png.c` (real, working, in `101.mutaclsym🧟‍♂️️+18.01`) converts `rgb_frame.raw` into an actual viewable PNG — built specifically because an agent can't look at a live GLUT window. Port this (or just do direct pixel-buffer sampling in Python, which is what was actually used this session — see §G) rather than relying on eyeballing a screenshot.

## C. Testing & CPU-safety discipline (standing, non-negotiable)

- **CPU safety is paramount** — this house has crashed from unthrottled idle-poll loops before. Every idle-sync PAL loop pattern uses `sleep <ms>` between poll iterations; never remove that. Every automated test must be `timeout`-wrapped.
- **`timeout` does not reliably kill backgrounded children** of the script it wraps — verify no leftover process afterward (`ps aux | grep yourproject`) and clean up by PID directly (`kill <pid>`) if anything survived. This was a real, repeated issue this session.
- **`pkill` may be sandboxed/blocked** in some environments — every invocation returned a non-zero exit regardless of pattern, including `--version`, in this session's own environment. Use `ps aux | grep` + targeted `kill <pid>` instead of assuming `pkill` works.
- **Never touch the user's own live testing sessions.** If you see `run-widget`/other long-running processes you didn't start, leave them alone — they're very likely the user's own open windows.
- **Cross-session state contamination**: shared (non-session-scoped) state files can get stomped by a stale concurrent session. Kill all stale sessions before every test, or you'll chase phantom bugs that are really just two test runs fighting over the same file.
- **Headless testing technique**: `NO_GL=1 bash button.sh run-app <focus_root>` (or your project's equivalent) gets a real running session with zero display dependency. Inject raw decimal keycodes directly into `interact_relay.txt` (one per line) to simulate exactly what the real engine's key-relay would write — this is how every fix in this document was verified without ever opening a real window.
- **Verifying pixel-level output without a screen**: read the raw RGBA buffer directly in Python (`open(path,'rb').read()`, index by `(y*W+x)*4`), sample known coordinates or scan for known colors. This is real, fast, and was how both a horizontal-mirror bug and an upside-down-camera bug were confirmed and fixed — pure reasoning about the math got both wrong on the first attempt.

## D. Widgets — a separate GL-window program paired to a host project

### D.1 What a "widget" actually is here

A **separate program** (own `system/` binaries, own GL window, own PAL/CHTPM session) that:
- gets spawned by a host project via a real OS process (`setsid ... button.sh run-widget <host_project_root> &`), passing the host's real project root as a focus argument — **not** a same-session screen/view change inside the host's own CHTPM layout (that was a real, corrected architecture mistake early in this house's own history building this — `@.apps/BOARD_WIDGET_ARCHITECTURE.md` §0).
- reads the host's own real files directly (e.g. `board.txt`) for real-time sync — no new IPC needed, just knowing which root to read.
- renders as ASCII (headless/no-DISPLAY fallback) or a real GL window (default when `$DISPLAY` is set).
- `setsid` is required when spawning — plain `system(cmd) + &` does NOT create a new process group, so a `timeout` wrapping the HOST project's own test run can cascade-kill a supposedly-independent widget process.

### D.2 Nav mode — the real mechanism, do NOT reinvent it

`onClick="INTERACT"` is a **reserved string** the shared `chtpm_parser_pal.c` engine special-cases entirely inside itself — NOT something reachable via a dynamically-generated `piece.pdl` METHOD row (those always become `onClick="KEY:N"`, confirmed via direct code read of the engine's own button-generator; only a small whitelist of literal parser commands like `LOAD_PROJECT:`/`BACK`/`RELEASE` are exceptions, and `INTERACT` isn't one of them). It must be a real, hand-written `<button onClick="INTERACT">` in the `.chtpm` XML itself:

```xml
<panel time_reactive="true">
    <module>system/prisc+x pal/main_module.pal</module>
    <interact src="pieces/apps/player_app/interact_relay.txt" />
    <button label="Nav Mode (camera + selector)" onClick="INTERACT" /><br/>
    <text label="${game_map}" /><br/>
    ${piece_methods}
</panel>
```

Once engaged, the engine itself: sets its own internal `active_index` (nothing for your op to track), relays raw keys (arrows remapped to sentinel 1000-1003) into whatever your `<interact src>` names, consumes ESC itself before your op ever sees it, and flips the `[>]`/`[^]` glyph automatically. It also exports `pieces/display/active_gui_is_typing.txt` (`"1"`=active,`"0"`=not) for your own status display — read this, don't invent your own flag. **Consequence**: your own menu_input op needs almost no gating logic — it's only ever invoked with camera/arrow codes while genuinely inside real nav mode, by construction. Full investigation: `&.widgits/interact-fix-widget.txt`.

### D.3 Scaffolding — copy `board-viewer`'s shape

```
your-widget/
  button.sh                # two profiles: run-app (ASCII/headless), run-widget (GL)
  default_op.txt            # registers your project's own ops
  scripts/build.sh           # compiles ops, copies system/ binaries
  ops/
    yourwidget_compose_frame.c
    yourwidget_menu_input.c
    yourwidget_render_3d.c     # only if doing a 3D view
  pal/main_module.pal
  pieces/
    chtpm/layouts/yourwidget.chtpm
    registry/fonts/ascii/       # copied from wsr-pal
    registry/emoji_assets/      # real voxel textures, see §E.3
  projects/your-widget/pieces/<piece_id>/   # holds the dynamically-regenerated piece.pdl
```

`scripts/build.sh`: copy (never symlink) `system/prisc+x`, `chtpm_parser_pal`, `chtpm_rgb_render`, `keyboard_input`, `renderer` from `014.wsr-pal💸️📌️+2/system/` — **wsr-pal's own `chtpm_rgb_render` already has BOTH the generic on-demand emoji-generation feature AND the `MAP3D_MARKER`/overlay-compositing feature needed for a 3D view (§E.1)**. Do NOT swap this for mutaclysm's own fork — mutaclysm's copy has zero on-demand emoji generation (it only recognizes emoji hand-curated from its own registry files, which won't exist in your project), and swapping to it silently breaks 2D emoji rendering entirely. This was a real, live-caught regression this session — an earlier research pass incorrectly concluded wsr-pal's copy lacked overlay support; it does not, verify directly with `grep -n "blit_overlay\|MAP3D" system/chtpm_rgb_render.c` before believing otherwise. `gl_mirror` also comes from wsr-pal (real `interact_relay.txt` key-forwarding; mutaclysm's own copy is mirror-only, no forwarding). Also copy `ops/+x/emoji_gen_atlas.+x` + `emoji_xtract.+x` from wsr-pal (§E.3).

## E. The 3D view — three real, separate pieces

### E.1 Avoiding the rgb_frame.raw race

If your own 3D-render op writes `pieces/display/rgb_frame.raw` directly, it races `chtpm_rgb_render`'s own unconditional re-render (§B) — a real, live-caught bug (3D frame briefly shows, then reverts to stale 2D content within ~30ms). **The fix**: your 3D op writes to a SEPARATE file — `pieces/display/rgb_frame_3d_overlay.raw` + `.receipt.txt` (format: `overlay_w=%d\noverlay_h=%d\n`, no checksum) — and never touches `rgb_frame.raw` at all. `chtpm_rgb_render` watches for a single `0x01` (SOH) byte as a line's first character in `current_frame.txt`; on finding it, composites your overlay in at that row, then skips `ceil(overlay_h/GLYPH_H)` further source lines. Your own 2D compose op must therefore emit, only while `render_mode==1`:
```c
fputc(0x01, out); fputc('\n', out);
for (int i = 0; i < N; i++) fputc('\n', out);  // N = ceil(overlay_h_px / 16), MUST match your 3D op's own overlay height
```
Keep this constant in sync manually between the two files — no shared-header convention in this house's self-contained-ops style, so this is a real, easy-to-silently-break invariant; comment it loudly in both files, pointing at each other.

### E.2 Camera controls — full key scheme (ported from mutaclysm's `ops/camera_control.c`)

| camera_mode | q/e (yaw) | r/t (pitch) | w/a/s/d (pan) | c/v (z-level) | f (reset) |
|---|---|---|---|---|---|
| 1 — first person | ±10° | ±10°, clamp[-89,89] | ❌ locked to anchor | ❌ | yaw=180,pitch=6 |
| 2 — third person | ±10° | ±10° | ❌ locked to anchor | ❌ | yaw=180,pitch=6 |
| 3 — free roam | ±10° | ±10° | ✅ pans z/x | ✅ | pan=0,yaw=180,pitch=-90 |
| 4 — bird's-eye | ❌ no-op | ❌ no-op | ✅ pans y/x, ABSOLUTE coords | ✅ | pan **centers on your anchor/selector**, NOT (0,0) |

`'0'` toggles `render_mode` (bidirectional). `'1'`-`'4'` switch `camera_mode`, only while `render_mode==1`. **Real bug already fixed**: mode 4's default/reset pan must center on your widget's own selector position (matching where the 2D view starts), not `(0,0)` (the board's corner) — both the `'1'-'4'` switch handler and your render op's own read-side default need this.

### E.3 Camera basis math — two empirically-verified branches, do not collapse to one formula

```c
Vec3 dir = { cos(pitch)*sin(yaw), sin(pitch), cos(pitch)*cos(yaw) };
forward = normalize(dir);
Vec3 right, up;
if (fabs(forward.y) > 0.999) {                 // near-vertical (bird's-eye-like)
    Vec3 fallback_up = { 0, 0, 1 };
    right = normalize(cross(fallback_up, forward));
    up    = normalize(cross(right, forward));
} else {                                        // general/near-horizontal (FPS-style)
    Vec3 world_up = { 0, 1, 0 };
    right = normalize(cross(world_up, forward));
    up    = normalize(cross(forward, right));
}
```
Two earlier single-formula attempts each fixed one branch while silently breaking the other (a horizontal mirror in one case, upside-down in the other) — this is a well-known top-down-vs-forward-facing camera convention ambiguity, not something you can derive correctly by pure algebra. **Verify empirically** (§C, controlled test board with asymmetric corner markers + direct pixel sampling) before trusting any camera math, including this, if ported to a different coordinate convention.

### E.4 Real raymarching, not a rasterizer

A **rasterizer** (project 3D geometry to screen space, sort back-to-front, fill polygons with solid colors) is fundamentally different from, and visually inferior to, real raymarching — and was explicitly rejected in this house once asked directly ("did we do the real raymarching or cheat?"). **If asked for "real 3D" or "like mutaclysm," build the raymarcher.** Real raymarching = a per-pixel loop casting a ray through 3D space, testing it against actual geometry via an Amanatides & Woo grid-DDA walk, sampling real texture data at the hit point. Port these four pieces verbatim from mutaclysm's `ops/compose_rgb_frame.c`:
1. **`ray_aabb_hit_3d()`** — slab-method ray/box intersection, self-contained.
2. **`box_face_uv()`** — hit point + face index → 2D texture UV.
3. **`get_voxel8_cached()`/`sample_voxel8_pixel()`** — real voxel-texture CSV loading/sampling (resolution-agnostic despite the "8" in the name; size your pixel buffer for your assets' actual resolution).
4. **The DDA loop** — per pixel, `ray_dir = normalize(forward + right*a + up*b)` where `a=(sx-W/2)/focal, b=(H/2-sy)/focal`, then Amanatides & Woo grid-step testing `ray_aabb_hit_3d` per cell until first hit.

This house's own board-viewer simplified mutaclysm's floor-pass/wall-raymarch split into ONE unified per-cell AABB test (thin slab for flat/water terrain, real tall box for raised terrain) — reasonable if your terrain model is "one scalar height per cell," not mutaclysm's richer walkable/furniture registry. **Performance**: a 640×480 per-pixel raymarch against a ~14×14 board rendered in ~70ms — fast enough for every idle tick; verify your own timing before assuming this holds at a different scale.

### E.5 Real textures via the on-demand emoji-voxel pipeline — don't hand-pick colors

`system/chtpm_rgb_render.c` (wsr-pal's copy) has a genuine, working "GENERIC ON-DEMAND EMOJI GENERATION" path: any unrecognized UTF-8 codepoint gets shelled out to `ops/+x/emoji_gen_atlas.+x <emoji> <tmp.png>` (real FreeType + `NotoColorEmoji.ttf`) then `emoji_xtract.+x <tmp.png> 0 16 <csv>`, cached forever at `pieces/registry/emoji_assets/<hex-codepoint>/voxels_16.csv`. If your 2D compose op emits real emoji per terrain type, those exact voxel assets are already on disk by the time you build a 3D view — point your raymarcher's texture sampler at the same hex-codepoint path your 2D glyph-mapping uses, and 2D/3D show consistent textures for free. Also check `101.mutaclsym🧟‍♂️️+18.01/pieces/registry/emoji_assets/` for existing hand-curated assets (`t_grass`, `t_tree`, `t_water_dp`, `hero`, `zombie`, `xlector`, etc.) worth reusing directly.

## F. Pitfalls — every one a real, live-caught bug

1. **A dynamically-generated piece.pdl METHOD row can never trigger `onClick="INTERACT"`.** §D.2.
2. **`(key-'0')-1` is CORRECT for standard `${piece_methods}` numbered dispatch — do not "fix" it there.** §A.3 has the full, corrected writeup after a real mistake was made and caught this session. Only reading raw keys OUTSIDE that system needs the plain `key-'0'` form.
3. **`'q'` must never quit anything** — a standing house rule, already enforced in `chtpm_parser_pal.c`/`keyboard_input.c`, but `gl_mirror.c` (`014.wsr-pal💸️📌️+2/system/gl_mirror.c`) had a leftover exception (remapped Ctrl+C to literal `'q'`, forwarded it as content, THEN quit on it) — fixed at the source this session; verify the fix is still present before assuming `'q'` is safe to bind to anything real.
4. **Camera orientation bugs are not obvious from code review** — verify empirically, every time. §E.3, §C.
5. **3D view's default camera position must match where the 2D view starts** (board center/selector default), not `(0,0)`.
6. **Don't unconditionally pad rendered cells with literal spaces** — the font rasterizer already advances by real pixel width per glyph; unconditional padding produces a visible, unwanted gap. Only add extra characters (like a selector bracket) around genuinely-different cells.
7. **A state file never explicitly symlinked in `button.sh` writes silently into the ephemeral session dir and vanishes.** §A.2. This exact bug class has recurred across multiple unrelated projects.
8. **Cross-session state contamination** via shared, non-session-scoped state files. §C.
9. **`pkill` may be sandboxed/blocked**; use `ps aux | grep` + `kill <pid>`. §C.
10. **A running session's `.pal` script loads once at startup, not per-tick** — op *binary* rebuilds apply live (symlinked `ops/`), but editing the `.pal` script's own call sequence needs a real session restart to take effect.
11. **`system() + &` does not create a new process group** — `setsid` is required when spawning a widget you want genuinely independent of the spawning process's own signal/timeout handling.
12. **Never swap `chtpm_rgb_render` for mutaclysm's own fork casually** — it lacks the generic on-demand emoji-generation feature wsr-pal's copy has, and swapping to it silently breaks 2D emoji rendering while "fixing" 3D overlay support that wsr-pal's copy already had all along. Verify feature presence directly (`grep`) rather than trusting an earlier research pass's conclusion — one was wrong about this exact thing this session.
13. **Doc comments can be stale** — verify against real code before trusting a comment's claim about current behavior, especially anything load-bearing. §A.4.

## G. When unsure whether to deviate from precedent (mutaclysm, or any other reference project)

**Ask, don't guess.** Standing instruction, repeated directly multiple times: *"trust mutaclysm and ask me if you're unsure that you may have false assumptions when you want to deviate for parity."* Concretely:
- If a reference project has a real, working mechanism for something you need, go read the actual code before designing your own — don't assume a simpler-looking approach is equivalent (§D.2's `onClick="INTERACT"` mistake is the canonical example of this going wrong).
- If you genuinely need to simplify relative to the reference (e.g. a single-scalar-height terrain model vs. a full walkable/furniture registry), that's fine — say so explicitly as a deliberate, scoped-down choice, not an oversight.
- If the reference project's own code has a real, discovered inconsistency (its own comment claims parity between two code paths that don't actually match), don't silently propagate the bug — flag it, and target the STATED intent, not the buggy implementation.
- Never invent a screen/menu/interaction pattern from scratch when real precedent exists somewhere in this house — read it first.
