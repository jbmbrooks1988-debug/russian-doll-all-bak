# khtpm/X11 → RGB-frame refactor (design notes, not started)

**Status:** idea captured 2026-08-12 during db-hq's first build, not
scheduled. This document exists so the reasoning survives even though no
code has changed yet - direct instruction: "we may even go back and
refactor all x11 to use rgb converter."

## The idea

Every X11-rendered surface in the house (khtpm taskbar strip, db-hq,
future `-hq` apps, and eventually entity/context windows too) currently
draws straight into a Pixmap/Window using Xlib/Xft calls (`XFillRectangle`,
`XftDrawStringUtf8`, etc.), then blits that Pixmap to the real window with
`XCopyArea`. The GL/GLUT entity-mirror family (`system/gl_mirror.c` +
`system/chtpm_rgb_render.c`, see `au11-hq/HQML-DESIGN+PLANS.md`'s "Why
db-hq doesn't render through raw-RGB + GL textures" section for the full
comparison) does something structurally different: it composes a plain
RGBA8 byte buffer first (`pieces/display/rgb_frame.raw` +
`rgb_frame.receipt.txt`), independent of any window, and only THEN pushes
that buffer onto a screen (via a GL texture + one textured quad).

The refactor idea: give every X11 surface that same two-step shape -
**compose into a plain RGB byte buffer first, present it second** - so the
compose step becomes decoupled from having a live X11 window at all.

## Why this is worth doing (direct quotes, 2026-08-12)

- "it was to have the rgb frames and beable to send them wherever we
  want" - the RGB buffer is a portable artifact once it exists: it can be
  written to disk (already true, `dump_rgb_png.c`), streamed, diffed,
  compared frame-to-frame, or fed to a different output entirely -
  none of which a Pixmap tied to a live X connection can do.
- "we rather have a x11 rgb renderer after converterting to rgb from a
  headless converter of the kthpm" - a compose step that doesn't require
  `XOpenDisplay` to succeed means khtpm layouts become testable/
  screenshot-able in CI or from an agent with no real display attached,
  the same way `dump_rgb_png.c` already lets an agent "see" a GLUT window
  it can't otherwise look at.
- Today db-hq's own debug PNG dump (`dump_frame_png()` in
  `khtpm_hq_render.c`, bound to 'p') has to go the OTHER way - read a
  live Pixmap back out with `XGetImage` after the fact - which is more
  fragile (as its current unresolved blank-frame bug shows) than if the
  frame had been a plain buffer from the start.

## What "headless converter of khtpm" would mean concretely

Split each renderer into two independent stages:

1. **Compose** - walk the element tree (post-CSS, post-layout, exactly
   like today's `layout_pass()`/`assign_nav_indices()`) and rasterize it
   into a plain `unsigned char[h][w][3or4]` buffer. Needs a *software*
   text rasterizer and shape-fill routines that don't depend on an open
   X `Display` - i.e. the same category of thing `chtpm_rgb_render.c`'s
   `load_glyphs()`/`blit_char()`/`blit_text()` already are, OR (lower
   effort) keep using Xft but render into an `XImage` backed by malloc'd
   memory rather than a server-side Pixmap (Xft/Xrender still needs a
   `Display` connection to allocate fonts/colors even if not showing a
   window, so this wouldn't be FULLY headless without also swapping to a
   software font rasterizer - worth flagging as the real fork in the
   road before committing to an approach).
2. **Present** - take the buffer from step 1 and either: (a) push it to
   a real window via `XPutImage`/`XShmPutImage` (fast path, what today's
   interactive windows would use), or (b) write it to disk as
   `rgb_frame.raw` + receipt for `dump_rgb_png.c` to pick up (debug/agent
   path), or (c) nothing at all - just keep the bytes in memory for a
   test assertion.

## Candidates for this refactor, roughly in order of size

1. **db-hq** (`khtpm_hq_render.c`) - smallest, newest, already has a
   `dump_frame_png()` stub to replace/fix. Good first target once this
   is actually scheduled.
2. **khtpm taskbar** (`khtpm_strip_parser.c`/`khtpm_strip_layout.c`) -
   larger, has the two-process manager pairing to preserve, higher risk
   (it's the ONE taskbar in daily use - see khtpm_strip_parser.log
   uptime expectations). Would need the same "don't regress existing
   .chtpm rendering" discipline `au11-hq/HQML-DESIGN+PLANS.md`'s own risk
   table already calls out for the CSS layer.
3. **Entity/context GL windows** - these already effectively do this
   (they're the ORIGINAL of the pattern), so "refactoring" them really
   just means confirming `dump_rgb_png.c`'s tooling covers whatever new
   khtpm-family output shows up, not rewriting their renderer.

## Open questions (not decided, flagging for whenever this is picked up)

- Software font rasterizer (own fixed bitmap glyphs, like
  `chtpm_rgb_render.c`'s) vs. keeping Xft but writing to a malloc'd
  `XImage` - the former is truly headless (no `Display` needed at all
  for compose), the latter is way less code to write but still needs an
  X connection open, just not a mapped/visible window. Needs a decision
  before any implementation starts.
- Where would non-debug consumers of a "sent wherever we want" RGB frame
  actually live? Not scoped yet - this doc only covers getting the frame
  INTO a portable buffer, not what else might eventually read it.
- Performance: `XCopyArea`/`XPutImage` of a full frame every redraw is
  already what happens today (Pixmap blit); moving compose client-side
  (malloc'd buffer + `XPutImage`) is roughly the same cost. A software
  font rasterizer would trade GPU/Xrender-accelerated glyph drawing for
  CPU blitting - fine at khtpm's scale (small windows, infrequent
  redraws), untested at anything bigger.

## Phase 0: isolated compose→X11 test (small, first, standalone)

Direct instruction (2026-08-12): prove the two-stage split on a small
isolated case before touching db-hq or the taskbar at all - "can we do
it in a small section first." events-hq doesn't exist yet (checked:
`&.hq-apps/` only has `db-hq/` so far), so this phase's own job is
building just enough of a minimal events-hq SCREEN to have something
real to compose - not the whole app from
`au11-hq/HQML-DESIGN+PLANS.md`'s Use Case 1 spec, just one static-ish
screen (title + a few text rows + one button, no live event-editing
logic yet) to prove the render path against.

**Scope, deliberately minimal:**
1. New standalone test binary, e.g.
   `*.livedesk-taskbar/ops/khtpm_rgb_test.c` - NOT wired into any
   taskbar cell, NOT replacing anything, throwaway-if-it-doesn't-pan-out.
2. Pick the lower-effort option from this doc's own "open questions"
   list first (decide it now rather than leave it open): keep Xft, but
   render into a malloc'd buffer instead of a server-side Pixmap -
   `XCreatePixmap`/`XftDrawCreate` already work against any drawable, so
   the swap is: allocate `unsigned char *rgb = malloc(w*h*3)` up front,
   draw exactly as db-hq's `draw_elem()`/`redraw()` already do today
   (same Xft calls) but into a Pixmap that's never shown, then instead
   of `XCopyArea` (Pixmap→Window), read that Pixmap back with
   `XGetImage` ONE time into the `rgb` buffer (reusing the exact
   byte-layout fix already made in db-hq's `dump_frame_png()` - standard
   TrueColor `0xRRGGBB`, not the zeroed mask fields) - this proves the
   "compose is a portable buffer, present is separate" shape without yet
   committing to a full software font rasterizer. True headless (no
   `Display` at all) stays a later, separate step if this proves out.
3. **Present**, both paths, so the comparison is real:
   (a) `XPutImage` the `rgb` buffer into a plain window - confirms the
   buffer is genuinely presentable, not just PNG-dumpable.
   (b) `stbi_write_png` the same buffer straight to disk (no `XGetImage`
   round-trip needed THIS time, since the buffer already IS the frame) -
   compare byte-for-byte against a PNG dumped the OLD way
   (`XGetImage`-after-`XCopyArea`) to confirm the two compose paths
   produce identical pixels before trusting the new one.
4. One minimal events-hq screen to render: reuse dashboard.chtpm/
   khtpm_css_parser.c's own tag-tree + CSS approach (don't reinvent
   parsing) with a throwaway `events-hq-test.chtpm`/`.css` - title bar
   text "events-hq (test)", 3-4 static text rows, one button, no
   sidebar/tabs/nav-index system needed for this test (out of scope -
   this phase is about the RENDER PATH, not events-hq's real UI).

**Exit criteria for this phase:** a PNG written via the new compose-
first path is pixel-identical (or close enough to eyeball) to one
written the old way, AND `XPutImage` shows the same content in a real
window. If both hold, the split works and is worth extending to db-hq
for real; if not, the doc's "open questions" section above needs
revisiting before going further - don't propagate the pattern to a real
app on the strength of an untested assumption.

**Explicitly NOT in this phase:** true headless (Display-less) compose,
a software font rasterizer, wiring into the taskbar's db cell, or any
real event-editing logic - all deferred until Phase 0 itself proves out.
