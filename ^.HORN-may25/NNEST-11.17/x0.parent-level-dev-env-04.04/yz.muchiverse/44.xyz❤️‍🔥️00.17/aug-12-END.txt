Status: FIXED, confirmed via real physical keystrokes (arrow keys
logged and acted on), not just XTest or the relay. Root cause was
architectural (override_redirect itself), not a missing X11 call - five
different call-level fixes were tried first and none of them could have
worked, because the actual problem was one level up. Read this whole
section before touching ANY future -hq window's focus handling.

WRONG TURNS TRIED FIRST (each a real, reasoned attempt - not guesses -
but all addressing the wrong layer):

1. soft_focus() (XRaiseWindow + XSetInputFocus + XFlush) once after
   mapping - ported from khtpm_strip_parser.c's taskbar_soft_focus().
2. soft_focus() re-asserted on every click too.
3. Real XGrabKeyboard (5-attempt retry) - ported from &.widgits/
   tile-picker/ops/tp_desktop_window.c's open_context_menu(), which DOES
   reliably work for ITS OWN popups. Required first fixing WM_CLASS to
   "MuchiverseLivedesk" (Mutter's xwayland-grab-access-rules allowlists
   by WM_CLASS, confirmed via `gsettings get org.gnome.mutter.wayland
   xwayland-grab-access-rules` -> ['MuchiverseLivedesk']; db-hq had been
   using a different class, so any grab was silently doomed from the
   start - same root cause tp_desktop_window.c itself originally hit,
   see $.crypts/enable_xwayland_grabs.sh). Verified via real XTest key
   injection that digit-jump + Enter worked through this path - but
   XTest injects at the X server/Xwayland level directly and does NOT
   prove real physical keystrokes take the same path. Direct user
   correction, right to be skeptical: "did u try real sim x11".
4. Re-grab on EVERY click, plus a dedicated right-click force-focus
   action matching the taskbar's own right-click semantics
   (khtpm_strip_parser.c :1633-1642). A real physical click+type test
   with this in place showed a genuine FocusIn immediately followed by
   FocusOut - the window got focus for an instant and lost it again
   before typing could land.
5. KISS hail-mary: studied 01.muchi-pals-🥚️-13.01/system/egg_window.c
   (a real entity/"context" window, ALSO launched fresh from a click,
   confirmed to work in daily use) and found it does ZERO focus/grab
   calls at all - stripped ALL of db-hq's own focus machinery out to
   match that bare-minimum behavior exactly (gated behind a new
   #.desktop/hq_ui.pdl `focus_grab` key so it could be toggled back
   without a rebuild). RESULT: WORSE, not better - direct report "its
   legit not getting focus wheni i click with mouse or rightclick". This
   was the moment the real root cause finally surfaced: pointer/click
   events reached the window FINE the whole time (proving the window,
   event delivery, and DISPLAY connection were never the problem) - but
   FocusIn genuinely never fired, no matter what was tried, at any
   step above.

THE ACTUAL ROOT CAUSE, confirmed (not guessed):
`gsettings get org.gnome.mutter focus-change-on-pointer-rest` -> true
on this system - a real, automatic Mutter WM focus policy. That policy
(and every other WM-level focus policy Mutter has) only applies to
windows Mutter actually MANAGES. `override_redirect` windows are
EXPLICITLY EXEMPT from window-manager focus handling by X11 protocol
definition - that's the whole point of the flag. So no client-side call
(XSetInputFocus, XGrabKeyboard, right-click force-focus, anything)
could ever have fixed this: Mutter was structurally never going to
consider db-hq's window for real focus transfer AT ALL, click or no
click, because it was override_redirect. The taskbar's own
override_redirect windows only "get away with it" because they grab
initial focus once, early in a session, and mostly never need it back -
not because override_redirect genuinely supports reliable focus under
this compositor. This is a real, house-wide gotcha for any FUTURE
override_redirect window that needs to reliably regain keyboard focus
after the user's attention has been elsewhere - not just a db-hq quirk.

THE ACTUAL FIX (khtpm_hq_render.c's main(), 2026-08-12):
Stopped being override_redirect entirely. db-hq is now a normal,
WM-MANAGED window (confirmed via a real position shift on map - Mutter
placed it at 198,104 instead of the requested 100,100, something it
only does to windows it actually manages) so Mutter applies its real
focus policy to it exactly like any other app on the desktop. The
visible chrome (title bar/border) is suppressed instead via the
standard `_MOTIF_WM_HINTS` property (flags=2/MWM_HINTS_DECORATIONS,
decorations=0) - confirmed working via `xprop _NET_FRAME_EXTENTS` ->
"not found" (zero WM-drawn frame) on the live window. Also set
real ICCCM `WM_HINTS` (input=True) and registered `WM_DELETE_WINDOW`
via XSetWMProtocols, both real conventions for a managed window that
override_redirect windows never need. CONFIRMED via real physical Left
arrow keypresses actually being received and logged
("REAL KeyPress received: keysym=Left") - the first genuine physical
keyboard delivery of the entire session.

RGB REFACTOR - intentions, all captured in !.khtpm-rgb-refactor.md
(house root, this session)
----------------------------------------------------------------------

Not started, deliberately scoped small first. Full reasoning lives in
that doc; short version:

- Every khtpm window today composes directly into a server-side X
  Pixmap via Xlib/Xft, then blits it. The GL/GLUT entity-mirror family
  (chtpm_rgb_render.c/gl_mirror.c) does something structurally
  different: composes into a plain portable RGB byte buffer FIRST,
  independent of any window, presents it second (GL texture upload).
- Why this matters (direct quotes captured in the doc): "it was to have
  the rgb frames and beable to send them wherever we want", and a
  headless compose step would make khtpm layouts testable/
  screenshot-able without a live X connection at all - the same reason
  dump_rgb_png.c exists for GL windows an agent can't otherwise "see".
- Real fix already applied this session as a preview of why this
  matters: db-hq's own debug PNG dump WAS broken (solid black) for most
  of the session specifically because reading pixels back OUT of a live
  Pixmap after the fact (XGetImage) is more fragile than if the frame
  had started as a portable buffer to begin with (see the XGetImage
  zeroed-mask bug above) - a lived example of the doc's own argument #3.
- Phase 0 (added this session, per direct instruction "can we do it in
  a small section first"): a throwaway standalone test binary, NOT
  wired into anything real, that composes ONE minimal events-hq screen
  (events-hq itself doesn't exist yet - just a title + a few text rows
  + one button, reusing dashboard.chtpm/khtpm_css_parser.c's own
  tag+CSS approach) into a malloc'd-buffer-backed Pixmap, presents it
  BOTH via XPutImage to a real window AND via stbi_write_png straight to
  disk, and compares that against a PNG dumped the OLD way
  (XGetImage-after-XCopyArea) to confirm both paths produce identical
  pixels before trusting the split further. Exit criteria and full step
  list are in !.khtpm-rgb-refactor.md's own "Phase 0" section - read
  that before starting, don't re-derive it.
- Explicitly NOT decided yet: software font rasterizer (truly headless,
  more code, chtpm_rgb_render.c's own approach) vs. malloc'd XImage +
  Xft kept (way less code, still needs a live Display connection just
  not a mapped window). Doc's own "open questions" section has the full
  tradeoff - decide this BEFORE writing Phase 0's compose step, not
  during.
