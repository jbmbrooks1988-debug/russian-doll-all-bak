## 🛠️ 2. How to work here — your methodology (read before doing ANYTHING)

This section is the actual valuable part. Skipping it will cost you
hours you don't need to lose.

### 2.1 — Verify with REAL signals, never trust one source
A file log, a build's own "OK" message, or your own memory of what you
just did are **not proof**. Before declaring anything working:
- Check real running processes: `ps aux | grep -iE "khtpm_strip_parser|tp_desktop_window"`
  (or `pgrep -af "<pattern>"`).
- Check real files changed: `cat`/`stat` the actual state file, not just
  a log that claims it changed.
- For visual/window state: `DISPLAY=:0 xwininfo -root -tree 2>/dev/null | grep MuchiverseLivedesk`
  shows real X11 windows.
- Cross-check at least two of the above before trusting a result. This
  house's own standing lesson (`!.HOUSE_STDS.md`): "Doc comments can be
  stale — verify against real code." The same applies to your own
  assumptions mid-session.

### 2.2 — The debug log: your primary tool
`#.desktop/khtpm_strip_frame_history.txt` — one line per redraw tick,
showing header/bottom focus, active scope, nav position, cli-io state,
digit buffer, element count. Truncated fresh every launch. **Read this
instead of guessing** what the UI is doing. `tail -1` after any action to
see current state; `tail -N` for a sequence.

### 2.3 — Testing input WITHOUT a human at the keyboard
You have **no way to click a mouse or press a real key** in this
environment (no `xdotool`/`xte`/`ydotool` — confirmed absent, don't waste
time re-checking). Use the **agent relay** instead:

```
echo "56" >> "#.desktop/livedesk_agent_relay.txt"   # sends ASCII '8'
echo "13" >> "#.desktop/livedesk_agent_relay.txt"   # sends Enter
```

One decimal ASCII code per line. `13`=Enter, `27`=Escape, `8`=Backspace,
`48`-`57`=digits `0`-`9`, `32`-`126`=other printable. **Sleep ~1-1.5s
between sends** — this is a two-process system (parser → manager →
parser), noticeably slower to settle than a single process; rushing
input causes ghost failures that look like bugs but are just timing.

There's a ready-made harness wrapping this:
`#.desktop/harnesses/khtpm-livedesk-taskbar/nav.sh` — `nav <n>` (jump to
nav number N + Enter), `row <n>` (same, for a submenu row), `key <name>`,
`type <text>`, `frame [n]` (tail the frame history). Use `HOUSE="$PWD" bash
.../nav.sh nav 3` style invocation from the house root.

For **entities** (not the taskbar), the equivalent channel is each
entity's own `<pals-dir>/interact_relay.txt` — write `RUN_METHOD:<Label>`
to trigger a context-menu action by name. ⚠️ **Caveat, learned the hard
way**: this goes through a *different* internal code path than a real
mouse-click or a real Enter-keypress (there are, as of this writing,
**three separate, only-partially-unified implementations** of "run this
menu action" in `tp_desktop_window.c` — mouse-click, keyboard-Enter, and
`RUN_METHOD`-by-label all have their own inline copy of similar logic).
They mostly agree now (see §4 below for the mismatch just fixed), but
don't assume a `RUN_METHOD` test result perfectly predicts real-keyboard
or real-mouse behavior — if something matters, ask the user to confirm
live, especially for entity context-menu changes.

### 2.4 — Build + relaunch cycle
```
sh $.crypts/button.sh run        # the ONE real entry point — kills, relaunches taskbar + all entities from autostart.pdl
sh $.crypts/button.sh reset      # harder version: guaranteed-clean kill + rebuild + relaunch
sh *.monads/*.livedesk-taskbar/ops/run_khtpm_strip.sh new   # taskbar only, build+relaunch
```
For entity binary changes: `cd "&.widgits/tile-picker" && gcc -Wall -Wextra -O2 -o "ops/+x/tp_desktop_window.+x" "ops/tp_desktop_window.c" -lX11 -lXext -lGL -lGLX`
(exact flags matter — copied from `&.widgits/tile-picker/scripts/build.sh`, don't guess your own).

⚠️ **Known environment flakiness**: a backgrounded X11 launch
(`setsid env DISPLAY=:0 ... &`) will *sometimes* silently produce zero
running processes on the first attempt, with no error. This is a known
quirk of this specific tool sandbox, not your code. **Always verify with
a fresh `pgrep` after a real `sleep`; if nothing's running, just retry
the exact same launch once** — it reliably works the second time.

### 2.5 — Before assuming a string comparison is right, COUNT IT
This bit multiple real bugs tonight: `strncmp(str, "some literal", N)`
where `N` was hand-typed and just *wrong* by one — made whole features
(session switching, desk switching) **silently, permanently non-functional**
for an entire session before being caught. Before trusting any hardcoded
length constant against a literal string, run:
```
printf '%s' "the literal string" | wc -c
```
Do this *every time* you write or touch one of these, not just when
debugging. It takes 5 seconds and prevents hours of confusion.

### 2.6 — When something "should" work but doesn't, add a real debug trace
Don't keep re-reading code and re-guessing. A temporary `fprintf(stderr,
...)` or `fopen("/tmp/debug.txt", "a")` trace at the exact decision point,
rebuilt and re-tested, gets you ground truth in one round-trip instead of
five. Remove it once you have your answer — don't leave debug scaffolding
in committed code.

### 2.7 — Small, scoped changes; verify each one live
Don't batch five unrelated changes into one build-and-test cycle. This
house's real sessions have repeatedly found that a fix which "should"
work reveals a *second*, different bug the moment you actually test it
live. Fix one thing, rebuild, verify with real signals (§2.1), then move
to the next.

## 🎯 4. YOUR FIRST TASK — two new header cells

Add two new persistent header cells to the taskbar:

1. **`menus`** — placed right after `plugins`. Dynamically populates its
   own submenu from user-created menu definitions (see §4.3 — this is a
   real design decision you get to make, not a fixed spec).
2. **`date/time`** — placed right after `network` (i.e., the new last
   cell). Shows the current date/time. **Right now, show it in Chinese**
   — this is deliberately a smoke test that the mechanism is genuinely
   dynamic (recomputing live, not a static string), not a real feature
   requirement. Must be changeable to English via a `.pdl` config key.
   Later (not your job today) this cell will show *in-game* time instead
   of real time.

### 4.1 — The exact current cell layout (read this before editing anything)

`*.monads/*.livedesk-taskbar/khtpm_strip_header.chtpm` currently has,
in order:
```
1=HQ  2=USER  3=file  4=desks  5=pals  6=palettes  7=edit
8=player  9=db  10=plugins  11=store  12=network
```
Cells 6/7/9/10/11/12 (`palettes`/`edit`/`db`/`plugins`/`store`/`network`)
are currently **inert placeholders** — they render, they're navigable,
but clicking/activating them does nothing real yet (confirmed: no
submenu content wired). You are not expected to fix those — just don't
be surprised they're empty.

### 4.2 — ⚠️ A REAL LANDMINE you must handle correctly

Inserting `menus` after `plugins` (position 10) makes it the new position
11, **shifting `store`→12 and `network`→13**. Adding `date/time` after
the new `network` makes it position 14.

**The number 13 is NOT free.** `khtpm_taskbar_manager.c`'s own
`ktb_hq_open()` already uses `which == 13` as an *internal-only* marker
for the session picker (reached only via the file cell's "load" row, never
a direct header click — see that function's own comment, grep
`which == 13` to find it). If `network` becomes cell 13, a header click on
`network` and the internal session-picker mechanism will collide.

**Fix this properly, don't just avoid it by luck**: renumber the internal
session-picker marker to something clearly out of the real header-cell
range — e.g. `which == 100` — updating both `ktb_hq_open()`'s own check
and wherever else `13`/`KTB_LIVEDESK_DYN_MAX`-adjacent code assumes that
specific value (grep the whole file for the literal `13` near `hq_open`/
`which` to find every spot). This also future-proofs against the *next*
person who adds a 15th cell.

You'll also need to update, everywhere a literal `12` currently means
"how many real header cells exist":
- `KTB_STRIP_N_CELLS` in `khtpm_taskbar_manager.h` (currently `12` →
  becomes `14`).
- `khtpm_taskbar_manager.c`'s own header comment listing cell order
  (search `1=HQ, 2=USER...`) — update it, it's load-bearing documentation
  other functions' own comments point back to.
- Every `onClick="ACTIVATE:N"` in `khtpm_strip_header.chtpm` for `store`
  and `network` — bump both by 1 (11→12, 12→13).
- The `.chtpm` file's own header comment listing cell order (same file,
  top of file) — keep it in sync, it's what the NEXT agent after you will
  trust.

### 4.3 — Building the `menus` cell (dynamic submenu)

Follow the **exact existing pattern** other dynamic cells already use —
don't invent a new one. Look at `livedesk_build_session_menu()` or
`livedesk_build_desk_menu()` in `khtpm_taskbar_manager.c`: each scans a
real directory, builds `HQMenuItem` rows from what it finds, returns a
count. `ktb_hq_open()`'s own `if (which == N) n = livedesk_build_X_menu(...)`
dispatch is where you wire a new one in.

**Real design decision, yours to make**: there is no existing "plugins"
or "user menus" directory convention in this house yet (checked — none
exists). Pick a real, sensible location (e.g. something under
`#.desktop/`, matching how `#.desktop/livedesk_taskbar.pdl` and friends
already live) and document your choice clearly in a comment, the same
way every other real decision in this codebase is documented inline —
that's the house's own standing convention, not optional flourish.

Minimum viable v1: scan a directory for files (or subdirectories) with
some agreed naming/content convention, list one row per thing found,
each row's `command` can literally be a placeholder (`void`, or a real
launch command if you want to make it functional) — the point of this
task is a *working, live, dynamically-populated* menu, matching what
"user created menus" implies, not a fully-designed plugin runtime.

### 4.4 — Building the `date/time` cell

This one's simpler — it doesn't need a submenu, just a live label. Look
at how `${username}`/`${file_label}`/`${desks_label}` already work (grep
`var_username` in `khtpm_strip_parser.c` and `khtpm_taskbar_manager_main.c`'s
`publish_var_fragments()`): the manager computes a small string and
writes it to its own `strip_var_*.txt` file; the parser reads it back via
`sp_get_var()` and substitutes it into a `${var}` placeholder in the
`.chtpm` layout. Follow this **exact** pattern for a new `${datetime}`
var:
1. Manager: new function (real C `strftime`, or `popen()`-out to `date`
   if you want the Chinese locale specifically — check what locales are
   actually installed, `locale -a`, before assuming `zh_CN.UTF-8` exists;
   if it doesn't, using `date` with an explicit format + a manual
   Chinese weekday/month lookup table is a safe fallback that doesn't
   depend on system locale data).
2. Publish it as `strip_var_datetime.txt` (same `write_small_file()`
   pattern every other var uses — copy it, don't reinvent).
3. `.chtpm`: add the new cell as `<text>${datetime}</text>` or a
   non-interactive `<button>` (whichever the layout format's own docs —
   `khtpm-strip-parser-SCOPE.md` in the same taskbar dir — say is right
   for a display-only, non-clickable cell; read that scope doc's tag
   vocabulary section before guessing).
4. `.pdl` config key for language: follow the SAME pattern
   `strip_x_offset`/`strip_y_offset` already use in
   `#.desktop/livedesk_taskbar.pdl` — a new `SECTION | datetime_lang |
   zh` (or `en`) row, read via the same `read_key_value()` helper every
   other `.pdl` config read in this file already uses. Default to `zh`
   per the direct instruction (Chinese first, as the "is this really
   dynamic" test), switchable to `en`.

**Recompute it live** — don't cache it once at manager startup. Check how
often `publish_var_fragments()` already runs (it runs on every
`dispatch_code()` call, i.e. every input) and either compute datetime
fresh every time that function runs, or add your own lightweight timer
tick if that's too frequent (a real per-second `strftime()` call is cheap
either way, no caching needed for this).

### 4.5 — Verify this task properly before calling it done

- Build clean (`sh build_khtpm_strip.sh`, check for `error`, ignore
  pre-existing `warning`s not related to your change).
- Relaunch fresh (`sh $.crypts/button.sh run`), verify via `ps aux` that
  exactly one taskbar is running (§2.1 discipline).
- Use the agent relay (§2.3) to navigate to your new cells and confirm,
  via `khtpm_strip_frame_history.txt`, that `element_count` grew by 2 and
  the new cells' labels/onClick show up correctly in the log.
- For `date/time` specifically: check the actual value in
  `strip_var_datetime.txt` twice, a few seconds apart, and confirm it
  genuinely changed — that's your proof it's live, not static.
- Report back to the user with what you built and how you verified it —
  don't just say "done," show the evidence (matching every other real fix
  in `AU11-khtpm-gap-fixes.txt`, if you want a model for how this house
  expects work to be reported).
