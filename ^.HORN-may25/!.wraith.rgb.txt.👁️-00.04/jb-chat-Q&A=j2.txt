• Yes: in this plan, GL should render RGB frames, not own font rendering.

  The font path should be:

  CHTMGL text / ASCII cells
    -> colored cell frame
    -> glyph rasterizer converts characters to pixels
    -> RGB/RGBA framebuffer
    -> GL presenter uploads framebuffer as texture

  So GL does not need to know about fonts, buttons, text layout, CHTMGL tags, or
  UI semantics. It just gets a finished RGB/RGBA frame and displays it.

  For fonts specifically, we have two reasonable stages:

  1. Early stage: use a built-in bitmap font atlas, like 8x8, 8x13, or 8x16.
     Each ASCII cell has char, fg_rgb, bg_rgb, style, and object_id. The
     rasterizer paints the background, then paints glyph pixels in foreground
     color into current_frame.rgb.txt or rgba.bin.

  2. Later stage: use FreeType or a packed font atlas.
     Still the same contract: text becomes pixels before GL. GL only uploads the
     resulting framebuffer texture.

  So the GL presenter is basically:

  read rgba.bin / rgb.txt
  glTexSubImage2D(...)
  draw one full-screen quad

  If we ever let GL render fonts directly, that should be a separate debug/
  experimental renderer, not the main wraith-pm contract. The main contract is:
  fonts convert to RGB before GL.

🆎️
Key takeaway: Wraith should not be “CHTMGL directly to GL.” It should be
  CHTMGL + state -> wraith_parser.c element tree -> colored ASCII frame
  artifacts -> optional RGB/GL/HDMI output.
