RE-WRAITH CLEAN PLAN J4

Purpose:
This is a pre-code plan for fixing Wraith without first absorbing Wraith's
current implementation assumptions. It is based only on the intended Wraith
direction, the current workspace summary, and the proven patterns observed in
`fuzz-op` and `mouse-test`.

Clean-room rule:
- Do not assume Wraith's current file names, control flow, parser contract,
  or state layout are correct.
- When Wraith code is finally opened, evaluate it against this plan instead of
  letting the current code define the architecture.

1. What the references prove

From `fuzz-op`:
- The project manager should own sovereign runtime state.
- The visible layout can be thin and mostly just project manager projection.
- File-backed state plus manager-written `gui_state.txt` is a valid TPMOS
  pattern.
- Input history should be routed into project-owned state transitions, then
  persisted, then rendered.
- The layout shell is not the application brain.

From `mouse-test`:
- Raw mouse events can be consumed from a project session history file.
- Mouse motion can mutate manager state directly.
- GUI state can be rewritten as a narrow projection artifact.
- A display pulse should happen only after state changes.

What this means for Wraith:
- Wraith must be a desktop manager with project-owned state and composition.
- Wraith should not be a decorative layout pretending to be a desktop.
- Mouse and keyboard input should mutate explicit desktop/window state.
- Rendering should be a consequence of state mutation, not the source of truth.

2. Wraith target model

Wraith should be treated as a sovereign desktop runtime with these layers:

- input ingestion layer
  Reads keyboard, numeric nav, mouse move, mouse down, mouse up, and drag
  intent from a history source.

- desktop state layer
  Owns desktop-wide state:
  - active window id
  - focused control or nav target
  - nav buffer
  - nav scope
  - mouse x/y
  - mouse button state
  - drag active flag
  - drag target id
  - drag origin mouse x/y
  - drag origin window x/y

- window registry layer
  Owns canonical per-window data:
  - id
  - title
  - x
  - y
  - w
  - h
  - z
  - visible
  - focused
  - movable
  - resizable
  - projected surface source

- projected surface layer
  Each visible subwindow should read from file-backed surface artifacts rather
  than hidden widget memory.

- composition layer
  Produces one deterministic desktop frame from desktop state, window geometry,
  chrome, and projected window surfaces.

- presentation bridge
  Hands the composed frame to the existing TPMOS visible path without giving
  that path ownership over desktop behavior.

3. Architecture decisions to enforce when reading Wraith code

- The manager must be the owner of desktop truth.
- The visible desktop must be composed from files, not inferred from tags at
  render time.
- The layout wrapper should stay thin. If the layout is doing desktop logic,
  that is a design smell.
- Mouse handling must target real hit regions:
  - titlebar
  - body
  - control buttons
  - resize edges or corners
- Numeric nav must target real desktop objects or projected surface controls,
  not fake sketch labels unless those labels are truly part of the surface.
- Desktop state and window state should be explicit files, not scattered
  implicit globals.
- Render pulses should happen after meaningful state change, ideally with
  change guards to avoid spam.

4. Likely failure modes to look for in current Wraith code

When the code is opened, actively look for these problems:

- layout-first logic where the desktop is still effectively a `.chtpm` or
  `.chtmgl` demo instead of manager-owned state
- fake windows made from static text blocks instead of movable window objects
- hard-coded menu rows masquerading as real app/window navigation
- mouse metadata being emitted without any real geometry mutation
- drag flags existing without actual drag target resolution or geometry writes
- nav buffer or jump semantics still owned by the legacy theater instead of
  Wraith-owned state
- duplicate or desynced history paths
- multiple competing sources of window geometry truth
- render loops that repaint continuously instead of pulsing on change
- code that updates visible frame text directly without first updating
  canonical state

5. Inspection order once Wraith code is allowed

Read Wraith in this order:

1. `project.pdl`
   Determine entry points, project identity, and declared runtime contract.

2. manager source
   Find who currently owns input, state mutation, window registry, and render
   triggering.

3. session state files
   Check whether desktop state and window geometry are already canonical or
   fragmented.

4. parser or input bridge
   Confirm where keyboard and mouse events actually land.

5. composition code
   Determine whether the system truly composes windows from state and projected
   surfaces.

6. layouts
   Verify the shell is thin and not acting as the hidden application brain.

7. emitted artifacts
   Confirm what files exist for frame, hit map, focus state, and window state.

6. Rewrite strategy

Apply this sequence if the current Wraith code is messy:

Phase A: establish one source of truth
- create or normalize a canonical desktop state file
- create or normalize a canonical window registry file
- remove duplicate ownership of x/y/z/focus/drag state

Phase B: lock input routing
- unify the history/event path
- define one Wraith-owned interpretation for:
  - arrow keys
  - digits
  - enter
  - mouse move
  - mouse down
  - mouse up
- separate top-level desktop nav from in-window nav

Phase C: implement real hit testing
- titlebar click focuses and selects a window
- titlebar drag mutates window x/y
- control hit regions call explicit window actions
- body click sets active window and forwards focus appropriately

Phase D: implement real window registry behavior
- bring clicked window to front by z update
- clamp movement to desktop bounds
- preserve focused window and active control in state
- support overlapping windows as peer objects

Phase E: normalize projected surfaces
- each window body should point at a file-backed source
- Wraith composes those sources instead of embedding fake content text in the
  shell

Phase F: harden rendering
- compose desktop frame from canonical state only
- emit hit map and focus artifacts from the same pass
- pulse render only when the composed result or relevant state actually changes

7. Behavioral contract Wraith should eventually satisfy

Minimum desktop behavior:

- one outer shell composition that reads like a desktop, not a dashboard
- one movable overlapping content window
- active window focus state
- visible z-order changes on selection
- live mouse cursor state
- live titlebar drag
- keyboard nav that targets real desktop/window objects
- file-backed projected subwindow content
- auditable frame artifacts derived from canonical state

8. What not to preserve from existing Wraith code if found

- static sketch labels treated as the real application model
- tag-flattened pseudo-windows
- passive mouse telemetry with no state mutation
- theater-owned nav semantics where Wraith claims ownership but does not
  actually have it
- any architecture where visible text output is more authoritative than
  canonical state files

9. Concrete questions to answer immediately when opening Wraith

- Where is the single history path for Wraith input?
- What file is the canonical desktop state file?
- What file is the canonical window registry?
- What file is the canonical composed frame?
- Does the manager own z/focus/drag truth, or does the layout/parser leak into
  that role?
- Are projected window bodies real file-backed surfaces or still placeholders?
- Does mouse down identify a target region and mutate state, or only log data?
- Does any numeric nav target real window ids or real surface-local controls?

10. Success criteria for the eventual fix

The Wraith fix is correct only if all of these become true:

- desktop state is explicit and singular
- window geometry is explicit and singular
- input path is explicit and singular
- the layout wrapper is thin
- the manager owns desktop mutation
- composition produces the visible desktop from state and projected surfaces
- mouse drag visibly moves a real window
- focus and z-order changes are reflected in canonical state and rendered frame
- future agents can inspect files and understand the desktop without guessing

Short version:
Use `fuzz-op` for sovereign manager/state/render ownership. Use `mouse-test`
for raw mouse event ingestion and pulse-on-change behavior. Reject any Wraith
implementation that lets the layout shell, static sketch rows, or passive
metadata pretend to be a real desktop manager.
