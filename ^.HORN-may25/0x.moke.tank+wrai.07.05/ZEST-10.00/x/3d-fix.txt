## What this means

**This is very unlikely to be a source-code regression or a stale/corrupt
data file** — every file that plausibly determines 3D rendering behavior
was checked and matches (or the ops's own nav-numbering, already
understood and unrelated to whether tiles render). Combined with the map
disappearing in BOTH the current tree and the earlier `x/ZEST-09.00+8TWIN/`
rollback (per the user's own report), while this THIRD reference tree
works — the bug is either:

1. Something in a file I didn't think to check (a candidate list is
   below, for whoever continues this), or
2. A genuine runtime-only behavior — something about the ray marcher's
   actual math that only misbehaves for specific input combinations not
   distinguishable by reading the code (e.g. a boundary condition in
   `ray_aabb_hit()`'s slab test, or `raymarch_tile_grid()`'s DDA step,
   that only misfires for certain camera angles/positions — camera_mode=3's
   exact values weren't hand-verified against the AABB math, only
   observed as "not obviously wrong"), or
3. Something about process/session lifecycle not captured by comparing
   files at rest (e.g. a currently-running process somewhere holding
   stale in-memory state, or a first-open-vs-toggle-later distinction —
   the live `session/state.txt` snapshot checked above was already in
   `3d_voxel` mode; whether the bug happens on FIRST toggle specifically,
   vs. persists afterward, vs. only happens after some other sequence of
   actions, was not established).

## Update: one real, non-trivial code difference DOES exist — `orchestrator.c`

After the user specifically asked whether the CHTPM parsers themselves
were diffed (they hadn't been yet — a real gap in the first pass of this
investigation), checked all three files in `pieces/chtpm/plugins/`:
`chtpm_parser.c` and `chtpm_player.c` are byte-identical between current
and the alt tree (same as everything else checked so far) — but
**`orchestrator.c` differs by 74 lines, and it's not cosmetic.**

The current tree's `chtpm_thread_func()` (the function that launches
`chtpm_parser.c` as a subprocess at orchestrator startup) is wrapped in
explicit `/* RE-WRAITH: ... */` comments and does something the alt
tree's version does not: it waits 50ms, reads
`pieces/apps/player_app/manager/state.txt`'s `project_id` (currently
`wraith-alpha`), looks up that project's OWN `project.pdl` for
`META | parser | ...` and `META | entry_layout | ...` fields, and
launches `chtpm_parser.c` with whatever it finds there — falling back to
the hardcoded defaults (`pieces/chtpm/plugins/+x/chtpm_parser.+x`,
`pieces/chtpm/layouts/os.chtpm`) only if nothing is found. The alt
tree's version has none of this — it always launches with the hardcoded
defaults, unconditionally, regardless of `project_id`.

Confirmed concretely: `projects/wraith-alpha/project.pdl` (current tree)
declares `entry_layout = projects/wraith-alpha/layouts/alpha-shell.chtpm`
— not `os.chtpm`. With `project_id=wraith-alpha` (its current live
value), the current tree's orchestrator boots the parser directly into
Wraith's own `alpha-shell.chtpm`, not the generic OS desktop shell. No
`META | parser` override exists in either `wraith-alpha`'s or
`piececraft-wraith`'s own `project.pdl` (checked, absent from both), so
the parser BINARY itself still resolves to the same default either way
— only the STARTING LAYOUT differs.

**Asked the user directly whether the alt tree's "piececraft-wraith
works perfectly" test was reached the same way (through the Wraith
desktop chrome, launcher row, embedded window) as the current tree's
broken test — confirmed yes, same interaction pattern from the user's
perspective.** This doesn't cleanly rule the orchestrator difference in
or out: it's consistent with either "this difference is irrelevant to
the 3D bug" or "the alt tree's `os.chtpm` also leads into
`alpha-shell.chtpm` via a normal in-app click rather than an
orchestrator-level auto-boot, arriving at the same end state through a
different startup path the user wouldn't necessarily notice or think to
mention." Not resolved by file comparison — this is the one place where
"same user-visible interaction" doesn't guarantee "same underlying code
path," and it's the only place in this entire investigation where the
two trees' actual source code differs in a way that isn't trivially
harmless (unlike every nav-offset diff elsewhere, which was fully
explained and dismissed).

**This is now the leading, still-unconfirmed candidate** — not because
it was reasoned out from what SHOULD go wrong, but because it's the
single non-identical, non-trivial piece of code left standing after
checking everything else (both parsers, the ray-marcher, `wraith_gl.c`,
piececraft-wraith's own ops/manager, tile registry, maps, camera
defaults, config resolution, binary freshness) and finding them all
identical or harmlessly offset.
