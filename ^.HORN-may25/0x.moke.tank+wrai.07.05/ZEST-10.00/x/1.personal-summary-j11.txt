PHASE 1: WHAT I CHANGED IN THE WRAITH DESKTOP, AND WHY
=====================================================================

The problem: when you open a project like wrai-text-editor inside the
Wraith desktop (as a window in the taskbar), the desktop was NOT
actually reading that project's own layout file (the file that defines
what buttons and boxes look like). Instead, every project that wanted
real buttons/framing in its window had to hand-write that structure
directly in program code (C code), duplicating what the layout file
already said. Two copies of the same UI, only one of which was ever
actually used.

This is NOT how the rest of this codebase works. Everywhere else
(including agy-text-editor, which is the reference for "correct"), a
project writes VALUES to a state file, and one generic system reads the
layout file plus those values and produces the final screen. One source
of truth, one merge step.

**What I built:** a real version of that merge step, but only for
Wraith's desktop windows in ASCII (text) mode. It's a new function in
the desktop's shared code (`wraith-alpha_manager.c`) that:
1. Checks if a project has a `gui_state.txt` file (the values file).
2. Checks if that project isn't using a different, older special mode
   (`is_map_control` — piececraft-wraith uses this).
3. If both checks pass: opens the project's real layout file, reads its
   values file, and produces the actual merged screen — just like agy
   does.

**Why this is the right direction:** it removes the need for hand-
duplicated code per project, which is both wasted work and a source of
bugs (the two copies can drift apart, and did — that's why
wrai-text-editor initially looked wrong compared to agy).

PHASE 5: BUGS YOU MAY RUN INTO, AND ONE THAT CAUSED REAL CONFUSION TODAY
=====================================================================

**The "8" key vs. clicking the on-screen button mismatch.** You found
that pressing the "8" key directly on your keyboard correctly switches
piececraft-wraith into 3D mode, but clicking the on-screen "[8] 2D/3D"
button does NOT work correctly — and you confirmed this same mismatch
happens on OTHER projects too, not just piececraft-wraith.

This is a big deal for how today's investigation went: I spent a
significant amount of time assuming the 3D map disappearing was a bug
specifically in piececraft-wraith's 3D drawing code. Once you reported
that hotkey-vs-click behaves differently, and that this happens
everywhere (not just in 3D, not just in piececraft-wraith), it became
clear the REAL bug is probably in how on-screen button clicks get
translated into key presses in general — a much more basic, more
widely-affecting bug than "piececraft-wraith's 3D view is broken."

**Practical effect:** if you see something that looks broken specifically
after CLICKING a numbered button (rather than pressing the matching key
directly), suspect this same click-vs-key mismatch first, before
assuming the feature itself is broken. This may explain other odd
behavior you run into that isn't otherwise written up here.

**On the fs fix specifically:** as covered in Phase 3, the fs fix that
went in today was a real, correct fix for the SPECIFIC symptom you
reported (numbers repeating) — but it's not the "real" fix, because the
number is still hand-typed rather than computed automatically. Plain,
non-Wraith projects (confirmed: `+-demo` exists and works this way
already) don't have this problem at all, because their numbering is
never hand-typed in the first place. That's the standard the nine
Wraith projects should eventually be moved to.

**Why pressing Enter on settings pages didn't work, but clicking did
(found and fixed):** You reported that pressing Enter on a settings
page button didn't move to the next page — it only moved after you
clicked the screen with the mouse. I'd already made one fix (a missing
relay case for the SETTINGS_PAGE: command) that was necessary but
turned out not to be the real problem.

The actual bug: when you press Enter on a keyboard, the command has to
travel from the on-screen text renderer to the desktop's "brain"
process through a small hand-off file. That hand-off file's name was
being built wrong for every window opened inside the Wraith desktop
(settings, fs, and every other embedded project) — so the command was
being written to a file that literally nobody was ever reading. It
just vanished, silently, every time, for every keyboard-driven button
in every embedded window. Mouse clicks never had this problem because
mouse clicks take a shortcut straight into the brain process and skip
that hand-off file entirely — which is exactly why "click works,
keyboard doesn't" was the symptom.

This is fixed now (the hand-off file name is built correctly). It's a
foundation-level fix, not settings-specific — it should also make any

settings) more reliable than it's been, since this bug applied broadly,
