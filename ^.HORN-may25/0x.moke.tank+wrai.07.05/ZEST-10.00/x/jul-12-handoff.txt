### 3. Universal context menu, opened by hotkey OR right-click (last, per user: prove emoji first)

New this session, expanded from "emoji picker hotkey" to a bigger,
more useful design: ONE key, working identically across every Wraith
screen (any embedded project, or the desktop itself), that opens a
context menu whose CONTENTS depend on whatever is currently focused —
mirroring how the chrome "&" resize/window-geom icon already scopes
itself to whichever window is focused
(`open_window_geom_for_project(window->project_id)`). The emoji picker
becomes the first thing this menu offers (when a text-editing field is
focused), not a special-cased binding of its own.

Per `emoji-phase1-infrastructure.md`'s own roadmap note: "Phase 1
unblocks Phase 2 (context menus), which unblocks Phase 3 (window-geom
verification)" — documented order is Phase 1 → picker → window-geom,
though the user raised window-geom alongside this today, so treat
ordering as a live discussion, not a hard rule.

**Hotkey choice — investigated 2026-07-12, concrete finding, not just
an open question anymore:**

User's own suggestion was Shift or Alt alone. Traced the actual LIVE
input readers for both paths (not just similarly-named files — same
"confirm what's actually live" discipline as
[[wraith-window-geom-blank-rootcause]]):
- ASCII: `pieces/keyboard/plugins/keyboard_input.c` (this is the binary
  `orchestrator.c` actually launches, NOT `input_capture.c` or
  `input_dispatcher.c`, which exist in the tree but aren't spawned).
- GL: `projects/wraith-alpha/ops/wraith_gl.c`'s `keyboard()`/
  `special_keyboard()`.

Findings:
- **A bare Shift or Alt press alone is not detectable in either path.**
  Terminals never send a distinct signal for "a modifier went down" by
  itself — a modifier only changes what byte arrives when combined
  with another key. `keyboard_input.c` reads raw bytes off `/dev/tty`
  with no channel for "modifier alone," and GLUT's `glutGetModifiers()`
  only reports modifier state DURING a real key event — freeglut never
  fires any callback for a bare modifier tap. This isn't a
  this-codebase limitation, it's how terminals and GLUT work.
- **Shift+letter is a bad choice specifically for an editor**: in the
  ASCII path, Shift+M simply arrives as the byte for `'M'` — there is
  no separate "shift was held" signal, so it's indistinguishable from
  the user just typing a capital letter, which happens constantly
  while editing text. Ruled out.
- **Alt+letter is partially there**: GL gets it for free via
  `glutGetModifiers()` returning `GLUT_ACTIVE_ALT` during any keyboard
  callback. ASCII does NOT support it yet — `keyboard_input.c`'s
  `editorReadKey()` only recognizes the 3-byte arrow-key escape shape
  (`ESC [ A/B/C/D`); an Alt+letter sequence arrives as `ESC` + letter
  (2 bytes, no `[`), which the current code would misread as a bare
  ESC and silently discard the letter. Fixable, but not yet done —
  real, scoped implementation work in `editorReadKey()`'s escape
  handling.
- **Ctrl+letter already works end-to-end, right now, in BOTH paths** —
  it's the exact mechanism `Ctrl+C` uses for shutdown already:
  `keyboard_input.c` disables `ISIG` in raw mode so Ctrl+C arrives as
  literal byte 3 (`main()`'s `if (c == ((('c') & 0x1f))) break;`), and
  `wraith_gl.c`'s `keyboard()` checks `key == 3` the same way. Ctrl+
  letter combos always produce bytes 1-26, which can never collide
  with normal printable typing (32-126) or the existing 1000-1003
  arrow codes — this property is exactly what a "safe everywhere,
  including while typing" hotkey needs.

**Recommendation: bind the context menu to Ctrl+<letter>, not a bare
modifier.** It's the only option that's already proven working in both
renderers today, needs zero new escape-sequence parsing, and can't
collide with either normal typing or existing nav bindings by
construction. Exact letter still open (candidates worth considering:
`G` for "menu"-adjacent mnemonic-free availability, or `/` — pick
something not already meaningful in INTERACT-mode's WASD/backspace/
enter set or the desktop's own digit/arrow nav). Alt+letter remains a
real option later if Ctrl+letter turns out to collide with something
not yet found, but would require the `editorReadKey()` escape-parsing
work above first — start with Ctrl+letter since it needs no new
plumbing.

**User follow-up (2026-07-12): what about Ctrl+Alt (no letter)?**
Same wall as bare Shift/Alt — a terminal (and GLUT) only ever produce
an event when a NON-modifier key is pressed; holding any combination of
ONLY modifier keys, however many, with nothing else, still generates
zero bytes on the tty and fires no GLUT callback. Ctrl+Alt+<letter>
(three keys, one of them real) WOULD be technically detectable in GL
via `glutGetModifiers()`'s bitmask (`GLUT_ACTIVE_CTRL | GLUT_ACTIVE_ALT`
together), but is significantly less portable on the ASCII side —
different terminal emulators encode Ctrl+Alt+letter inconsistently
(some send a meta-escaped control byte, some don't distinguish it from
plain Ctrl+letter at all), so it would need real cross-terminal testing
with no guarantee of consistent results. Since plain Ctrl+letter is
already 100% collision-free with normal typing on its own, requiring
Alt too buys no real safety margin — stick with plain Ctrl+<letter>.

**User follow-up: right-click should also open it.** Confirmed via code
this is a small addition, not new plumbing — the mouse button number is
ALREADY captured end-to-end in both paths: GL's `mouse(int button, ...)`
callback gets GLUT's raw button constant, and ASCII's SGR mouse mode
(`keyboard_input.c`'s `editorReadKey()`, the `\x1b[<Pb;Px;PyM` parse)
already decodes button 0/1/2 (left/middle/right) and both reach
`wraith-alpha_manager.c`'s `handle_mouse(int btn, int x, int y)`
(~l.4543) with a comment already documenting the SGR code meanings.
Nothing branches on button value today, though — GL's `mouse()` and
`handle_mouse()` both treat every button identically (hit-test/activate
the same way regardless of which was pressed). Adding right-click
support is one new `if (btn == 2)` (ASCII) / `if (button ==
GLUT_RIGHT_BUTTON)` (GL) branch in each, not a new capability.

**User follow-up: the menu should be "just a new project window," like
the "&" resize icon, selectable from a list of "projects" then
"desktop" (or other currently-open projects/tabs) — is there already a
registry of open windows a new project could read?** YES, confirmed
live: `projects/wraith-alpha/session/desktop_ui_state.txt`, rewritten
by `update_state()` on every single state change (not a one-time
snapshot), with a full per-slot registry:
`desktop_registry_<N>_id` / `_title` / `_project_id` / `_instance_no` /
`_state` / `_open` / `_minimized` / `_visible`. Verified live content
this session — e.g. `desktop_registry_2_project_id=wraith-alpha/
wraith-projects/wrai-text-editor`. This is plain text, already kept
current, and readable by any project's own ops with zero new export
work — a new "context-menu" project's ops can parse this file directly
to enumerate other open windows/tabs, exactly the way the taskbar
itself is presumably driven from the same source
(`sync_registry_from_disk()` reads it back into `g_windows[]` on
manager startup — same file, round-trip confirmed).

This confirms the "just a new project window" architecture is
plausible without inventing a new registry: the context-menu project
would be launched the same way `open_window_geom_for_project()` launches
window-geom (`launch_window_instance(...)`), and its own layouts would
read `desktop_ui_state.txt` to list "Projects" (open windows) and offer
a "Desktop" entry for desktop-level actions, mirroring window-geom's
own `wg_target.txt`-style "which thing am I acting on" pattern rather
than reinventing one.

## Standing rules carried forward from this session

- **Bible section 11 REUSE RULE**: check `pieces/system/` for an
  existing shared Op before writing new manager/ops logic from scratch.
- **Verify with real evidence, not guesses**: this session's real bugs
  were all found by reading two functions side by side and comparing
  their actual criteria/formats, not by re-theorizing from a
  screenshot. Screenshots show symptoms; code comparison shows causes.
- **Distrust comments that assert two things are "in sync" or
  "mirrored"** without a shared helper enforcing it — that's exactly
  the shape of bug #8 (nav-slot count) and the stale KPI A2 comment
  above. Prefer one function driving both consumers over two
  independently-maintained copies of the same criterion.
- **One-shot event files (queues) must be cleared by their reader
  immediately after consuming**, or they silently re-apply forever —
  bug #10's `state_changed.txt` bug, same shape as the earlier
  `is_map_control` clobber bug (piececraft-wraith, then wrai-text-
  editor) but for a different field. Any new `session/` file that
  represents a queued transition, not a persisted setting, needs this.
- **`wraith_gl.c` is the one shared GL process for every Wraith
  project** — a bug or fix there is repo-wide, not project-specific.
  Check it first for "works in ASCII, breaks in GL" reports.
