## PART 1: CURRENT ARCHITECTURE ANALYSIS

### 1.1 PIECECRAFT-3D (GL-OS Legacy, Authoritative Reference)

**Location:** `projects/piececraft-3d/`

**Entry Point:** `layouts/main.gltpm` (GL/voxel renderer)
**Fallback:** `layouts/main.chtpm` (ASCII placeholder)

**Key Characteristics:**
- **GL-first design**: Expects GL presenter and voxel rendering pipeline
- **Overlay nav buttons**: Camera/movement controls rendered ON TOP of the 3D view
- **Full-screen game surface**: Uses entire GL window for world view
- **Manager path:** `projects/piececraft-3d/manager/+x/piececraft-3d_manager.+x`
- **Map files:** `maps/map_01_z0.txt` (simple ASCII grid format)
- **No project pieces:** Uses minimal architecture without embedded piece state

**Data Flow:**
1. Player sends input via keyboard/controller
2. Manager routes input and updates internal state
3. Manager calls `render_map.+x` op to rebuild display
4. GL presenter reads and renders the voxel scene

**Current Limitation:**
- Tightly coupled to GL rendering pipeline
- ASCII layout is just a stub, not functional
- No TPMOS-compliant project piece structure

### 1.2 FUZZ-OP (ASCII-First, TPMOS-Compliant, Actively Maintained)

**Location:** `projects/fuzz-op/`

**Entry Point:** `layouts/fuzz-op.chtpm` (ASCII primary)
**Alternative:** GL presenter can also render (via Wraith as a project window)

**Key Characteristics:**
- **ASCII-first design**: Works equally well in terminal or GL window
- **Embedded nav controls**: Numbered buttons (1-9) for methods/actions BELOW the map
- **Sovereign map viewport**: `${game_map}` variable shows rendered map
- **Full selector implementation**: Shows active target, position, state
- **Manager path:** `projects/fuzz-op/manager/+x/fuzz-op_manager.+x`
- **Map interaction:** Via `INTERACT` button + arrow keys to move selector
- **Z-level control:** 'x' key to ascend, 'z' key to descend
- **Entity selection:** Enter key on same position as another entity selects it
- **Method calls:** Keys 2-9 invoke methods on active piece (via PDL)

**Input Routing Example:**
```
KEY_PRESSED: 1003  → DOWN arrow
→ route_input(1003) in manager
→ Updates xlector pos_y
→ Calls render_map op
→ Updates ${game_map}
→ Parser re-renders frame
→ User sees map updated in next frame
```

**Current Strength:**
- Fully TPMOS-compliant
- Data-driven (no hardcoded methods)
- Works in both ASCII and GL contexts
- Reusable patterns for game projects

## PART 2: YOUR QUESTIONS ANSWERED

### QUESTION 1: Should piececraft-wraith be 2D only, or support both 2D and 3D?

**Recommendation: Support both 2D and 3D modes**

**Why:**
1. **Reusability:** Same input/selection system works for both
2. **Game design flexibility:** You want RPGs (2D good) and realistic games (3D good) both available
3. **TPMOS precedent:** Fuzz-op doesn't bake in visual mode; it just manages state and lets presenter decide
4. **Camera state already tracks 3D:** `cam_x`, `cam_y`, `cam_z`, `cam_pitch`, `cam_yaw`, `cam_roll` are in state

**Implementation approach:**
- Add a `display_mode` variable: either `2d_topdown` or `3d_voxel`
- Wraith ASCII always shows 2D map + debug info
- Wraith RGB presenter renders based on `display_mode`
- Input handler routes movement/selection the same way regardless of mode

---

### QUESTION 2: Should game map take up the whole terminal screen?

**Recommendation: YES, for full-screen immersion**

**Current fuzz-op layout (compact):**
```
╔════════════════════════════════════╗
║ LAYOUT ID: game.chtpm              ║
║ GAME MAP:                          ║
║  [Control Map]                     ║
║ ${game_map}  (map here)            ║
║ [Response] [Methods]               ║
╚════════════════════════════════════╝
```

**Recommended hybrid for piececraft-wraith:**
```
ASCII mode (terminal):
  - Top 90% = game map (no decorative border)
  - Bottom 10% = status line showing position/tile/available methods
  - Optional debug overlay (toggle with key)

GL mode (Wraith RGB):
  - Full screen = 3D voxel or 2D topdown based on display_mode
  - Overlay nav buttons on edges (like piececraft-3d does)
```

**Why this is better:**
- Immersive gameplay experience
- Status line provides critical feedback
- Allows overlay buttons in GL mode without ASCII parity issues

### QUESTION 3: Why does piececraft-wraith have no map responsiveness?

**Root Cause (Confirmed):**

Piececraft-wraith lacks THREE critical pieces:

1. **No manager daemon** → Input never gets routed or processed
2. **No input op** → Commands from history.txt are not interpreted
3. **No piece state** → No `xlector` entity to move, no map selection logic

**Evidence:**
- `session/history.txt` shows keypresses (1003=DOWN, 1000=LEFT, etc.) from Jul 2 03:36
- But `session/state.txt` shows no updates (still has old selected_cell=4,2,0 from June 29)
- Layout shows `${game_map}` but it's static (never re-rendered after input)

**Comparison to fuzz-op:**
```
Fuzz-op working flow:
  Input → Manager reads history.txt → route_input() → Updates piece state → Renders map → Parser re-renders frame

Piececraft-wraith current flow:
  Input → History recorded in session/history.txt → (nothing happens) → Static frame shown
```

**What's missing to fix it:**
1. Manager daemon (`piececraft-wraith_manager.+x`) that:
   - Monitors `session/history.txt` for NEW lines
   - Parses KEY_PRESSED codes (1003=DOWN, 1000=LEFT, etc.)
   - Routes movement to xlector piece state
   - Updates game state in `session/state.txt`

2. Input op (`ops/+x/render_map_wraith.+x`) that:
   - Reads xlector position and map_id
   - Generates ASCII map with selector marked
   - Outputs map text for substitution into `${game_map}`

3. Piece structure for xlector:
   - Even if not in `pieces/` directory, need stored state for: pos_x, pos_y, pos_z, current map
   - Can live in `session/xlector_state.txt` or similar

## PART 3: DESIRED STATE & ARCHITECTURE

### 3.1 Full-Screen Game Map Layout

**New piececraft-wraith ASCII layout proposal:**

```xml
<chtpm>
  <!-- Full-screen game map with no decorative frame -->
  <text label="${game_map}" /><br/>

  <!-- Single-line status bar at bottom -->
  <text label="[Mode: ${display_mode}] [Xelector: (${xel_x},${xel_y},${xel_z})] [Tile: ${active_tile}] [Methods: ${piece_methods}]" /><br/>

  <!-- Optional debug line (conditionally shown) -->
  [IF_DEBUG_MODE]
  <text label="[DEBUG] Camera: (${cam_pitch}°,${cam_yaw}°) | Active: ${active_piece} | Map: ${active_map}" /><br/>
  [ENDIF]
</chtpm>
```

**Advantages:**
- Full screen dedicated to game world
- Critical info always visible in status line
- Compact and TPMOS-aligned
- Leaves room for overlay buttons in GL mode

## PART 4: IMPLEMENTATION ROADMAP

### Phase 1: Add Manager & Basic Input Routing

**Goal:** Make piececraft-wraith playable and responsive

**Key files to create:**

1. **Create manager:**
   - Path: `projects/wraith-alpha/wraith-projects/piececraft-wraith/manager/piececraft-wraith_manager.c`
   - Base it on `projects/fuzz-op/manager/fuzz-op_manager.c`
   - Key changes:
     - Read from `session/history.txt` instead of `pieces/apps/player_app/history.txt`
     - Write state to `session/state.txt` instead of `projects/*/pieces/*/state.txt`
     - Call ops with Wraith paths
     - Simpler (no TPM mirror sync, no PDL parsing initially)

2. **Create render op:**
   - Path: `projects/wraith-alpha/wraith-projects/piececraft-wraith/ops/+x/render_map_wraith.+x`
   - Input: xelector pos (x,y,z), map_id
   - Output: ASCII map text with xelector marked at current position
   - Example:
     ```
     ####################
     #..................#
     #...T..........R...#
     #..................#
     #.........T........#
     #....R.>...........#  <- xelector at (6,5,0) shown as >
     #..................#
     #...........T......#
     #..................#
     ####################
     ```

3. **Create xelector state:**
   - Store xelector position in `session/state.txt` or separate file
   - Tracks: pos_x, pos_y, pos_z, current_map, active_piece

4. **Update layout to work with manager:**
   - Add module reference so Wraith knows manager is running
   - Change static buttons to use proper onClick handlers
   - Status line subscribes to state variables

**Testing flow:**
```
User presses DOWN arrow
→ Wraith appends "KEY_PRESSED: 1003" to session/history.txt
→ Manager wakes up, detects new line
→ Calls route_input(1003) → updates xelector pos_y
→ Calls render_map_wraith op
→ Op generates new map with xelector at (4,3,0) instead of (4,2,0)
→ Manager updates session/state.txt with new pos_y
→ Parser notices state changed, re-renders layout
→ Terminal shows map updated with xelector moved down one row
→ User sees responsiveness!
```

## PART 6: CLARIFYING QUESTIONS & DECISIONS

**DECISION:** Use ASCII tiles (# . T R) for MVP.
- **Try emojis in future phase:** Yes, Wraith RGB is texture-based so emojis should work
- **MVP scope:** Stick with simple ASCII symbols
- **Future:** Emoji tile support can be added after core gameplay works
- **Reference:** Emoji-studio project demonstrates emoji rendering in Wraith

### 2. Xelector Behavior

**Question:** When xelector moves, should screen center on it or is the entire map always visible?

**DECISION:** Keep existing functionality from fuzz-op 2D and piececraft-3d MVP.
- **Xelector** is the player-controlled game piece on the map (moves with arrow keys)
- Map is 10x10, fits on screen, so always visible
- No scrolling behavior for MVP
- Future: Can add camera following if maps grow larger

### 3. Piece Interaction

**Question:** What happens when you "interact" with a tile? Pick up items, dig/place blocks, talk to NPCs?

**DECISION:** Defer to methods/ops phase (not MVP).
- MVP: Just select and view
- Methods/actions: Will be handled through ops and button-invoked methods
- Can expand interaction model later

### 4. Camera in 2D Mode

**Question:** Should camera angle affect what you see in 2D topdown mode?

**DECISION:** Pure top-down, camera angle DOES NOT affect 2D view.
- 2D mode: Always top-down view
- Z-level changes: Determine which map slice is displayed
- Camera state still tracked (for 3D mode switching), but 2D rendering ignores it
- Future: 2D mode can add rotation hotkeys to rotate the board view

### 5. Wraith RGB Overlay Buttons

**Question:** Should UI buttons float over game world (like piececraft-3d) or in side panel?

**DECISION:** Floating overlay buttons (like piececraft-3d) when in GL mode.
- **Optional:** Using collapsible menu tag (like +-demo/ `6.[+]`) for nav options
- Menu overlays full-screen `${game_map}` without permanently consuming space
- **Feasibility:** May need special layout tag to enable overlay mode (investigate in Phase 1)

### 6. Save/Load Game State

**Question:** Support saving progress or just playable reference implementation?

**DECISION:** Defer to future ops/methods phase (not MVP).
- MVP: No save/load
- Later: Will implement through dedicated ops and methods
- Can be added after core gameplay is solid
