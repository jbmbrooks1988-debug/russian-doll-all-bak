# Project Pieces Proposal - Jan 2026

## Overview
This document outlines the architectural changes needed to transition from hardcoded entities to a flexible project-based system where entities are defined in project-specific files. This will enable saving/loading different games/configurations from project directories.

## Current State Analysis
- Entities are currently hardcoded in plugins (`emoji_entity_manager.py`, `terrain_generator.py`, `entity_manager.py`)
- Different plugins manage different entity types (terrain vs emoji entities)
- Data is loaded from fixed directories (`data/entities`, `^.fin_mc_8&16_c2--]FIXD/mc_extracted_csvs_8x8`)
- No mechanism for saving/loading different configurations/projects

## Proposed Architecture

### 4. Piece Rendering Configuration

Different render styles should be configurable per piece:

#### Render Styles
- `extruded`: 2D image extruded into 3D (8 layers deep) - used for emoji entities
- `six-faced`: 2D image applied to all 6 faces of a cube - used for terrain blocks
- `custom`: Loaded from 3D voxel CSV files
- `flat`: 2D image displayed as a flat plane
- `transformed`: Custom transformations applied to voxel data

### 5. Unified Entity Loading System

Instead of separate plugins for different entity types, create a unified system:

```python
class UnifiedEntityLoader:
    @staticmethod
    def load_entity(piece_definition):
        """Unified method to load any type of entity based on definition"""
        entity_type = piece_definition.get("type", "generic")
        
        if entity_type == "emoji_entity":
            return UnifiedEntityLoader._load_emoji_entity(piece_definition)
        elif entity_type == "terrain_block":
            return UnifiedEntityLoader._load_terrain_block(piece_definition)
        elif entity_type == "custom_model":
            return UnifiedEntityLoader._load_custom_model(piece_definition)
        else:
            return UnifiedEntityLoader._load_generic_entity(piece_definition)
    
    @staticmethod
    def _load_emoji_entity(definition):
        """Load emoji-style entity with deep extrusion"""
        entity = Entity3D(definition["id"])
        # Apply render style based on definition
        if definition.get("render_style") == "extruded":
            entity.load_2d_tile_deep_extrude(definition["source_file"])
        return entity
```

## Recommendation: Consolidate Entity Management

**Answer to question**: Yes, it would be better to consolidate terrain and emoji entity plugins into a unified system. Benefits:

1. **Reduced Code Duplication**: Both plugins have similar logic for loading and rendering voxel models
2. **Consistent API**: Single interface for all entity types
3. **Flexible Project System**: Easy to define mixed entity types in projects
4. **Maintenance**: Easier to maintain and extend one system vs. multiple systems
5. **Performance**: Shared optimization strategies across all entity types

The unified system would use piece configuration files to determine rendering differences (extruded vs six-faced vs custom models) rather than having separate plugins.

## Conclusion

This architecture provides a flexible foundation for project-based game configuration while maintaining backwards compatibility. The piece definition files allow for complex, configurable game elements while keeping the underlying rendering system unified and efficient.
