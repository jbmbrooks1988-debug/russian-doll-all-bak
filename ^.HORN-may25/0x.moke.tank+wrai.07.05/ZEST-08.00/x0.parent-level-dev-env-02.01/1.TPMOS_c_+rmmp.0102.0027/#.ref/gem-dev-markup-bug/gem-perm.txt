# Architecture Plan: y/n Permission System for gem-dev

To implement a robust "y/n" permission system that intercepts AI tool execution without breaking the existing pipeline or violating Gemini API constraints, we will modify `projects/gem-dev/manager/gem-dev_manager.c`.

## 1. Core Concepts & API Constraints
* **Gemini Tool Lifecycle**: When the Gemini API returns a `functionCall`, the manager must eventually respond with a `tool` role message containing the results. If we drop the turn or fail to respond to a `functionCall`, the context chain breaks, causing subsequent API calls to fail.
* **Non-Blocking Interception**: We will introduce a new state `PENDING_PERM`. Instead of executing tools immediately inside `check_ai_status()`, the manager will save the tool details, transition to `PENDING_PERM`, and wait for user input.
* **Safe Rejection**: If the user denies permission ('n'), we must still feed a response back to the AI (e.g., `"Error: Permission denied by user."`) so the model can gracefully continue or explain its failure.

## 2. State Modifications
We will introduce three static global variables to track the deferred tool state:
```c
static char g_pending_tool_name[128] = "";
static char *g_pending_args_json = NULL;
static char *g_pending_function_call = NULL;
```

## 3. Pipeline Interception in `check_ai_status()`
Currently, `check_ai_status()` handles the tool execution immediately when `tool_name` is parsed. We will replace the immediate execution block with a state-deferral block:

```c
    if (tool_name && strlen(tool_name) > 0) {
        // Defer execution and request permission
        strncpy(g_pending_tool_name, tool_name, sizeof(g_pending_tool_name) - 1);
        g_pending_args_json = args_json;         // Transfer ownership
        g_pending_function_call = function_call; // Transfer ownership
        
        snprintf(g_ai_state, sizeof(g_ai_state), "PENDING_PERM");
        snprintf(g_fsm_state, sizeof(g_fsm_state), "WAIT_PERM");
        snprintf(g_sys_msg, sizeof(g_sys_msg), "Execute %s? (y/n)", tool_name);
        
        char format_buf[4096];
        snprintf(format_buf, sizeof(format_buf), "Tool Execution Request\nTool: %s\nArgs: %s\n\nType 'y' to allow or 'n' to deny.", tool_name, args_json ? args_json : "{}");
        format_response(format_buf);
        
        free(tool_name);
        free(text_content);
        return; // Return to main loop without executing or querying AI
    }
```

## 4. Input Processing in `process_input_trigger()`
We will intercept the user input when the manager is in the `PENDING_PERM` state. 

```c
void process_input_trigger(void) {
    char *input = get_gui_var("input_text");
    if (input && strlen(input) > 0) {
        char *trimmed = trim_str(input);
        
        if (strcmp(g_ai_state, "PENDING_PERM") == 0) {
            // Clear input text in UI
            char *path = "projects/gem-dev/manager/gui_state.txt";
            FILE *f = fopen(path, "a"); if (f) { fprintf(f, "input_text=\n"); fclose(f); }
            
            if (strcasecmp(trimmed, "y") == 0 || strcasecmp(trimmed, "yes") == 0) {
                execute_pending_tool();
            } else if (strcasecmp(trimmed, "n") == 0 || strcasecmp(trimmed, "no") == 0) {
                deny_pending_tool();
            } else {
                snprintf(g_sys_msg, sizeof(g_sys_msg), "Invalid response. Type 'y' or 'n' for %s.", g_pending_tool_name);
            }
        } else {
            // Standard flow: forward input to AI
            char *path = "projects/gem-dev/manager/gui_state.txt";
            FILE *f = fopen(path, "a"); if (f) { fprintf(f, "input_text=\n"); fclose(f); }
            start_ai_query(input);
        }
    }
    if (input) free(input);
}
```

## 5. Deferral Execution Handlers
We will extract the original tool execution block into `execute_pending_tool()` and add a corresponding `deny_pending_tool()` function.

### `execute_pending_tool()`
This function will run the tool exactly as it used to, write the output to the context, and call `start_ai_query(NULL)` to resume the AI's processing.

### `deny_pending_tool()`
This function will skip tool execution entirely, append the function call and a rejection payload to the context, and call `start_ai_query(NULL)` so the AI knows its request was explicitly denied:
```c
void deny_pending_tool(void) {
    char *ctx_file = "projects/gem-dev/state/context.json";
    
    snprintf(g_ai_state, sizeof(g_ai_state), "ACTING");
    snprintf(g_sys_msg, sizeof(g_sys_msg), "Tool execution denied by user.");
    
    char *a_args[] = {"projects/gem-dev/ops/+x/json_state", "append", ctx_file, "assistant", g_pending_function_call, NULL};
    run_tool(a_args[0], a_args, false);
    
    char *t_args[] = {"projects/gem-dev/ops/+x/json_state", "append", ctx_file, "tool", "Error: Permission denied by user.", NULL};
    run_tool(t_args[0], t_args, false);
    
    // Clean up state
    if (g_pending_args_json) { free(g_pending_args_json); g_pending_args_json = NULL; }
    if (g_pending_function_call) { free(g_pending_function_call); g_pending_function_call = NULL; }
    g_pending_tool_name[0] = '\0';
    
    start_ai_query(NULL); // Let AI process the denial
}
```

## 6. Why This Won't Break Functionality
1. **Main Loop Preserved**: The `main` loop continues running and updating UI frames smoothly because `PENDING_PERM` acts as a passive wait state without blocking `usleep()`.
2. **Context Integrity**: By feeding back `"Error: Permission denied by user."` on rejection, we comply with the Gemini API's strict requirement that all tool invocations must have a matching response in the chat history.
3. **No Threading Race Conditions**: Everything runs inside the single-threaded manager loop, ensuring no asynchronous collisions between user inputs and tool evaluations.
