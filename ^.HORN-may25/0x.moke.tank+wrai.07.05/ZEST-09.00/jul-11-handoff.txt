## WHAT'S CONFIRMED WORKING (tested live, tonight)

- All the nav/dispatch bugs from earlier tonight: settings multi-page,
  piececraft-wraith arrow nav, the nine-project hardcoded-nav-number
  cleanup, cli_io generic support, RE-WRAITH dead code removed. Full
  detail in j11.wraith-foundation-fix-fut.txt.
- `pieces/system/file_ops/` — four new shared, reusable, CLI-tested Ops
  (`text_edit_key.+x`, `text_editor_view.+x`, `file_copy.+x`,
  `dir_browse.+x`). Each independently verified via direct CLI
  invocation (Bible section 12) before anything was wired up to them.
- `agy-text-editor` — refactored to call the shared Ops instead of its
  old ~1114-line inline implementation (Bible section 11 compliance).
  Compiles clean. Also fixed a REAL, confirmed-live bug in
  `layouts/file_browser.chtpm`: its two `<cli_io>` fields never declared
  `target_id`, so typing into either one collided on the same fallback
  gui_state key and forced a full layout re-parse on every keystroke,
  wiping the input buffer each time. Fixed by adding `target_id` to both.
- `wrai-text-editor` — full editor port from agy's UX (real editing,
  File Menu, File Browser+search, Save/Load), built on the same shared
  Ops. Page switching uses `PROJECT_PAGE:`, a newly-generalized version
  of settings' own `SETTINGS_PAGE:` mechanism (now scoped to whichever
  project window is active, not hardcoded to settings — see
  `wraith-alpha_manager.c`'s `route_command()`).
- Confirmed live: Editor page renders correctly (box frame, INTERACT
  button, cursor `[X]` marker at 0,0), File Menu renders and its
  NEW FILE button works end to end (response confirmed: "New file
  created (buffer cleared)."), page navigation between editor/file_menu
  works, and a fresh window now correctly opens on the Editor page
  (manager's `trigger_initial_render()` resets `session/state.txt` +
  `session/state_changed.txt` before first render — this was also
  broken tonight: state persists per-PROJECT not per-window-instance,
  so a reopened window used to silently resume wherever a previous
  instance left off).
- Also fixed live during this build: `session/wraith_body.txt` was
  being written with multi-row values (the editor viewport, the
  directory listing) as ONE physical line each — correct for
  `${var}` substitution into ASCII's `.chtpm` templates, but GL's
  `append_project_probe_body()` reads that file line-by-line with a
  256-byte buffer, so the oversized single line got truncated mid-tag
  and corrupted everything read after it (this is why GL's INTERACT
  button wasn't activating). Fixed with `write_markup_as_lines()`,
  which splits on `<br/>` boundaries before writing.

characters.** Last live frame showed the Editor page rendering

**Leading theory, unconfirmed:** `chtpm_parser.c`'s own "Normal nav
mode" handler for an `onClick="INTERACT"` button
(`else if (strcmp(el->onClick, "INTERACT") == 0) { active_index = ...;
export_active_index(); }`, around line 2540ish as of tonight — search
for it, don't trust the line number) sets ASCII's *local* active_index
(hence the `[^]` glyph you see) but does **not** call `send_command()`
— it never explicitly relays "INTERACT" to the desktop. Whether
`is_map_control` actually reaches `1` at the `wraith-alpha_manager.c`
level therefore depends entirely on THAT process's own, separate,
independent watch of the shared `pieces/keyboard/history.txt` file
(`route_input()`'s `action_for_nav_index()` lookup against the live GL
objects file) correctly finding this button's `action=INTERACT` entry
— which depends on tonight's `wraith_body.txt` line-splitting fix
having actually taken effect for a *specific* live frame, which was
not re-verified after that fix landed. It's plausible is_map_control
never actually reaches 1, so every subsequent keystroke gets silently
dropped by `route_input()`'s normal (non-map-control) branches instead
of being forwarded to the project as `KEY_PRESSED:` — which would
explain "shows active locally, but typing does nothing" exactly.

**Concrete debugging plan (don't re-theorize, just check these in order):**
1. Open the editor, press Enter on EDIT TEXT (INTERACT), then check

   — does it show `is_map_control=1`? (Note: this file gets rewritten by
   THIS project's own ops on every invocation, so check it
   IMMEDIATELY after pressing Enter, before typing anything else, or
   check `alpha_manager.log` instead — search for
   "Command received: INTERACT" right after the Enter keypress.)
2. If `is_map_control` never reaches 1: the bug is in the GL-side
   `action_for_nav_index()` dispatch not finding this button's action.
   Check the live `current_frame.objects.pdl` receipt for a `nav=`
   entry with `label=EDIT TEXT (INTERACT)` and confirm it has
   `action=INTERACT` — if the label is there but action is empty/wrong,
   `wraith_body.txt`'s line-splitting still isn't feeding
   `emit_embedded_line_objects()` correctly for this specific button
   (re-check `write_markup_as_lines()` and the exact bytes in
   `session/wraith_body.txt` right after opening the editor).
3. If `is_map_control` DOES reach 1: check
   `projects/wraith-alpha/wraith-projects/wrai-text-editor/session/history.txt`

   `ops/src/wraith_project_input.c::process_history()` — check it's

4. If history.txt shows nothing after typing: the bug is upstream, in
   `wraith-alpha_manager.c::route_input()`'s `read_project_map_control()`

   would be a bigger, shared-infrastructure bug, not a wrai-text-editor

   piececraft-wraith (which DOES successfully use this exact
   is_map_control + raw-key-forwarding mechanism for its own movement

## Standing rule, tonight's biggest architectural lesson

Bible section 11's REUSE RULE was NOT being followed before tonight —
agy-text-editor's entire manager was one 1114-line file with editing/
file/directory logic hardcoded inline, which is exactly what that
section's MANDATE prohibits. Before building ANY new manager/ops logic
from scratch, check `pieces/system/` first for an existing shared Op
that already does what you need, and if the logic is genuinely new but
reusable, build it there — not inline in a project-specific manager or
ops file. This isn't a one-time cleanup; it's the standing discipline
for everything built from here forward.
