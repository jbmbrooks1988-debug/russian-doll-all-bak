HOW TO FIX THE cli_io MULTI-FIELD COLLISION BUG (CHTPM-family parsers)
=======================================================================
Written 2026-07-06. For sharing with another agent/session working in a
similar (but not necessarily identical) CHTPM-derived codebase. This is
a practical runbook of what was actually done and actually worked,
including the two related gotchas that were NOT obvious up front and
cost real time to find. Read the whole thing before starting -- the
gotchas at the end are not optional footnotes, they are what makes a
"fixed" parser still look broken in a live test.

============================================================
1. THE BUG, IN ONE PARAGRAPH
============================================================
Every `<cli_io>` element's typed input (Enter/backspace/keystroke) gets
written via `save_to_gui_state("input_text", buffer)` -- HARDCODED to
the literal string `"input_text"`, regardless of the element's own `id`
or a `target_id` attribute some layouts already try to use. If a screen
has more than one `cli_io` field at once, they all share this single
global slot: typing in field B overwrites field A's saved value, and on
reparse only one field (whichever the restore logic happens to pick)
gets anything restored into it at all. This is a real, common bug in
any CHTPM-lineage parser that predates multi-field forms.

============================================================
2. HOW TO CONFIRM YOU HAVE THIS BUG BEFORE FIXING ANYTHING
============================================================
1. `grep -n "target_id" your_parser.c` -- if this returns nothing (or
   only unrelated hits like a differently-named `active_target_id`
   selector variable), the attribute is not being parsed at all.
2. `grep -n 'save_to_gui_state("input_text"' your_parser.c` -- if there
   are multiple call sites (Enter / backspace / printable-char), they
   are all writing to the same hardcoded key.
3. Find the `UIElement` (or equivalent) struct definition and confirm
   it has no `target_id`-equivalent field.
4. Find `parse_attributes()` (or equivalent) and confirm it is an
   explicit if/else-if allow-list with no `else` catch-all -- confirms
   any attribute not in the list (including `target_id`) is silently
   parsed-and-discarded, never stored anywhere.
5. Find the layout(s) that actually TRY to use two `cli_io` fields at
   once (grep for `<cli_io` count > 1 in one file). If they already
   write `target_id="1"` / `target_id="2"` (or similar) expecting
   independent fields, that confirms someone already intended this and
   it's silently broken today.
If steps 1-4 all confirm, you have this exact bug. Proceed to section 3.

============================================================
3. THE FIX -- 4 CODE CHANGES, IN ONE FILE
============================================================
All four changes go in the SAME parser file. Do them in this order;
each one is small and independently compile-checkable.

3a. Add a field to the element struct
--------------------------------------
Find the struct's `id` field (or equivalent) and add a sibling field
right after it:
```c
char target_id[MAX_ATTR_LEN];  /* Keys cli_io gui_state slot; falls back to shared "input_text" when unset */
```
Confirm elements are `memset(el, 0, sizeof(UIElement))` (or equivalent)
before `parse_attributes()` runs on them -- this matters: it guarantees
`target_id[0] == '\0'` (empty) for any element that doesn't set the
attribute, so the "falls back to old behavior when unset" logic in 3c/3d
below is safe. If elements are NOT zeroed fresh each parse, stale data
could leak between reparses -- check this before assuming it's safe.

3b. Parse the attribute
------------------------
In `parse_attributes()`, add a branch mirroring the existing `id`
branch:
```c
else if (strcmp(name_start, "id") == 0) { strncpy(el->id, val_start, MAX_ATTR_LEN - 1); }
else if (strcmp(name_start, "target_id") == 0) { strncpy(el->target_id, val_start, MAX_ATTR_LEN - 1); }
```
(Exact variable names -- `name_start`, `val_start` -- will differ per
codebase; match whatever the existing `id` branch uses.)

3c. Key the write sites
------------------------
Find every `save_to_gui_state("input_text", buffer)` call (typically
3: Enter, backspace, printable-char, all inside the same cli_io
key-handling block) and change each to:
```c
save_to_gui_state(el->target_id[0] ? el->target_id : "input_text", el->input_buffer);
```
This preserves old single-slot behavior for any cli_io tag that doesn't
set `target_id` -- nothing else in the codebase breaks.

3d. Key the restore-on-reparse
--------------------------------
This is the part that's easy to skip and then wonder why typed text
still gets wiped. Most of these parsers rebuild their element list from
scratch on every parse (`element_count = 0` at the top of the parse
function) -- so without a restore step keyed the same way as the write
side, whatever the user just typed vanishes on the next re-render.

Find wherever the codebase ALREADY restores the single shared
"input_text" value into a cli_io element on parse (search for
`get_var("input_text")` or the function that reads it back). Two
different shapes were seen across two real codebases fixing this exact
bug the same day:

  Shape A (a dedicated restore function, e.g.
  `sync_cli_input_from_gui_state()`): rewrite it to loop every cli_io
  element and, for ones with `target_id` set, restore from
  `get_var(el->target_id)` instead of the shared slot / first-element
  fallback -- elements without `target_id` keep the old behavior
  unchanged.

  Shape B (restore logic inline inside the parse loop, one `if
  (strcmp(tag_name, "cli_io") == 0)` block per legacy restore
  mechanism): ADD a new block, after the existing legacy ones, so a set
  `target_id` wins without deleting the old behavior:
  ```c
  if (strcmp(t->tag_name, "cli_io") == 0 && el->target_id[0]) {
      const char* targeted_val = get_var(el->target_id);
      if (targeted_val && targeted_val[0] != '\0') {
          strncpy(el->input_buffer, targeted_val, sizeof(el->input_buffer) - 1);
      }
  }
  ```

Either shape works -- match whichever your codebase already has, don't
invent a third pattern.

3e. Compile-check
-------------------
`gcc -Wall -o /tmp/test_parser your_parser.c <same flags your build
script already uses>` -- expect the same pre-existing warnings your
codebase always has, zero NEW errors.

============================================================
4. IF YOUR CODEBASE HAS MORE THAN ONE PARSER FILE
============================================================
Check for this before declaring victory. A codebase can easily have
TWO independent forks of the same parser lineage (e.g. one generic/
shared engine used by most projects, plus one project-specific fork
with extra desktop-shell features bolted on) that do NOT share code at
build time. Fixing one does NOT fix the other -- confirmed the hard way:
one fix applied to a shared `chtpm_parser.c` left a completely separate
`wraith_parser_alpha.c` (a ~2700-line fork) with the identical bug,
unfixed, because nothing shared code between the two files. If your
codebase has this shape, repeat section 3 in EACH parser file
separately, and don't assume grep-ing one file's fix status tells you
anything about the other.

============================================================
5. TWO RELATED GOTCHAS THAT LOOK LIKE THE SAME BUG BUT AREN'T
============================================================
Both of these were found live-testing a real fix and cost real
debugging time before being root-caused. Check for both if your fixed
parser STILL shows wrong/stale/shared values after section 3 is done
and compiled.

5a. gui_state file SCOPING can be wrong even when the KEY is right
---------------------------------------------------------------------
If your desktop/shell model lets ONE layout file host many different
embedded "windows"/projects without literally changing which layout
file is being parsed (i.e. some `active_project_id`-style variable
reassigns what's embedded, but the parser's own idea of "which
project" -- typically derived from the CURRENT LAYOUT PATH -- never
changes because the outer shell's layout path is constant) -- then
`save_to_gui_state()`/its restore counterpart can be resolving EVERY
embedded window's gui_state.txt to the SAME (wrong) file: the shell's
own, not the embedded project's. Symptom: target_id keys ARE being
written/read consistently, but always to/from the wrong project's
gui_state.txt, so a value that's supposedly "correct" per your fix
still never shows up where expected.

How to check: find how your parser derives "which project's
gui_state.txt to use" (usually a `project_id`-style var, derived from
the current layout path). If your desktop shell's OWN layout path
never changes when switching embedded content, that derivation is
almost certainly wrong for the embedded case. Look for a SEPARATE,
already-correct variable your desktop manager writes every frame (e.g.
something like `desktop_focused_window_project_id`) that DOES track the
真-embedded project, and prefer that when resolving gui_state scope for
the shell-hosted case specifically. Fix narrowly (a small helper
function used at exactly the read and write call sites), not by
overwriting the shared project-id variable globally -- that variable is
almost always load-bearing for other unrelated things elsewhere in the
same file, and auditing all of those for safety is a much bigger job
than the actual bug warrants.

5b. Chrome/body-line length limits can silently mangle multi-tag rows
---------------------------------------------------------------------
If your desktop shell composes a project's dynamic body content by
reading its output line-by-line and wrapping each line in a bordered/
padded template (common in ASCII-box desktop chrome), check whether
that wrapping step TRUNCATES lines to a fixed width. If a `cli_io` +
button row's raw markup (tags + quoted attributes) is longer than that
width, truncation can land mid-tag, producing malformed markup that
confuses the parser's tokenizer for everything after it on the same
composed frame -- this looks exactly like more cli_io/target_id
breakage (garbled/squished rows, wrong-looking values) but is actually
unrelated to anything in section 3.

How to check: find the body-line-embedding function (often has an
escape hatch like "if the line already starts with a markup character,
append it raw/unbounded; otherwise wrap+truncate it"). If so, the fix
for any multi-tag row you add is simply to make sure the WHOLE line
starts with a real tag (e.g. prefix bare label text with a `<text
label="..." />` tag instead of writing it as plain text before the
interactive tags) so it takes the unbounded path instead of the
truncated one.

============================================================
6. THE OPERATIONAL GOTCHA THAT WASTES THE MOST TIME
============================================================
If your parser is a LONG-LIVED PROCESS (started once for the whole
session, not relaunched per navigation the way per-project manager
processes often are), recompiling its `.+x`/binary does NOT make an
ALREADY-RUNNING instance pick up the fix. A stale in-memory process
will keep exhibiting the exact original bug no matter how correct your
new source is, and can even produce NEW-looking corruption if some
OTHER part of the system (e.g. a per-project manager that DOES relaunch
fresh) starts feeding it content shaped for the new, not-yet-loaded
code. Before concluding a fix "didn't work" from a live retest: kill
and fully restart the WHOLE stack (not just recompile), then retest.
This one is easy to lose an hour to before realizing it's not a logic
bug at all.

============================================================
7. HOW TO VERIFY WITHOUT A REAL TERMINAL (headless, no /dev/tty)
============================================================
If the parser needs `/dev/tty` for its normal input path but the
project's own file-based input mechanism doesn't (check: does it read
key codes from a plain file like `KEY_PRESSED: <code>` lines, separate
from actual keyboard hardware capture?), you can drive it directly:
  1. `cd` to the project root first (path resolution is usually
     `getcwd()`-based).
  2. Launch the parser binary directly with whatever layout path it
     needs as argv[1] (check the binary's own main() for how it takes a
     starting layout).
  3. Append properly-formatted key-press lines to whatever file the
     main loop polls (check the exact required format -- many of these
     are picky about it, e.g. requiring a full `[TIMESTAMP]
     KEY_PRESSED: <code>` prefix, not just a bare number).
  4. Inspect whatever the composed-frame output file is.
  5. Kill ONLY the process you started (check `ps aux` for its exact
     PID first; don't kill-by-name if anything else with the same
     binary name could be running from an unrelated session/enclosure
     on the same machine -- check the FULL PATH in ps output before
     touching anything).
  6. If your test reuses a stateful, append-only key-history file
     across multiple manual process launches, TRUNCATE it before each
     fresh launch, or the new process may replay the ENTIRE existing
     history from the start (some of these parsers don't skip ahead to
     current end-of-file on startup) -- this looks exactly like a bug
     (duplicated/doubled text) but is purely a test-methodology
     artifact, not a real defect. Confirm which behavior your specific
     binary has (skip-to-EOF at startup vs. always-read-from-zero)
     before trusting a headless test's results.
