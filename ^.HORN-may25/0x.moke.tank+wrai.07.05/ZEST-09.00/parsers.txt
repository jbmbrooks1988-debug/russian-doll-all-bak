PARSERS.TXT — cli_io parsing, and why GL does NOT need its own parser
======================================================================
Written 2026-07-06. Answers: "what about the cli_io parser?" and
"will GL need one too?" Confirmed by reading the actual code (not
assumed), same rules as the handoff.

============================================================
1. THERE IS EXACTLY ONE cli_io / chtpm PARSER IN THIS REPO
============================================================
File: projects/wraith-alpha/ops/wraith_parser_alpha.c

Confirmed via `grep -rl "cli_io" projects/wraith-alpha` — this file is
the ONLY hit in the entire wraith-alpha tree. There is no second
parser anywhere, GL-specific or otherwise. This is the file the
handoff's section 2e target_id fix applies to, and it is STILL the
only place that fix needs to happen.

Status re-confirmed live just now: zero occurrences of "target_id" in
this file (grep only turns up unrelated "active_target_id" selector
variable, not the cli_io attribute). Only one global slot
("input_text") exists. Nothing has changed since the handoff was
written — the fix in handoff section 2e is still exactly correct and
still not applied.

============================================================
2. WHAT wraith_parser_alpha.c ACTUALLY DOES
============================================================
It is the ASCII-mode renderer AND the only input-state parser:
  - parse_chtm() reads a project's .chtpm layout file, builds
    UIElement[] (including cli_io elements), rebuilding from scratch
    every call (element_count = 0 at top -- this is WHY the
    handoff's step 4, the target_id-keyed restore-on-reparse, is
    mandatory, not optional).
  - Its cli_io key-handling block (Enter / backspace / printable char)
    calls save_to_gui_state("input_text", el->input_buffer) --
    hardcoded key, confirmed still true.
  - It writes pieces/display/current_frame.txt (plain ASCII text --
    NOT rgba32, NOT a GL texture). Confirmed via grep: this file
    writes current_frame.txt, not current_frame.rgba32.

So: cli_io state, input focus, typed text, +/- button KEY: dispatch,
target_id (once fixed) -- ALL of it lives and is decided here, in ONE
place, regardless of which renderer the user is looking at.

============================================================
3. WHERE GL FITS IN -- IT IS A DOWNSTREAM DISPLAY, NOT A PARSER
============================================================
Files: projects/wraith-alpha/ops/wraith_gl.c (615 lines, read in full)
       projects/wraith-alpha/plugins/wraith_rgb_daemon.c (~2995 lines)

Traced the actual per-frame pipeline in wraith-alpha_manager.c
(spawns both as child processes, ~line 4009-4048) plus what each file
reads/writes:

  wraith_parser_alpha.c
        |  writes pieces/display/current_frame.txt (ASCII text)
        v
  wraith_rgb_daemon.c  (a plugin, always running alongside)
        |  rasterizes that ASCII text frame into pixels:
        |    - projects/wraith-alpha/session/rgb/current_frame.rgba32
        |    - pieces/display/current_frame.meta.pdl (cell geometry)
        |    - pieces/display/current_frame.objects.pdl (clickable
        |      element hit-boxes + their action strings)
        v
  wraith_gl.c  (a separate ops binary, GLUT window)
        |  loads current_frame.rgba32 as a GL texture and displays it
        |  (see load_texture()/display() -- pure texture blit, zero
        |  UIElement/parse_attributes/cli_io/input_buffer code --
        |  grep for all of those in wraith_gl.c returns NOTHING)
        |  on mouse click: hit_test_semantic_action() looks up the
        |  click position against current_frame.objects.pdl's
        |  precomputed hit-boxes (produced by the daemon, ultimately
        |  derived from wraith_parser_alpha.c's own element layout)
        |  and resolves to an action string
        |  on keyboard: append_keyboard_event() / append_project_command()
        |  just appends raw key codes / resolved commands to the SAME
        |  history files (pieces/keyboard/history.txt,
        |  projects/wraith-alpha/session/history.txt) that
        |  wraith_parser_alpha.c already reads to drive its cli_io
        |  state machine in ASCII mode.

In other words: GL mode never parses cli_io, never touches
UIElement, never calls save_to_gui_state, and never sees target_id.
It captures raw input, translates it into the exact same command/key
vocabulary ASCII mode uses, and hands it back to the one real parser
(wraith_parser_alpha.c) through shared history files. The rendering
side is one-way (parser -> ASCII text -> rasterized texture -> GL
window); the input side loops back into the same parser from both
renderers.

============================================================
4. DIRECT ANSWER
============================================================
- The cli_io parser bug (single global "input_text" slot, no
  target_id) lives ONLY in wraith_parser_alpha.c. Confirmed still
  unfixed, still exactly as described in the handoff's section 2e.
- GL does NOT need, and must not get, its own copy of this fix.
  wraith_gl.c contains no cli_io/UIElement logic to patch -- it is a
  pixel-texture viewer + raw-input forwarder. Fixing
  wraith_parser_alpha.c once fixes both renderers simultaneously,
  because both are backed by the same current_frame.txt -> state
  pipeline and the same underlying gui_state / history files.
- This is also *why* the original handoff (section 3f) explicitly
  says to verify the whole picker/editor flow once in GL mode as well
  as ASCII: not because GL needs separate code, but because it is a
  genuinely separate rendering + input-capture path reading the
  *same* state, and a bug in the shared rasterization/hit-testing
  step (wraith_rgb_daemon.c's objects.pdl hit-boxes, or wraith_gl.c's
  own coordinate mapping) could still make GL-mode clicks land on the
  wrong element even after wraith_parser_alpha.c itself is fixed.
  That's a separate, lower-probability failure mode worth a quick
  visual check, not a second parser to write.

============================================================
5. PRACTICAL CONSEQUENCE FOR THE PLAN IN THE HANDOFF (section 3a)
============================================================
No changes to the plan. Apply the 5-step target_id fix exactly as
specified in the handoff, in wraith_parser_alpha.c only. No
corresponding edit is needed in wraith_gl.c or wraith_rgb_daemon.c.
When verifying (handoff section 3f), the GL-mode pass is testing the
rasterize+hit-test path's fidelity to the parser's layout, not
re-testing the cli_io fix itself.

============================================================
6. A SECOND, INDEPENDENT PARSER: pieces/chtpm/plugins/chtpm_parser.c
   -- NOT in the original handoff, confirmed live, has the SAME bug,
   AND is already broken in a shipped project today.
============================================================
This was NOT flagged anywhere in the original handoff and I was not
tracking it until asked directly. Confirmed by reading the code just
now -- this is real, not speculative.

6a. What this file is
----------------------
File: pieces/chtpm/plugins/chtpm_parser.c (2690 lines), compiled to
pieces/chtpm/plugins/+x/chtpm_parser.+x (rebuilt 2026-07-06, so it's
live/current, not stale).

This is a SECOND, SEPARATE chtpm/cli_io engine -- not the same file
as projects/wraith-alpha/ops/wraith_parser_alpha.c, though clearly
the same lineage (identical variable names: last_synced_input_text,
digit_accum, same UIElement-style struct, same tokenize/parse_chtm
shape). wraith-alpha forked its own copy (wraith_parser_alpha.c) to
add desktop/window-manager-specific behavior; every OTHER top-level
project in projects/*  (checkers, hangman, quiz-engine, bot-editor,
user, ~40 total -- confirmed via `ls projects/`) is launched directly
by pieces/chtpm/plugins/orchestrator.c using THIS shared binary
instead (orchestrator.c line 345/399: hardcodes
"pieces/chtpm/plugins/+x/chtpm_parser.+x" as the parser for every
project it launches). wraith-alpha_manager.c itself references this
file by name in a comment (line 337) confirming it's understood as
"the shared parser" distinct from wraith-alpha's own fork.

6b. Confirmed: identical bug, same root cause
-----------------------------------------------
  - UIElement struct here (~line 78-88) has no target_id field --
    confirmed by reading the struct definition directly.
  - parse_attributes() (line 1492) is a hardcoded if/else-if chain
    with NO catch-all/default branch -- confirmed by reading the
    whole function. It recognizes: label, href, onClick, id,
    visibility, fg, bg, source, prefix, suffix, time_reactive. Any
    other attribute (target_id, input_mode, etc.) is tokenized then
    silently discarded. Nothing stores it anywhere.
  - sync_cli_input_from_gui_state() (line 159-188) restores exactly
    ONE shared "input_text" gui_state var, and even its own fallback
    logic exposes the collision: if no cli_io element has literal
    id="input_text" (normal case), it picks the FIRST cli_io element
    in the layout and dumps the shared state into THAT one only.
    Every other cli_io field on the same screen never gets restored
    on reparse.
  - The 3 write sites (Enter ~line 2485, backspace ~line 2508,
    printable-char ~line 2519) all call
    save_to_gui_state("input_text", el->input_buffer) unconditionally
    -- same hardcoded key as wraith_parser_alpha.c, confirmed by
    reading each call site directly.
  - parse_chtm() (line 1599) resets element_count = 0 at the top --
    confirmed -- so exactly like wraith_parser_alpha.c, elements are
    rebuilt from scratch every frame and nothing survives a reparse
    without a keyed restore step.

6c. This is not hypothetical -- it's live-broken right now
-------------------------------------------------------------
projects/user/layouts/user_signup.chtpm (line 6-7):
  <cli_io id="username_input" label="Enter username" target_id="1" />
  <cli_io id="password_input" label="Enter password" target_id="2"
          input_mode="password" />

This is the exact layout the original handoff pointed at as evidence
the bug exists -- but "user" is a standalone top-level project run
via the orchestrator, so it's parsed by chtpm_parser.c, NOT
wraith_parser_alpha.c. Both target_id="1"/"2" attributes are silently
dropped today. Today, on this actual project: typing in the password
field after the username field overwrites the same "input_text" var
the username field wrote; on the next reparse, only the FIRST cli_io
element (username_input) gets anything restored into it at all. This
is a real, currently-shipped, user-facing bug, independent of and
unrelated to the window-geom feature being built. (Also noticed in
passing: input_mode="password" is likewise in the allow-list gap and
is silently ignored today -- a second, separate gap worth its own
follow-up, not conflated with the target_id fix.)

6d. The fix is the same shape, applied to this second file
---------------------------------------------------------------
Mirrors the handoff's section 2e fix exactly, just in
pieces/chtpm/plugins/chtpm_parser.c instead of/in addition to
wraith_parser_alpha.c:
  1. Add `char target_id[MAX_ATTR_LEN];` to UIElement (~line 78-88).
  2. Add an `else if (strcmp(name_start, "target_id") == 0) { strncpy(
     el->target_id, val_start, MAX_ATTR_LEN - 1); }` branch in
     parse_attributes() (~line 1508, right after the `id` branch).
  3. Change the 3 save_to_gui_state("input_text", el->input_buffer)
     call sites (~2485, 2508, 2519) to
     save_to_gui_state(el->target_id[0] ? el->target_id : "input_text",
     el->input_buffer) -- preserves old single-slot behavior for any
     cli_io tag that doesn't set target_id.
  4. Rewrite sync_cli_input_from_gui_state() (line 159-188) to loop
     every cli_io element and, for each one with el->target_id[0] set,
     restore from get_var(el->target_id) instead of the shared
     "input_text" var / first-element fallback. Elements with no
     target_id keep falling back to the existing single-slot behavior
     so old layouts (with only one cli_io field and no target_id) are
     unaffected.
  5. Compile-check: this file is built via compile_op in
     #.dev-storage/#.tools/compile_all.sh line 149 -- confirmed --
     so `./button.sh compile` picks it up automatically once edited;
     no build-script change needed.

6e. Scope / relationship to the window-geom task
------------------------------------------------------
These are TWO independent instances of the same bug class in TWO
different files that happen to share a lineage but do not share code
at build time (no #include between them -- confirmed neither file
includes the other). Fixing one does not fix the other.
  - wraith_parser_alpha.c's fix is REQUIRED for the window-geom
    picker/editor (handoff section 2e/3a) -- that feature is
    hosted under wraith-alpha and only ever reached through that
    parser.
  - chtpm_parser.c's fix is NOT required for window-geom to work
    (window-geom never runs through chtpm_parser.c/orchestrator).
    It IS required to actually fix projects/user/layouts/
    user_signup.chtpm and any other orchestrator-launched project
    using multiple simultaneous cli_io fields with target_id today.
  - Recommend treating this as its own separate fix/task, not folded
    silently into the window-geom work, since it touches a shared
    engine used by ~40 other projects and its own verification
    (recompile + relaunch "user" standalone via the orchestrator,
    confirm both signup fields hold independent text) is unrelated to
    anything in wraith-alpha's desktop.
