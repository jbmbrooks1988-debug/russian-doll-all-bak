4. PICECRAFT-WRAITH CAMERA-RESET BUG (DONE, not user-reported --
   found while investigating something else, then fixed on request)
================================================================================

Unrelated tangent that came up mid-session: piececraft-wraith's map
camera was supposed to reset to neutral immediately on window open, but
visually waited for the first keypress.

Root cause: `reset_project_view_from_default()` (in
wraith-alpha_manager.c) correctly writes the neutral camera into
`session/state.txt` on open. But the actual 3D camera scene
(`scene.objects.pdl`'s `camera=` line) is only regenerated by
`ops/src/wraith_project_input.c`'s `main()`, and ONLY when it finds a
NEW keystroke since last run (`if (changed) { ...; write_scene(...); }`).
piececraft-wraith_manager.c (the one-time init manager) never invoked
that ops binary at all -- it only ran its own older, unrelated 2D ASCII
`render_map()`.

Fix:
  - `ops/src/wraith_project_input.c`: added an additive `--force` flag
    (argv[2]) that bypasses the `changed` gate for exactly one
    invocation. Normal per-keystroke behavior completely untouched.
  - `manager/piececraft-wraith_manager.c`: added
    `trigger_initial_scene_render()`, mirroring `terminal_manager.c`'s
    already-proven `trigger_initial_render()` pattern (fork+execl+waitpid),
    calling the ops binary once at startup with `--force`.

Verified: both compiled clean, both real `+x` binaries rebuilt in
place. NOT live-tested by the user (this was a side-quest fixed on
request, then the session moved back to the main window-geometry arc
before it got re-verified live). If picking this back up, opening
piececraft-wraith fresh and confirming the camera looks neutral
immediately (no keypress needed) is the outstanding check.

### 5a. The investigation (read this before touching rendering code again)

Traced the FULL pipeline for how Wraith's desktop actually reaches
pixels, end to end:

  wraith-alpha_manager.c's build_desktop_shell_markup()
    -> writes desktop_shell_markup= into session/alpha_state.txt
    -> wraith_parser_alpha.c (Wraith's OWN ~2700-line reimplementation
       of the classic chtpm parser, NOT pieces/chtpm/plugins/chtpm_parser.c)
       substitutes it into alpha-shell.chtpm, parses the WHOLE thing
    -> compose_frame() writes the result to pieces/display/current_frame.txt
       (a plain, flat, sequential text stream -- confirmed via a FULL
       trace of render_element(): there is NO row/column cursor
       ANYWHERE in it, pure strcat()-based accumulation)
    -> wraith_rgb_daemon.c's render_ascii_frame() reads that file,
       blit_char()'s each character as an 8x16 pixel glyph -- this is
       ASCII mode.

  SEPARATELY, GL mode reads pieces/display/current_frame.objects.pdl
  instead -- built by write_semantic_projection_files() in
  wraith-alpha_manager.c, an entirely independent description of the
  same screen (real x/y/w/h/label/action per OBJECT, used for both
  GL-mode drawing AND mouse/keyboard hit-testing).

KEY FINDING: these are TWO INDEPENDENTLY-WRITTEN DESCRIPTIONS of the
same screen. Nothing forces them to agree except careful, matching
arithmetic on both sides. This is the single most important thing to
understand before changing ANYTHING about how windows are positioned or
rendered -- see section 5c for how this bit us again later.

### 5b. The fix

New shared helper:
  `resolve_window_content_origin(window, &row_offset, &col_offset)` --
  resolves a window's saved x/y into row/col offsets, {0,0} by default.
  Called from BOTH sides so they can't drift apart by construction:

  - Visual side: `append_with_origin_offset(out, size, raw, row_offset, col_offset)`
    -- pads a composed markup block with leading spaces / blank lines.
    Confirmed (from the render_element() trace) this is the ONLY
    positioning mechanism available at this layer -- there's no
    coordinate API to call instead.
  - Semantic side: every window-owned OBJECT's x=/y= in
    write_semantic_projection_files() (chrome row, title, panel, all
    three chrome buttons, body-text lines, launcher rows) gets this
    same offset added. `append_project_scene_objects()` (a project's
    own scene.objects.pdl content) needed the SAME treatment too --
    found while implementing, not in the original plan; its signature
    now takes win_row_offset/win_col_offset.

Scope, deliberately: only the window's OWN title bar + content moves.
The outer desktop frame border and the taskbar stay fixed (matches how
write_semantic_projection_files() already separates "wraith_root"/
"desktop_banner"/"footer_band"/"taskbar" from window-owned objects).

6. SETTINGS HUB + WINDOW-GEOM (DONE, partially live-tested)
================================================================================

Doc: settings-hub-window-geom-design-j5.md -- READ THE REVISION NOTE AT
THE TOP, the first version of this design was wrong (see below) and was

### 6a. What it is

Two real, independent, standalone Wraith projects:

  projects/wraith-alpha/wraith-projects/settings/
    project.pdl, manager/settings_manager.c, layouts/settings.chtpm

  projects/wraith-alpha/wraith-projects/settings/window-geom/
    project.pdl, manager/window-geom_manager.c, layouts/window-geom.chtpm,
    settings_entry.pdl (the marker settings' own discovery scan reads)

`settings` scans its OWN directory for `settings_entry.pdl` markers
(discovery, not hardcoding -- adding a second settings entry later
means adding one marker file, zero code changes) and renders them as
`<button href="...">` links. Clicking one uses TPMOS's existing,
already-shipping `href`/`current_layout` navigation mechanism (same
thing `terminal.chtpm`'s "Back to Wraith Desktop" link already uses) --
NOT the Window/g_windows[] desktop-shell system at all.

### 6b. The design correction that happened mid-session (important)

The FIRST version of this design made `window-geom` an internal MODE
inside a single persistent `settings` window, specifically to avoid a
nesting restriction found in `project_dir_for_window()` (it rejects any
project_id containing a `/`). That turned out to be solving the wrong
problem -- `href` navigation doesn't go through `project_dir_for_window()`
at all (it's a completely separate, simpler "swap which file is being
read" mechanism, confirmed by tracing `wraith_parser_alpha.c`'s
`current_layout` global and its `parse_chtm()` read loop). So the
REVISED, ACTUALLY-BUILT design is simpler: two genuinely separate
projects, connected by ordinary hrefs, nested on disk under settings/
purely for organization (disk nesting has zero functional consequence
for href-reached projects). If you see references to "settings as one
persistent window with internal modes" anywhere, that's the ABANDONED
first draft -- the real code does NOT work that way.

### 6c. window-geom's scope (deliberately narrower than first proposed)

Originally proposed: window-geom shows "a nav list of every open
window to pick from." Building it surfaced that NO existing file
exposes every open window -- only the currently ACTIVE one
(desktop_focused_window_id/_title, and a NEW additive line added today,
desktop_focused_window_project_id, in write_projection()). Building a
true multi-window picker would need a SECOND, larger change to
write_projection() (a full window-list export) that was never proposed
or approved. So: **window-geom currently shows ONLY the active
window's geometry, read-only. It is NOT a multi-window picker yet.**

It DOES have the dual-invocation discovery mechanism fully built and
tested:
  - `session/wg_target.txt` (a single line, a project_id) -- if
    present, window-geom shows/would-edit THAT specific project
    (the "opened from a chrome-bar button on that project" case --
    the button itself was never built, but the file-based handoff
    mechanism it would use is done and tested).
  - If absent, falls back to whichever window is currently active
    (the "opened from settings, generically" case).

Verified standalone (all three cases: no target + no active window;
target set to a real project; no target + active window simulated) --
see the design doc for exact commands. NOT yet live-verified inside a
real running session (only exercised by running the compiled managers
directly and inspecting the output files).

7. GL-MODE GAPS FOUND AND FIXED (DONE, one item still needs live re-test)
================================================================================

This section covers three related-but-separate bugs, all found because
the user asked "why does GL mode look different from ASCII" and then
"why no nav number" and I kept tracing one level deeper each time.
Full detail in 2fix.txt's dated entries -- this is the condensed
version.

### 7a. GL mode never re-parsed embedded markup (label showed raw tag text)

ASCII mode re-parses embedded `<text>`/`<button>` tags in a project's
`session/wraith_body.txt` (that's how buttons embedded in body text
work at all -- confirmed via `append_project_probe_body()`'s "pass
through verbatim if the line starts with '<'" convention, then
re-parsed by wraith_parser_alpha.c). GL mode's equivalent
(`project_probe_body_lines()` inside `write_semantic_projection_files()`)
just copied the WHOLE raw line into one OBJECT's label= field, with
zero tag-parsing. Confirmed via the actual GL receipt
(current_frame.receipt.pdl) that `chtmgl-video-isolate`'s own
Play/Pause buttons ALREADY had this exact bug -- pre-existing, not
something introduced by settings.

Fix: new `extract_attr()` (bounded memmem-based attribute scanner) and
`emit_embedded_line_objects()` (walks a line tag-by-tag, emits one real
OBJECT per chunk with its own x/y/w/label/action). Wired into the
body-line loop: lines starting with '<' get parsed properly now; all
other lines (the vast majority) are completely untouched.

### 7b. Embedded objects had no nav number (nav=0 always)

`g_max_index`/`launcher_start` (the formulas controlling how many
keyboard-Tab slots exist and where subsequent ranges like the taskbar
begin) had NO concept of embedded body-tag objects -- only
scene.objects.pdl's author-declared nav controls were counted
(`count_project_nav_controls()`, confirmed against piececraft-wraith's
REAL file: nav=5..22, contiguous, author-chosen).

Fix: split `count_project_nav_controls()` into `count_scene_nav_controls()`
(unchanged original logic) + new `count_embedded_body_nav_slots()`
(counts labeled chunks in wraith_body.txt), summed. In
write_semantic_projection_files(), `next_body_nav = 5 + count_scene_nav_controls(...)`
is computed before the body-line loop and threaded through
emit_embedded_line_objects() as an in-out counter -- only chunks with a
real action (actual buttons, not decorative <text> border pieces)
consume a slot.

Verified against REAL project files, not just logic: a standalone test
(nav_count_test.c, see 2fix.txt) run against piececraft-wraith's actual
scene.objects.pdl (18 controls, nav=5..22) combined with settings' real
body -- confirmed the new range starts at 23, no collision with
launcher_start=25. Also confirmed settings alone (no scene file) starts
correctly at nav=5 -- which happens to match what ASCII mode
independently shows too (a nice consistency bonus, not a requirement).

### 7c. href actions were silently inert in GL mode (found during
    end-of-session code review, NOT reported live by the user)

The deepest one. Even with (a) and (b) fixed, actually CLICKING/
activating the button in GL mode would have done NOTHING, because:
- ASCII mode's href navigation is handled entirely in-process by
  wraith_parser_alpha.c's own element tree (it owns the click, never
  calls into wraith-alpha_manager.c at all for this).
- GL mode's click/Enter path is completely different
  (wraith_gl.c's hit_test_semantic_action() -> route_command() in
  wraith-alpha_manager.c), and route_command() had literally no
  recognized prefix for a raw layout path -- it would silently drop it.

Fix: found `request_layout_change()` ALREADY EXISTED in
wraith-alpha_manager.c, fully correct, and completely unused (the
compiler had been flagging it as dead code all session -- I saw this
warning multiple times before realizing what it was). It already writes
to `pieces/display/layout_changed.txt`, which wraith_parser_alpha.c
ALREADY polls and applies (confirmed by reading its poll loop directly:
reads the last non-empty line, sets current_layout, re-parses). Added
one fallback branch at the end of route_command(): any command
containing ".chtpm" that matched nothing else now calls
`request_layout_change(cmd)`. This is wiring up dead, correct,
pre-existing code -- not new infrastructure.

**THIS IS THE ONE ITEM IN THIS WHOLE SESSION THAT HAS NOT BEEN TESTED
AT ALL BEYOND A CLEAN COMPILE.** It was found and fixed in the final
minutes of the session during a deliberate "look for bugs" pass, after
the user's last live check. If you do ONE live test before anything
else tomorrow, make it this one: switch to GL mode, click "Window
Geometry" in the settings menu, confirm it actually navigates to the
window-geom screen (not just that it LOOKS clickable).

### 7d. Two more bugs found in the same final review pass (also untested live)

- `extract_attr()`'s attribute search wasn't anchored to a word
  boundary -- fixed by prefixing the search pattern with a space
  (every real attribute in this codebase's generated tags is
  space-preceded; confirmed, not assumed). Not a live bug against
  current markup, but was a latent one.
- `project_probe_body_lines()`'s storage buffer (`char[16][160]`) was
  smaller than the 256-byte read buffer it copies from, adding an
  unnecessary second truncation ceiling. Confirmed LIVE against the
  real settings body line (231 chars) -- it got cut at 159, mid-attribute
  on the trailing decorative border tag. Landed harmlessly this specific
  time (the actual button was earlier in the line, unaffected; the
  malformed-tag guard in emit_embedded_line_objects() safely dropped the
  cut-off trailing tag rather than misrendering) -- but a longer href
  path or project name would have cut into the button itself. Fixed by
  widening to `char[16][256]` to match.

Both fixed, both compiled clean (diffed warning-for-warning against the
prior build, zero new warnings), real binary rebuilt. Neither
independently live-tested (bug 2's fix is implicitly covered by
whatever live test you do on the settings menu generally, since it's
the same body line).

11. KEY THINGS A FUTURE AGENT MUST KNOW BEFORE TOUCHING THIS CODE AGAIN
================================================================================

1. **ASCII mode and GL mode are two almost-entirely-separate rendering
   pipelines** reading from two different files
   (current_frame.txt vs current_frame.objects.pdl), built by two
   different pieces of code (wraith_parser_alpha.c's render_element()
   vs wraith-alpha_manager.c's write_semantic_projection_files()).
   ANY change to how something renders or gets clicked needs to be
   checked against BOTH, independently. This bit us three separate
   times today (labels, nav numbers, href activation).

2. **href navigation lives entirely inside wraith_parser_alpha.c's own
   process memory** (the `current_layout` global). The ONLY way another
   process (wraith-alpha_manager.c) can trigger a layout switch is via
   the file-based `request_layout_change()` -> `layout_changed.txt` ->
   wraith_parser_alpha.c's poll loop mechanism. This ALREADY EXISTED
   and was unused all session until the very end -- don't reinvent it.

3. **`project_dir_for_window()` rejects any project_id containing a
   `/`.** This only matters for projects that need to be a real `Window`
   in the g_windows[]/taskbar system. Projects reached purely via href
   (like window-geom) never hit this function at all -- disk nesting is
   fine for them.

4. **Two independent nav-index systems exist and are NOT the same
   thing:** wraith_parser_alpha.c's own auto-incrementing interactive-
   element counter (drives the visual "[ ] N." prefix in ASCII mode,
   and which item gets focused as you press arrow keys) vs.
   wraith-alpha_manager.c's own self-contained g_max_index/
   launcher_start arithmetic (drives GL mode's nav numbers and which
   index means what for dispatch_menu_index()). They happen to often
   agree by coincidence of careful ordering, but nothing enforces it.
   Extending ONE does not automatically extend the other.

5. **`manager/state.txt` and `session/state.txt` are DIFFERENT
   conventions for DIFFERENT purposes**, easy to confuse:
   - `session/wraith_body.txt`, `session/state.txt` etc. = the
     desktop-EMBEDDED (Window/g_windows[]) convention, read by
     wraith-alpha_manager.c's append_project_probe_body() /
     write_semantic_projection_files().
   - `manager/state.txt` = the STANDALONE/href-reached convention, read
     generically by wraith_parser_alpha.c's load_vars()/load_state_file()
     via a project_id derived from the current_layout path
     (set_project_id_from_layout()), completely independent of the
     Window system. `settings` and `window-geom` both use ONLY this
     second convention (plus, as of the wraith_body.txt fix, settings
     ALSO writes the first one, so it works via either entry path).

6. **This codebase's own `snprintf`-truncation compiler warnings
   (dozens of them, pre-existing, present in every build all session)
   are NOT bugs** -- they're GCC being cautious about generously-sized
   MAX_PATH buffers. The discipline used all session: after any change,
   diff the FULL warning list against the previous build; only NEW
   warnings (or a changed warning COUNT beyond an expected +/-1 for
   known reasons like a newly-used/unused function) are worth
   investigating. Don't chase the pre-existing ones.

7. **Verify standalone before integrating, every time.** Nearly every
   fix in this session was proven correct in an isolated test file
   (extracted copies of the real function, run against real project
   data) BEFORE being wired into the live wraith-alpha_manager.c and
   compiled. This caught real bugs before they shipped (e.g. the nav
   counting arithmetic was verified against piececraft-wraith's actual
   18-control scene file before trusting it). Keep doing this.
