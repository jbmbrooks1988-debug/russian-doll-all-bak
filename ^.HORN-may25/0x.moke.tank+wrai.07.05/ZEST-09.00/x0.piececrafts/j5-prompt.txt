1. PROBLEM 1 — REAL ROOT CAUSE FOUND. THE PROMPT'S THEORY IS *REJECTED*.
--------------------------------------------------------------------------------
The original prompt's central theory ("the single mega-variable
`window_geom_display` is a novel/untested pattern; the fix is to switch
to multiple small variables like user_profile.chtpm") is WRONG, and doing
that refactor would NOT fix the blank. Evidence:

  a. The value IS correctly on disk:
     manager/state.txt contains a full, correct, ~230-char
     `window_geom_display=Source: active window...\n...` line.
  b. substitute_vars() (l.443-469) DOES correctly expand `${var}` and DOES
     convert literal `\n` -> real newline. The mega-variable substitution
     path works fine. Tested by reading the function, not assumed.
  c. The length-limit theory is DEAD: MAX_LABEL_LEN and MAX_VAR_VALUE are
     both 65536 (l.54, l.62). A ~230-char value is nowhere near any cap.
  d. The nested-project_id theory is ALSO essentially dead for the *initial*
     derivation: set_project_id_from_layout() (l.924) parses
     `.../settings/window-geom/layouts/...` correctly to
     `wraith-alpha/wraith-projects/settings/window-geom`. The deep nesting
     does NOT break it.

THE ACTUAL BUG (confirmed, in load_vars(), wraith_parser_alpha.c):
  1. l.993  set_project_id_from_layout() sets project_id CORRECTLY to
            "wraith-alpha/wraith-projects/settings/window-geom".
  2. l.1008 `const char* proj_id = get_var("project_id");`
            -- captures a POINTER into the vars[] slot's value buffer.
  3. l.1011 load_state_file("projects/wraith-alpha/session/alpha_state.txt")
            reads that file's LINE 1, which is literally `project_id=wraith-alpha`,
            and calls set_var("project_id","wraith-alpha") -> l.375 overwrites
            the slot IN PLACE. `proj_id` now silently reads "wraith-alpha".
  4. l.1074-1077 builds project_state_path from the (now-clobbered) proj_id:
            "projects/wraith-alpha/manager/state.txt"
            -- THE WRONG FILE. window-geom's own manager/state.txt is never
            loaded, so `window_geom_display` is never set -> renders blank.

  Independent corroboration: pieces/display/current_frame.audit.txt shows
  `project_id=wraith-alpha` even while current_layout.txt points at
  window-geom.chtpm. That mismatch is the clobber, visible in the artifacts.

  This is a GENERIC bug: ANY href-reached project whose own manager/state.txt
  vars it depends on will render blank, because alpha_state.txt's
  `project_id=wraith-alpha` always wins the clobber. window-geom is just the
  first project to actually depend on it. (The already-working href examples
  -- terminal.chtpm, fs.chtpm "Back to Desktop" -- don't hit this because
  they have no dynamic ${var} of their own to lose.)

  CORROBORATION (added after the first review, per user's push to actually
  check): this is a textbook instance of the project's OWN documented
  Golden Pitfall #31 in !.TPMOS_ONBORD_BIBLE_10.md:
    "#31 App Layout project_id Drift: When loading an APP layout via href,
     explicitly set project_id to match the app, otherwise PDL lookups fail."
  set_project_id_from_layout() at l.993 IS the #31 mitigation. The bug is
  that a LATER state-file load (alpha_state.txt at l.1011) silently re-drifts
  project_id back to "wraith-alpha" after the mitigation already ran. So the
  fix (re-assert project_id after the last state load) is not a novel idea --
  it's re-applying the documented #31 remedy at the point it currently gets
  undone.

  EMPIRICAL CONFIRMATION (2026-07-05, after a real `button.sh r` session):
  the user drove the live path Loader -> wraith-alpha -> Terminal -> settings

    window_geom_display loaded: 0 times  -> frame renders blank.
  Meanwhile window-geom's OWN manager/state.txt DOES contain the correct
  window_geom_display value -- proving the manager side is fine and the fault
