==================================================
BUG
==================================================

Symptom:
- some Wraith projects appear to open in the GL/Wraith desktop window
- but the ASCII "mother terminal" / desktop shell does not show the expected project body
- instead it can remain on launcher-like content or show a fallback/missing-body state

Important clarification from user:
- the project launch itself is happening
- the problem is specifically the ASCII terminal-equivalent / frame-debug path
- additional clarification:
  - the mother terminal should always remain an ASCII surface
  - the GL presenter may be in `GL` mode at the same time
  - the shell/debug row in the mother terminal should not mirror the GL presenter selection state

==================================================
ROOT CAUSE FOUND IN CURRENT EPOCH
==================================================

The Wraith ASCII shell reads project-owned session files for non-terminal project windows:

- `session/wraith_body.txt`
- `session/state.txt`
- `session/scene.objects.pdl`

The manager path is in:
- `projects/wraith-alpha/manager/wraith-alpha_manager.c`

Relevant behavior:
- `project_probe_body_lines(...)` reads `session/wraith_body.txt`
- `append_project_scene_objects(...)` reads `session/state.txt` and `session/scene.objects.pdl`

If these files are missing, the project may still launch as an active Wraith window, but the ASCII shell degrades to fallback text such as:
- `Missing project body file: session/wraith_body.txt`

So this is not primarily a launcher-dispatch bug.
It is a project-ownership / session-file completeness bug for ASCII frame-debug rendering.

FIX RULE GOING FORWARD
==================================================

This should be treated as part of the reusable Wraith project contract, not as optional polish.

==================================================
INVESTIGATION
==================================================

### A. Why ASCII and GL disagree on row `1`

Current understanding:
- GL selector state comes from `current_frame.objects.pdl` written directly by `wraith-alpha_manager.c`
- ASCII shell rendering depends on parser-composed `current_frame.txt` from `desktop_shell_markup`

Likely issue:
- the manager-owned semantic object path marks row `1` selected correctly
- but the shell-markup path is not faithfully reflecting that same nav-selected state for the title button in the mother terminal

This means the two surfaces are not deriving the selector glyph from the same final truth.

### B. Why row `1` disappears after clicking `ASCII`

This one is not random.

The screenshot shows:
- `Idx:8`

So after the user clicks or navigates to `ASCII`, focus genuinely moves to the debug selector control.

That explains why row `1` is no longer the active selector in either surface afterward.

Question is not "why did it vanish?" but:
- should toggling view mode steal nav focus?

Current recommendation:
- no, presenter/view toggle should change mode without permanently stealing primary window-nav focus
- after mode switch, focus should likely return to the previously active shell/window control, usually row `1`

### D. Why `FS_SCROLL_DOWN` showed as unhandled

Root cause:
- earlier runs were carrying stale generated project/session output from before command trimming and scroll handling were aligned
- the source path now handles `FS_SCROLL_DOWN`, but old `wraith_body.txt` / desktop state could still show:
  - `Last: Unhandled command FS_SCROLL_DOWN`

Rule going forward:
- treat generated session files as cache-like runtime outputs
- when validating a scene/action fix, confirm the underlying source and then regenerate the project/session output before trusting stale body text

### E. Utility strip layout rule

For filesystem-style browser projects in Wraith:
- utility controls may share the same scene `y`
- ASCII shell should mirror same-`y` scene objects onto one rendered line
- this keeps GL and frame-debug ASCII close enough to compare without screenshots
- the standardized form is:
  - `^_UP`
  - `v_DOWN`
  - thumb/range indicator on the same row
  - then content rows below, one selectable item per row

FOURTH BUG IN SAME AREA
==================================================

Observed after `fs` became live:

- GL used `session/scene.objects.pdl` and showed the real file rows
- ASCII mother terminal only showed `session/wraith_body.txt`
- after partial fixes, ASCII then mirrored only part of the scene and initially lost file names after the first token

Root cause chain:

1. Wraith body text is plain summary/context, not the true project nav layer.
2. Real numbered nav rows belong in `scene.objects.pdl`.
3. ASCII shell originally ignored project scene rows.
4. After ASCII began reading project scene rows, label parsing still truncated at spaces.

Fix direction now in effect:

- `wraith_body.txt` carries compact summary lines only
- `scene.objects.pdl` carries the real file rows
- ASCII shell appends project scene controls into `desktop_shell_markup`
- `fs` scene labels were rewritten to single-token forms such as:
  - `DIR:pieces/`
  - `FIL:file-op-dox.txt(3KB)`

This preserves parser/nav agreement and keeps ASCII/GL closer to the same truth.

FIFTH BUG / FEATURE GAP
==================================================

Observed:

- GL had room to show more live rows than ASCII
- ASCII row budget was tighter because it spent lines on summary text
- directory changes still depended on explicit user action to rerender

Current implementation direction:

- compress ASCII summary lines
- add project-owned scroll controls:
  - `^_UP`
  - `v_DOWN`
  - thumb/range indicator
- remove visible refresh button
- add project-owned watcher op plus session marker file

This is both a bug fix and a reusable Wraith project pattern.

Root cause:
- it is coming from the scaffold `fs/session/scene.objects.pdl`
- I added a `panel` object there as part of the earlier minimal project-scene bridge

That panel is being rendered inside the already existing Wraith project window, so it looks like an accidental extra inner framed box.

This is a scaffold-content mistake, not a deep renderer bug.
