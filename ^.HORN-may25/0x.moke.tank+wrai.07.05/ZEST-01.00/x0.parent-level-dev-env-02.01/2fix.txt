## Active Fix 1: Window Chrome And Interact Startup State

Live screenshot:
- `Screenshot from 2026-06-27 22-27-33.png`

Observed:
- `wraith-3d-cube` is in interact mode.
- cube key controls work and update project state/body.
- GL shows the projected wireframe cube.
- `Control_Map` is now visible as a toolbar/headerbar-ish control.
- normal window chrome controls are not visually complete enough around the project-specific toolbar control.
- the project started in active `is_map_control=1`, so it showed `[^]` immediately instead of requiring click/Enter.
- this was caused by persisted project state, not by a fresh intentional default.

Expected:
- new windows should start in shell/window-nav mode unless the project explicitly declares a resume policy.
- `Control_Map` should show `[>]` when selected but inactive.
- pressing Enter or clicking the `Control_Map` affordance enters interact mode and changes it to `[^]`.
- entering `INTERACT` for a `${game_map}` payload should sandbox input like `fuzz-op` / `fuzz-op-gl`.
- selected map control should remain visibly active as `[^]`.
- the visible control may live in a project headerbar, toolbar, side menu, overlay, or footer as the project layout requires, but it must not replace or erase normal Wraith window focus/chrome controls.
- the `${game_map}` surface should stay payload-only for cube/map/model rendering.
- while `is_map_control=1`, keyboard control belongs to the project map surface.
- external Wraith nav should not move or show active focus changes from map-control keys.
- `ESC` is the escape hatch back to external Wraith nav.

Receipt finding:
- the manager/export side can already report the game map as `nav_selected=1` with `nav_selector_glyph=^`.
- therefore the remaining issue is UI modeling/render placement, not just missing manager state.

Fix direction:
- keep project scene records migrated away from `nav=<n> action=INTERACT` on `role=game_map` and into a project UI control:
  - `tag=control`
  - `role=window_toolbar_item`
  - `action=INTERACT`
  - `target_surface=game_map`
- keep the `${game_map}` surface as payload-only:
  - `role=game_map`
  - `nav=0`
  - `action=NONE`
- while `is_map_control=1`, pin/render the project-local interact control as `[^]`.
- on new project window launch, reset or initialize `is_map_control=0` without writing a fake user `ESC` event.
- keep key events appended to project `session/history.txt` and processed by project-owned `ops/+x/wraith_project_input.+x`.

## Active Fix 4: CHTMGL Fill Priority And Generic Window Move/Resize

Live screenshot:
- `Screenshot from 2026-06-27 23-45-34.png`

Observed:
- `chtmgl-wraith` now opens and shows representative controls/widgets.
- panel/window regions are not visually filled strongly enough, so body text and controls appear to bleed through or visually collide.
- some CHTMGL sub-panels look like outlines instead of real filled containers.
- Wraith subwindows are not yet draggable or resizable.

Expected:
- container objects such as project panels, widget panels, visual panels, and `${game_map}` surfaces should fill their background before text/controls are drawn above them.
- fill order should be auditable in receipts so an agent can tell whether overlap is source order, z-order, clipping, or missing fill.
- normal Wraith host window chrome stays separate from project-local CHTMGL controls.
- project-local controls may be headerbar, toolbar, side panel, footer, menu, or overlay controls if they declare `target_surface=game_map`.
- host windows should become movable by titlebar/drag-region and resizable by edge/corner handles.

Fix direction:
- first fix RGB fill priority for CHTMGL/project containers:
  - draw filled panel/surface backgrounds before control/text glyphs
  - preserve border visibility
  - preserve nav focus/highlight visibility above fills
  - receipt should report fill rect, border rect, z, parent/container, and clipping result
- then implement generic host window movement/resizing:
  - add file-owned window geometry in the Wraith session/window registry
  - export semantic host controls like `role=window_titlebar action=WINDOW_DRAG window_id=<id>`
  - export resize handles like `role=window_resize_handle action=WINDOW_RESIZE edge=se window_id=<id>`
  - GL input writes semantic drag/resize events, not direct geometry mutation
  - manager consumes events, clamps geometry, writes registry, and exports next frame
  - receipts include old rect, raw/mapped mouse, hit action, delta, clamp reason, and final rect

Do not:
- hardcode CHTMGL, Piececraft, cube, or Emoji window behavior into `wraith-alpha_manager.c`.
- let project-specific ops own host drag/resize.
- fix overlap by hiding text without receipt evidence.

Applied partial fix:
- `wraith-alpha_manager.c` now exports `project_body_text` at `z=14` instead of `z=22`, so project scene panels/surfaces can cover audit body text in GL.
- `chtmgl-wraith` static scene records were raised to panel `z=24`, controls `z=30+`, and preview `z=34`.
- this should reduce CHTMGL panel bleed, but receipts/screenshots still need live verification.
