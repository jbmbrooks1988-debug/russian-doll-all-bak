# WRAI Pro Fix J25

Purpose:
- Capture the blank-project failure mode and the final fix path in one place.
- Keep this separate from the architecture and task docs.

Status:
- The launcher rows and taskbar rows are now manager-projected from runtime state instead of fixed slot math.
- The remaining risk is not a second parser or GL corruption. The live parser/button numbering contract still does not match the manager's dispatch assumptions.
- The manager now computes launcher range and taskbar range from the current launcher PDL and visible window registry.
- `Enter` now dispatches through the same dynamic menu model that renders the shell.
- The parser must expand raw fragment variables before tokenization, otherwise the shell markup is treated like plain text and the UI breaks.
- Even if the active window is missing, the desktop shell should render the minimal taskbar-only bootstrap view from the reference frames, not a fake desktop chrome.
- The persistent taskbar `Terminal` launcher is a bootstrap control, not a live window entry. That distinction is still not fully preserved in the runtime index model.

Observed behavior:
- `terminal` still behaves as the control case.
- `blank-proj` is visible and focusable in the Wraith launcher body.
- Pressing `blank-proj` in the window body still does not open the blank project window.
- The parser labels the live window body rows as `1. [terminal]` and `2. [blank-proj]`, but the manager still interprets low indices like `2` and `3` as chrome actions instead of launcher selections.
- The persistent taskbar `Terminal` launcher and the live `Terminal #N` windows both appear in the bar, but they are not yet modeled as separate classes cleanly enough for dispatch.
- Repeated terminal launching should work forever, with each new terminal getting the next virtual process/window number and leaving earlier terminals in the taskbar.

Root cause:
- Wraith Alpha already has a real launcher manifest at `projects/wraith-alpha/wraith-projects/launcher/piece.pdl`.
- That file defines the launcher methods in order:
  - `terminal` -> `DESKTOP_ACTION:launch_terminal`
  - `blank-proj` -> `DESKTOP_ACTION:launch_blank_project`
- The launcher body is now rendered from that manifest, and the manager uses the same manifest count when computing focus ranges.
- The old bug was not just a zero-based/one-based mismatch. It was a static shell contract that assumed launcher rows and taskbar rows would never change size.
- The parser still exports the focused GUI index to `pieces/display/active_gui_index.txt`, but the manager now maps that selection against a runtime-built menu model before dispatch.
- The current bug is more specific: after raw fragment expansion, the parser's visible numbering for shell controls does not line up with the manager's hardcoded semantic buckets for chrome, launcher body, and taskbar.
- The most concrete cause in the latest broken build is that the active window chrome was rendered as literal text, not as real parser buttons.
- That means the parser only exposed these live controls:
  - launcher body rows
  - taskbar rows
- In that broken state, the parser's first real interactive row was `terminal`, second was `blank-proj`, third was the persistent taskbar `Terminal`, and fourth was the first live taskbar window.
- The manager, however, still dispatched as if the shell had four chrome controls first:
  - `1` title/focus
  - `2` open/fullscreen stub
  - `3` minimize
  - `4` close
- So the parser and manager were both internally consistent, but they were consistent with two different control maps.
- The shell also has two different terminal concepts:
  - the persistent bootstrap launcher `Terminal`
  - live terminal windows such as `Terminal #6`, `Terminal #7`, `Terminal #8`
  Those need separate dispatch semantics and separate numbering treatment.

Code evidence:
- `projects/wraith-alpha/manager/wraith-alpha_manager.c` now builds `desktop_shell_markup` from the live launcher PDL and the live window registry.
- `route_command()` still routes `DESKTOP_ACTION:launch_terminal` and `DESKTOP_ACTION:launch_blank_project` through the shared launch helper/table.
- `route_input()` now resolves `Enter` through a dynamic menu dispatcher instead of hardcoding `5/6/7+`.
- `blank-proj` was not failing because the project scaffold was fake. It was failing because the shell contract was static.
- The latest runtime frames show `Manager Index: 2` while the visible focus is on `blank-proj`. That proves the manager is still receiving a low body-local index and not a chrome-aware shell index.
- The latest runtime frames also show `Manager Index: 3` on the persistent taskbar `Terminal`, after which the active window gets minimized/closed instead of launching a new terminal. That proves the manager is still conflating taskbar launcher focus with chrome control indices.
- The direct reason those indices were low is now known: the parser never had interactive chrome rows in that build, because the title bar was plain text.

Cause/effect proof from runtime:
- The latest failing runs showed that the shell could render `blank-proj`, but the focus path and the launch path disagreed on row identity.
- The old `5/6/7+` logic was the cause of the mismatch.
- Once the dynamic dispatcher is active, `Enter` should land on the same row the parser exported.
- In the latest frames:
  - bootstrap view shows `[TASKBAR] [1. Terminal]`
  - opening terminal creates `Terminal #2`
  - body view shows `1. terminal` and `2. blank-proj`
  - taskbar shows `3. Terminal` and `4. Terminal #2`
  - selecting `2` does not launch blank-project in the expected window-flow
  - selecting taskbar `3. Terminal` minimizes/closes instead of launching a new terminal
  That means the parser is numbering only real buttons, while the manager is dispatching as though chrome buttons `1-4` already exist.

Current working model:
- `blank-project` is a real Wraith context.
- It lives under `projects/wraith/wraith-projects/blank-project/`.
- It should open inside the same Wraith desktop session.
- It should use the same standard window chrome and taskbar behavior as the other Wraith windows.
- It should open only when its launcher row is explicitly selected by the user.
- The desktop shell is not supposed to hardcode row numbers. It should derive them from the launcher PDL plus the live window registry.
- `terminal` is also a real Wraith context under `projects/wraith/wraith-projects/terminal/`, and every terminal launch path should resolve there, including the default taskbar/bootstrap terminal.
- Infinite terminal opening is valid behavior. Every activation of the persistent taskbar `Terminal` launcher should create another terminal window with the next VPID/window number and keep older live terminal windows in the taskbar.

Most direct fix:
- Restore the top window chrome as real parser buttons instead of literal text.
- Make the parser expose the standard active-window control order again:
  - `1` title/focus
  - `2` open/fullscreen stub
  - `3` minimize
  - `4` close
  - `5..` launcher body rows
  - trailing taskbar rows
- Keep the launcher rows as real `<button>` controls in `alpha-shell.chtpm`.
- Reuse the existing launcher PDL as the source of truth for method order and command strings.
- Keep terminal and blank-project on the same project-launch helper/table so the code path stays reusable.
- On Enter, first sync `g_active_gui_index` from `pieces/display/active_gui_index.txt`, then route the selection through a dynamic dispatcher that knows the launcher count and the current visible window count.
- Only launcher rows should resolve through the launcher PDL; taskbar rows should map to the current visible window registry instead of a fixed offset.
- Preserve launcher-range indices in the manager so rows like `blank-proj` are not collapsed back to the window chrome.
- Keep the manager thin and do not invent a second parser path.
- Split shell controls into three explicit runtime groups:
  - window chrome controls
  - active-window launcher body controls
  - taskbar controls, where slot 1 is always the persistent `Terminal` launcher and later slots are live windows
- Make the parser/manager handoff carry shell-global control identity, not body-local display numbering.

What this fixes:
- The parser and manager return to one shared index contract.
- `blank-proj` becomes a real launch action instead of a dead label.
- The code path stays reusable because the render and dispatch sides both read the same launcher PDL.
- The terminal control case remains intact.
- Later save/load can reuse the same session registry without inventing a new launch model.
- The manager and parser now agree on the live selection before Enter is handled, and the shell no longer assumes fixed launcher/taskbar indices.
- Raw fragment expansion prevents the manager-generated shell from being printed literally.
- The desktop shell keeps its visual shape while still using runtime data for launcher/taskbar rows.
- The bootstrap view stays faithful to the earlier good-looking frames while the launch path remains dynamic.
- Infinite terminal creation remains supported instead of being capped or collapsed into one reusable terminal slot.

False assumptions to remove:
- `wraith_body_content` is not the truth source for launcher dispatch.
- A visible launcher row is not enough unless Enter resolves to a real command.
- `href` should not replace launcher command dispatch.
- `blank-proj` should not spawn a second GL session or escape the Wraith desktop.
- The parser's visible focus is not enough unless the manager ingests the exported active GUI index.
- The launcher range is not the same as the window-chrome range.
- The launcher manifest should not be treated as static just because the current project only has two entries.
- The taskbar range should not be hardcoded to a trailing block of 20 rows.

Implementation contract:
1. Keep the launcher UI real in `alpha-shell.chtpm`.
2. Resolve launcher selection from `wraith-alpha/wraith-projects/launcher/piece.pdl`.
3. Dispatch `blank-proj` through `DESKTOP_ACTION:launch_blank_project`.
4. Keep the manager responsible for registry, focus, launch, and restore state.
5. Keep the nested project ID `wraith/wraith-projects/blank-project` intact.
6. Keep the persistent taskbar `Terminal` launcher separate from the live window registry.
7. Allow repeated terminal launches forever, with monotonically increasing VPID/window numbering.

Expected result:
- `terminal` remains the control case.
- `blank-proj` launches a `Blank Project` window inside the current Wraith session.
- No new parser architecture is required for this slice.
- Selecting the persistent taskbar `Terminal` launcher always opens another terminal window.
- Older terminal windows remain available in the taskbar as separate live windows.
