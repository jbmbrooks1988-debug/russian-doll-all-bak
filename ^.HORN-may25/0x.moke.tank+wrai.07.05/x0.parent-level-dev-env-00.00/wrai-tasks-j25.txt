# WRAI Tasks J25 Report

Scope:
- Reviewed the active `1.TPMOS_c_+rmmp.0102.0026` tree.
- Ignored `x0.moke-` as requested.
- Focused on the Wraith Alpha desktop/session path and the GL presenter/renderer path because the prompt mixes both behaviors.

## Findings

### 1. The visible debug output is baked into the UI, not just console noise.
- `projects/wraith-alpha/layouts/alpha-shell.chtpm` renders a dedicated debug block on screen:
  - `Open Windows: ${desktop_window_count}`
  - `[ DESKTOP DEBUG ]`
  - `[ PARSER BYPASS DEBUG ]`
- `pieces/apps/gl_os/layouts/desktop.chtpm` does the same with visible `BG`, `Windows`, `Manager Index`, `Manager Mouse`, and parser debug text.
- In `pieces/apps/gl_os/plugins/gl_desktop.c`, the frame builder also emits frame/history/debug output and writes it into `current_frame.txt`, `frame_history.txt`, and `audit_frame.txt`.

Interpretation:
- The debug clutter is not accidental logging alone. It is part of the current render contract, so trimming it requires changing the layouts and the frame composition path, not just silencing `printf`.

### 2. `blank-proj` is the launcher alias, and `blank-project` is the real Wraith test project target.
- `projects/wraith-alpha/wraith-projects/launcher/piece.pdl` maps:
  - `terminal -> DESKTOP_ACTION:launch_terminal`
- `blank-proj -> DESKTOP_ACTION:launch_blank_project`
- `blank-proj` should resolve to a real project directory, like a template-style project, rather than a placeholder window.
- The intended first test project is `blank-project`, and it should open inside the existing Wraith desktop session as a window titled `Blank Project`.
- The `wraith/wraith-projects/blank-project` tree is the right place for that project scaffold.
- The GL presenter should remain a single IO mirror for the whole Wraith session, not one instance per launcher action.
- Nested project IDs must survive layout parsing so `wraith/wraith-projects/blank-project` does not collapse to `wraith`.
- All Wraith-opened projects should use the same desktop window chrome and controls as terminal windows.

Interpretation:
- The wrong behavior came from treating `blank-proj` as a synthetic window only. It needs a real project directory backing it.
- The bottom toolbar must list every non-closed window in the current session, not just minimized ones.

### 3. The GL presenter is display-only, so it does not round-trip input back into history.
- `projects/wraith-alpha/ops/wraith_gl.c` only registers:
  - `glutDisplayFunc(display)`
  - `glutTimerFunc(...)`
- It has no keyboard callback and no mouse callback.
- `projects/wraith-alpha/plugins/wraith_rgb_daemon.c` only watches frame markers and rasterizes `pieces/display/current_frame.txt` into `projects/wraith-alpha/session/rgb/current_frame.rgba32`.
- For GL-OS, `pieces/apps/gl_os/plugins/gl_os_renderer.c` does log mouse clicks and mouse motion to `pieces/apps/gl_os/session/history.txt`, but it also has no keyboard callback.

Interpretation:
- If the expectation is that the GL window should preserve mouse and keyboard provenance in history, that behavior is not implemented in the presenter path. Input capture is split across other processes, and keyboard provenance is not mirrored by the GL window itself.

### 4. The “8 terminal sessions open” state comes from persisted registry files, not from a missing save/load feature.
- `projects/wraith-alpha/manager/wraith-alpha_manager.c` writes the active registry into:
  - `projects/wraith-alpha/session/alpha_state.txt`
  - `projects/wraith-alpha/session/desktop_ui_state.txt`
- That state includes:
  - `desktop_window_count`
  - `desktop_open_window_count`
  - `desktop_next_instance_no`
  - per-slot `desktop_registry_*` entries with open/minimized/visible flags
- On startup, `sync_registry_from_disk()` reads `desktop_ui_state.txt` back into the registry and restores `g_window_count`, `g_next_instance_no`, and the per-slot window states.
- `launch_terminal_instance()` increments `g_next_instance_no` and appends new terminal instances into the registry rather than creating ephemeral windows.

Interpretation:
- The system already persists terminal/session state. The count is not a placeholder; it is reconstructed from disk. That is why the UI can show 8, 12, or more terminals even before a new save/load feature exists.

### 5. Wraith Alpha already archives keyboard input and project commands separately.
- `projects/wraith-alpha/manager/wraith-alpha_manager.c` appends raw keys to `projects/wraith-alpha/session/history_archive.txt`.
- It also reads both:
  - `pieces/keyboard/history.txt`
  - `projects/wraith-alpha/session/history.txt`
- `route_command()` understands desktop actions like `DESKTOP_ACTION:launch_terminal`, `minimize_terminal`, `close_terminal`, and `restore_terminal`.

Interpretation:
- Wraith Alpha has a split input model already. The missing piece is not generic persistence; it is a clearer ownership boundary for where mouse/key provenance should be logged and which session files should be the source of truth.

## Wraith Session Model

This is the part that matters most for the next stage:

- Save/load is for the entire Wraith session environment, not just a terminal buffer.
- That means the session scope includes the desktop shell, terminal instances, focused project, layout selection, registry state, history, and whatever other session-owned files Wraith needs to restore the same theater.
- `blank-project`, `terminal`, and the Wraith desktop shell all need to be real project-backed contexts, not fake placeholders or separate OS instances.
- Later, the same save/load boundary can become login/auth if we wrap the restore operation in a password gate.

`op-ed` is the precedent here:
- It saves and loads whole game folders, not isolated widget state.
- That is the right model for a virtual OS too, because the OS session is a sovereign folder-context, not a single file.

## Reusable Ops

The bible says this explicitly, and the codebase supports it:

- Prefer reusable Ops whenever possible.
- Managers should orchestrate, not reimplement every mutation inline.
- If a save/load or restore action already exists as a project-level Op, reuse it instead of adding one-off logic in the manager.
- The longer-term Wraith shape should be "OS shell uses reusable ops for session/project lifecycle", not "manager grows custom glue for every new feature".

## Working Assumptions

- The `blank-project` action should become a real project/session context under the Wraith model, not just a dead-end placeholder.
- The current “open windows” count in Wraith Alpha is intended to reflect persisted registry state.
- The GL presenter should write provenance events somewhere durable if the history is meant to reflect actual mouse/keyboard interaction from that process.
- The future `session-manager` can be a real Wraith project, but the save/load boundary should stay entire-session-wide.
- `blank-proj` should resolve to the blank-project directory, not a synthetic placeholder window.
- The bottom toolbar should behave like a live session window list, so open windows are visible there immediately.
- The manager may request a same-session layout switch when opening `blank-project`; that is still one Wraith desktop environment, not a second OS.

## Questions To Resolve Before Implementing Anything

1. Should `blank-project` stay as a regular project-backed Wraith window like `terminal`, or should it get dedicated window chrome or state rules later?
2. For the session save/load path, do you want the restore operation to be its own reusable Op from day one?
3. For history capture, should the manager own all input logging, or do we want the GL presenter to append session events too?
