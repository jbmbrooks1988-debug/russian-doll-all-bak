## Active Fix 5: Webcam Shared-KVP Regression

Observed:
- `web-cam` shows the first webcam frame, then stops appearing live.
- ASCII preview can show stale `missingno.png` content instead of current webcam data.
- this started after moving webcam status / marker / frame transport toward shared KVP memory.

What went wrong:

1. Wake-up seam mismatch:
- `wraith-alpha_manager.c` still wakes active project input from a real file append on `session/fs_watch.marker`.
- current manager logic:
  - `stat("%s/session/fs_watch.marker")`
  - compare `st_size`
  - call `run_active_project_input_op_mode("marker_tick")`
- after the KVP change, webcam `pulse_marker()` writes `session/fs_watch.marker` into shared memory by default, not to the file manager watches.
- result:
  - the project gets its initial render/update path
  - later webcam frames do not keep waking project input
  - live streaming appears frozen even though capture may still be running

2. Blob priority is too aggressive:
- `wraith_project_input.c` currently prefers `wkdb_read_blob_direct("session/current_frame.png", ...)` before any file fallback.
- there is no freshness comparison between:
  - shared-memory blob generation
  - shared-memory `frame_epoch`
  - on-disk `session/current_frame.png`
- if a stale blob already exists in shared memory, it wins every time.
- that explains why `missingno.png` can persist in the ASCII preview after the manual blob test.

3. Shared memory name was global:
- earlier DB proof used a Wraith-local singleton name
- current TPMOS-shared seam now uses TPMOS naming and shared ownership instead

Expected:
- webcam marker updates must remain visible to the existing Wraith manager wake-up path until the manager itself gains a memory-backed watcher seam.
- ASCII preview should prefer the newest available frame, not blindly prefer any blob.
- manual blob tests such as `missingno.png` must not poison future webcam sessions.

Fix direction:

Phase 1:
- keep the immediate webcam regression investigation grounded in standard ownership, not just local patching.
- do not grow implementation-heavy header ownership further

## Active Fix 6: Browser GL Scene/Receipt Format Drift

Observed:
- `wraith-browser` ASCII looks correct in the mother terminal.
- `wraith-browser` GL does not match the ASCII body.
- live GL shows:
  - labels truncated at spaces
  - button labels split into fragments
  - document text columns colliding or compressing
  - receipt-derived scene truth looking more coherent than the final GL result

Live evidence:
- user screenshot: `Screenshot from 2026-07-02 01-17-38.png`
- browser ASCII body at the same time is structurally correct
- browser generated scene now contains explicit GL objects such as:
  - `browser_addr`
  - `browser_page`
  - `browser_js`
  - `browser_counter`
  - `browser_doc_panel`
  - `browser_doc_01..07`

What went wrong:

1. Scene object format is not quote-safe
- `wraith-browser/session/scene.objects.pdl` currently emits lines like:
  - `label=JS:on|Last:JS counter_inc`
  - `label=[H1] Controlled JS Lab`
  - `label=This page is the first compatibility seam. Scripts are executed by a dedicated TPMOS op, not by hidden window logic.`
- those are human-readable, but the current Wraith scene/receipt chain was never standardized for arbitrary free-text labels in object records.

2. Receipt exporter and GL parser do not share a strict reversible scene grammar
- `wraith_rgb_daemon.c` receipt parse path uses:
  - `label_start = strstr(line, "label=");`
  - `action_start = strstr(label_start, " action=");`
- this means the daemon depends on field order and unescaped sentinel tokens.
- once labels contain rich text, punctuation, spaces, or any future ` action=`-like substring, the format becomes brittle.

3. The GL object model is better suited to short chrome labels than paragraph text
- current working projects mostly emit short labels like:
  - `PROJ:blank-project/`
  - `Thumb:[#-------]1-6/10`
  - `Video_Poster`
  - single-cell image preview labels
- browser attempted to push paragraph-scale page text directly into `label=` fields on `tag=text` scene objects.
- that is outside the stable proven envelope of the current scene-object grammar.

4. The old browser nested-panel bug was real, but this is a second bug
- first bug:
  - browser panel used `source=session:wraith_body`
  - GL rendered a nested framed block
- second bug after replacing that:
  - explicit browser scene objects are now generated
  - but their label payloads exceed what the current scene/receipt/GL contract safely supports

Code evidence:
- generated browser scene:
  - `projects/wraith-alpha/wraith-projects/wraith-browser/session/scene.objects.pdl`
- GL parse path:
  - `projects/wraith-alpha/plugins/wraith_rgb_daemon.c`
  - `parse_frame_objects()`
  - `label_start = strstr(line, "label=");`
  - `action_start = strstr(label_start, " action=");`
- receipt writing path also serializes `label=` as plain inline text

Expected:
- a browser scene must render the same logical text structure in ASCII and GL.
- scene object records must support rich text payloads in a standardized reversible way.
- receipts must prove exactly what text was intended, not only what survived ad hoc field slicing.

Fix direction:

Phase A: immediate stable browser fix
- do not encode paragraph text directly in object `label=` fields.
- keep object labels short and chrome-safe only:
  - `Home`
  - `Audit`
  - `JS_Lab`
  - `Document`
- for body/document text, use one of:
  - a dedicated `source_ref`/text-file payload field for row text
  - a text-grid payload file referenced by object id
  - or a browser-specific `body_surface` object whose file payload is rendered by a dedicated text-grid renderer

Phase B: proper Wraith scene standard fix
- define a quote-safe object field encoding standard for scene records:
  - either quoted values
  - escaped values
  - or length-prefixed/text-file-backed payloads
- ensure:
  - scene writer
  - receipt exporter
  - GL parser
  all use the same reversible contract

Recommended TPMOS/Wraith direction:
- long-form text should not live in ad hoc inline `label=` fields.
- inline `label=` remains for small UI labels and nav controls.
- browser/document/editor surfaces should use payload-backed text grids or text assets, which also keeps ops reusable and auditable.

Status:
- root cause confirmed.
- browser GL object generation itself is no longer the main issue.
- the remaining defect is scene text payload format/transport, not browser navigation logic.
- treat the earlier project-local seam as replaced

Standard correction required before broadening the fix:

1. No implementation-heavy `.h` seam:
- `wraith_share_kvp.h` currently contains real implementation:
  - process launch
  - shmem attach
  - file mirroring
  - text/blob read-write helpers
- this violates the local TPMOS preference against `.h`-driven implementation.
- future refactor should move this logic into normal `.c` ops/units.

2. No Wraith-local naming for a TPMOS-wide service:
- this service is useful beyond Wraith and should not stay named:
  - `wraith_share_kvp_*`
- preferred future naming:
  - `tpmos_share_kvp_db`
  - `tpmos_share_kvp_read`
  - `tpmos_share_kvp_write`
  - `tpmos_share_kvp_dump`

3. No project-local lazy ownership for a shared service:
- current startup path is project-local and lazy:
  - `web-cam` seam calls `wkdb_ensure_daemon(...)`
  - that launches `ops/+x/wraith_share_kvp_db.+x`
- this is acceptable only as a proof seam.
- long-term ownership should move to TPMOS orchestration or an equivalent shared startup layer, not remain inside one project.

4. Standard-first hypothesis:
- user direction for current epoch:
  - adhere to TPMOS standards first, because ownership/naming/seam violations may be the reason the webcam bug is still muddy.
- future agents should not frame this as "cleanup after the bug".
- the structural correction is part of the bug fix.

Current practical stance:
- share-KVP refactor into TPMOS-shared ownership is done
- live webcam frame cache is also in place
- file-visible `session/fs_watch.marker` still remains important until manager wake is generation-native

Phase 2:
- make frame selection freshness-aware:
  - compare blob generation / blob-written epoch / status `frame_epoch` / file mtime
  - only use blob when it is known to be current
- add explicit blob reset or overwrite on webcam start

Phase 3:
- replace global DB naming with project-scoped naming so one run cannot inherit stale blob state from another

Architectural note:
- this regression is not evidence that the shared-KVP idea is wrong.
- it shows that the current proof moved the producer side of the seam before moving the watcher/consumer wake-up contract.
- the manager still depends on file growth, so webcam cannot go fully memory-first on marker signaling yet.

Applied repair and current state:
- `wraith_webcam_capture.c`
  - writes status through TPMOS shared KVP
  - writes live decoded frames through `tpmos_live_frame_cache`
  - sampled PNG snapshot remains for audit/fallback instead of hot transport
  - redraw pulses now happen on raw-frame arrival rather than file mtime polling
- `wraith_project_input.c`
  - ASCII preview now prefers the live frame cache first
  - file and blob paths are fallback, not first-choice hot truth
- `wraith_rgb_daemon.c`
  - webcam image panel now also prefers the live frame cache first
  - this removes the earlier source mismatch where ASCII could be real-time but image preview still lagged on sampled PNG

Why this repair is correct for now:
- the current webcam hot frame truth is now memory-first
- file artifacts are retained for audit/fallback
- manager wake and full redraw policy are still not fully generation-native, so not every remaining latency source is solved yet

Remaining proper fix:
- move manager wake-up to a reusable backend-aware seam
- then add blob/file freshness comparison before promoting webcam fully memory-first

Current status after structural TPMOS pass:
- webcam is working again after:
  - removing the implementation-heavy project `.h` seam
  - moving share-KVP ownership into TPMOS-shared `pieces/chtpm/ops`
  - renaming the seam toward `tpmos_share_kvp_*`
- standard compile path is clean again
- however, the webcam lane is still visibly slow

Why it is still slow:

1. Conservative fast-profile capture/output:
- current fast profile was still effectively low-frame-rate:
  - video4linux input rate modest
  - ffmpeg output filter limited
- that makes the preview feel behind even when the path is technically alive

2. Coarse frame-change polling in the capture daemon:
- webcam daemon only checks `current_frame.png` mtime on a sleep loop
- coarse sleep means frame detection and marker writes lag behind capture

3. Full project redraw on each frame:
- each marker wake still causes project input to rebuild:
  - `state.txt`
  - `webcam_preview.grid.pdl`
  - `wraith_body.txt`
  - `scene.objects.pdl`
- that is acceptable for proof and audit, but it is heavier than a future decoded-frame/shared-surface lane

Near-term fix direction:
- keep the proof auditable and file-keyed
- raise the fast-profile capture/output rate moderately
- tighten frame-detect polling moderately
- do not remove current audit files to chase speed

Longer-term speed direction:
- move away from PNG-as-hot-transport
- use decoded-frame caching or shared-memory/ring-buffer handoff for hot media frames
- keep the same logical file-path keys for audit dumps/snapshots
