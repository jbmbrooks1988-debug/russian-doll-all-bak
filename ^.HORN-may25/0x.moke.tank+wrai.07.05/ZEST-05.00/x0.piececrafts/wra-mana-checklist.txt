THE PATTERN (proven twice: piececraft-wraith, then fs)
--------------------------------------------------------------------------------

For any project that already has ops/src/wraith_project_input.c (the
synchronous hot-path input handler), adding a TPMOS-compliant manager is
mechanical — do NOT duplicate the ops file's logic in the manager. The
manager's only job is to be the thing the layout loads (the "script tag"),
plus trigger one initial render so the window isn't blank before the
first keypress.

### Step 1: Create manager/<project>_manager.c

Minimal, init-only — no persistent loop, no input polling thread. Copy
this shape (this is fs_manager.c's actual structure, works as-is for any
project with an existing ops/wraith_project_input.c):

```c
#ifndef _GNU_SOURCE
#define _GNU_SOURCE
#endif
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <ctype.h>
#include <time.h>
#include <stdarg.h>
#include <sys/wait.h>

#define MAX_PATH 4096
char project_root[2048] = ".";
char project_session_dir[2048] = ".";
char debug_log_path[4096] = "";

char* trim_str(char *str) { /* standard trim, copy from any existing manager */ }
int root_has_anchors(const char* root) { /* checks for pieces/ + projects/ dirs */ }
void resolve_paths() { /* find project_root via location_kvp, set project_session_dir */ }
void log_debug(const char* fmt, ...) { /* append to debug_log.txt */ }

void trigger_initial_render() {
    /* fork()/exec()/waitpid() the project's own
       ops/+x/wraith_project_input.+x with project_dir as argv[1] —
       exactly what wraith-alpha's run_active_project_input_op() does
       on every keypress. Running it once here means the window shows
       real content immediately, not a blank/stale frame. */
}

void trigger_render() {
    /* append "X\n" to pieces/display/frame_changed.txt */
}

int main() {
    resolve_paths();
    log_debug("<Project> Manager Started");
    trigger_initial_render();
    trigger_render();
    log_debug("<Project> Manager init complete (hot path owned by ops/wraith_project_input.c)");
    return 0;
}
```

### Step 2: Compile it

```
gcc -std=gnu11 -Wall -O2 manager/<project>_manager.c -o manager/+x/<project>_manager.+x
```

No special flags needed (no pthread, since there's no persistent thread).

### Step 3: Add to project.pdl

```
META | manager | projects/wraith-alpha/wraith-projects/<project>/manager/+x/<project>_manager.+x
```

This is the field `wraith-alpha_manager.c`'s `launch_project_manager()`
actually reads to auto-launch the manager when the project window opens
— this is the real trigger mechanism.

### Step 4: Add <module> tag to the layout

```xml
<module>projects/wraith-alpha/wraith-projects/<project>/manager/+x/<project>_manager.+x</module>
```

Add this as the first line inside the layout's root tag (right after
`<panel>` or `<chtpm>`). This is the declared, TPMOS-compliant "this
project loads a manager" shape — matches the standing HTML/`<script>`
principle even though (per tonight's investigation) Wraith doesn't
currently parse this tag to trigger anything itself; the real launch
happens via project.pdl's `manager=` field. Both should be present:
project.pdl for the actual mechanism, the layout for correctness/future-
proofing (Wraith may be refactored later to read this tag directly,
matching a more literal HTML/JS model — see conversation with user about
Wraith eventually becoming browser-like).

### Step 5: Verify standalone before touching Wraith

```bash
rm -f session/debug_log.txt
./manager/+x/<project>_manager.+x
cat session/debug_log.txt   # should show "Manager Started" + "init complete"
grep -E "^status|^<some key field>" session/state.txt   # confirm existing state untouched
```

### Step 6: Clear any stale lock, reload in Wraith

```bash
rm -f session/.manager.lock
```

Then reopen the project in Wraith and check `session/debug_log.txt` for
the manager's startup log lines.

--------------------------------------------------------------------------------
WHAT NOT TO DO
--------------------------------------------------------------------------------

- Do NOT put per-keypress state mutation in the new manager. That's what
  caused the input-lag bug fixed earlier tonight (documented in
  ARCHITECTURE-RGB-RENDERING.md / HANDOFF-WRAITH-STATE-MYSTERY.md) — a
  manager with its own polling thread races against Wraith's synchronous
  per-keypress render call. If a project's ops/wraith_project_input.c
  already owns the hot path (true for all 7 "needs a manager" projects
  above), leave it exactly as-is. The manager is init-only.
- Do NOT skip a project because "it already works fine without one" —
  see the standing rule at the top of this file.
- Do NOT use system() calls in the new manager for launching the op —
  use fork()/exec()/waitpid(), matching TPMOS convention and what
  fs_manager.c/piececraft-wraith_manager.c already do.
- Do NOT write project.pdl or session state files non-atomically
  (direct fopen(path,"w") without a temp-file+rename). This exact
  mistake (inherited from the wraith-3d-cube reference pattern originally
  copied for piececraft-wraith) caused a real, reproduced bug tonight:
  Wraith's read_project_map_control() re-reads state.txt on every
  keystroke, and a non-atomic write left a race window where it could
  read a truncated file mid-write. Fixed in piececraft-wraith's
  ops/wraith_project_input.c; check whether any of the 7 pending
  projects' existing wraith_project_input.c files have the same gap
  while touching them for this migration (worth auditing, not yet done
  for these 7).
