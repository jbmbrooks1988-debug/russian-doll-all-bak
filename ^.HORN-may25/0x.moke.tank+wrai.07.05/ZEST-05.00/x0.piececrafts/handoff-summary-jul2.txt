WHAT DOESN'T WORK (The Real Problem)
================================================================================

HYPOTHESIS: The issue is NOT the manager launch or state updates.
The issue is LAYOUT RENDERING and VARIABLE SUBSTITUTION in Wraith.

EVIDENCE:
1. piececraft-wraith layout contains:
   <text label="${game_map}" />
   <text label="[${display_mode}] [Xelector: (${xel_x},${xel_y},${xel_z})]" />

2. These variables should be read from gui_state.txt:
   - Manager writes gui_state.txt with all these values
   - Layout should read ${game_map} via substitution

3. BUT: When project displays, no variables are substituted
   - Layout appears static/blank
   - ${game_map} shows literally, not the content
   - No xelector or coordinates visible

POSSIBLE ROOT CAUSES (to investigate):

A) WRAITH DOESN'T PARSE CHILD PROJECT gui_state.txt
   - Wraith may only read wraith-alpha's own gui_state.txt
   - Child projects' state files might be invisible to layout parser
   - Solution: Need to understand how Wraith projects expose state to parent

B) LAYOUT PARSER DOESN'T TRIGGER AFTER MANAGER UPDATES
   - Manager updates state.txt but layout isn't re-rendered
   - Frame composition happens once at load, not on state change
   - Solution: May need to trigger frame_changed.txt marker

C) VARIABLE SCOPING ISSUE
   - ${game_map} might need special syntax or path reference
   - Child project variables might need namespace (${piececraft.game_map}?)
   - Solution: Check how variable substitution works in nested contexts

D) LAYOUT/RECEIPT ARCHITECTURE MISMATCH
   - Wraith-hosted projects may not support dynamic state projection
   - Layout files might be terminal (no real-time updates from manager)
   - Solution: May require structural change to how Wraith handles child projects

================================================================================
AGENT FINDINGS (Critical Architectural Insights)
================================================================================

From investigation of Wraith + TPMOS standards:

1. WRAITH IS FILE-BACKED REACTIVITY, NOT DAEMON ORCHESTRATION
   - Wraith manager updates state files (pieces/world/*/state.txt)
   - Parser reads those files and composes frame
   - No inter-process variable sharing
   - Each piece publishes view.txt, Wraith composes them

2. SUB-PROJECTS (LIKE PIECECRAFT-WRAITH) ARE "PIECES"
   - Should work like Terminal window or Inspector window
   - Should have their own manager writing view.txt
   - Wraith parser should read their view.txt and include in composed frame
   - Expected flow: piececraft-wraith_manager → writes view.txt → Wraith reads → renders

3. THE LAYOUT TAG `<module>` IS INFORMATIONAL, NOT EXECUTABLE
   - Top-level projects (op-ed, fuzz-op) have managers launched by Player App
   - Wraith-hosted projects need equivalent: parent (wraith-alpha) launches child
   - WE IMPLEMENTED THIS - wraith-alpha now spawns piececraft-wraith_manager
   - ✓ This part is CORRECT and WORKING

4. MISSING PIECE: CONTENT PROJECTION
   - Piececraft-wraith manager writes game_map.txt locally
   - But Wraith's layout can't access it (scoping/path issue)
   - Solution likely: Manager should write to wraith-alpha's view.txt instead
   - OR: Different mechanism for content projection from child → parent
