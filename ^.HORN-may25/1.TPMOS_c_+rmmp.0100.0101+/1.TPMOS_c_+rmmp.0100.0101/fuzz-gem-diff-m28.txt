# TPMOS Technical Report: Fuzz-Op vs. Gem-Dev Menu Systems (M28)

## 1. The Symptom
In `gem-dev`, the completion suggestions (triggered by `*`) were appearing as raw markup text (e.g., `<button ... />`) instead of interactive navigation buttons. After an initial fix attempt, the area appeared blank or broke the ASCII box borders.

## 2. The Root Cause: Attribute Nesting (Pitfall #103)
The `chtpm_parser.c` uses a two-pass substitution system:
- **Pass 1 (Naked):** Substitutes variables that are NOT inside XML tags. This allows injecting new XML elements (like buttons).
- **Pass 2 (Scoped):** Substitutes variables inside attribute values (like `label="${var}"`). The result is treated as plain text.

`gem-dev` was using `<row label="Suggestions: ${completion_area}" />`. Because `${completion_area}` was inside a tag, the parser substituted it in Pass 2, turning the button markup into a literal string.

## 3. Comparison: Fuzz-Op vs. Gem-Dev

| Feature | Fuzz-Op (Working) | Gem-Dev (Fixed) |
| :--- | :--- | :--- |
| **Variable Slot** | `${piece_methods}` at top level. | `${completion_area}` at top level. |
| **Manager Markup** | `<button label="..." /> <br/>` | `║ <button label="..." /> padding ║ <br/>` |
| **Borders** | Layout provides `║` around variable. | Manager provides `║` per-line for multi-line. |
| **Parsing** | Pass 1 injects buttons; Pass 2 ignores. | Pass 1 injects buttons; Pass 2 ignores. |

## 4. The Final Solution

### A. Layout Fix (`gem-dev.chtpm`)
Move the variable out of the `<row>` tag so the parser can tokenize the injected buttons.
```xml
    <text label="╠══════════════════════════════════════════════════════════════════════════════╣" /><br/>
    ${completion_area}
    <text label="║  " /><cli_io id="input_text" label="Ask Agent: " /><text label="  ║" /><br/>
```

### B. Manager Fix (`gem-dev_manager.c`)
The manager must now take responsibility for the borders and padding to keep the box aligned.
- Use `append_aligned_suggestion()` to wrap each button in `║` borders.
- Use `<br/>` instead of `\n` to ensure clean line breaks between suggestions.
- Ensure the padding math matches the 80-character box width.

### C. Fallback Fix
If no matches are found, the manager should publish a correctly bordered "no matches" text line:
`║  (no matches)                                                            ║<br/>`

## 5. Troubleshooting: Advanced Architectural Risks (What if I'm wrong?)
If completion fails despite a clean build, suspect these deeper systemic issues:

1. **Navigation Index Collision:** The CHTPM parser automatically assigns `1-9` keys to interactive elements. By injecting 5 buttons at the top level, we may be shifting the "Static" buttons (Clear, Switch API) to indices > 9, making them unreachable, or creating duplicate key bindings that confuse the dispatcher.
2. **The Pulse/Write Race Condition:** The manager writes `gui_state.txt` and then pulses `frame_changed.txt`. If the parser reads the KVP file while the manager is still `fprintf`ing (a partial write), the markup will be truncated, causing the XML tokenizer to silent-drop the malformed tags.
3. **Substitution Recursion Limit:** If the injected `<button>` markup relies on variables that require a *third* substitution pass (e.g., `${var}` inside an injected attribute), the parser may not resolve them, leading to empty labels or dead links.
4. **The "Naked" Pass Paradox:** If the parser's `substitute_vars_naked` logic has been updated to be "too safe," it might reject injected `<` characters to prevent XSS-style injection, effectively neutralizing the "Thin Theater" dynamic menu pattern.
5. **Double-Border Desync:** If the parser's internal row-rendering logic adds its own `║` markers based on the layout's `<panel>` width, our manager-side borders will cause "Double Bordering" (║║), which may push the text beyond the render buffer, causing a silent crash of the render thread.
