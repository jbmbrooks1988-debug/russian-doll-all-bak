BUG #1 - POV/CAMERA COORDINATES MAY NOT MATCH WHAT'S ON SCREEN (UNCONFIRMED)
========================================================================
Status: reported by user, not yet reproduced or diagnosed. User can feel
something is off but can't pin down exactly what. Do this next session.

Context: right after fixing the stale-camera-anchor bug (see prior
session - camera-fix.txt, now resolved: ops/compose_frame.c ~line 696
and ops/compose_rgb_frame.c ~line 1592 now anchor on xlector_x/y when
interact_mode==1, else hero px/py), the user suspects the POV/camera
coordinates still don't line up with what's actually rendered on
screen. This could be:
  - an off-by-one or off-by-half in the viewport centering math (cam_x/
    cam_y = anchor - viewport_dim/2, or similar, in compose_frame.c and
    compose_rgb_frame.c)
  - a mismatch between which coordinate space the anchor is read in
    (tile coords vs pixel coords vs the 3D render_3d_view()'s own
    facing-based camera, which is a SEPARATE camera concept from the
    scrolling 2D viewport - see camera-fix.txt, these two were
    deliberately not unified)
  - a clamp-to-map-bounds edge case near map edges where the viewport
    stops scrolling but the anchor keeps moving, so the anchor drifts
    off-center within the frame without it being "wrong" exactly - just
    non-obvious/confusing to a human watching it
  - the ASCII (compose_frame.c) and RGB/GL (compose_rgb_frame.c) mirrors
    disagreeing with each other (remember: this project's own
    convention is duplicate logic per-op, no shared headers - a fix or
    bug in one never automatically applies to the other, this has
    already bitten this project once for the anchor bug itself)
