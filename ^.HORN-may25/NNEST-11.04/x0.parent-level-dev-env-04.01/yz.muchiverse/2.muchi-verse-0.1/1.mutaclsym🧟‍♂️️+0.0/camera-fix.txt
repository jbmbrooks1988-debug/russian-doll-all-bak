CAMERA-FOLLOWS-DEAD-ANCHOR BUG - CHECK MUTACLSYM FOR THE SAME PATTERN
Written 2026-07-21, handed off from the $.4x family's own session (see
$.4x/handoff-possession-4x.txt sec. 5 for the full original writeup -
this is the condensed version specifically for checking mutaclsym).

========================================================================
THE BUG, AS FOUND IN THE $.4x PROJECTS (civ-pal, angler-empires,
pal-craft, muchimon-pal)
========================================================================
Each project's own compose_frame.c/compose_rgb_frame.c has a real,
working SCROLLING camera - cam_x/cam_y, computed by centering a fixed-
size viewport (40x16) on a "current position" and clamping to the map's
own bounds so the viewport never scrolls past the map's real edge. This
part was always correct.

The bug: the anchor was hero/state.txt's own px/py (the hero's static
spawn position) - which NEVER MOVES in these projects' own possession-
based control model (a whole separate correction this session: the
player controls a free "xlector" cursor and/or a possessed piece, never
a directly-walked hero avatar anymore). Every one of these projects'
own maps is ALREADY wider than the 40-col viewport, so the camera had
been silently frozen on the dead spawn tile the entire time - never
actually scrolling, just showing a static slice, with no visible error
(the game still "worked," it just never panned).

THE FIX: the camera anchor is now:
  - xlector_x/xlector_y (the free cursor's own live position) by
    default, OR
  - the currently-POSSESSED piece's own live pos_x/pos_y, read fresh
    from THAT instance's own state.txt each frame, whenever something
    is actually possessed (checked via a possessed_id field != "none").
Both compose_frame.c (ASCII) and compose_rgb_frame.c (GL/RGB mirror)
needed the identical fix independently - they are two separate
rendering pipelines in this whole family, a fix to one never
automatically applies to the other (this has bitten this session
multiple times, worth remembering generally, not just for this bug).

========================================================================
WHAT TO ACTUALLY CHECK IN MUTACLSYM
========================================================================
mutaclsym is architecturally different from the $.4x projects - it uses
the REAL shared chtpm_parser.c/chtpm engine (the $.4x projects' own
possession/interact model was reverse-engineered FROM chtpm's own real
source this session, see !.pal-standards.txt sec. 28/30 for that whole
story), not the flat PDL-action-bar engine the $.4x projects share. It
may not have this exact bug at all, or may have a differently-shaped
version of it. Don't assume it's broken - CHECK:

1. Find mutaclsym's own equivalent of a "center the viewport on the
   player" camera calculation - likely in its own compose_frame-
   equivalent op, or possibly in wraith_rgb_daemon.c-style GL rendering
   if mutaclsym has a 3D/RGB mirror mode (PIECECRAFT-WRAITH-
   ARCHITECTURE.md sec. 3 describes a real ray-marched camera system
   in a SIBLING project, piececraft-wraith - worth checking if
   mutaclsym shares any of that camera code, or has its own separate
   copy).
2. Ask: what position does that camera center on? Is it a value that
   ACTUALLY updates every time the player moves (good), or a cached/
   static field that could go stale under some control scheme (the
   exact bug class found here)?
3. mutaclsym's own real chtpm engine may ALREADY correctly follow
   whatever piece chtpm's own active_target_id names (chtpm's real
   architecture, sec. 28's own citation, already handles "which piece
   is currently being controlled" as a first-class concept) - if so,
   this bug may simply not exist there, since chtpm's own real design
   doesn't have the same "dead hero position" leftover the $.4x
   projects had to clean up from their mansion-sim origins.
4. If mutaclsym DOES turn out to have an analogous stale-anchor bug,
   the fix shape is: read the position from wherever chtpm's own
   active_target_id/currently-controlled-piece ACTUALLY lives (not a
   separately-cached hero field), fresh, every frame - same principle
   as the fix above, adapted to mutaclsym's own real data source rather
   than copied verbatim (the $.4x fix's own possessed_id/xlector_x/y
   field names are specific to that family's own PDL-engine shape, not
   directly portable).

========================================================================
HOW TO VERIFY EITHER WAY (same method used to find/fix this in $.4x)
========================================================================
1. Confirm the map is actually wider/taller than the rendered viewport
   for at least one real mutaclsym map - if every map fits within one
   screen, camera-follow bugs are invisible by construction and this
   may not be worth chasing at all.
2. Move/control a piece far enough from spawn that a working camera
   would have to scroll, then check whether the rendered frame's own
   visible content actually shifted (compare two frames before/after
   a long walk, same way $.4x confirmed its own fix: "viewport content
   visibly shifted as a possessed Settler walked 25+ tiles right").
3. Live-test through the REAL running process (not just reading code) -
   this whole $.4x thread's own biggest lesson, restated once more
   here: several "should be fine" assumptions this session turned out
   wrong only once actually run.
