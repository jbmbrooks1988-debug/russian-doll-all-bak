========================================================================
0. WHAT STAYS, WHAT CHANGES
========================================================================
KEEP AS-IS: the whole render/input/turn loop (prisc+x, renderer,
keyboard_input, move_player, end_turn, compose_frame/compose_rgb_frame),
the registry file pattern, pickup/drop/activity/talk/choice/
scene_reader ops, save_game, title_input, compose_title_frame. This
project's own overworld (walk around towns/routes, talk to NPCs, walk
into tall-grass encounter zones) is a near-1:1 fit for the EXISTING
mansion-sim loop (locations.txt rooms -> towns/routes, activities.txt
-> NPC interactions, monster_types.txt -> already exists and is already
the right shape for wild encounters, characters.txt -> town NPCs/
trainers). Less new engine work than pal-craft (sec. 1 there was a real
gap); closer to angler-expanses' shape (mostly reskin + one real new
subsystem).

THE ONE REAL NEW SUBSYSTEM: turn-based BATTLES (wild encounter or
trainer battle - species stats, moves, type effectiveness, catching)
and a player's own PARTY of caught muchimon with individual, persistent
state (level, current hp, learned moves) - this is what pickup/drop/
activity don't already cover, and is this doc's real design work
(sec. 3/4).

3. MUCHIMON SPECIES + MOVES - REGISTRY EXTENSIONS
========================================================================
  monster_types.txt gains (appended columns, not reordered):
    ...existing id|name|glyph|hp|damage|unicode...|type_id|
    move_ids_csv|catch_rate|base_xp_yield
    type_id: references a new pieces/registry/types/type_chart.txt
    (id|name|strong_against_csv|weak_against_csv - the classic type-
    effectiveness table, same bank shape as everything else).

  New registry: pieces/registry/moves/move_bank.txt
    id|name|type_id|power|accuracy|pp
    (a move is just another swappable-behavior bank row, same idea as
    job_types.txt in angler-expanses or civ_tech_bank.txt in muchi-civ -
    "what a move DOES" is a small, self-contained calculation an op
    performs by looking up this row, not hardcoded per-species).

Wild encounter selection reuses the existing decision_mode per-instance
convention (monster_types.txt's own documented header comment) for
IN-BATTLE behavior (does a wild muchimon flee below some hp%, same
flee_hp_pct field already documented there) - not new machinery, the
convention already anticipates exactly this use.

========================================================================
4. PLAYER'S PARTY - BANK (species) vs. INSTANCE DIR (caught muchimon)
========================================================================
Same split as angler-expanses sec. 3/muchi-civ sec. 3, applied to
caught muchimon instead of anglers/units - the split exists precisely
for this shape of problem (many possible types, few actually-owned,
stateful individuals).

  monster_types.txt (sec. 3, extended) IS the bank - species templates,
  static.

  A CAUGHT muchimon is a living instance with real accumulated history
  (level, current hp, learned moves subset, nickname) - gets a piece
  dir: pieces/apps/player_app/party/<instance_id>/state.txt
  (species_id references monster_types.txt, level, current_hp,
  known_move_ids_csv, nickname) - lives under the player's own app dir
  (matching pieces/apps/player_app/'s existing role as player-owned
  persistent state, same directory today already holds history.txt),
  NOT under a world_<region_id>/ dir, since the party travels with the
  player across regions/worlds, unlike angler-expanses' anglers or
  muchi-civ's units which are tied to a specific world/planet.
  Max-6-party-slot enforcement lives in the catch-attempt op (sec. 5),
  not in the directory structure itself (an over-limit catch simply
  fails/prompts a swap, matching this family's "validate at the
  boundary, not by inventing a new structural constraint" preference).

  A WILD muchimon encountered but not yet caught is NOT a piece dir at
  all - it's an ephemeral in-battle value (species_id + a rolled level/
  hp, held in battle state, sec. 5) until/unless a catch attempt
  succeeds, at which point it's promoted into a real party piece dir.
  This mirrors angler-expanses' own "not every NPC needs a piece dir,
  only ones that accumulate real individual history" rule exactly.

========================================================================
5. BATTLE MODE - A NEW MODE FLAG, REUSING interact_mode's OWN SHAPE
========================================================================
New hero/state.txt fields: battle_mode=0/1, battle_opponent_kind=
wild|trainer, battle_opponent_ref (instance id or bank id depending on
kind), battle_turn=player|opponent, plus small per-side working fields
(active_party_slot, opponent_current_hp if wild/ephemeral).

  New op: ops/battle_start.c - triggered from move_player.c's own
  tall-grass-tile encounter roll (reuse terrain_types.txt: a new
  t_tall_grass row with an encounter_table reference - TBD exact
  column shape, same registry-extension pattern as sec. 3) or from
  talk.c's existing NPC-interaction path when is_trainer=1 (sec. 2).
  Sets battle_mode=1, populates the ephemeral or trainer-team opponent.

  New op: ops/battle_choice.c - the battle-mode input handler (same
  role as choice.c already plays for the action-bar footer today,
  same shape, gated by battle_mode==1 the same way interact_mode==1
  already gates move_player.c/compose_frame.c's own alternate paths
  per dox 04 sec. 1's proven precedent in the sibling pal-craft
  project). Handles move selection, computes damage via move_bank.txt
  power/accuracy + type_chart.txt effectiveness, applies to
  battle_opponent's or the active party instance's current_hp.

  New op: ops/battle_catch.c - the catch-attempt op (sec. 4's promote-
  ephemeral-to-instance step), gated to wild battles only
  (battle_opponent_kind=wild), reads catch_rate off monster_types.txt,
  rolls against it (weighted by opponent's own current_hp%, standard
  Pokemon-style "easier to catch when weakened" - exact formula TBD
  with user, not decided in this doc), on success creates the new
  party piece dir (sec. 4) and ends the battle.

  compose_frame.c gains a battle-mode render branch (same "if
  (mode_flag) render_X() else render_normal()" shape dox 04 sec. 2.3
  already uses for render_mode==1's 3D branch) - a battle-specific
  ASCII layout (both sides' hp/level, a move-selection footer) instead
  of the normal map view. No compose_rgb_frame/3D work implied or
  needed for this project - battles are ASCII-only, matching Pokemon
  Red/Blue's own 2D-only presentation, an explicit non-goal to add 3D
  here.

6. EXPLICITLY DEFERRED
========================================================================
- Multiple regions/generations beyond the first world_<region_id>.
- Breeding, evolution (a real, later registry extension - evolve_to_id/

  just not designed further here).

- PvP/networked trainer battles (PAL-NET-STANDARD exists and is proven
  elsewhere in this family - not assumed needed yet).
- SCALE_BANK: unlike angler-expanses/muchi-civ (which juggle many
  simultaneously-simulated tribes/civs), muchimon-pal has only ONE
  live battle at a time and a small bounded party - no real off-screen-
  fidelity question exists yet to warrant a SCALE_BANK section. Revisit
  only if a future feature (e.g. simulating an NPC's own team growth
  over time while off-screen) actually creates one.

8. REVISED MODEL - FREE POSSESSION, ON-MAP TACTICS BATTLES, MUCHIBOXES

8.1 POSSESSION - FREE, NOT FIXED
------------------------------------------------------------------------
Uses the exact civ-pal/angler-empires model, !.pal-standards.txt sec.
28/30/31, unmodified - xlector (free cursor) possesses whatever real
instance is at the cursor on Enter, ESC relinquishes back to xlector
(never both in one press), possession persists across interact-mode
toggling. possession_config.txt: mode=free.

Possessable targets, all real instances the same bank-vs-instance-dir
split already covers (sec. 3/4 of this doc, unchanged):
  - the player's own starting character (still exists, still the
    default-possessed thing at game start - "there is a main playable
    character" - just not PERMANENTLY locked to it).
  - any trainer once captured ("trainers also have personal health,
    skills and can choose to engage in battle... and can also be
    captured" - a trainer is a real, possessable instance once caught,
    same mechanism as a muchimon).
  - any caught muchimon, per the party/muchibox rules in sec. 8.3.

8.2 BATTLES - ON-MAP TACTICS, NOT A SEPARATE SCREEN
------------------------------------------------------------------------
REPLACES draft 1 sec. 5 entirely (that section's own battle_mode flag/
separate ASCII layout/ops/battle_start.c-battle_choice.c-battle_catch.c
design is WITHDRAWN - not built, don't resurrect it).

Battles happen ON THE MAIN MAP - a tactics-style engagement, not a mode
switch to a dedicated screen. Concretely (mapping onto mechanisms this
family already has, not new machinery):
  - Wild encounter trigger: unchanged from draft 1 - a tall-grass
    terrain tile (t_tall_grass-equivalent) rolls an encounter.
  - On trigger, the wild muchimon (or a trainer's own team) is SPAWNED
    as a real instance directly on the map (same spawn_unit.c-shaped op
    this family already uses, sec. 4's own pattern) - not an ephemeral
    battle-only value like draft 1's sec. 5 assumed. It is a real,
    possessable-by-nobody-yet (enemy-owned) piece sitting on real map
    tiles, engaged the same way any tactics game engages a unit -
    movement, attacks, positioning all happen on the SAME grid the
    player already walks around on, not a teleport to a separate
    battle arena.
  - Trainers "deploy their muchimon once battle is initiated" - a
    trainer instance, on engaging, spawns its own team onto the map the
    same way (same op, different owner).
  - A turn passes each turn (already this family's own standard turn-
    tick convention, end_turn.c-equivalent, sec. 28.4's gating on
    interact_mode==1 still applies) - NOT a separate battle-turn
    counter, the SAME turn counter the rest of the game already uses.
  - Day/night cycle: time passes every turn (a real, new mechanic -
    a day_time or similar field ticking every real turn, wrapping at
    some project-defined day length - not designed further here, just
    named as a real requirement for a later pass).

8.3 MULTI-ENTITY DEPLOYMENT, FOLLOW/PLACED/AUTO MODES, MUCHIBOXES
------------------------------------------------------------------------
"During wild battles, user can deploy more than one entity... these can
be controlled manually or be set to auto mode where they will do 1 act
per turn (as all entities)." Concretely:
  - Each captured muchimon/trainer instance gets a mode field (its own
    state.txt, matching this family's own per-instance-state
    convention already documented in monster_types.txt's header
    comment for decision_mode): follow | placed | auto.
    - follow: trails the player's own currently-possessed piece,
      "caterpillar party" style (Pokemon's own classic follow mechanic,
      named directly by the user) - a real movement-following op,
      matching this family's own decision_mode tiering (monster_types.
      txt sec. cited above already documents exactly this "instance-
      level AI mode" pattern, reused here not reinvented).
    - placed: stays exactly where set, does nothing on its own (a
      stationary, player-positioned piece - e.g. guarding a spot).
    - auto: AI-controlled, "1 act per turn" - same decision_mode tier
      concept, a real per-instance AI pass each turn (module TBD, not
      designed further here - matches this family's own SCALE_BANK/
      registry+switch precedent for "which AI module handles this
      instance," zest-er-summary sec. 4.5/4.6).
  - Manual control of a deployed entity = simply possessing it (sec.
    8.1) - no separate "manual battle control" mechanism needed, this
    IS what free possession is for.
  - Muchiboxes: a real, possibly-recursive container - "can hold many
    items/entities/muchimon, and have their own dropdown menu (which
    may contain more muchiboxes or entities who are holding their own
    muchiboxes with things inside)." This is a genuinely new data
    shape for this family (recursive containment, not just a flat
    inventory list) - NOT designed further in this doc (a real,
    separate design pass is warranted given the recursion), flagged
    here as a named, real requirement rather than silently deferred
    without a trace. Do not build muchiboxes ad hoc when this is
    eventually picked up - write its own short design note first,
    same "design-doc-first" discipline as everything else in this
    family.

8.4 WHAT THIS SECTION DOES NOT DECIDE (real gaps, named not solved)
------------------------------------------------------------------------
- Muchibox's own recursive data shape/file format.
- The exact auto-mode AI module(s) for deployed entities.
- Day/night cycle's own concrete day-length/effects.
- Tactics-battle-specific mechanics beyond "it happens on the real map,
  turns already tick the way they always do" - real attack/damage/
  positioning rules for a multi-entity-per-side tactics engagement are
  a separate, later design pass, not assumed solved by "reuse the map."
