P1.0 THE STANDING RULE THIS WHOLE SESSION KEPT RE-LEARNING THE HARD WAY
------------------------------------------------------------------------
When a working reference implementation exists for the thing that's
broken (gem-dev's manager, pal-chat-irc's chat_inbox_watcher.c), read
ITS actual handling of that specific step BEFORE forming a new theory
or adding debug instrumentation to the broken project. This has to be
re-checked for EVERY new symptom, not just once per debugging session -
direct user correction, verbatim: "why aren't u religiously comparing
to that instead of making things up that u keep getting wrong. if its
not in a working code example. dont even modify our code." Every real
fix below (P1.1-P1.4) was found this way; every wasted detour (a PID-
reuse theory, ad-hoc debug logging, a from-scratch persistent-daemon
rewrite proposal) happened exactly when this rule was skipped.

P1.1 A "SINGLE-OWNER POLL STATE" FILE IS NOT THE SAME KIND OF SHARED
     DATA AS A MULTI-USER DATABASE - DON'T SYMLINK IT ACROSS SESSIONS
------------------------------------------------------------------------
pal-chat-irc's own button.sh correctly keeps TWO different kinds of
per-project data in two different places: `users/`/`rooms/` (real
multi-user data, symlinked/shared on purpose - many real sessions
legitimately mutate it together, and every write into it is guarded
idempotently, e.g. chat_inbox_watcher.c's own `already_has_line()`) vs.
`pieces/apps/player_app/state.txt` (this session's own exclusive
poll/UI-ownership bookkeeping, written fresh into `$SESSION_DIR` on
every single `run`, never shared). A new project's own button.sh can
get this WRONG by pattern-matching the shared half without checking
whether ITS OWN "state.txt-shaped" file is actually the same kind of
data - muchi-pal-agent's `pieces/world_01/session_01/chat/state.txt`
(holding `ai_state`/`curl_pid` - single in-flight-API-call ownership,
not multi-user anything) was symlinked shared exactly like `rooms/`,
on exactly this mistaken analogy. Real, live-caught consequence: two
`button.sh run`s (old sessions never fully killed - see P1.1a) both
polled and mutated the same `ai_state`/`curl_pid` fields at once,
producing the SAME assistant reply logged twice for one turn. Fix:
copy the file into `$SESSION_DIR` fresh on every `run` (seed from the
canonical copy for cross-run continuity if wanted, persist back on
exit) exactly like `pieces/apps/player_app/state.txt` already does -
continuity and exclusivity are separate concerns, don't trade one for
the other.

P1.1a A CLOSED TERMINAL SENDS SIGHUP, NOT INT/TERM - TRAP IT, AND STILL
      REAP BY BINARY IDENTITY ON THE NEXT `run` AS A BACKSTOP
------------------------------------------------------------------------
`trap '...' EXIT INT TERM` (pal-forum's own original shape, copied
project to project) never catches a terminal window closing - that
sends SIGHUP. Add it to the trap. Even with that, ALSO reap any live
instance of the project's own binaries at the START of the next `run`
(matching sec. 0-CORRECTED item 4's own liveness-based single-instance
precedent for `launch_module()`) - match by BINARY IDENTITY
(`/proc/$pid/exe` resolving under the project root), never by `cwd`
alone. Live-caught why cwd-only isn't enough: a rogue prisc+x/
chtpm_parser_pal pair had been running for over an HOUR with cwd == the
project root itself, launched directly (bypassing button.sh entirely,
likely stray direct-invocation testing per this family's own §6 testing
discipline) - a cwd-scoped-to-pieces/sessions/ guard never saw it, and
it kept mutating the canonical shared files the whole time. Also: after
any kill, re-verify with a SECOND `ps` check before trusting it worked -
a clean exit code is not proof of a real kill (cause not fully
confirmed here, possibly a sandboxed-tool signal-delivery quirk; the
operational lesson stands regardless of the exact mechanism).

P1.2 ON COMPLETION, THE PROCESS THAT DETECTED IT MUST TRIGGER THE
     RENDER ITSELF - NEVER JUST PING A MARKER AND TRUST A LATER,
     SEPARATE POLL TO NOTICE
------------------------------------------------------------------------
Two independent, already-proven references agree on this, exactly:
  - gem-dev_manager.c's own main loop: the SAME function that just
    detected an HTTP response finished calls `write_gui_state();
    trigger_render();` itself, unconditionally, right there (line
    ~1408-1427) - it never relies on some OTHER, later poll to notice
    and redraw on its own schedule.
  - pal-chat-irc's `ops/chat_inbox_watcher.c` own `trigger_render()`
    shells out to `chat_compose_frame.+x` DIRECTLY the instant new data
    is detected - that file's own header comment documents the EXACT
    failure this avoids, live-caught there first: "that marker only
    tells [the renderer] re-read whatever's currently in view.txt - it
    does NOT regenerate view.txt itself... the marker got pinged but
    view.txt stayed stale."
A one-shot op that only appends to a marker file and returns, trusting
a SEPARATE poll instruction elsewhere to notice the marker changed and
decide to re-render, has an unbounded window between "actually done"
and "visibly done" - live-caught in muchi-pal-agent as a real answer
computed and saved correctly in the background while the screen stayed
frozen on "Thinking..." until the whole app was killed and restarted
(a fresh start's own unconditional startup `compose_frame` just picked
up the already-correct data off disk). Fix, ported directly: the
completion-detecting op calls the render op itself (`system("./ops/+x/
compose_frame.+x")`), synchronously, in addition to any marker file
other code still watches - not instead of, in addition to, matching
chat_inbox_watcher.c's own belt-and-suspenders shape exactly.

P1.3 A CURL TIMEOUT NUMBER "PROVEN" BY A COMMENT IS NOT THE SAME AS A
     REAL, HARD-WON FIGURE FROM A REFERENCE PROJECT'S OWN DEBUG HANDOFF
------------------------------------------------------------------------
`connect_op.c`'s own comment claimed "groq-ollama (8B) in <1s" and used
a 30s `--max-time`. gem-dev's own real debugging handoff doc for THIS
EXACT model on THIS EXACT host (`#.dox/groq-api-handoff.txt`,
`llama3-groq-tool-use:8b` on `10.0.0.144:11434`) explicitly needed 600s
and treats a curl timeout (exit 28) as a real, expected, DISTINCT
failure mode from connection-refused (exit 7) - not a rare edge case.
An 8B model's cold model-load time under concurrent load can easily
exceed 30s even though a WARM model answers in under a second - the
30s figure was true for the warm case only, generalized wrongly. Fix:
match gem-dev's own real numbers verbatim (`-sS --max-time 600`), and
surface curl's own real exit code as two DIFFERENT user-facing
messages (timeout vs. unreachable), not one generic "could not
connect" - a slow cold-loading model and a genuinely dead host are not
the same situation and shouldn't read as one to the user.

P1.4 ALWAYS CHECK FOR error.message BEFORE FALLING BACK TO A GENERIC
     "EMPTY OR UNPARSEABLE RESPONSE"
------------------------------------------------------------------------
A real Gemini (or any REST JSON API) error body is shaped
`{"error":{"message":"..."}}` and contains neither the success-shaped
"text"/"content" field NOR a functionCall - code that only ever tries
to extract the success shape and falls through to a generic parse-
failure message on "found nothing" silently swallows the API's own
real, specific error text (a malformed function-declaration schema, a
safety block, an invalid key, a quota hit) every single time. gem-dev_
manager.c's own check_ai_status() already does this correctly (an
`error.message` extraction, tried only when both real fields come back
empty) - port it verbatim into any project's own response parser that
doesn't have it yet, don't assume "unparseable" is ever the most useful
message available.
