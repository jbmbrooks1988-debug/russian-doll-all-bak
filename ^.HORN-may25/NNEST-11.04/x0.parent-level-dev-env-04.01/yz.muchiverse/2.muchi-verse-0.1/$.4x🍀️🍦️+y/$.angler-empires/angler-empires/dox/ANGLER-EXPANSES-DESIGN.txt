NEW CONTENT / NEW MECHANIC (this is the actual design work):
- 7 planets (1 home + 6 enemy), each an island-shaped map, each with its
  own 7-person tribe.
- Fortress-building: designate/dig/build orders queued by the player,
  executed over turns by dwarf (angler) AI, same decision_mode
  per-instance-state convention monster_types.txt already documents.
- Multi-world state: which planet is "active" (rendered), persistent
  state for the other 6 while off-screen.

existing pc_you/yh_01_leader palette), 6 enemy tribes each get one fixed

========================================================================
3. THE ANGLERS - NPC BANK (types) vs. PIECE DIR (living instances)
========================================================================
Per zest-er-summary sec. 4.4: don't give every one of the 49 (7 tribes x
7) anglers a full stateful piece dir by default - that's the mistake the
"bank vs instance dir" split exists to prevent. ONE FILE, MANY ROWS for
TYPES/TEMPLATES; a real per-instance piece dir ONLY for a specific,
stateful, LIVING individual that accumulates real history over time.

  pieces/registry/anglers/angler_bank.txt (the bank - replaces
  characters.txt's role as the source of angler TEMPLATES):
    id|name|glyph|color|role|default_outfit|tribe_id
    role: same Dwarf-Fortress-labor-role list as draft 1 (miner,
    builder, forager/angler-proper, defender, crafter, scholar/medic).
    tribe_id: which of the 7 tribes (angler_home + 6 enemy tribe ids,
    sec. 5) this row belongs to.

  Per-tribe roster = 7 bank rows sharing one tribe_id. Home tribe's 7
  rows are the starting colony; the player's own row keeps is_player=1
  (still a column, matches characters.txt today).

  A LIVING INSTANCE (a specific angler that's actually spawned into a
  world_<planet_id>/map_start) gets a piece dir ONLY because it needs
  real mutable state over time (hp, current job assignment, inventory,
  position, decision_mode - same per-instance-state convention
  monster_types.txt's own header comment already documents for
  monsters): pieces/world_<planet_id>/map_start/anglers/<instance_id>/
  state.txt, mirroring hero/ and monsters/'s existing directory shape
  exactly - no new directory convention invented, this is the same
  pattern move_player.c/tick-monster ops already read/write.

  Concretely: angler_bank.txt says WHO CAN EXIST (7 roles x 7 tribes,
  49 rows, static content); world_angler_home/map_start/anglers/*/
  state.txt says WHO ACTUALLY IS, right now, on this planet, with what
  hp/job/position (dynamic, mutated every turn). Same split as
  model_list.txt (bank) vs. state.txt's current_model_id (active
  instance) elsewhere in this family - not new machinery.

Exact names/flavor TBD with user - this doc fixes the bank/instance
split and role list, not final names.

========================================================================
4. BUILDING THE EXPANSE - REGISTRY + SWITCH + SELF-CONTAINED OPS
========================================================================
Goal: Dwarf-Fortress-style "designate an area/tile -> a job gets queued
-> an idle angler walks there and executes it over N turns -> the tile/
piece changes state." Per zest-er-summary sec. 5 ("every sub-ask reduces
to the SAME three ingredients... a registry, a switch op, small self-
contained ops") this is not a new mechanism to invent - it's the exact
model_list.txt/switch_model.c shape applied to jobs instead of AI
providers.

  New registry: pieces/registry/jobs/job_types.txt (the bank - names
  swappable job behaviors, exactly like model_list.txt names swappable
  provider_kinds):
    id|name|glyph_while_pending|turns_to_complete|requires_role|
    result_terrain_or_furniture_id
    (mirrors terrain_types.txt/monster_types.txt/angler_bank.txt's own
    pipe-delimited registry shape - no new file format invented)

  New op: ops/designate.c - the "switch" op (matches switch_model.c's
  own shape: look up a job_types.txt id, write a handful of state.txt
  fields, done). Player marks a tile/region for a job id, which writes
  a pending-job entry as its own small piece with its own state.txt
  (job_id, target_x, target_y, turns_remaining, assigned_angler_id) -
  same "each pending job is its own stateful piece" pattern as an
  angler instance (sec. 3) or a monster instance.

  New op: ops/tick_jobs.c - a TICK-DRIVEN poll (same shape as
  irc_agent_poll.c/check_response.c: cheap no-op check first, real
  work only when a pending job actually exists), called from end_turn.
  Assigns an idle angler instance whose bank role matches
  requires_role, advances turns_remaining, and on completion mutates
  map.txt/furniture.txt exactly the way pickup/drop already mutate
  items - no new mutation mechanism, reuse the existing terrain/
  furniture write path. Compose ops stay untouched (sec. 20's ONE
  VISIBLE FRAME WRITER RULE, per PAL-NET-STANDARD sec. 6's own
  documented gotcha: tick_jobs.c must re-run compose_frame after a
  real change, pinging frame_changed.txt alone is NOT enough).

  Angler idle-labor AI reuses move_player.c's existing decision_mode-
  driven pathing (tier-0 "always chase" vs tier-1 "weighted", the same
  per-instance state.txt field monster_types.txt documents) applied to
  "walk to nearest pending job matching my own bank role" instead of
  "walk to nearest player" - no new pathfinding invented.

Exact job list (dig, build wall, build furniture, stockpile management)
is a second pass once the rename + bank + one working job_types.txt row
(recommend: dig, only mutates terrain walkable/glyph, smallest slice)
is proven end-to-end - same "prove one thing before generalizing"
discipline as everywhere else in this family.

========================================================================
5. 7 PLANETS / 6 ENEMY TRIBES + SCALE_BANK FOR SIMULATION FIDELITY
========================================================================
Each planet = one world dir (pieces/world_<planet_id>/map_start/...),
same directory shape as today's single world. Home planet is
pieces/world_angler_home (sec. 2). The 6 enemy planets get their own
world_<planet_id> dirs, each with its own map.txt (island shape, reuse
terrain_types.txt rows), its own 7-row slice of angler_bank.txt (all
is_player=0, tribe_id = that planet), and its own spawned angler
instances (sec. 3).

Switching the RENDERED/active planet: pieces/system/active_planet.txt
(matches pieces/system/title_state.txt's existing one-line-state-file
convention exactly), read by compose_frame to decide which
world_<planet_id>/map_start it composes from - not a new mechanism.
Traveling between planets (ship? portal? instant "embark elsewhere"?)
is NOT decided in this doc - next conversation, per user's own framing.

SCALE_BANK - how deeply to simulate OFF-SCREEN tribes (zest-er-summary
sec. 4.6, applied here directly rather than inventing a bespoke "cheap
mode" flag): simulation fidelity is a property of (entity_type, domain)
pairs, not one global on/off switch. A pipe-delimited bank, same shape
as sec. 4's job bank:
    entity_type|domain|scale_level|module_id
    tribe|labor_jobs|large|tick_jobs_full     (active/rendered planet)
    tribe|labor_jobs|small|tick_jobs_abstract (off-screen planets - job
                                                 counters advance on a
                                                 coarse tick, no real
                                                 per-angler pathing)
    tribe|combat|small|none                   (no inter-tribe combat
                                                 yet - sec. 6 deferred)
    tribe|population|small|static_seven        (fixed 7-per-tribe, no
                                                 growth/death sim yet)
A per-game config (or simply: "large for whichever tribe_id matches
active_planet.txt, small for the other 6") picks the active scale_level
per row - same registry-vs-active-selection split as model_list.txt vs.
state.txt's current_model_id. This directly replaces draft 1's vague
"recommend enemy tribes advance only when active, not decided" note
with the family's own actual mechanism for exactly this decision -
still not fully decided WHICH module_id each cheap row should point to
yet, but the SHAPE of the decision is now fixed, matching every other
fidelity choice in this family.
