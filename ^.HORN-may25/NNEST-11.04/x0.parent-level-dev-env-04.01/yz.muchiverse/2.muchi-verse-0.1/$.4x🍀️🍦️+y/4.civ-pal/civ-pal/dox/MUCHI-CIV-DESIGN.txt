Written 2026-07-21. Renaming "muchi-civ" -> "muchi-civ", reskinning the
existing PRISC (ops+pieces+pal) mansion-sim engine into a Civilization-
style 4X: multiple cities per civ, tech, on a SOLAR SYSTEM map (planets
are the "map tiles"/embark sites, not a single continent - direct user
correction: "not a world map a solar system map").

Written per yz.muchiverse/$.zest-er-summary-FIN.txt's own standing
conventions - reuses the REGISTRY + SWITCH + SELF-CONTAINED OPS pattern,
the BANK-vs-INSTANCE-DIR split, and SCALE_BANK throughout, same as
angler-expanses/dox/ANGLER-EXPANSES-DESIGN.txt (draft 2, sibling project,
read first if this doc is unclear anywhere - identical engine, identical
family conventions, different content). Nothing below invents a new
mechanism where an existing family pattern already fits.

========================================================================
0. WHAT STAYS, WHAT CHANGES
========================================================================
KEEP AS-IS: the whole render/input/turn loop (prisc+x, renderer,
keyboard_input, move_player, end_turn, compose_frame/compose_rgb_frame),
the registry file pattern (glyph|id|name|...|unicode|rgb_top_emoji),
pickup/drop/activity/talk/choice/scene_reader ops, save_game,
title_input, compose_title_frame.

RENAME (mechanical, sec. 2): pieces/world_muchi_civ_home[_template] ->
pieces/world_<planet_id> per planet (same directory shape angler-
expanses already establishes - this project reuses THAT convention
directly, not a separate one). project.pdl/button.sh/README/comments
swept for "tempt"/"Muchi Civ" -> "muchi-civ"/"Muchi Civ".

NEW CONTENT / NEW MECHANIC:
- A solar system map: N planets, each an embark/city site (like Civ's
  own map tiles), NOT one continuous world map - direct user framing.
- Multiple CITIES per civ, spread across multiple planets a civ
  controls - the actual 4X difference from angler-expanses' one-
  expanse-per-tribe model.
- A tech tree (civ-wide, unlocks buildings/units/city actions).
- Multiple civs (player + AI), each able to found/grow/lose cities.

========================================================================
3. UNITS & CITIZENS - BANK (types) vs. PIECE DIR (living instances)
========================================================================
Same split as angler-expanses sec. 3, applied to Civ's own unit/citizen
concept instead of anglers - not a new mechanism.

  pieces/registry/units/unit_bank.txt (types/templates):
    id|name|glyph|color|category|move_range|attack|defense|
    required_tech|build_cost
    category: settler|worker|military|(future eras add rows, not new
    columns - same "add a new base per new kind as needed" precedent
    PAL-NET-STANDARD sec. 3 uses for port bases).

  A LIVING unit instance (spawned, has real position/hp/orders) gets a
  piece dir: pieces/world_<planet_id>/map_start/units/<instance_id>/
  state.txt (unit_type_id, civ_id, hp, x, y, orders, decision_mode -
  same per-instance-state convention monster_types.txt documents).

  Cities are NOT bank rows (a city isn't a type, it's a specific
  place) - a city is a locations.txt row (sec. 1) PLUS its own
  piece dir for mutable city state: pieces/world_<planet_id>/
  map_start/cities/<city_id>/state.txt (owning civ_id, population,
  production_queue, built_buildings_csv, current_tech_progress if
  tech is tracked per-city rather than per-civ - TBD, sec. 4 assumes
  per-civ for now, simpler).

========================================================================
4. TECH TREE - REGISTRY + SWITCH, NOT A NEW MECHANISM
========================================================================
  pieces/registry/tech/civ_tech_bank.txt (the bank):
    id|name|prereq_ids_csv|turns_to_research|unlocks_unit_ids_csv|
    unlocks_building_ids_csv
    (same pipe-delimited shape as job_types.txt in angler-expanses
    sec. 4 - a tech is just another swappable "unlock" entry, same
    registry idea as model_list.txt naming swappable AI providers).

  Per-civ ACTIVE research state (not a bank row - this is the "which
  option is currently selected" half, same split as state.txt's
  current_model_id elsewhere): pieces/world_<planet_id>/map_start/
  civs/<civ_id>/state.txt gets current_tech_id + tech_turns_progress
  fields (civ state may end up living in ONE place shared across that
  civ's own planets rather than duplicated per-planet - TBD once
  sec. 5's system-vs-planet split is settled, flagged not decided).

  New op: ops/tick_research.c - tick-driven poll (cheap no-op unless a
  civ has an active current_tech_id), advances tech_turns_progress,
  on completion unlocks unit_bank.txt rows gated by required_tech and
  appends to that civ's own available-buildings list. Same shape as
  angler-expanses' tick_jobs.c - a poll op, not a per-keypress mutation
  (matches PIECECRAFT-WRAITH-ARCHITECTURE.md sec. 1's own "never put
  per-keypress state mutation in a background/poll process, mutation
  belongs in the synchronous hot-path op" rule, applied here as "tech
  progress advances on end_turn's own tick, not on arbitrary keypresses").

========================================================================
5. SOLAR SYSTEM MAP - THE ACTUAL NEW TIER (not in angler-expanses)
========================================================================
Angler-expanses has 7 planets but no strategic "map between them" -
travel is explicitly deferred there. Muchi-civ NEEDS a real system-
level map since multiple civs contend for multiple planets - this is
the one genuinely new tier this project adds beyond angler-expanses'
pattern.

  pieces/registry/system/planet_bank.txt (which planets exist, static
  template data): id|name|glyph|orbit_slot|size|starting_resources_csv
  (orbit_slot is a simple integer ring position, not real orbital
  mechanics - matches this family's "don't pre-design fields for a
  project that doesn't exist yet" PAL-NET-STANDARD sec. 5 precedent;
  real orbital movement is not in scope).

  Per-planet OWNERSHIP/dynamic state (which civ controls it, if any):
  pieces/system/system_map/<planet_id>_owner.txt (one small state
  file per planet, same shape as pieces/system/active_planet.txt/
  title_state.txt's existing one-fact-per-file convention - not a
  single big system file, so ownership changes never risk a partial-
  write race across multiple planets at once).

  Active/rendered planet: pieces/system/active_planet.txt, identical
  mechanism to angler-expanses sec. 5 - if that project builds this
  first, port it here rather than re-deriving.

  Movement BETWEEN planets (a ship/unit's own inter-planet travel) is
  the one piece of real new engine work neither angler-expanses nor
  the current 2D engine has any pattern for yet (angler-expanses
  explicitly deferred this too) - flagged for a follow-up design pass,
  not decided in this doc. Recommend starting with the SIMPLEST version
  that's provably not wrong (a fixed travel_turns cost per planet pair,
  stored as a small pieces/registry/system/travel_costs.txt table) over
  inventing real pathing/orbital mechanics prematurely.

========================================================================
6. SCALE_BANK - PER-CIV, PER-PLANET SIMULATION FIDELITY
========================================================================
Same fidelity-per-(entity_type, domain) idea as angler-expanses sec. 5,
applied to a bigger space here (many civs, many planets, many cities -
simulating everything at full fidelity every turn is real waste):
    entity_type|domain|scale_level|module_id
    civ|city_management|large|tick_cities_full   (player's own civ,
                                                    and whichever AI
                                                    civ's planet is
                                                    active/rendered)
    civ|city_management|small|tick_cities_abstract (other AI civs -
                                                    production/growth
                                                    advance on a coarse
                                                    tick, no per-tile
                                                    work simulated)
    civ|diplomacy|small|none                     (deferred, sec. 7)
    civ|combat|small|abstract_resolve             (deferred detail,
                                                    sec. 7 - a coarse
                                                    win/loss roll, not
                                                    real unit-vs-unit
                                                    combat resolution,
                                                    until that's built)
Same registry-vs-active-selection split as elsewhere in this family -
not fully decided which module_id each row should point to yet, but
the SHAPE is fixed, matching every other fidelity choice in this
family (zest-er-summary sec. 4.6).
