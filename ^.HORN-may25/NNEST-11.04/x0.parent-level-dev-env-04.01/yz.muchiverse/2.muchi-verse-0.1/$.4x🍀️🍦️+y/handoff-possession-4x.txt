2. THE CONFIG-DRIVEN "FIXED vs FREE" MECHANISM (sec. 31.4) - BUILT, ONE
   SIDE PROVEN, OTHER SIDE NOT YET EXERCISED
========================================================================
pieces/system/possession_config.txt (mode=free|fixed,
fixed_target_id=<id>) exists in all four $.4x projects now. The
force-clamp code (choice.c, right after possessed_id is read) is
IDENTICAL in all four. free-mode has been proven working in civ-pal/
angler-empires/muchimon-pal; fixed-mode has been proven working in
pal-craft. What has NOT been tested: flipping an already-fixed
project's config to free (or vice versa) at runtime and confirming the
swap actually takes effect with zero code changes - the mechanism
SHOULD just work (same clamp code path, just reading a different config
value), but "should just work" isn't the same as verified. Worth a
quick real test before trusting it blind if this ever matters for real
debugging.

3. JOB DESIGNATION + IDLE-LABOR AI FOR ANGLER-EMPIRES - BUILT AND
   LIVE-VERIFIED END-TO-END (2026-07-21, later same session - this
   WAS "not started" a few paragraphs below when this doc was first
   drafted; that framing is now stale, kept only for its own real
   design citations)
========================================================================
Built: pieces/registry/jobs/job_types.txt (one row: dig), ops/
designate.c (queues a job at xlector's current position - a real
"designate_dig" METHOD on xlector's own piece.pdl, digit-selected then
Enter, NOT the unconditional bare-Enter possess check - see the real
bug this surfaced, next paragraph), ops/tick_jobs.c (assigns the
nearest idle angler whose role matches, walks it one tile per real
turn toward the target - greedy, no obstacle pathfinding - then works
the job once adjacent, mutating map.txt on completion via the existing
terrain-registry glyph lookup, same file-rewrite shape every other
mutating op in this family uses). Wired into default_op.txt/pal/
main_loop.pal (tick_jobs runs every real gameplay tick, same
interact_mode==1 gate end_turn.c already uses).

REAL BUG FOUND AND FIXED while building this: ops/choice.c's own
sec. 30.1 "unconditional possess-on-Enter" check had NO guard against a
real, deliberate digit selection - it consumed EVERY Enter while
dispatch_id=="xlector", including one right after the player pressed
'3' to select "designate_dig". Fixed with one added condition
(`action_cursor < 2`) - the unconditional possess-check now only fires
on a BARE Enter (nothing digit-selected), a real digit selection always
wins. This is a genuinely reusable lesson for any FUTURE xlector method
added to any $.4x project (pal-craft/muchimon-pal's own xlector piece.
pdl currently only has "scan", so they haven't hit this yet, but WILL
the moment a second real xlector method gets added there too - check
this exact guard exists before assuming a new method's digit-dispatch
will actually fire).

Live-verified, full loop, through the real prisc+x/pal loop (not a
synthetic op call): designated a dig job on a wall tile 4 steps from
spawn, walked away, let ticks run - Grubb (the miner-role angler)
autonomously walked to the job, worked it, and the wall tile in
map.txt actually changed from '#' to '.' on completion, job piece
correctly removed, angler's own job_id cleared back to "none".

Still real, still open (not done, not silently assumed): only ONE job
type exists (dig). designate.c hardcodes "dig" rather than taking a
real job_id argument, because ops/choice.c's own generic exec_handler
dispatch wraps a piece.pdl METHOD row's handler string in ONE pair of
shell quotes - an embedded argument (e.g. "designate.+x dig") would be
treated as one broken literal path, not command+arg. A second job type
needs either its own designate_<job>.c (mechanical, same shape) or a
real fix to choice.c's own arg-passing - flagged, not decided.
Pathing is greedy/single-axis only, no obstacle avoidance - fine for
this proof, will need real pathfinding once maps have interior walls
between an angler and its job. The pending job has no visible glyph_
while_pending marker on the map yet (job_types.txt has the column,
nothing reads it) - purely cosmetic gap, not functional.

5. CAMERA-FOLLOWS-DEAD-HERO BUG - FOUND AND FIXED IN ALL FOUR PROJECTS
   (2026-07-21, later same session, direct user question: "are we sure
   we have a separate camera than view so it will scroll?")
========================================================================
Real, family-wide bug: compose_frame.c's/compose_rgb_frame.c's own 2D
viewport camera (cam_x/cam_y, VIEWPORT_W=40/VIEWPORT_H=16, clamped to
map bounds - a REAL scrolling camera, confirmed structurally present)
centered on px/py - the dead hero position that never moves in this
control model. Every map in all four $.4x projects is already WIDER
than the 40-col viewport (the shared mansion-derived map.txt is ~65-73
chars), so this bug was ALREADY LIVE, not theoretical - the camera
would have stayed frozen on the spawn point the whole time, silently
showing a static slice instead of ever scrolling. Same root cause as
the 3D camera bug fixed earlier this session ("the 3d camera needs to
move with the xelector").

FIX, applied identically to compose_frame.c AND compose_rgb_frame.c in
ALL FOUR projects (civ-pal, angler-empires, pal-craft, muchimon-pal):
camera anchor is xlector_x/xlector_y by default, OR the POSSESSED
piece's own live pos_x/pos_y while something is possessed (read fresh
from that instance's own state.txt each frame - move_player.c's own
possession-redirect block updates the possessed piece's position every
step but never touches xlector_x/xlector_y, so xlector alone would have
left the camera frozen at the possession point for civ-pal/muchimon-
pal's own direct-control genre specifically). All four compile clean;
civ-pal live-verified scrolling for real (viewport content visibly
shifted as a possessed Settler walked 25+ tiles right).

STILL NOT DONE: the 3D mirror's own camera (compose_rgb_frame.c's
render_3d_view()) still only follows xlector, not a possessed piece -
same gap named (not fixed) in that function's own header comment
earlier this session, not revisited here (this section's fix was
scoped to the 2D viewport specifically, prompted by the 2D scrolling
question).
