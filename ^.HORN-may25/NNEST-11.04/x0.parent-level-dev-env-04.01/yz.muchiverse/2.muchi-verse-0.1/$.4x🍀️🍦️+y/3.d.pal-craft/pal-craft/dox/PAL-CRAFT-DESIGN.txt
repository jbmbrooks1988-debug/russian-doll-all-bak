========================================================================
0. WHAT STAYS, WHAT CHANGES
========================================================================
KEEP AS-IS: the whole render/input/turn loop (prisc+x, renderer,
keyboard_input, move_player, end_turn, compose_frame), pickup/drop/
activity/scene_reader ops, save_game, title_input, compose_title_frame,
the registry file pattern in general. compose_rgb_frame.c ALREADY has a
working ray-marched 3D mirror (see dox/04-3d-view-and-interact-mode-
status.txt in this same project - render_mode/camera_mode, project_3d(),
raymarch_walls_3d(), voxels_16.csv per-face textures already wired) -
this is a huge head start, not a gap to fill from zero.

WHAT ACTUALLY CHANGES (the real design work, not a straight reskin):
today's engine has exactly ONE map.txt per world (a single flat 2D
grid, no Z-concept at all - grep confirms zero "z" fields in map_start/
state.txt today). A Minecraft clone needs real vertical layering
(dig down, build up). Piececraft-wraith already solved this EXACT
problem in this same family, sec. 1 ports its solution.

========================================================================
1. THE Z-LAYER MAP FORMAT (ported from piececraft-wraith, not invented)
========================================================================
Piececraft-wraith's real, working shape (read directly, not
paraphrased-then-guessed):
  - ONE FLAT 2D TEXT GRID FILE PER Z-LEVEL: maps/map_01_z0.txt,
    map_01_z1.txt, map_01_z2.txt - each file is a complete, ordinary
    glyph grid (same shape as this project's own map.txt already is),
    stacked as a Z-INDEXED SET OF FILES, not one combined 3D array in
    one file. z0 is presumably ground level, z1/z2 build upward (or
    the reverse for digging down - confirm the sign convention against
    piececraft-wraith's own compose/render code before assuming,
    ASSUMPTIONS.md doesn't state it outright).
  - assets/tiles/registry.txt: glyph=id mapping (this project's
    terrain_types.txt already has an equivalent glyph column - reuse
    terrain_types.txt's existing shape, don't adopt a second registry
    format for the same concept).
  - assets/tiles/<id>.tile.txt: per-tile properties - tile_id, label,
    rgb_top, rgb_side (NEW - this project's terrain_types.txt only has
    rgb_top today, no side-face color, because its own 3D mirror never
    needed one until now), extrude (block height, NEW), solid (NEW -
    distinct from walkable: a solid block occupies the voxel and blocks
    movement/ray-marching; walkable is about surface standability),
    walkable (already exists in terrain_types.txt).

  PORT PLAN for this project's own registries (not a rewrite of
  terrain_types.txt's existing pipe-delimited row shape - an ADDITION
  of columns piececraft-wraith proved necessary):
    terrain_types.txt gains: rgb_side(R,G,B)|extrude(float)|solid(0/1)
    appended after today's rgb_top_emoji column (append, don't
    reorder - every existing op that reads this file by fixed column
    index would break on a reorder; grep every terrain_types.txt
    reader before landing this, per this family's own "if it's not in
    a file, it's a lie, but a reordered file is a worse lie" discipline
    - not stated verbatim anywhere but consistent with every other
    append-only registry change in this family's history).

  WORLD DIRECTORY SHAPE: pieces/world_<name>/map_start/map_z<N>.txt,
  one file per Z-level (piececraft-wraith's exact convention), N=0 is
  the starting/surface level. hero/state.txt gains a pos_z field
  (today only has pos_x/pos_y). move_player.c gains up/down (dig/climb)
  as new input actions - NOT wasd, since dox 04's own status doc
  already documents wasd being fully reassigned to 3D camera pan in
  THIS project specifically (render_mode==1, camera_mode==3) - pick
  new, currently-unused keys (candidate: '<'/'>' or space/shift,
  matching this family's existing stairs-up/stairs-down glyph
  convention <>/t_stairs_up/t_stairs_down as a mnemonic, TBD with user).

========================================================================
2. BLOCK PLACEMENT/DIGGING - REGISTRY + SWITCH, REUSING PICKUP/DROP
========================================================================
Minecraft's core loop (mine a block -> get an item -> place a block
elsewhere) maps directly onto ops this project ALREADY has, not new
machinery:
  - Mining a block = pickup.c's own item-pickup path, generalized: the
    "item" produced is a block-item whose id matches the mined tile's
    own terrain id (a new pieces/registry/block_items/block_items.txt
    bank: block_id|item_id|display_name - same bank-naming-a-swappable-
    thing pattern as everything else in this family). On pickup, the
    source tile at (x,y,z) mutates to whatever "air"/empty terrain id
    this project defines (a NEW terrain_types.txt row, walkable=1,
    solid=0, glyph likely space or '.').
  - Placing a block = drop.c's own item-drop path, generalized: the
    dropped block-item mutates the TARGET tile (adjacent to the player,
    at the currently examined/faced cell - reuses interact_mode's own
    xlector cursor from dox 04 sec. 1, already fully working, to pick
    the target cell) to the terrain id block_items.txt maps that item
    back to.
  No new op needed for the CORE mine/place loop - pickup.c/drop.c
  already own "mutate a piece, mutate an inventory," this just points
  them at terrain (via the new block_items.txt bank) instead of only
  items/furniture. If pickup.c/drop.c's current code assumes items-
  only mutation paths that don't generalize cleanly, that's the one
  real coding investigation before this slice is provably true - flag,
  don't assume, per this family's "read it, don't guess" rule.

========================================================================
3. WORLD GENERATION - REGISTRY + SWITCH (SCALE_BANK's own sec. 4.5
   terrain-generation mapping, applied directly)
========================================================================
zest-er-summary sec. 4.5 already names the exact mechanism for this:
"a terrain_registry.txt naming swappable generator ops... picking a
generator becomes a registry lookup." Applied here:
  pieces/registry/worldgen/worldgen_bank.txt: id|name|module_id
    (e.g. flat_test|Flat Testbed|worldgen_flat, hand_authored|Hand-
    Authored|worldgen_none [today's existing hand-drawn map.txt files
    stay valid, unchanged, as the "no real generation" module], later:
    perlin_biomes|Perlin Biomes|worldgen_perlin - NOT built in this
    pass, named here only so the bank has a real second row to grow
    into later, same "prove one thing before generalizing" discipline).
  A per-world config picks which worldgen module_id built THIS world's
  own map_z*.txt files (write-once, at world creation - not regenerated
  every load) - same registry-vs-active-selection split as everywhere
  else in this family.
  RECOMMEND starting with worldgen_none (hand-authored, matches today's
  actual map.txt authoring workflow exactly) for the first real vertical
  slice - a real procedural generator is a separate, later design pass,
  not blocking the core dig/place/render loop above.

========================================================================
4. SCALE_BANK - CHUNK/RENDER-DISTANCE FIDELITY
========================================================================
The one Minecraft-specific fidelity question this family's SCALE_BANK
idea maps onto directly: how much of the Z-layered world gets actively
simulated/rendered at once.
    entity_type|domain|scale_level|module_id
    world|chunk_render|large|raymarch_full_radius   (near the player -
                                                       compose_rgb_frame's
                                                       existing ray
                                                       marcher, unchanged)
    world|chunk_render|small|ascii_2d_only           (far/off-screen
                                                       areas - fall back
                                                       to the existing,
                                                       already-cheap 2D
                                                       ASCII compose_
                                                       frame path, which
                                                       never reads
                                                       render_mode at all
                                                       per dox 04 sec. 2)
This reuses dox 04's own EXISTING 2D/3D split as the two scale tiers,
rather than inventing a third rendering mode - the "cheap" tier already
exists and is already proven working, this section just names it
formally as a SCALE_BANK row instead of leaving it an implicit default.
