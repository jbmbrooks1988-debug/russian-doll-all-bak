COMMON-OPS-CATALOG.txt
Written 2026-07-21, companion to pal-op-handoff.txt. This is a straight
inventory of REAL, ALREADY-BUILT, ALREADY-PROVEN ops from the OTHER muchi-
verse family (shared-ops/, 1.muchi-pal-agent🤖️/, 1.pal-chat-irc/) that the
$.4x game family (civ-pal, angler-empires, pal-craft, muchimon-pal, pal-op)
does NOT currently use, but plausibly could. Not a decision document - the
point is comparison. Every entry below says what the op does, where it
lives, and a concrete (not vague) note on what it would take/enable if
ported into one or more $.4x projects. Read yz.muchiverse/$.zest-er-summary-
FIN❤️‍🔥️+.txt for the full original context on all of these.

================================================================================
1. NETWORKING - shared-ops/palnet_peer.c
================================================================================
WHAT IT IS: one reusable, symmetric peer-to-peer companion process (NOT a
client/server split - every instance of this binary is identical). Reads
yz.muchiverse/2.muchi-verse/PAL-NET-STANDARD.txt for the full design; this
file IS that doc's reference implementation.
  Usage: palnet_peer.+x <own_kind> <project_id> <piece_id_or_-> \
                        <outbox_file> <inbox_file> [seek_kind]
  - Discovery is a flat presence-directory scan (deliberately NOT p2p-net's
    own ring/leader-election topology - this is for a small, known number
    of local nodes, not an open peer set).
  - Real TCP sockets for actual data transfer; presence/discovery itself
    is file-based.
  - CRITICAL SHAPE: it is a STANDALONE OP, never embedded in a GUI process.
    A GUI/game process never touches a socket directly - it only ever
    writes an outbox_file and reads an inbox_file, the exact same file-
    based mechanism every other piece of state in this whole family
    already uses. palnet_peer.+x is launched as a companion process
    (persistent for an "always publishing" node, short-lived for a single
    transfer) and does 100% of the actual networking on the game's behalf.
  - Already proven working: zoo_window.c/egg_window.c use it today for
    live pet drag-and-drop export/import between two running instances.

WHERE IT COULD GO IN $.4x (concrete, not hypothetical):
  - civ-pal: multiplayer would mean two running civ-pal instances trading
    unit/tile state - palnet_peer.+x's own outbox/inbox shape is already
    exactly "hand a piece's state.txt to another running instance," which
    is what civ-pal's own spawn_unit.c-created instance dirs already look
    like. No new networking code needed, just an outbox/inbox convention
    for units, matching pet_export.c/pet_import.c's own shape (see sec. 2).
  - muchimon-pal: trading a captured muchimon between two players is
    LITERALLY the same shape as the egg/zoo pet-export use case already
    proven - a muchimon instance dir is already a self-contained piece,
    same as a pet.
  - angler-empires: lower priority (DF-style single-colony sim doesn't
    obviously need cross-instance networking yet) but the SAME mechanism
    would apply if inter-colony trade/diplomacy is ever wanted.
  - pal-craft: a shared-world multiplayer voxel session is the most
    complex case (continuous position sync, not a one-shot export/import)
    - palnet_peer.+x's own "persistent for a publish-forever node" mode is
    the right starting shape, but this would need real design work first,
    not a direct port.
  WHAT PORTING ACTUALLY TAKES: copy palnet_peer.c in as a local copy (same
  "duplicate, don't share" convention every $.4x project already follows
  for system/*.c), then write ONE new op per project that (a) picks an
  instance to export, writes its state.txt-equivalent to an outbox_file,
  launches palnet_peer.+x, and (b) on the receiving side, reads whatever
  lands in the inbox_file and materializes a new instance dir from it
  (basically a "spawn from received data" variant of the existing spawn_
  <kind>.c ops). This is a real, scoped, one-project-at-a-time task, same
  "prove one thing before generalizing" discipline as everywhere else in
  this family.

2. NETWORKING SUPPORT - shared-ops/pet_export.c / pet_import.c
================================================================================
WHAT THEY ARE: the actual "serialize a piece to a transferable file" /
"materialize a piece from a received file" pair that sits ON TOP of
palnet_peer.c's raw transport - these are the ops that know WHAT a pet's
state actually looks like; palnet_peer.c itself is content-agnostic.

WHERE IT COULD GO IN $.4x: this is the missing half of sec. 1's own civ-pal/
muchimon-pal notes above - pet_export.c/pet_import.c are the concrete
TEMPLATE for the "export a unit/muchimon instance"/"import a received
unit/muchimon instance" ops each project would need to write. Read these
two files FIRST before writing any $.4x equivalent, rather than re-deriving
the shape from scratch.

3. AI PROVIDER ARCHITECTURE - 1.muchi-pal-agent🤖️/ops/
================================================================================
3.1 The registry+switch pair
  pieces/registry/models/model_list.txt (pipe-delimited: id|provider_kind|
  api_url|model_name, or repurposed fields for iqabod - see that file's own
  header) is the BANK; ops/switch_model.c is the SWITCH (looks up an id,
  rewrites state.txt's current fields, done - a rebuild-free behavior
  change). This is the EXACT same registry+switch shape !.pal-standards.txt
  already documents for the $.4x family (bank_rel_path/known_projects.txt/
  possession_config.txt etc.) - not new machinery, but a concrete, already-
  working REFERENCE IMPLEMENTATION of it for "which AI behavior is active."

WHERE IT COULD GO IN $.4x: angler-empires' own idle-labor AI (ops/
  tick_jobs.c - nearest-matching-role assignment, greedy walk, no
  pathfinding) is currently ONE hardcoded routine. Per zest-er-summary's own
  sec. 4.4 (written for mutaclysm, equally true here): replace the single
  hardcoded "assign nearest idle angler" decision with a registry (e.g.
  angler_ai_behaviors.txt: id|kind|param - "nearest"|greedy|-, "role_
  priority"|weighted|<role_order>, etc.) + a switch op, so a colony's own
  labor-assignment STRATEGY becomes swappable without touching tick_jobs.c
  itself. Same applies to muchimon-pal's wild encounter logic (currently
  a flat 1-in-5 roll always spawning sparkit) - a real encounter-table
  BANK (already named as a gap in session-handoff.txt) is the exact same
  pattern, not a new one.

3.2 The tick-driven poll pattern
  ops/check_response.c (self-filters: no-op unless ai_state=THINKING) and
  1.muchi-pal-agent🤖️'s own ops/irc_agent_poll.c (no-op unless actually
  active) are the reference shape for "cheap check every tick, real work
  only when something is actually in flight."
  ALREADY INDEPENDENTLY PRESENT IN $.4x: angler-empires' own ops/
  tick_jobs.c already follows this exact shape (called every turn from
  main_loop.pal, does real work only for angler/job pairs that actually
  need it) - this is a validation signal, not a gap. Worth knowing so
  nobody "introduces" this pattern into angler-empires thinking it's new;
  it already independently converged on the same design.

3.3 The multi-provider request/response split
  send_message.c builds one of 4 request shapes (ollama/gemini/llamacpp/
  iqabod) depending on provider_kind; check_response.c parses whichever
  shape was actually sent. Non-blocking by design - forks a child, records
  its PID in state.txt, returns immediately; check_response.c's own tick
  polls kill(pid, 0) for liveness (can't waitpid() since the forking
  process already exited) rather than blocking the whole game loop on a
  network call.
  WHERE IT COULD GO IN $.4x: this is the CONCRETE mechanism for adding any
  kind of "smart" AI to a $.4x project without freezing the game loop on
  it - e.g. if angler-empires' own AI ever wanted an LLM-backed decision
  (not just greedy/nearest logic) for something higher-level like fortress
  strategy, this fork+PID+poll pattern is exactly how to add it without
  blocking turn advancement. Not needed for anything currently planned,
  but the RIGHT shape if "smarter than greedy" AI is ever actually wanted.

3.4 The tool-calling convention (gemma "TOOL: <verb> <args>" - see
    pal-op-handoff.txt sec. 4.1 for the fuller writeup)
  A plain-text keyword convention (no JSON needed) that any model without
  native tool-calling can emit, parsed by a small dedicated parser, then
  dispatched to existing provider-agnostic tool ops (file_ops.c, edit_
  file.c, cmd_exec.c, list_dir.c, search_in_files.c, web_search.c).
  WHERE IT COULD GO IN $.4x: this IS the mechanism that already lets
  pal-agent drive pal-op today (see pal-op-handoff.txt sec. 4.1). The SAME
  parser/dispatch shape, with a different verb set, is exactly how an
  agent could drive/playtest any of the 4 GAME projects too - e.g.
  TOOL: move_player <direction>, TOOL: designate_job <type> <x> <y>
  (angler-empires), TOOL: capture <target_id> (muchimon-pal) - each verb
  mapping onto that project's own existing choice.c/move_player.c dispatch
  the same way pal-op's own verbs would map onto map_edit_input.c. Nothing
  built yet for any $.4x game; flagging because it's the same reusable
  parsing-layer investment regardless of which project it's aimed at.

4. CHAT/MESSAGING PRIMITIVES - 1.pal-chat-irc/ops/
================================================================================
chat_create_user.c / chat_post_message.c (direct_ops backend - reads/writes
rooms/<room>/messages.txt directly, no chtpm/UI involvement needed at all)
are the exact shape irc-agent-0000 uses to act as a bot participant without
a human ever seeing its own UI.
  WHERE IT COULD GO IN $.4x: if any $.4x project ever wants an in-game
  "chat" or "message log broadcast to other running instances" feature
  (e.g. a shared angler-empires colony-status feed, or a muchimon-pal
  in-game announcement system), chat_post_message.c's own direct-file-
  append shape (rooms/<room>/messages.txt) is the simplest possible
  reference - much simpler than palnet_peer.c's own live-socket approach,
  appropriate when the "networking" need is really just "append to a
  shared log another process/instance also tails," not live bidirectional
  transfer.

5. EVENT/BLOCK-STYLE AUTHORING - pal-op's OWN new event editor (this
   session, NOT from the other family - listed here because it's the
   right generalization target per the user's own "events/scratch
   blocks... use them in the most projects possible" ask)
================================================================================
WHAT EXISTS NOW: pal-op's ops/map_edit_input.c has a small, fixed, digit-
selected catalog of 3 canned event types (message/teleport/spawn) that an
author places onto a tile, written as a real x|y|op_id row into the TARGET
project's own pieces/<world_dir>/map_start/events.txt. This is a small,
real "Scratch-style block" system already - choose a canned behavior block,
place it, done, no code written by the author. See pal-op-handoff.txt sec.
2.5/3.1 for the full status (author-time only right now, nothing reads it
back at runtime yet).

THE ACTUAL GENERALIZATION OPPORTUNITY (direct answer to "incorporate these
events/scratch blocks... into the most projects possible"): the highest-
leverage move is NOT to rebuild this event system separately inside each
of the 4 game projects. It's to:
  1. Build ONE shared op - e.g. dispatch_event.c - that any project can
     drop in locally (same duplicate-per-project convention as everything
     else), which reads that project's OWN events.txt, checks whether the
     mover's new (x,y) has a row, and dispatches by op_id:
       message  -> append to message_log.txt (every $.4x project already
                   has this file and convention)
       teleport -> rewrite the mover's own pos_x/pos_y fields directly
       spawn    -> system() call to that project's own spawn_<kind>.+x,
                   the EXACT pattern pal-op's own map_edit_input.c already
                   uses to spawn instances from the editor side
  2. CORRECTED 2026-07-21 (direct user question: "do u understand that
     rpgmaker events are meant to be built 'ON PAL' (invisible to the
     average player)?"): dispatch_event.c must NOT be a function called
     from inside each project's own move_player.c - that threads event
     logic through hand-written movement code, exactly the opposite of
     "invisible to the player, a separate layer the engine runs." It
     should be its OWN standalone op, registered in default_op.txt, added
     as a NEW LINE in each project's own main_loop.pal right after
     move_player - the same shape angler-empires' own tick_jobs is
     already called right after end_turn. See pal-op-handoff.txt sec. 3.1
     for the full corrected plan (exact state fields, exact pal/main_
     loop.pal diff, muchimon-pal chosen as the first project).
  3. This closes pal-op-handoff.txt's own sec. 3.1 gap (runtime event
     triggering) for ALL FOUR projects in one pass, rather than as four
     separate, project-specific efforts - because the CATALOG (message/
     teleport/spawn) and the STORAGE FORMAT (events.txt) are already
     project-agnostic by construction (pal-op writes the same row shape
     regardless of which project it's editing).
  BUILD ORDER: pick ONE project (muchimon-pal is the best fit - it
  already has message_log.txt and a working capture/attack dispatch
  pattern in choice.c to model dispatch_event.c's own "read a row, match
  by id, act" shape against), prove dispatch_event.c works end-to-end
  there, THEN copy it into the other 3 - same "prove once, then spread"
  discipline as every other pattern in this family.
  FUTURE EXTENSION (not now): once this works, "op selection" could grow
  beyond the 3 canned ops (op-ed's own real Phase A vision) - but per
  SCALE_BANK's own "prove one thing before generalizing" rule (zest-er-
  summary sec. 4.6), get 3 canned ops working at runtime in one project
  before adding a 4th type or trying to generalize the catalog itself.
