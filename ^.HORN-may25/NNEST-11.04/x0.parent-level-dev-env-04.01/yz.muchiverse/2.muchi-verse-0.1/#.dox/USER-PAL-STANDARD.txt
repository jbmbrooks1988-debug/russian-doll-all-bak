USER-PAL STANDARD - architecture for a single, cross-app identity/
login registry living in yz.muchiverse/2.muchi-verse/user-pal/ (an
existing, empty placeholder directory - confirmed empty before writing
this doc, not assumed). Written 2026-07-19 per direct user instruction:
"i want the login screen to be the only thing on the screen. the
reason? i wanna create the ability for an external login in the
'user-pal' directory, that will let user simply 'login, or logout'
save logged in user data in one place and every app with a login
screen can auto fill or something, and that is the location where all
the user data, wallet data, games ownership, pet ownership etc should
be stored... i like our modules to be flexible enough that they can
work the way they currently works, or work using user-pal as well."
This doc is architecture + a v1 scope, not a finished implementation -
see sec. 5 for what's deliberately not built yet.

========================================================================
0. WHY THIS SHAPE
========================================================================
Every app in this family (pal-forum, pal-chain, pal-chat-irc, ...)
currently owns its own, separate `users/<user_id>/` identity - a forum
account and a chain wallet share nothing today, not even a user_id
namespace. The user's own request has TWO parts that must not be
conflated:

  (a) a real, standalone identity/login REGISTRY (create account, log
      in, log out - "one place") that other apps can OPTIONALLY read
      from to auto-fill their own, still-separate login screens.

  (b) a longer-term goal of user-pal eventually being the actual
      storage location for wallet/pet/game-ownership data itself, not
      just identity.

v1 (this doc) builds ONLY (a). (b) is real but explicitly deferred -
see sec. 5 - because it would mean pal-chain's own wallets/ and
pal-forum's own users/ stop being that app's own local, "solo-
shippable" data (GRAND-ARCHITECTURE.md's own zippable/runnable-alone
principle for every project in this family) and start being a HARD
cross-project dependency, which is a much bigger structural change
than "add an auto-fill." Building (a) first, live-verifying it, and
only then deciding how much of (b) to take on, matches this family's
own established pattern of shipping the real small thing before the
speculative large one (see PAL-FORUM-STANDARD.txt sec. 6, PAL-REFACTOR-
STANDARD.txt's own "changes HOW never WHAT" caution against building
ahead of a verified need).

========================================================================
1. IDENTITY REGISTRY
========================================================================
Location: user-pal/users/<user_id>/profile.txt (key=value, same shape
as every other app's own profile.txt in this family):
    user_id=<chosen handle>
    display_name=<free text>
    created_at=<unix epoch>

No password in v1 - matches pal-forum's own forum_create_user.c
precedent exactly (local-first, no auth layer invented where none was
asked for). user_id is the ONE thing every app-specific account in
this family could in principle share, but v1 does NOT enforce or
require that pal-forum's/pal-chain's own user_ids match a user-pal
user_id - see sec. 4.

Op: ops/userpal_create_account.c - `userpal_create_account.+x
<user_id> <display_name>` - refuses if the user_id directory already
exists (same collision rule as forum_create_user.c/
chain_create_wallet.c).

========================================================================
2. CURRENT LOGIN STATE - user-pal/current_login.txt IS NOT A PER-
SESSION FILE, ON PURPOSE
========================================================================
Every other app in this family keeps a per-session "who's logged in
right now" file (pal-forum's own net/session.txt) that lives INSIDE
that invocation's own session directory (pal-standards.txt sec. 23)
and is thrown away when that session exits - correct for THAT file,
because it answers "who is this one running window logged in as,"
and two concurrent windows must never share that answer.

user-pal/current_login.txt answers a DIFFERENT question: "which
identity did the user last log into user-pal itself as, on this
machine, so any app that starts up later can offer to auto-fill it."
That has to OUTLIVE any single session, or "save logged in user data
in one place" (the user's own words) would mean nothing - a value
that vanishes the moment one terminal window closes isn't "saved
anywhere." So this file lives at user-pal's own REAL project root,
never inside a pieces/sessions/<id>/ directory, and is treated as
SHARED, PERSISTENT DATA exactly like pal-forum's own users/ directory
is (pal-standards.txt sec. 23's own "what stays shared" list) - if
user-pal ever grows session isolation for its own chtpm UI (it
should, being a new project - sec. 3), current_login.txt gets
symlinked INTO each session dir read-only, never copied, never itself
session-scoped.

    current_login.txt:
        current_user_id=<user_id, or empty/absent if logged out>
        logged_in_at=<unix epoch>

Ops:
  ops/userpal_login.c - `userpal_login.+x <user_id>` - refuses if the
    user_id doesn't exist under users/ (same shape as
    forum_switch_user.c), else overwrites current_login.txt.
  ops/userpal_logout.c - `userpal_logout.+x` (no args) - overwrites
    current_login.txt with an empty current_user_id.
  ops/userpal_whoami.c - `userpal_whoami.+x` (no args) - prints
    current_user_id, or "none" if logged out. Exists mainly so a human
    (or a shell script in another project's own build/test flow) can
    check the current state without hand-parsing the file; the real
    cross-app read path (sec. 4) reads the file directly, not this op,
    since an op only ever runs inside ITS OWN project's pal runtime
    (PRISC_PROJECT_ROOT scoped to that one project) - there is no
    mechanism for pal-forum's own pal script to invoke an op living in
    a sibling project's own ops/ tree.

========================================================================
3. user-pal's OWN chtpm UI
========================================================================
user-pal gets a real, minimal chtpm UI of its own (login.chtpm: two
`<cli_io>` fields - user_id_input, display_name_input - plus
${piece_methods} for LOGIN/CREATE ACCOUNT/LOGOUT), built the SAME way
as every other project in this family: real `<module>` persistent
loop, real `<cli_io>`, real `${piece_methods}`, zero hardcoded menus
(pal-standards.txt sec. 0-CORRECTED, sec. 12). Since this is a brand
NEW project being built after session isolation was already proven
(pal-standards.txt sec. 23), it gets session isolation from day one in
its own button.sh, copying pal-forum's own button.sh `run` action
shape exactly rather than retrofitting it later - direct user
instruction: "lets build wise of that and add it to our standards as
we set out to do the irc" (i.e. build new things the RIGHT way from
the start, the way pal-chat-irc is also meant to be built).

user-pal's own users/ directory (identity data) and current_login.txt
(sec. 2) are SHARED, PERSISTENT data - symlinked into each session
dir, never copied, never deleted on session exit. Only the usual
ephemeral UI state (keyboard history, interact_relay, gui_state,
per-session net/ scratch if user-pal ever needs its own palnet_peer
instance) is session-scoped.

user-pal is otherwise a completely ordinary, standalone,
independently runnable project - `cd user-pal && ./button.sh run`
works with zero other projects present, same "solo-shippable"
guarantee every project in this family has (sec. 0's own resolution
of the tension between that guarantee and cross-app integration: the
INTEGRATION is optional, user-pal itself is not optional-shaped).

========================================================================
4. THE INTEGRATION PATTERN - HOW OTHER APPS "CAN WORK THE WAY THEY
CURRENTLY WORK, OR WORK USING USER-PAL AS WELL"
========================================================================
Direct user instruction: "i like our modules to be flexible enough
that they can work the way they currently works, or work using
user-pal as well." That means the integration must be:
  - OPT-IN: an app with no sibling user-pal directory (a solo-shipped
    zip of just pal-forum, say) must work exactly as it does today,
    with zero errors, zero missing files, zero degraded behavior
    beyond simply not getting the auto-fill.
  - AUTO-FILL, NEVER AUTO-LOGIN: user-pal having a current_user_id
    pre-fills that app's OWN login screen's user_id field with that
    value - it does NOT skip the login screen, does NOT silently log
    the user into that app, and does NOT assume the app-specific
    account with that user_id even exists yet. The user still clicks
    Log In (or Create Account, if this is their first time in that
    particular app) same as always - matches sec. 1's own point that
    v1 does not unify user_id namespaces across apps, only offers a
    convenient starting guess.
  - NEVER A HARD DEPENDENCY: no app's own build.sh, default_op.txt, or
    ops may fail, warn, or refuse to run because user-pal is missing.
    The read is a plain file-existence check, done ONCE, at session
    start, not woven into the app's own per-keystroke or per-request
    logic.

THE REAL MECHANISM (reference implementation: pal-forum/button.sh,
sec. 6): a sibling app's own button.sh `run` action, AFTER creating
its session directory but BEFORE launching chtpm_parser_pal, checks
for `../user-pal/current_login.txt` relative to its own SCRIPT_DIR. If
present and non-empty, it reads current_user_id and seeds that app's
OWN gui_state.txt (projects/<app>/manager/gui_state.txt) with
`user_id_input=<that value>` - the SAME key chtpm_parser_pal.c's own
sync_cli_input_from_gui_state() already reads on every render
(shared-ops/chtpm_parser_pal.c line ~255-280, confirmed by direct
source read: it restores any cli_io element's own input_buffer from
gui_state.txt keyed by that element's target_id, BEFORE the user types
anything). No chtpm_parser_pal.c changes needed at all - the existing
gui_state.txt restore path IS the auto-fill mechanism, seeding it one
line earlier than a real keystroke would have. If the file is absent,
this is a no-op and the field starts empty exactly as it does today.

This is a BUTTON.SH-LEVEL integration, not a compose_frame/menu_input-
level one, specifically because button.sh already runs once per
session, already has the real SCRIPT_DIR, and is the one place a
missing-sibling-directory check is naturally a no-op rather than
something every render call has to re-guard.

========================================================================
5. DEFERRED TO A LATER PHASE - NOT V1
========================================================================
- Unifying user_id namespaces across apps (so "jb" in pal-forum and
  "jb" in pal-chain are provably the same person, not just the same
  string).
- Centralizing actual wallet balances / pet or game ownership INTO
  user-pal's own storage, replacing pal-chain's own wallets/ and
  whatever future muchi-pals/zoo_0000 ownership files with references
  into user-pal instead of each app's own local copy. This is the
  user's own longer-term goal ("that is the location where all the
  user data, wallet data, games ownership, pet ownership etc should be
  stored") but is a real, hard cross-project dependency the moment any
  app REQUIRES it rather than merely reading an optional auto-fill
  value - it breaks solo-shippability (sec. 0) unless and until that
  tradeoff is deliberately made, app by app, with its own doc section
  the way this one exists for identity/login. Not attempted here.
- Auto-login (vs. auto-fill) - explicitly rejected in sec. 4, not a
  "not yet," a real design decision: a saved identity should never be
  able to silently act as a saved credential for every app on the
  machine.
- Password/auth of any kind - v1 has none, matching every other app in
  this family's own v1 (sec. 1).

========================================================================
6. REFERENCE IMPLEMENTATION STATUS - BUILT, THEN REVERTED (2026-07-20)
========================================================================
pal-forum/button.sh and pal-chat-irc/button.sh both implemented sec.
4's integration pattern (one file-existence check + one gui_state.txt
seed line, placed after session-dir creation and before
chtpm_parser_pal launch) and it worked exactly as designed - the
User ID field showed the last user-pal identity pre-filled on first
render, confirmed live.

REMOVED from both, same day, on direct user correction: "i dont want
it to default to saying 'jb'... default still has 'jb' in it for some
reason" - said TWICE, the second time after the field-label fix
(sec... see pal-standards.txt's own cli_io rendering note) had already
addressed the "which field is this" ambiguity sec. 4 was partly
defending against. This is a genuine "don't want the feature," not a
display nit - auto-fill silently carrying a PREVIOUS test identity
into a fresh login screen was confusing/unwanted in practice, however
well-reasoned the design was on paper.

The DESIGN (sec. 2-4 above) is kept documented as real, working,
available-if-wanted-later - not deleted, since it wasn't a bug, it was
a direct product decision to not have this specific UX right now. Any
future re-adoption should probably make it explicitly opt-in (an env
var or a real "remember me" toggle a user asks for), not default-on
whenever user-pal happens to have someone logged in, which is the
shape that was tried and rejected.
