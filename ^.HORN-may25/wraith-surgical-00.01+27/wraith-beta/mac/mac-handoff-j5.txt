## 5. GUIDANCE: TPMOS STANDARD PIPELINES
Do not reinvent the wheel. Study these existing, working TPMOS implementations to understand the expected input-render cycle:

### 1. `projects/fuzz-op/`
- **Why:** This is the gold standard for canonical input history ownership.
- **Study:** Observe how `fuzz-op_manager.c` polls history, mutates state, and triggers the marker *atomically*.

### 2. `projects/op-ed/`
- **Why:** This is the gold standard for Parser-owned visible frame truth.
- **Study:** Observe how the Parser reads state and how the Manager polls history without competing with the Parser for "bridge" logic.

### 3. Key TPMOS Principle: The Marker Contract
- **Contract:** Any state change MUST be followed by a growth in a marker file (`frame_changed.txt`).
- **Standard:** The Renderer (or Parser-triggered renderer) MUST only pulse when the marker size changes. 
- **Rule:** If you see "identical frame" pulses, you have violated the **Marker-Driven Only** rule. Check for extra `dirty=1` assignments or race conditions where the Composer writes stale data *after* the Parser has already composed.

## 6. THE ARCHITECTURAL PARADOX
We have achieved **Architectural Parity** (the road network is standard), but we have not yet achieved **Runtime Parity** (the data flow is blocked).

- **The Trap:** When architecture is fixed but behavior is stubborn, we are dealing with **Hidden State Pollution** or **Logic Traps** that don't violate standards but break execution.
- **Hypothesis:** 
  1. **Atomic Update Failure:** The Manager might be updating state files non-atomically. If the Parser reloads while the Manager is halfway through a file write, it sees garbage or stale data.
  2. **Initialization Race:** `ensure_default_state` or `normalize_boot_state` might be clobbering the `active_gui_index` *after* the input has been processed.
  3. **Logic Loop:** `route_input` is being called, but the specific conditional branch for the key is not executing as expected, or `g_active_gui_index` is being reset elsewhere in the loop.

**Guidance:** Do not look for structural "bridge" issues anymore. Focus entirely on the **atomic integrity of the Manager's update loop** and ensure that `active_gui_index` cannot be overwritten by initialization functions during the update cycle.

## 7. TPMOS GOLD STANDARD: FUZZ-OP INPUT POLLING
To solve the "No Keys" issue, the next agent MUST implement the input polling pattern used by `fuzz-op` (the gold standard for TPMOS input).

### THE FUZZ-OP PATTERN:
`fuzz-op` uses dedicated input threads (`input_thread` and `gltpm_input_thread`) that strictly adhere to:
1. **Direct History Polling:** They poll history files (`history.txt`) without passing through an intermediate bridge.
2. **Robust Truncation Handling:**
   ```c
   if (st.st_size > last_pos) { ... }
   else if (st.st_size < last_pos) last_pos = 0; // RESET ON TRUNCATION
   ```
3. **Atomic Input Routing:** They call `route_input()` directly inside the polling loop, ensuring input is processed as soon as it appears in the history file.

### ACTIONABLE GUIDANCE FOR NEXT AGENT:
- **Refactor `history_thread` in `wraith-pm_manager.c`:** Use the `fuzz-op` thread pattern. It is proven to work.
- **Remove Logic Fragmentation:** The Manager must be the sole consumer of `pieces/keyboard/history.txt`. If you have multiple threads polling (e.g., one for raw keys, one for commands), ensure they do not compete for file locks.
- **Traceability:** Keep the debug logging enabled until the key injection path is definitively proven. The current log `[DEBUG] route_input parsed key 1003` is evidence that the input *reached* the Manager—the failure is likely inside the `route_input` logic itself or the way the Manager mutates the session files afterward.
