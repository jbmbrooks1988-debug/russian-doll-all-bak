# TPMOS BEHAVIORAL DISCIPLINE & STABILITY (tpmos-discipline-clues-j5.txt)
Date: 2026-06-05

## 1. THE ARCHITECTURAL PARADOX
Wraith's instabilities are not caused by multi-process concurrency. They are caused by **Tight Coupling**.
Standard TPMOS is stable because it is a **loosely-coupled asynchronous system** where each process operates as an independent agent linked by unidirectional pipes (Files/Markers).

Wraith became unstable by attempting to force a **tightly-coupled synchronous system** into an asynchronous, multi-process environment.

## 2. THE THREE RULES OF DISCIPLINE

### Rule 1: Strict Ownership of State & Truth
- **Manager:** The ONLY process allowed to mutate state files (`state.txt`, `nav_state.txt`).
- **Parser:** The ONLY process allowed to compose the visible frame (`current_frame.txt`).
- **Renderer:** The ONLY process allowed to output to the terminal.
- **NEVER CROSS THESE LINES.** The Parser should never attempt to modify Manager state files, and the Manager should never attempt to compose the final frame.

### Rule 2: The Marker Contract
- State mutation MUST be atomic.
- State mutation MUST be followed by a single write-append to a marker file (e.g., `frame_changed.txt`).
- The listener (e.g., Parser) MUST only react when the marker file's size increases (`fstat` growth).
- Violating this (e.g., calling `render()` directly inside the Manager's input loop) creates the "Two Identical Pulses" race condition.

### Rule 3: Robust History Polling (The `fuzz-op` Standard)
When polling history files, always use the robust truncation handling pattern found in `fuzz-op`:

```c
// Reference: projects/fuzz-op/manager/fuzz-op_manager.c (input_thread)
if (st.st_size > last_pos) {
    // Process new input
} else if (st.st_size < last_pos) {
    last_pos = 0; // RESET ON TRUNCATION
}
```
