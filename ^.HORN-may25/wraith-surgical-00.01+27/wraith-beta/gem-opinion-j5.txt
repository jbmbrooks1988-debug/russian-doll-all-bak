# WRAITH STABILITY ANALYSIS (gem-opinion-j5.txt)
Date: 2026-06-05

## The Core Problem
Wraith is currently caught in an **Architectural Paradox**. We have successfully adopted the TPMOS "road network" (manager-parser separation), but we are failing to achieve "runtime honesty" (data integrity).

The root cause of the current instability (e.g., input received but state not updated, "Two Identical Pulses" rendering race) is not multi-process concurrency, but rather **Tight Coupling** where it should be **Loose Asynchrony**. The system is violating the core TPMOS principle that process agents must communicate *only* through unidirectional pipes (files and markers).

## The Definitive Fix Path
For a future agent to "fix this once and for all," they MUST enforce the following, starting immediately:

### 1. Strict State/Frame Ownership (Rule 1)
- **Manager:** The ONLY process allowed to mutate state files (`state.txt`, `nav_state.txt`).
- **Parser:** The ONLY process allowed to compose the visible frame (`current_frame.txt`).
- **Violation Check:** If the Parser is modifying *any* Manager-owned state file, or the Manager is performing *any* rendering, this is a fatal flaw that MUST be refactored.

### 2. The Marker Contract (Rule 2)
- State mutation MUST be atomic.
- State mutation MUST be followed by a single write-append to the marker file (`frame_changed.txt`).
- **Eliminate Eager Rendering:** The Parser MUST remove all instances of `compose_frame()` triggered by key processing. The Parser MUST *only* react to growth in `frame_changed.txt`. This eliminates the "Two Identical Pulses" race condition.

### 3. Robust Polling (`fuzz-op` Standard)
- Replace all current polling logic with the `fuzz-op` pattern.
- This includes robust truncation handling (checking if `st.st_size < last_pos` and resetting).

### 4. Compositor Migration (Architectural Goal)
- The current `wraith_composer.+x` fork-and-exec model is a performance bottleneck and a source of race conditions.
- The path forward is to move taskbar/window-registry logic into variables managed by the Manager, and let the Parser render these variables directly within `current_frame.txt`.

## TPMOS Standard Resolutions
*Following the directive to "do whatever TPMOS does":*

1.  **Atomic Persistence:** Wraith MUST adopt the TPMOS atomic write pattern: write state to a temporary file (`.tmp`), then perform a POSIX `rename()` to the target file (`nav_state.txt`). Direct truncation/overwriting is explicitly prohibited.
2.  **Manager Loop:** Wraith MUST implement the standard TPMOS `main()` loop structure with explicit `usleep(active ? 16667 : 100000)` throttling based on focus/input status.
3.  **Compositor Migration:** Taskbar and window registry logic will be transitioned to **KVP variables** published by the Manager in `gui_state.txt`. The Parser will interpret these variables at runtime during its main composition loop, eliminating the need for `wraith_composer` executable altogether.

## Actionable Code Modification Steps
*Prioritized path to runtime honesty:*

1.  **Phase A: Atomic State Updates (High Priority)**
    - Identify all `fopen(..., "w")` calls in `wraith-pm_manager.c` that modify `nav_state.txt` or `state.txt`.
    - Refactor to `fopen(..., "w")` on a `.tmp` file, then `rename()` to the final destination.
2.  **Phase B: Eliminate Eager Rendering (High Priority)**
    - Search for `compose_frame()` inside `wraith_parser.c` (specifically within input handling callbacks).
    - Remove these calls completely.
    - Ensure the Parser's main loop *only* calls `compose_frame()` when `fstat()` detects growth on `frame_changed.txt`.
3.  **Phase C: Polling Loop Refactor (Medium Priority)**
    - Update `history_thread` in `wraith-pm_manager.c` to use the `fuzz-op` truncation-safe polling pattern (`st.st_size < last_pos` check).
4.  **Phase D: Decommission Compositor (Future Goal)**
    - Replace `fork()`/`exec()` calls for `wraith_composer.+x` in the Manager with logic that updates `gui_state.txt` with window/taskbar data.
    - Update the Parser's composition function to read these new variables from `gui_state.txt`.
