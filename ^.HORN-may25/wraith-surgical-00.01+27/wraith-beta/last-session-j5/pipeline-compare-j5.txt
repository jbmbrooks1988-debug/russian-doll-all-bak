WRAITH PIPELINE COMPARISON J5
Date: 2026-06-05

Purpose:
To compare the Wraith input-to-display pipeline against working TPMOS ASCII
standards (fuzz-op, op-ed) and identify why Wraith produces stale output.


1. The TPMOS Standard Pipeline (fuzz-op, op-ed)

Flow:
[Input] -> [Manager] -> [Marker] -> [Parser] -> [Renderer]

Detailed Steps:
1. Input: User presses key; key appended to pieces/apps/player_app/history.txt.
2. Manager: Polls history; mutates internal state (e.g., last_key = "UP").
3. State Write: Manager writes to pieces/apps/player_app/manager/state.txt.
4. Marker: Manager appends to pieces/display/frame_changed.txt.
5. Parser: Sees marker; calls load_vars().
6. Load Vars: Parser reads player_app/manager/state.txt (gets fresh last_key).
7. Compose: Parser renders the .chtpm layout using fresh variables.
8. Output: Parser writes to pieces/display/current_frame.txt and pulses renderer.

Result:
High-speed, variable-driven rendering. The parser is the ONE source of truth
for the visual frame.


2. The Current Wraith Pipeline

Flow:
[Input] -> [Manager] -> [Composer] -> [Marker] -> [Parser] -> [Renderer]

Detailed Steps:
1. Input: Same as standard (player_app/history.txt).
2. Manager: Polls history; updates projects/wraith-pm/session/state.txt.
3. Composer: Manager FORKS projects/wraith-pm/ops/wraith_composer.+x.
4. Composer Logic: Reads session/state.txt, BUT also polls global keyboard
   history and OVERWRITES current_key (Split-brain bug).
5. Frame Write: Composer writes a static text block to manager/view.txt.
6. Marker: Manager checks if view.txt hash changed, then hits display marker.
7. Parser: Sees marker; loads variables.
8. Compose: Parser renders wraith-shell.wrai, which just embeds ${module_path}
   (the static view.txt).
9. Output: Parser writes to pieces/display/current_frame.txt.

Result:
Stale output. The "Composer" step introduces latency and a competing truth.
If the Composer's hash-check fails or it reads stale global history, the
Parser simply re-renders a stale text block.


3. Key Pipeline Dissonances

Dissonance A: Split Truth
Standard: Parser owns the layout and variables.
Wraith: Composer tries to be a "mini-parser" that pre-renders a text frame.

Dissonance B: Redundant Markers
Standard: Manager hits marker immediately after state change.
Wraith: Manager waits for a forked process (Composer) to finish, then hashes
        files, then hits marker. This is slow and prone to "no-change" drops.

Dissonance C: Variable Desync
Standard: Parser loads variables directly from the Manager's state file.
Wraith: Parser loads a "view" variable which is a static snapshot of what the
        Composer thought the state was 100ms ago.


4. Alignment Prescription

To fix Wraith and make it as reliable as op-ed/fuzz-op:

1. REMOVE the Composer from the real-time path.
   - The Manager should NOT fork wraith_composer on every keypress.
   - The Manager should just update state.txt and hit the marker.

2. ENHANCE the Parser/Layout.
   - The wraith-shell.chtpm layout should use variables directly (e.g.,
     ${current_key}, ${taskbar_clock}) instead of relying on a pre-rendered
     taskbar in view.txt.

3. UNIFY State Loading.
   - Ensure wraith_parser.c loads all Wraith session files in load_vars().
   - (This was started in the previous fix pass).

4. REMOVE global keyboard polling.
   - The Composer (if used for background audits) and the Parser must trust
     the Manager's history-driven state.


Conclusion:
Wraith's "Composer" layer is a performance and reliability bottleneck. By
aligning with the Standard TPMOS "Manager-Variable-Parser" flow, we eliminate
stale frames and restore high-speed key feedback.
