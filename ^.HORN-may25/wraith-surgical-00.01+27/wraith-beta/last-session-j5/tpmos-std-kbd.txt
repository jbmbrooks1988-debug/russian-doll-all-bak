TPMOS STANDARD KEYBOARD INVESTIGATION
Date: 2026-06-05

Purpose:
This file records the current investigation into TPMOS-standard keyboard input
flow, using existing TPMOS and `fuzz-op` behavior as the reference instead of
inventing new Wraith-only assumptions.


1. The TPMOS standard path

The standard TPMOS keyboard path is simple:

1. keyboard capture writes to `pieces/keyboard/history.txt`
2. the active runtime reads from that history file
3. the active runtime mutates its own state
4. the active runtime triggers a render pulse
5. the visible frame updates from that state

This means the first truth source is:

- `pieces/keyboard/history.txt`

If the key is not there, the input problem is before the app.
If the key is there, the input problem is inside the app/runtime pipeline.


2. What TPMOS keyboard capture actually does

From:

- `pieces/keyboard/src/keyboard_input_linux.c`
- `pieces/keyboard/plugins/keyboard_input.c`

Observed standard behavior:

- arrow keys are translated to:
  - `1000` left
  - `1001` right
  - `1002` up
  - `1003` down
- those are appended to `pieces/keyboard/history.txt` as:
  - `KEY_PRESSED: <code>`
- ordinary printable keys are also written there
- keyboard capture is suppressed only if GL-OS has focus via:
  - `pieces/apps/gl_os/session/input_focus.lock`

Important standard:
- keyboard capture is global first
- app behavior is downstream of that file


3. What playrm / TPMOS standard apps do

From:

- `pieces/apps/playrm/plugins/playrm_module.c`
- `pieces/apps/playrm/layouts/game.chtpm`

Observed standard behavior:

- playrm reads and reacts through standard runtime state and ops
- playrm triggers visible updates by hitting:
  - `pieces/display/frame_changed.txt`
- project/game interactions use an `<interact>` target such as:
  - `pieces/apps/player_app/history.txt`

Important standard:
- the app owns one clear input history channel
- the app mutates its own state from that channel
- render is explicitly pulsed


4. What fuzz-op does

From:

- `projects/fuzz-op/manager/fuzz-op_manager.c`
- `projects/fuzz-op-gl/manager/fuzz-op-gl_manager.c`

Observed standard behavior:

- the manager resolves one input history path
- for fuzz-op style projects that is typically:
  - `pieces/apps/player_app/history.txt`
- the manager polls that file directly
- `KEY_PRESSED:` lines are interpreted there
- visible state is updated by the manager
- render is triggered after state mutation

Important standard:
- one manager
- one history source
- one polling loop
- one render pulse path

This is the key reference:
- `fuzz-op` does not try to split key ownership across multiple competing
  histories for basic behavior


5. What Wraith currently does differently

Wraith currently has multiple overlapping keyboard-related paths:

1. global raw keyboard file:
- `pieces/keyboard/history.txt`

2. Wraith shell interact target:
- `projects/wraith-pm/session/history.txt`

3. parser-local key handling:
- `projects/wraith-pm/ops/wraith_parser.c`

4. manager key handling:
- `projects/wraith-pm/manager/wraith-pm_manager.c`

This is already more complex than the standard TPMOS / fuzz-op pattern.


6. What the current evidence says

Live evidence from the current workspace:

- `pieces/keyboard/history.txt` DOES contain live arrow keys during Wraith use
- example live values observed:
  - `1002`
  - `1003`
  - `1000`
  - `1001`
- so raw keyboard capture is working

At the same time:

- `projects/wraith-pm/session/history.txt` mainly contains mouse move commands
- it is not reliably receiving the same keyboard stream

That means the current Wraith break is NOT:
- keyboard hardware capture
- terminal raw mode decoding
- basic TPMOS arrow-key encoding

The break is downstream:
- Wraith’s live runtime is not using the standard single-history ownership
  pattern cleanly


7. The actual divergence from the standard

The TPMOS / fuzz-op standard is:

- one active history source for the runtime
- manager or runtime reads that source
- state changes
- pulse render

Wraith drifted into:

- raw keyboard history exists
- parser may read that history
- parser may inject into Wraith session history
- manager may read Wraith session history
- manager may also now read raw keyboard history
- composer may read session state
- composer may also now read raw keyboard history

That is too many parallel truths.

This is why behavior feels inconsistent even when some individual pieces work.


8. What the standard suggests the fix should be

Derived from TPMOS and fuzz-op:

The simple fix should be:

1. choose one authoritative keyboard source for Wraith runtime behavior
2. have one Wraith owner consume it
3. mutate one canonical Wraith nav state
4. pulse render once

There are two defensible standard-aligned choices:

Option A:
- `wraith_parser` owns live keyboard semantics
- it reads `pieces/keyboard/history.txt`
- it writes canonical Wraith state directly
- manager stops competing for top-level nav semantics

Option B:
- Wraith manager owns top-level launcher nav
- it reads `pieces/keyboard/history.txt` directly
- parser stops being a required bridge for top-level launcher movement

For the immediate bug, Option B is the faster practical standard because:

- the key is already present in raw keyboard history
- manager already knows how to mutate selected index
- manager already knows how to update the terminal view
- manager already knows how to trigger render

That matches fuzz-op more closely than the current multi-bridge Wraith flow.


9. Current Wraith-specific conclusion

The current Wraith issue is not:
- "arrow keys do not exist"

The current Wraith issue is:
- Wraith is still split between raw keyboard history, parser forwarding, and
  manager session-history polling

From the TPMOS/fuzz-op standard, the clean immediate rule is:

- for top-level Wraith launcher nav, use one direct source and one direct owner

10. Concrete Wraith bug found in code

After investigating the live Wraith path, the key-debug failure turned out to
be a stale-frame bug, not a missing-key bug.

The actual live display path is:

1. Wraith manager updates:
   - `projects/wraith-pm/manager/view.txt`
   - `projects/wraith-pm/manager/gui_state.txt`
2. Wraith manager pulses:
   - `pieces/display/frame_changed.txt`
3. `wraith_parser` sees the display pulse
4. `wraith_parser` composes the visible frame

The bug was:

- `wraith_parser` was composing on display pulse without first reloading the
  latest manager-owned `view.txt` / `gui_state.txt`
- so the visible frame could lag behind the real manager state
- this is why files could show:
  - `selected_index=2`
  - `current_key=e`
  while the visible frame still showed stale values like:
  - selector on item 1
  - `K:UP`

That is a standards violation because TPMOS expects:

- state/view update first
- then render from that updated state

not:

- pulse render from stale cached variables


11. Standards-aligned fix

The fix is:

- keep top-level Wraith launcher ownership in the manager for now
- let manager remain the source of updated `view.txt`
- on each display pulse, make `wraith_parser` reload live layout state before
  composing the frame

This restores the standard sequence:

1. key reaches `pieces/keyboard/history.txt`
2. Wraith manager mutates canonical launcher state
3. Wraith manager rewrites `view.txt`
4. display pulse fires
5. `wraith_parser` reloads the updated Wraith state/view
6. visible frame matches reality


12. Immediate rule for future Wraith keyboard work

Do not add more keyboard bridges.

For top-level Wraith launcher behavior:

- one keyboard source
- one owner
- one visible state path
- one render pulse

If the visible frame is stale, inspect the reload path before inventing a new
history file or fallback variable.

- read the raw key
- update `selected_index`
- rewrite `terminal_window.view.txt`
- update `current_key`
- pulse the frame

That is the standard shape.


10. Why the stale key label happened

The stale `K:UP` / `K:DOWN` behavior seen in Wraith does not mean the key did
not happen.

It means:

- the visible frame was not being rebuilt from the freshest authoritative key
  source in a clean single-owner path

That is another sign of too many parallel routes instead of one standard route.


11. Practical next-step rule for the next fix

Do not invent more bridges.
Do not add more fallback histories.
Do not add more places that interpret arrow keys.

Instead:

- collapse top-level Wraith launcher nav onto one TPMOS-standard path
- treat `pieces/keyboard/history.txt` as the first truth
- treat one Wraith runtime owner as the nav owner
- keep render pulse behavior explicit and singular


12. Bottom line

The TPMOS and fuzz-op standard does not support the current Wraith split-brain
keyboard path.

The standard points toward:

- one source
- one owner
- one state mutation path
- one pulse

That is the simple logic fix to derive from existing TPMOS behavior.
