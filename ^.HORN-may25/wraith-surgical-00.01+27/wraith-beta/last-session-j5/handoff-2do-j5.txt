Architectural standards to follow

Ground rule:
For every Wraith task, find the closest working TPMOS reference and adapt its
pattern. Do not guess. Do not freehand a new behavior model if the repo already
contains a standard.

Relevant standards for this task:

1. `fuzz-op`
- use as the pattern for:
  - canonical interact history
  - manager consuming one history source
  - state mutation followed by render marker
- key files:
  - `projects/fuzz-op/layouts/fuzz-op.chtpm`
  - `projects/fuzz-op/manager/fuzz-op_manager.c`

2. `op-ed`
- use as the pattern for:
  - one visible frame writer rule
  - manager polling `pieces/apps/player_app/history.txt`
  - parser owning `pieces/display/current_frame.txt`
- key files:
  - `projects/op-ed/layouts/op-ed.chtpm`
  - `projects/op-ed/manager/op-ed_manager.c`
  - `projects/op-ed/README.md`

3. core display renderer
- use as the pattern for:
  - parser writes `pieces/display/current_frame.txt`
  - parser appends `pieces/display/renderer_pulse.txt`
  - renderer only paints when pulse grows
- key file:
  - `pieces/display/renderer.c`

4. marker-file standard
- use as the pattern for:
  - redraw request via marker growth, not direct repaint assumptions
- key files:
  - `pieces/display/frame_changed.txt`
  - `pieces/master_ledger/frame_changed.txt`

Concrete render-chain references for the next agent:

1. `projects/fuzz-op/manager/fuzz-op_manager.c`
- `trigger_render()` is the example to copy for "state changed, request redraw"
- look at the path where it appends to `pieces/display/frame_changed.txt`
- also note it uses the session/project frame marker path alongside the global
  display marker
- the key idea is: manager mutates state first, then hits the marker, not the
  other way around

2. `projects/op-ed/manager/op-ed_manager.c`
- `write_editor_state(); trigger_render(); hit_frame_marker();` is the compact
  pattern to mirror
- this shows the intended order:
  - state write
  - render request
  - marker hit

3. `pieces/display/renderer.c`
- this is the authoritative visible-frame sink
- it reads `pieces/display/current_frame.txt`
- it only re-renders when `pieces/display/renderer_pulse.txt` grows
- the comment in that file spells out the pipeline:
  - input -> frame_changed.txt -> parser compose -> current_frame.txt +
    renderer_pulse.txt -> renderer display

4. `projects/op-ed/README.md`
- use the "One Writer Rule" note as the short policy statement
- `current_frame.txt` belongs to the parser
- daemons request redraws through marker files
