STANDARDS REFERENCE

Purpose:
This file explains a core Wraith onboarding rule:

- every Wraith task should begin by identifying an existing inspirational
  standard elsewhere in TPMOS

This does not mean:
- copy another subsystem literally
- force Wraith to become that subsystem

It does mean:
- do not guess from scratch when TPMOS already contains a nearby working
  pattern


How to use this rule

For each Wraith task, ask:

1. What is the exact behavior I am trying to fix or build?
2. Where in TPMOS, GL-OS, playrm, or fuzz-op does a similar behavior already
   exist?
3. What is the ownership pattern there?
4. What is the file-flow pattern there?
5. What should Wraith preserve from that pattern?
6. What should Wraith adapt instead of copying literally?


Examples of inspirational standards

Keyboard and input routing:
- use TPMOS keyboard capture and fuzz-op style manager ownership as the first
  reference
- see `tpmos-std-kbd.txt`

Desktop/window behavior:
- use GL-OS as the behavior reference for focus, open/close, z-order, and
  desktop illusion

Loader and menu flow:
- use TPMOS / playrm loader behavior as the reference for staged project
  selection and welcome flow

Projected content surfaces:
- use fuzz-op style file-backed projections as the reference for visible window
  content


What future agents must avoid

Do not:
- invent a new input path when an existing standard path already exists
- fix the final Wraith vision before proving the first behavior step
- mix parser-owned UI and composed desktop UI without checking existing TPMOS
  ownership patterns
- treat inspiration as direct copy-paste
- trust a stale visible frame or detached process chain before proving the live
  parser-manager-renderer path is active


Bottom line

Every Wraith task should have an inspirational standard.
Find that standard first, then adapt it to Wraith deliberately.
