WRAI BUGS
Date: 2026-06-05

Purpose:
This file records the actual investigation into why Wraith nav was not moving
with arrow keys the way regular TPMOS CHTPML and GL-OS CHTMGL nav does.


1. What I actually investigated

I checked the real Wraith code path, not just the docs or state files:

- `projects/wraith-pm/project.pdl`
- `projects/wraith-pm/layouts/wraith-shell.wrai`
- `projects/wraith-pm/ops/wraith_parser.c`
- `projects/wraith-pm/manager/wraith-pm_manager.c`
- `pieces/keyboard/history.txt`

I specifically traced:

- how keyboard input enters the parser
- how arrow keys are decoded
- when keys get forwarded into Wraith session history
- when the manager consumes that session history


2. What is NOT the bug

The problem is not:

- that `.wrai` is missing
- that `project.pdl` points at the wrong layout
- that arrow keys are not being written at all

Verified:

- `project.pdl` points to `projects/wraith-pm/layouts/wraith-shell.wrai`
- `wraith-shell.wrai` exists
- `pieces/keyboard/history.txt` contains arrow events such as
  `KEY_PRESSED: 1003`

So the keyboard capture layer is working.


3. The real bug

The real bug was nav ownership inside `wraith_parser`.

Wraith shell already declares:

- `<interact src="projects/wraith-pm/session/history.txt" />`

That means Wraith has a real manager-owned input channel ready to receive keys.

But `wraith_parser` was still doing this:

- in top-level nav mode, scan the parsed layout for any local navigable elements
- if any navigable elements exist, keep arrow handling inside the parser
- only forward arrows to Wraith session history if there are no local
  navigable elements

That behavior lived in `process_key()` in
`projects/wraith-pm/ops/wraith_parser.c`.

So the parser was effectively saying:

- "if I see anything I consider navigable, I own the arrows"
- "only if I see nothing navigable do I pass arrows to Wraith"

That is the wrong rule for Wraith shell.


4. Why that breaks the intended behavior

Regular TPMOS / GL-OS behavior feels consistent because the active surface owns
the nav.

Wraith shell intention is:

- shell-level top nav should belong to Wraith itself
- Wraith manager should receive arrow keys for shell selection
- parser should not silently compete with manager for the same arrows

Before the fix, Wraith had two different nav ideas at once:

- parser-local focus/nav
- manager-owned shell nav

That is why the arrow keys could look dead or inconsistent:

- the key was captured
- but it was being consumed by the wrong layer


5. The manager side was already capable

The manager was not the main bug here.

`projects/wraith-pm/manager/wraith-pm_manager.c` already handles:

- `1002` / `w` as up
- `1003` / `s` as down
- `13` / `10` as open/select
- digits for direct selection

So once the key reaches:

- `projects/wraith-pm/session/history.txt`

the manager can move the Wraith selector.

The missing part was making Wraith shell top-level arrows actually go there by
default.


6. The fix I applied

I changed `projects/wraith-pm/ops/wraith_parser.c`.

What changed:

- default `current_layout` now points to `wraith-shell.wrai`
- added a Wraith-specific top-level nav check
- when the current layout is Wraith shell and the interact target is
  `projects/wraith-pm/session/history.txt`, top-level nav keys are now treated
  as manager-owned

In practical terms:

- arrow up/down now forward into Wraith session history by default at shell
  top level
- digits now forward into Wraith session history by default at shell top level
- Enter now forwards into Wraith session history by default at shell top level

What I did not change:

- deeper parser interact-mode logic
- future window-level interact mode behavior
- mouse behavior

So this is a narrow shell-nav ownership fix, not a full interact-mode rewrite.


7. Why this matches the product intention

This aligns Wraith with the current blueprint direction:

- `wraith_parser` should be native to Wraith
- manager should own canonical shell/window state
- composer should render that truth

At the shell level, the parser should not pretend the shell menu is just a
generic parser menu if Wraith already has a dedicated session-history path and
manager.

So this change keeps the framework but removes the most obvious conflict:

- top-level Wraith shell nav now belongs to Wraith
- parser-local nav is no longer allowed to silently steal those keys first


8. Build result

I rebuilt:

- `projects/wraith-pm/ops/+x/wraith_parser.+x`

The rebuild succeeded.

There are still existing warnings in `wraith_parser.c`, including:

- misleading indentation
- unused mouse parameters
- some truncation warnings
- one unused helper

Those warnings are real but they are not the specific nav bug described here.


9. Current best explanation of the old failure

If the user pressed arrow down and the Wraith visible selector did not move,
the most likely reason was:

- the parser saw local navigable structure
- the parser kept the arrow for itself
- the manager never got the arrow in
  `projects/wraith-pm/session/history.txt`
- so the manager-owned selector state never changed

That is why the behavior did not match normal TPMOS / GL-OS expectations.


10. What still needs proving

This investigation and fix establish the likely root cause and correct the
routing rule.

What still needs human verification in a live run:

1. boot Wraith shell cleanly
2. press arrow down
3. confirm visible selector moves from `blank-proj` to `game-map`
4. confirm `nav_state.txt` updates to `selected_index=2`
5. press Enter
6. confirm only the selected project opens

If that passes, then Wraith shell nav is finally acting on the correct owner.


11. Bottom line

The problem was not "Wraith cannot open projects."

The problem was:

- Wraith shell arrow keys were still being interpreted by generic parser nav
  rules before they reached Wraith's own nav channel

That is now the main bug fix for this pass.
