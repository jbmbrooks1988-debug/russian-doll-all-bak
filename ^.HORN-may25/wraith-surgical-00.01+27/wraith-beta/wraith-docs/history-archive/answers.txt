WRAITH ANSWERS
Date: 2026-06-04

1. Why is game map already opened?

It is already opened because Wraith is currently restoring that state from its session files.

Current saved state says:
- focused_window=game_map_window
- open_game_map_window=true
- selected_index=2

Those values live in:
- 1.TPMOS_c_+rmmp.0102.0018/projects/wraith-pm/session/state.txt
- 1.TPMOS_c_+rmmp.0102.0018/projects/wraith-pm/session/nav_state.txt

So this is not the parser inventing a new game-map window on this frame. It is Wraith obeying previously saved state.

That behavior does NOT match the intended startup behavior we clarified.

Intended startup behavior:
- start with shell behavior like GL-OS
- keep one default terminal open for convenience right now
- do not auto-open game-map
- only open game-map after deliberate nav selection


2. If game map has focus, should its selector be active?

Yes. That is the intended behavior.

If a window has focus, its internal nav should own the active selector.

Right now Wraith does not do that correctly.

Right now:
- window focus can say game-map is focused
- but nav ownership is still effectively tied to the terminal menu path
- nav_scope is still saved as terminal_menu

So the visible result is inconsistent:
- desktop focus says game-map
- selector behavior still acts like terminal/menu owns nav

That is a real bug, not just a styling issue.


3. Is this different from chtpm_parser.c style?

Yes.

This Wraith path is different from the simpler parser-driven pattern.

In a more standard parser-led flow, one parser owns:
- focus
- nav
- current active interactive region

Wraith currently splits that responsibility across:
- wraith_parser
- wraith-pm_manager
- saved session state
- composer output

That split is why focus and selector activity can disagree.


4. Are we using chtpm_parser.c or wraith_parser.c here?

We are using wraith_parser.c for Wraith.

Confirmed in:
- 1.TPMOS_c_+rmmp.0102.0018/projects/wraith-pm/project.pdl

Current project wiring:
- parser = projects/wraith-pm/ops/+x/wraith_parser.+x
- manager = projects/wraith-pm/manager/+x/wraith-pm_manager.+x


5. What this means before we update the blueprint

The current implementation is still between two models:

Model A:
- desktop windows with real focus and real open/closed state

Model B:
- terminal-menu-first nav ownership

Your intention is clearer than the current code:
- window focus should determine which window's nav is active
- startup should not reopen game-map unless we explicitly want session restore
- default startup should be terminal only for now


6. Concrete correction to carry into the blueprint

Wraith should follow these rules:

- Startup:
  - shell/desktop flow
  - one default terminal window for now
  - no game-map window at boot

- Open behavior:
  - selecting game-map from terminal nav opens a new game-map window

- Focus behavior:
  - focused window owns active selector/nav
  - if terminal is focused, terminal menu selector is active
  - if game-map is focused, game-map selector is active

- State behavior:
  - open windows and focused window must agree with active nav owner
  - no split-brain state between focus and selector ownership


7. Practical next step

Before more behavior work, reset Wraith to the intended startup baseline:
- terminal open
- game-map closed
- terminal owns nav

Then fix nav ownership so focus and selector always move together.


8. Are we in a real interact mode, or just superimposing mouse over normal nav?

Right now, it is closer to superimposed mouse than to a true interact mode.

Meaning:

- the system has normal nav structures
- mouse/state artifacts exist beside them
- but there is not yet a clean, proven interaction mode where input ownership
  fully shifts into an interact-space runtime

So the current Wraith path is not yet strong evidence of:

- nav inside interact mode
- auto-interact mode with no prior selection
- mouse behavior inside a proven interact-mode system

That concern is valid.


9. Should interact mode be proven separately first?

Yes, that is a defensible order.

The cleaner order would be:

1. Prove a real interact mode by itself.
2. Prove nav works inside that interact mode.
3. Prove auto-interact mode can start without a prior selector step.
4. Prove mouse behavior inside that same mode.
5. Then bring those proven rules back into Wraith.

That is stronger than trying to make Wraith prove all of those things at once.


10. Why this matters

If Wraith tries to solve all of these layers at once, it becomes hard to tell
which failure belongs to:

- desktop window state
- nav ownership
- parser behavior
- interact-mode ownership
- mouse behavior

Separating interact-mode proof first would reduce confusion.


11. Best current interpretation

The safest current interpretation is:

- Wraith should not yet be treated as the proof of interact mode
- Wraith is currently a desktop-shell experiment that still rides on older nav
  assumptions
- if we want a rigorous foundation, we should prove interact mode separately,
  then reuse that model inside Wraith


12. Practical decision

So if we choose rigor over speed, the better path is:

- pause deeper Wraith interaction behavior work
- build or identify a smaller isolated interact-mode proof target
- prove:
  - nav in interact mode
  - auto-entered interact mode
  - mouse in interact mode
- then return to Wraith and apply those rules cleanly

If we do not do that, then Wraith remains a mixed experiment instead of a clean
proof.
