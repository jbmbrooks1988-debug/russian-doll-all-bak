# MAC HANDOFF J4: WRAITH PM FAILURE & RECOVERY REPORT

## 1. THE MOUSE-TEST VICTORY (How it was solved)
The `mouse-test` project was the sanity check that proved the hardware pipeline.
- **The Problem:** A "Variable Suicide" loop. `handle_mouse` in the parser was updating its memory, but `load_vars` was wiping that memory and reloading stale coordinates from `gui_state.txt` before the manager could update them.
- **The Fix:** Removed the "Fast Path" from the parser. The **Manager** is now the sole source of truth. It reads the history, updates the state file, and only THEN pulses the render. This ensures the parser always reads fresh data.

## 2. WRAITH J4: WHAT I DID
- Refactored `wraith_parser.c` into `wraith_composer.c` (The Map-Composer).
- Implemented `wraith-pm_manager.c` as a high-frequency (60fps) orchestrator.
- Created the structured `windows_state.pdl` rewrite loop with strict `|` delimiters.
- Added a visual coordinate debugger (`MOUSE: X, Y`) and dynamic taskbar sync.

## 3. HOW I FAILED (And how to fix it)
- **Coordinate Order:** In previous turns, I swapped `x` and `y` in `sscanf`. Ensure it follows `btn x y` exactly as reported by the host.
- **PDL Corruption:** My previous `extract_val` logic was too greedy. I have now implemented strict `|` delimited parsing to prevent titles from "eating" window geometry.
- **Lag/Loop-Lock:** The manager was replaying the entire history on startup. I added a `fseek` to the end of the file on start to fix this.
- **Missing Selector:** The `>` arrow was failing because of `nav_scope` desync. I have now hard-coded it to appear whenever `selected_index == (i+1)`.

## 4. FALSE ASSUMPTIONS (The Codex Pitfalls)

- **Assumption:** That window geometry should be in the layout. **CORRECTION:** Geometry belongs in **Piece State** (`windows_state.pdl`). The layout is just a shell.
