gem-xo suggestion autofill investigation
=======================================

Observed state from the live files:
- `projects/gem-xo/manager/gui_state.txt` contains `input_text=dir.txt`
- `pieces/apps/player_app/state_changed.txt` is being pulsed
- `pieces/display/active_gui_index.txt` currently contains `8`

That means the selection path is not failing to write the chosen text.
The remaining bug is downstream: the parser/UI is not reliably keeping
`cli_io` active after the autofill commit, so the next keystrokes do not
land in the input field the user expects.

What the code currently does
----------------------------

Selection path in `manager/gem-xo_manager.c`:
- reads the last `i...` entry from `pieces/apps/player_app/cli_buffers.txt`
- removes the `*`
- writes the selected path into `g_last_buf_input`
- writes `input_text` into `gui_state.txt`
- pulses `pieces/apps/player_app/state_changed.txt`
- pulses `pieces/display/frame_changed.txt`
- writes `pieces/display/active_gui_index.txt`

Parser path in `pieces/chtpm/plugins/chtpm_parser.c`:
- reloads `gui_state.txt` only when `state_changed.txt` grows
- for `cli_io id="input_text"`, it initializes `input_buffer` from
  `get_var("input_text")`
- it also has a second `cli_io` init path for `cli_input`
- `export_active_index()` uses the current `active_index` / `focus_index`
  to write a numeric GUI index, and `is_navigable()` treats `cli_io`
  specially when it is the active element

Most likely failure modes
-------------------------

1. Focus is being restored to the wrong control after selection.
   - We already confirmed the chosen path is written.
   - If `active_gui_index.txt` does not point back to the actual `cli_io`
     element, the input may render but not accept subsequent keys.

2. The parser is reinitializing `cli_io` from multiple sources.
   - `input_text` is the intended source for `gem-xo`.
   - `cli_input` is a separate fallback signal and can override the same
     `cli_io` buffer if it is populated.
   - If both sources are active in the same parse cycle, the selected path
     can appear to vanish or become non-editable.

3. The selection commit is correct, but the control never regains active
   status after the completion menu collapses.
   - This is consistent with the frames showing the cursor/underscore but
     no new typing taking effect.

Recommendation for the next fix
-------------------------------

- Treat autofill as a single atomic commit:
  - write `input_text`
  - pulse `state_changed.txt`
  - restore focus to the exact `cli_io` element that was active before the
    suggestion popup opened
- Remove any path that writes a non-numeric value into
  `pieces/display/active_gui_index.txt`
- Audit `cli_io` initialization so `input_text` is the only source for the
  gem-xo prompt after suggestion selection
- If `cli_input` is not needed for this layout, disable that fallback for
  `gem-xo` so it cannot overwrite the prompt buffer

Bottom line
-----------

The selected text is being saved. The remaining bug is focus/state
ownership: the parser is not consistently leaving `gem-xo`'s `cli_io`
active after completion commit, so the next keystrokes do not land in the
same input field.
