PAL-CHAT-IRC STANDARD - architecture for a local-first, IRC-style
chatroom app (named rooms, live-ish message streams, no personal
walls/follows/feed algorithm - that's pal-forum's job) living in
yz.muchiverse/2.muchi-verse/pal-chat-irc/ (an existing, empty
placeholder directory - confirmed empty before writing this doc, not
assumed), running over the same PAL-NET p2p network (shared-ops/
palnet_peer.c, reused unmodified - own_kind=irc_node, seek_kind=
irc_node, full mesh, same precedent as PAL-CHAIN-STANDARD.txt sec. 0 /
PAL-FORUM-STANDARD.txt sec. 0). Written 2026-07-19 per direct user
instruction: "we should fix that ux issue, and then begin making
another project that is more like irc chatroom than forum," later
sequenced explicitly AFTER session isolation (pal-standards.txt sec.
23) and user-pal (USER-PAL-STANDARD.txt) were both proven: "lets build
wise of that and add it to our standards as we set out to do the irc"
- meaning THIS project is the first one built with both of those from
day one, not retrofitted. This doc is architecture + a v1 scope, not a
finished implementation.

========================================================================
0. WHY THIS SHAPE - HOW IT DIFFERS FROM PAL-FORUM
========================================================================
pal-forum's data is USER-scoped (each user owns a wall, a following
list, likes) - a post belongs to its author, and OTHER users only see
it via the feed algorithm's own scan of who they follow. IRC has no
such ownership: a message belongs to a ROOM, and every node that has
ever seen that room's traffic keeps the same shared, append-only
message log for it, visible to anyone who opens that room - there is
no per-user wall, no follow graph, no feed computation, no likes/
retweets. This is a genuinely simpler shape than pal-forum, not a
reskin of it.

Location: pal-chat-irc/rooms/<room_name>/messages.txt - append-only,
pipe-delimited (matches every other record type in this family):
    MSG|<msg_id>|<room_name>|<user_id>|<timestamp>|<text>

A room is created implicitly the first time anyone posts to a name
that doesn't exist yet locally (mkdir -p, matching the "if it's not in
a file, it's a lie" - and "if it's not a directory yet, make it"
convention already used by forum_inbox_watcher.c's own ensure_user_dir
for an unknown author). No room membership list, no "who's currently
in the room" presence tracking in v1 (a real, named gap - see sec. 5).

========================================================================
1. IDENTITY - LOCAL FIRST, USER-PAL AUTO-FILL FROM DAY ONE
========================================================================
pal-chat-irc keeps its own local users/<user_id>/profile.txt (user_id,
display_name, created_at - same no-password v1 shape as
forum_create_user.c/userpal_create_account.c) and its own net/
session.txt (per-session current_user_id, INSIDE the session directory
- sec. 2 - not persistent, exactly like pal-forum's own net/
session.txt, NOT like user-pal's own current_login.txt; see USER-PAL-
STANDARD.txt sec. 2 for why those two are deliberately different
shapes).

Being built AFTER user-pal existed, pal-chat-irc's own button.sh wires
the USER-PAL-STANDARD.txt sec. 4 auto-fill integration in from the
start (copying pal-forum/button.sh's own reference implementation
verbatim, not reinventing it) - if ../user-pal/current_login.txt names
a logged-in identity, this project's own login screen's user_id_input
field starts pre-filled with it. Same rules as everywhere else this
pattern is used: auto-fill only, never auto-login, silent no-op if
user-pal isn't present, the user still clicks Log In/Create Account.

========================================================================
2. SESSION ISOLATION FROM DAY ONE
========================================================================
Unlike pal-forum (which had session isolation retrofitted mid-build
after the bug was live-caught) and pal-chain (backported after this
project - sec. 6), pal-chat-irc's own button.sh is written with
pal-standards.txt sec. 23's session-isolation shape from its very
first version: every "run" gets pieces/sessions/<id>/, symlinks back
to static/shared code (system/ops/pal/pieces/chtpm/default_op.txt/
projects/pal-chat-irc/pieces) and shared/persistent data (users/,
rooms/, current_login.txt-if-user-pal-present is read once at launch
not symlinked since it's a foreign project's own file, not this
project's), real private copies of ephemeral UI state, cwd-scoped
kill_own_module() for module reaping, deleted on exit. Copied directly
from pal-forum/button.sh's own proven "run" action, no design work
re-done.

========================================================================
3. SCREENS
========================================================================
login.chtpm - user_id_input, display_name_input cli_io fields,
  SIGNUP/LOGIN METHOD buttons (same shape as pal-forum's own login
  screen, minus the visibility-gated "Continue" button complexity -
  IRC has one obvious next screen, not a "home" hub).
room_list.chtpm - room_name_input cli_io field + JOIN_ROOM METHOD (types
  a new or existing room name, creates it locally if needed), PLUS a
  dynamic `${room_choices}` list of every room this node currently
  knows about (real clickable buttons, sec. 5's own "no longer
  deferred" update) - not a global registry (still only rooms this
  node has locally seen), but covers the common case of rejoining an
  already-active conversation without typing/remembering its name.
room.chtpm - shows the current room's own last N messages
  (newest-last, like a real terminal scrollback - matches sec. 25's
  own scrollback-preserving renderer default, which this project
  inherits unmodified), a message_text_input cli_io field, POST_MESSAGE
  METHOD, LEAVE_ROOM (back to room_list.chtpm) METHOD.

========================================================================
4. PROPAGATION
========================================================================
ops/chat_post_message.c - appends the MSG line to THIS node's own
rooms/<room>/messages.txt AND net/outbox.txt, exactly like
forum_post.c's own wall.txt + outbox.txt double-write.
ops/chat_inbox_watcher.c - PERSISTENT daemon (copied structurally from
forum_inbox_watcher.c, MSG is the only verb v1 needs to handle),
tails net/inbox.txt, strips palnet_peer's own "<sender_node_id>|"
prefix, mkdir -p's the named room locally if this node has never seen
it before, dedup-appends the line to that room's messages.txt
(already_has_line() guard, same shape as forum's own - palnet_peer's
backlog replay to a newly-connected peer can redeliver an already-seen
line).
No signature/authenticity check in v1 (same named gap as pal-chain
sec. 7 / pal-forum sec. 4).

========================================================================
5. DEFERRED TO A LATER PHASE - NOT V1
========================================================================
- Room membership / presence ("who's currently in this room right
  now") - v1 shows message history only, no live "user X joined" or
  online-user list.
- Message editing/deletion (append-only log, same as every other
  record type in this family - no verb for retracting a line).
- Private/DM-style messaging (that's pal-forum's own already-built
  DM feature - IRC here means public rooms only, v1).

NO LONGER DEFERRED (2026-07-20, direct user request: "occupied rooms
should show as a choice to join"): room_list.chtpm now shows every
room this node currently knows about (a `rooms/<name>/` subdirectory)
as a real, clickable `<button onClick="KEY:100+index">` choice,
alongside the existing type-a-name field - see sec. 3's own updated
screen description and chat_menu_input.c's own `write_room_choices()`/
`resolve_room_by_index()` for the mechanism (pal-standards.txt sec.
13's own dynamic-button convention, groq-ollama/mutaclsym precedent -
NOT `${piece_methods}`, since the room count is dynamic and piece.pdl
is a static file). This is still only a LOCAL view - "rooms this node
has seen" via its own `rooms/` directory, not a genuinely global
"every room that exists anywhere on the mesh" registry (no new
propagation of "here is the full list of rooms" between peers - a room
still only enters a node's own list once that node has posted to or
received a message naming it), but it solves the actual UX gap: a
returning or new user on an ALREADY-ACTIVE node no longer has to know
or guess a room name to rejoin a conversation already in progress.

========================================================================
6. ROLLOUT - SESSION ISOLATION BACKPORT ORDER
========================================================================
Per pal-standards.txt sec. 23's own updated rollout: pal-forum done →
pal-chat-irc (this doc, built session-isolated from day one) → THEN
backport the identical pattern into pal-chain's own button.sh (that
project predates session isolation entirely, sec. 2 of this doc is
new territory for it). pal-chain also gets the USER-PAL-STANDARD.txt
sec. 4 auto-fill wired in as part of that same backport pass, matching
pal-forum's and pal-chat-irc's own login screens.
