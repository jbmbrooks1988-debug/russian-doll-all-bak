## LOCAL PITFALL A: resetting pieces/world_01 from world_01_template
   silently discards live camera positioning - no error, no warning

SYMPTOM: after a session of real testing that used `rm -rf pieces/
world_01 && cp -r pieces/world_01_template pieces/world_01` as a
"clean slate" shortcut, the user reported the 3D camera view looked
"inverted/reset" compared to a carefully-positioned view from earlier
that day.

ROOT CAUSE: pieces/world_01_template/map_start/hero/state.txt has NO
camera fields at all (no cam_yaw/cam_pitch/cam_z_level/hero_z) - it's
a bare starter file. A LIVE, played hero/state.txt DOES accumulate
these fields once the player actually uses camera controls (q/e/r/t/
c/v/f, see ops/camera_control.c). Resetting from the template
silently drops them - the game then falls back to hardcoded code
defaults (yaw 0°, ground level) instead of erroring, so nothing LOOKS
broken - it just looks like the camera got flipped/reset, which is
exactly what happened, just not because of a code bug.

Confirmed via direct diff: camera_control.c, move_player.c,
compose_rgb_frame.c, choice.c, and system/chtpm_parser_pal.c were all
verified byte-identical against an earlier same-day snapshot
(101.mutaclsym🧟‍♂️️+18.0G) before concluding this was a data issue, not
a code regression - do that same verification before assuming code
changed, if this happens again.

FIX APPLIED: restored the real camera field values (cam_yaw=180.00,
cam_pitch=6.00, cam_z_level=2, hero_z=14, facing=1002, camera_mode=2,
render_mode=1) into BOTH the live pieces/world_01/map_start/hero/
state.txt AND pieces/world_01_template/map_start/hero/state.txt (per
direct instruction: also bake into the template, so a fresh "new
game" starts with this view too, not just the live session). Same fix
applied to 300.rtp-xyz and 300.rpg-xyz's own copies of both files -
they inherited the SAME bare template and were reset the same way
during unrelated testing.

LESSON FOR NEXT TIME: `rm -rf pieces/world_01 + cp -r template` is a
real, legitimate "new game" mechanism (ops/title_input.c's own
reset_world() does exactly this) - but using it as a casual test-setup
shortcut during agent testing silently discards whatever real
progress/positioning a human player has actually made. Before running
this reset during testing, check whether pieces/world_01/map_start/
hero/state.txt has content beyond the template's own bare fields
(camera fields being present is a good tell) - if so, it's real player
state, not a stale test artifact, and deserves a real backup first
(e.g. a manual `cp -r` snapshot) rather than being silently discarded.

## LOCAL PITFALL B: (300.rtp-xyz specific, cross-referenced here since
   the same daemon shape may get built for rpg-xyz/other clones)
   a manager daemon's own save/load `rm -rf` + `cp -r` chain,
   unguarded, deleted the live pieces/registry/ permanently

Full incident writeup: 300.rtp-xyz/save-load-report-j31.txt and the
rtp_manager.c source's own header comment on do_save_new()/do_load().
Short version: the original save code checked only a COMBINED shell
chain's final exit code, not each step - a silent `cp -r pieces/
registry` failure at save time meant a save slot was created with NO
registry/ subdirectory, and a later `rm -rf pieces/registry` (as part
of loading that same incomplete save) then had nothing valid to
restore FROM, permanently deleting the project's own real registry
content (this whole de-theme's own slime/slime_pup work) with zero
recovery path. Restored from 300.rpg-xyz's own intact copy (a real,
lucky mitigation - not something to rely on). Real fix: do_save_new()/
do_load() now check every step's own real result separately, and
do_load() specifically REFUSES to touch any live directory until the
save's own source content is confirmed to exist and be non-empty
first - see the function's own code/comments for the full guard.

LESSON: any future manager daemon in this house that does its own
save/load via shell-out cp/rm should follow this same "verify the
source before you dare rm -rf the destination" shape - a single
combined `&&`-chained shell command with only the FINAL exit code
checked is not enough to catch a silent mid-chain failure, especially
when run_command() (or any pattern that redirects both stdout/stderr
to /dev/null in the child) means no error message ever surfaces
anywhere for a human or agent to notice.
