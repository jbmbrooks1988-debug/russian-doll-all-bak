# Architecture Plan: '*' Trigger Completion System (Fuzz-Op Style)

Following the "Thin Theater / Manager Projection" philosophy from `fuzz-op`, we will implement path completion by having the manager project suggestion buttons into the UI.

## 1. Core Lifecycle
1.  **Trigger**: User types `*` (ASCII 42). The manager detects this key in `history.txt`.
2.  **State**: Manager enters `COMPLETION_MODE`.
3.  **Projection**:
    *   Manager reads current `input_text` from `gui_state.txt`.
    *   It identifies the path prefix after the last `*`.
    *   It calls `complete_path` to get matches.
    *   It generates button markup: `<button label="file.txt" onClick="CHOOSE:file.txt" />`.
    *   It writes this markup to `gui_state.txt` as `completion_area=...`.
4.  **Render**: CHTPM substitutes `${completion_area}` in `gem-dev.chtpm` and renders the buttons.
5.  **Selection**: User clicks a suggestion button. This injects `CHOOSE:file.txt` into `history.txt`.
6.  **Resolution**: Manager reads the `CHOOSE:` command, updates `input_text` in `gui_state.txt` (replacing the `*prefix` with the selection), and clears the `completion_area`.

## 2. Manager Modifications (`gem-dev_manager.c`)
*   **Key Monitoring**: Update the `main` loop to handle any key if `g_completion_mode` is active, not just Enter.
*   **Suggestion Op**: Implement a function that turns `complete_path` output into CHTPM button strings.
*   **Input Injection**: Implement logic to surgically replace text in the `input_text` variable.

## 3. UI Integration (`gem-dev.chtpm`)
Add a dynamic slot for suggestions:
```xml
    <text label="Suggestions: " />${completion_area}<br/>
```

## 4. Why this works
*   **No Parser Changes**: We use standard CHTPM substitution and button mechanics.
*   **Real-time Feel**: By pulsing `frame_changed.txt`, we ensure the UI updates as the user types after the `*` trigger.
*   **Consistent with Fuzz-Op**: Leverages the established pattern of manager-driven UI state.
