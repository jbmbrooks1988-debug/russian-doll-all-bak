You've hit on a very relevant point. While chtpm_parser.c is currently
  around 2,000 lines—which isn't massive for a core system component—it is
  definitely violating the Lite Modular Philosophy by becoming a "Master
  Manager" that knows too much about specific apps.

  Here is my expert analysis on where we can factor logic out into Ops or
  Modules to return to a pure "Theater" model:

  1. The "Obvious" Bloat: App-Specific Logic
  Currently, load_vars() contains hardcoded paths and logic for fuzz-op,
  gl-os, user, and the player_app. 
   * The Problem: The Parser (Theater) should be "dumb." It shouldn't know
     that fuzz-op needs to load pet_hunger.
   * The Fix: Each Module should be responsible for writing its own complete
     state to a standard gui_state.txt. The Parser should just blindly load
     gui_state.txt for the current project and nothing else.

  2. Candidate for a new "Discovery Op": Project Scanning
  The function load_projects_markup() scans the projects/ directory and
  generates CHTPM button strings.
   * The Problem: This logic is only used by the Project Loader.
   * The Fix: Move this into a standalone Op (e.g., get_projects_op.c). The
     Loader module would call this Op, which writes the XML markup to a
     variable. The Parser then simply renders ${project_list_markup}.

  3. Candidate for a "Metadata Op": Method Mapping
  The function load_dynamic_methods() reads Piece PDLs and converts
  METHOD|... lines into UI buttons.
   * The Problem: This is "Brain" logic living in the "Eyes."
   * The Fix: Move this into a get_piece_methods_op.c. The Manager (Brain)
     calls this Op when a piece is selected and updates the piece_methods
     variable. The Parser just displays the string it's given.

  4. Layout Resolution
  The logic in send_command() that handles LOAD_PROJECT and searches for
  entry_layout in project.pdl is quite heavy.
   * The Fix: This could be moved to the project_loader app module. The
     Parser should just receive a LAUNCH:path/to/layout.chtpm command.

  Summary Verdict:
  If you feel the Parser is "nearly done," it is stable enough to leave
  alone for now. However, if we were to do one final "Lite" pass, the most
  impactful change would be stripping the app-specific if (strcmp(proj_id,
  ...)) blocks from load_vars and moving that responsibility to the
  respective App Managers.

  This would shrink the Parser by 300-500 lines and make it a truly generic
  ASCII layout engine!
