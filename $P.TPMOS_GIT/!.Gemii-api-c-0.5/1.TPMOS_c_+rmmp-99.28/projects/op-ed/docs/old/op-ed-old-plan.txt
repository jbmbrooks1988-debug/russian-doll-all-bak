# OP-ED Project Progress & Roadmap Report (m23)
**Date:** 2026-05-23
**Status:** Planning & Scaffolding Phase

## 1. Current Progress Analysis

The `op-ed` project has a solid foundation for an ASCII-based RPG Maker, but several architectural inconsistencies and "scaffolding" relics need to be addressed to reach the modular "Sovereign Handover" model.

### Existing Strengths:
-   **Manager UI:** The `op-ed_manager.c` handles project switching, map palettes, and glyph palettes.
-   **Render Integration:** It already triggers `render_map.+x` and manages xlector (cursor) state.
-   **Event System:** A basic `trigger_event` mechanism is present, capable of calling PAL scripts via PRISC.

### Current Issues (The "Scaffolding" Problem):
-   **Asset Locations:** `maps/` and `pieces/fuzzpet_mirror/` are currently floating in the project root (`projects/op-ed/`) rather than being encapsulated within a game project directory.
-   **Path Hardcoding:** `scan_projects()` currently looks at the global `projects/` directory instead of `projects/op-ed/games/`.
-   **Internal Logic Bloat:** Much of the file and state syncing is hardcoded inside the manager, violating the "Muscle in Ops" principle.

---

## 2. The "Fuzz-Op Mirror" Lab Project

To accelerate development of the Player and Ops, we will use `fuzz-op mirror` as our primary laboratory project. This project will mirror the mechanics of the original `fuzz-op` but run entirely within the new `op-ed` architecture.

### Mirror Goals:
-   **Entity Simulation:** Recreate the "Fuzzball" (pet) entity with state fields: `hunger`, `happiness`, `energy`, and `level`.
-   **Action Ops:** Reuse or port the `fuzzpet_action.+x` muscle to handle `feed`, `play`, and `sleep` methods.
-   **PAL Orchestration:** Instead of a complex C manager, the mirror's logic (e.g., stats decay over time, level up) will be handled by a PAL script (`fuzz_loop.asm`) running in the Player.

### Structure:
`projects/op-ed/games/fuzz-op-mirror/`
├── `project.pdl` (Defines `player_piece=xlector` or `hero`)
├── `maps/map_0001.txt` (The pet's house)
├── `pieces/pet_01/`
│   ├── `state.txt` (Hunger=50, etc.)
│   └── `piece.pdl` (Methods: feed, play, sleep)
└── `scripts/fuzz_logic.asm` (Handles "End Turn" or "Tick" logic)

## 3. File-Op Setup & "Muscle in Ops" Integration

Taking a cue from the `agy-text-editor` pivot, we must move away from hardcoded file logic. 

**Reference to agy-text-editor:**
The main problem in `agy-text-editor` is "Memory Loss" — it tries to hold the entire document in RAM, which is fragile. `op-ed` should remain "Sovereign," where the files on disk ARE the truth, and the manager only updates those files via atomic Ops.

**Proposed Change:**
-   Implement/Use Global Ops: `load_file_op.+x`, `sync_state_op.+x`, and `project_scan_op.+x`.
-   **Game Project Structure:**
    `projects/op-ed/games/[GAME_ID]/`
    ├── `project.pdl` (Metadata)
    ├── `maps/` (Map TXT files)
    ├── `pieces/` (Entity folders/state.txt)
    └── `scripts/` (Local and Global PAL scripts)

---

## 4. The Player Architecture (Standalone & Modular)

The "Player" is distinct from the "Editor". While the Editor manipulates the game data, the Player interprets it.

### Macro Structure (PRISC Player Script):
-   The Player will likely be a specialized PAL orchestrator (e.g., `player_loop.asm`).
-   It will poll for input and, instead of the Editor's "xlector," it will move the `player_piece` defined in the game's `project.pdl`.
-   It will use the same "Muscle" Ops as the Editor (`move_entity.+x`, `render_map.+x`).

### Exporting:
-   **Local Play:** The Player runs within the `op-ed` tree, pointing its root to `projects/op-ed/games/[PROJECT]`.
-   **Exported Play:** A dedicated `export_game_op.+x` will:
    1. Create a new directory.
    2. Copy the Player binary and required global Ops binaries (`pieces/ops/+x/`).
    3. Copy the specific Game Project folder.
    4. Package it with a minimal TPMOS runtime (CLI Parser).

---

## 5. PAL Op Editor (Event Scripting)

The Editor needs to bridge the gap between map placement and behavioral logic.

-   **Piece-Local Events:** When a piece (e.g., `pet_01`) is selected in the editor and "Edit Script" is clicked, it should open `projects/op-ed/games/[PROJECT]/pieces/pet_01/on_interact.asm` in the editor.
-   **Global Events:** Access to scripts like `game_start.asm` or `on_tick.asm` that run regardless of which map/piece is active.
-   **Integration:** The Manager should handle the "Handover" by switching the active layout to the script editor and setting the `target_file` path.

---

## 6. Addressing Circular Dependencies

The project currently faces several potential circular dependencies which we will resolve through strict architectural layering:

-   **Editor vs. Player:** By extracting the core "Game Loop" and "Collision/Input" logic into standalone Ops, both the Editor and Player become thin wrappers around the same "Muscle". The Editor won't depend on the Player to "test" a map; it will simply call the same `render_map` and `move_entity` Ops that the Player uses.
-   **Dependency on global `projects/`:** By migrating to `projects/op-ed/games/`, we isolate the `op-ed` ecosystem. This prevents the Editor from accidentally trying to "load" the system OS or other unrelated projects.
-   **Manager vs. Ops:** The Manager will only provide high-level "intent" (e.g., "Load Map X"). The Ops will handle the low-level path resolution and file I/O. This keeps the Manager source code clean and focused on UI/UX.

## 7. Developer Roadmap & Logical Phases

### Phase 0: The Mirror Lab (Example Game)
-   Initialize `projects/op-ed/games/fuzz-op-mirror/`.
-   Setup `pet_01` with state and PDL methods.
-   Create a basic `fuzz_loop.asm` to simulate stats decay.

### Phase 1: Scaffolding Normalization (Immediate)
-   Move existing `maps/` and `fuzzpet_mirror/` pieces into the `fuzz-op-mirror` project dir.
-   Update `op-ed_manager.c` to scan `projects/op-ed/games/` instead of `projects/`.

### Phase 2: "Muscle" Migration
-   Replace internal `sync_state` and `load` logic in `op-ed_manager.c` with calls to shared Ops in `pieces/ops/`.
-   Verify that map switching and project loading still work via these Ops.

### Phase 3: Player Prototype (The Orchestrator)
-   Create `projects/op-ed/player/` containing a basic C or PAL-based player.
-   Implement the "Game Loop" that handles hero movement and collision without the Editor UI.

### Phase 4: Script Editor Integration
-   Connect the "EVENT" button in `op-ed.chtpm` to a working script editor.
-   Enable saving of `.asm` files directly into the piece's directory.

### Phase 5: Export & Standalone Packaging
-   Implement the `export_game` Op.
-   Test a standalone game running outside the main `op-ed` project directory.
