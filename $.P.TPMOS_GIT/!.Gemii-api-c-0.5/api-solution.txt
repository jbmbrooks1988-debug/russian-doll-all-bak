================================================================================
          TPMOS CLI AGENT (18+D-LITE) - PURE C GEMINI API SOLUTION
================================================================================

1. OVERVIEW
-----------
To strictly follow the specification of using 100% Pure C (no Python, Node, or external runtime dependencies), we will implement the Google Gemini API integration natively in C. We will leverage the project's fork-exec architecture:
1.  A new compiled C tool `./tools/gemini_payload_builder` will translate the flat conversation history (`state/context.json`) into the official Google Gemini REST JSON format.
2.  `agent.c` will use the system's `curl` binary via fork-exec to POST this payload directly to the Google Gemini API.
3.  `agent.c` will load the API key from the file `../!.google-api-py-00.01/google-lilsol-api-key.txt` (or the environment variable `GEMINI_API_KEY`) and pass it via the `x-goog-api-key` header.
4.  `agent.c` will parse Gemini REST responses natively using the existing `./tools/json_parser` by updating the target JSON key mappings.

2. DETAILED ARCHITECTURE
-------------------------

### A. New Tool: `./tools/gemini_payload_builder.c`
This tool will read a standard flat message history array from a JSON file and construct a Google Gemini-compliant request payload.
*   **Command Usage**:
    `./tools/gemini_payload_builder <input_messages_json> <output_gemini_json> [enable_tools_flag]`
*   **Key logic**:
    - Parses flat `role`/`content` JSON arrays using a simple, robust state-machine parser in C.
    - System messages are extracted and formatted into the top-level `"systemInstruction"` block.
    - User messages are formatted as `"contents"` with a `"text"` part.
    - Assistant messages that represent function calls (e.g., `{"name":"exec_cmd","args":...}`) are formatted as `"contents"` with a `"functionCall"` part.
    - Tool response messages are formatted as `"contents"` (role: `"user"`) with a `"functionResponse"` part, matching the tool name from the preceding function call.
    - If `enable_tools_flag` is `1`, it appends the static C agent tools definition schema (`tools` -> `functionDeclarations` for `exec_cmd`, `read_file`, `write_file`, etc.) using official OpenAPI definitions.

### B. Changes to `agent.c`
1.  **Resolve Model**:
    - Simplify/stub out `resolve_local_model()` to default `current_model` to `"gemini-2.5-flash"`.
2.  **API Key Loading**:
    - Read the Google Gemini API key from `../!.google-api-py-00.01/google-lilsol-api-key.txt` or `getenv("GEMINI_API_KEY")`.
3.  **Prompt Payload Compilation**:
    - Instead of directly using the Ollama-style prompt file, call:
      `./tools/gemini_payload_builder state/context.json state/prompt.json 1` (normal loop) or `0` (for summarization).
4.  **Network Call**:
    - Perform a `curl` call to the Google Gemini endpoint:
      `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent`
    - Inject the header: `-H "x-goog-api-key: <key>"`
5.  **Response Key Mappings**:
    - Parse the text output using `text` instead of `content`.
    - Parse the tool calls using `functionCall` instead of `tool_calls`.
    - Parse tool arguments using `args` instead of `arguments`.
6.  **Tool Call Logging**:
    - When a function call is matched, save its structure as `{"name":"<tool_name>","args":<args_json>}` to the assistant history, allowing `gemini_payload_builder` to reconstruct it perfectly on the next turn.

3. BENEFITS OF THIS PURE C APPROACH
-----------------------------------
*   **No new dependencies**: Relies purely on standard POSIX C library and the system `curl` binary.
*   **Maintains TPMOS Architecture**: Adheres strictly to the file-state fork-exec pattern of the `18+d-lite` skeleton.
*   **Minimal changes to C files**: Only requires adding one lightweight utility `gemini_payload_builder.c` and minor adjustments to `agent.c` key names and the curl execution vector.

4. STEP-BY-STEP PROGRESS & VERIFICATION
---------------------------------------
We have successfully implemented and refined the integration with the following enhancements:
1.  **Dynamic Model Resolution**:
    - `agent.c` reads the target model from `config/model.txt`.
    - If the file is empty, or the model name does not begin with `gemini-` (e.g. legacy Ollama models), it automatically falls back to `"gemini-2.5-flash"`.
    - The resolved model name is dynamically injected into the curl HTTP POST request URLs for both the summarization loop and the main assistant prompt loop.
2.  **Safety Verification on Assistant Tool Calls**:
    - `gemini_payload_builder.c` checks that the unescaped content of assistant history entries starts with `{` before parsing them for tool name and arguments. This prevents false positive matches on plain text containing quote/colon patterns.
3.  **JSON Payload Parsing**:
    - Handled standard tool responses natively and correctly escaped all payloads going into the context JSON state.
4.  **Improved Error Diagnostics**:
    - `agent.c` now captures and displays specific API error messages (e.g., "RESOURCE_EXHAUSTED", "INVALID_ARGUMENT") even when the network call fails. This ensures the user is informed about quota limits or context window exhaustion directly in the CLI.
    - Removed the `-f` flag from `curl` to ensure response bodies containing error details are always captured and analyzed.
